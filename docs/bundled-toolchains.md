### Sixth axis — bundled toolchains (Node-free build chain)

NPM toolchains that are plain TS/JS (no native addons) can be re-bundled with `gjsify build --app gjs` and run under GJS — a Node-free version of the tool without reimplementing it. NOT for native-addon tools (rolldown, oxc binaries) — those get the GI-bridge treatment (`@gjsify/{rolldown,lightningcss,oxfmt}-native` + dual-engine pick).

**Exemplar `@gjsify/tsc`** (`packages/infra/tsc/`): wraps upstream `typescript`'s `lib/_tsc.js` into a GJS bundle shipped as the `gjsify-tsc` bin; `typescript` stays a build-time devDependency; bundle COMMITTED to `dist/tsc.gjs.mjs` (paired `.gitignore` re-include); runtimes `{gjs:"polyfill",node:"none",browser:"none"}`; pinned `TYPESCRIPT_VERSION` in `src/index.ts` (tracks the workspace TS invariant, § Constraints).
|**gjsify SELF-HOSTS its type-checking on it**: every package `check` = `gjsify tsc --noEmit`, and `build:types` (the `.d.ts` emit, incl. project-reference variants) is ALSO `gjsify tsc` — emit validated BYTE-IDENTICAL to node tsc; perf ≈ 1.3× node tsc at full-workspace parallel scale (single-package startup-dominated). `typescript` is now only the seed the bundle is built from. A `@gjsify/tsc` bug breaks every `check`/`build:types` → guarded by `tests/e2e/self-host-tsc`.
|**default-library resolution**: tsc finds its `lib.*.d.ts` beside `_tsc.js`, so the ~108 libs ship INSIDE the package (`lib/lib*.d.ts`, COMMITTED via gitignore exception + reproduced by `build-bundle.mjs` before each bundle build) and the bundle's baked `__filename` spec is re-pointed `typescript/lib/_tsc.js` → `@gjsify/tsc/lib/_tsc.js` (always resolvable from the bundle). `build-bundle.mjs` does NOT blindly refresh: the pure `pickLibSource()` decides `refresh` only when the devDep EXACTLY matches the pin AND ships a complete set (has `lib.esnext.full.d.ts`, ≥ committed count), else `keep` committed, else `error` — a partial CI `typescript` install once copied a broken `lib/` over the correct committed one → the v0.7.2 Fedora-44 main-red `TS6053` cascade. Runtime resolution rides the shared `module-resolve` shim — `rewrite-node-modules-paths.ts` case 4 (CJS) uses the same location-INDEPENDENT resolver as ESM (it used to bake the build machine's absolute path → `TS6053` on every consumer).
|**the packer-glob lesson (v0.4.37–0.7.2 "empty lib/")**: the libs were on disk at pack time — the bug was gjsify's OWN packer not expanding `files` GLOBS: `lib/lib*.d.ts` matched 0 files (`npm pack` expanded it, `gjsify publish` silently did not; a plain-dir `["lib"]` would have worked). Fixed in `pack.ts` (`expandFilesPatterns`, e2e `publish-files-glob`) — but the lesson stands: after adding committed data files, **verify they are in the tarball** (`gjsify pack` + `tar tzf`), never assume a `files` glob ships them. **That instruction is now EXECUTED rather than remembered** — `scripts/verify-tarball-outputs.mjs` holds every declared entry point of every non-private workspace against the packer's own file list on every PR (§ Build outputs). A lesson addressed to a human is a lesson that lapses.
|**self-hosting on `gjsify tsc` is now complete: zero packages invoke a bare `tsc`.** Nine did (the six that OPEN `build:infra` — `vite-plugin-{blueprint,gettext}`, `rolldown-plugin-{pnp,deepkit,gjsify}`, `create-app` — plus `nativescript-vite`, `vite-plugin-gjsify` and `@gjsify/cli` itself), against 114 that already used `gjsify tsc`. Every one of the nine ALREADY ran `gjsify tsc --noEmit` for its `check` against the identical tsconfig, so only the EMIT half went through `node_modules/.bin/tsc` — npm's TypeScript launcher, whose `#!/usr/bin/env node` shebang is unrunnable on a Node-less GJS host. Not theoretical: on postmarketOS/aarch64 `gjsify run build:infra` died at its FIRST entry with `env: can't execute 'node'`. Verified per package that the swap is not merely green but EMIT-IDENTICAL to npm `tsc` (`@gjsify/cli`: 236 files byte-for-byte), which also settles the bootstrap question — `gjsify tsc` rides the COMMITTED `packages/infra/tsc/dist/tsc.gjs.mjs`, present in any fresh clone, so nothing in the chain needs a build to type-check or emit. `@gjsify/cli`'s own `build` is therefore NOT too bootstrappy for it. **A bare `tsc` in a `build` script is a regression** — the residual Node dependency is four `node scripts/*.mjs` calls, not the compiler (`status/open-todos.md`).
|pattern for a new bundled toolchain: infra package, `runtimes {gjs:polyfill,node:none,browser:none}` (never `polyfill` for a slot the tool isn't reimplemented for), `scripts/build-bundle.mjs` bundling the devDep's entry, committed `dist/<bin>.gjs.mjs` + gitignore exception + `files` entry, NAMESPACED bin (`gjsify-<tool>` — no PATH collision), metadata stub `src/index.ts` (`<TOOL>_VERSION`, bundle path resolver), runtime data files copied + committed + `files`-verified (rebuilt after every version bump — the build-copy runs BEFORE the bundle build so a local rebuild refreshes them).

### Bundled-artifact dependency classification — `dependencies` vs `devDependencies`

A package belongs in `dependencies` **IFF something a consumer runs needs it on disk at runtime.** The trap: "it's inlined into the GJS bundle ⇒ devDependency" holds ONLY when the bundle is the sole consumed artifact.
|**pure-bundle** (`@gjsify/tsc` — bin = the GJS bundle, no consumed Node `lib/`): bundled deps genuinely are devDependencies.
|**dual-entry** (`@gjsify/cli` — `bin: lib/index.js` Node entry AND `gjsify.bin: dist/cli.gjs.mjs`): npm wires the bin to the NODE entry, whose `lib/**` imports its deps from `node_modules` at runtime even though they are ALSO inlined in the GJS bundle. `cosmiconfig`, `yargs`, `get-tsconfig`, `pkg-types`, the `@gjsify/*` runtime set — all stay `dependencies`. Moving a `lib/**`-imported dep to devDependencies breaks `gjsify` as an npm dep — guarded by `tests/e2e/create-app` (scaffolds a consumer, runs the bin; a misclassified dep fails `ERR_MODULE_NOT_FOUND`).
|**cold-build corollary**: a `lib/**`-imported dep must be fully BUILT before anything spawns the Node CLI entry (ESM link time) — a dep whose `build:infra` step only emits `lib/types` makes `node <cli>` unloadable on a cold tree, while a warm cache hides it (and the failure blocks the cache save → self-sustaining). Both obvious escapes are circular (those deps' `build:gjsify` needs the native facade only the Node CLI can bootstrap), so `scripts/bootstrap-native-facades.mjs` tsc-emits `lib/esm` for the outliers in its `CLI_RUNTIME_DEPS` before spawning the CLI (mtime-skipped; root build re-emits with Rolldown later). An uncovered dep is caught by an explicit link probe with an actionable message.
|optional GJS-native fast-paths with an npm fallback → optional `peerDependencies` (`@gjsify/rolldown-native` ↔ npm `rolldown`). **A GLOBAL GJS install has no npm fallback** — and the native install backend never resolves peerDependencies — so the global installer lays the engine set down explicitly: `installGjsEnginePackages()` (`@gjsify/{rolldown,lightningcss,oxfmt}-native`) wired into `install -g` + `self-update`, best-effort per engine (missing platform prebuild warns + continues; `rolldown-native` failure is loud), before `linkGlobalBins`. Do NOT make these hard deps of `@gjsify/cli` (every Node/macOS/Windows `npm install @gjsify/cli` would fetch linux prebuilds). e2e `global-install-engine`.
|`gjsify self-update` resolves the production `dependencies` tree by default (`--skip-deps` = bundle-only fast path) so an update pulls matching bridges/engines instead of leaving them skewed; it also REPAIRS a prefix missing `rolldown-native` even when versions match. Safe only because every `@gjsify/*` is published — an unpublished workspace-internal package would 406 the resolve (the historical `@gjsify/v8` failure).
