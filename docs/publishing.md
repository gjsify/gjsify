# Publishing — first-publish bootstrap and release closure

> Detail for the root [AGENTS.md](../AGENTS.md) § Package convention.
> Read this BEFORE adding a new `@gjsify/*` name and before cutting a release —
> both failure modes below have stalled a release train in this repo.

### New `@gjsify/*` package: first-publish + Trusted Publisher bootstrap

npm Trusted Publishing (OIDC) requires the package to ALREADY EXIST — the **first publish is a manual maintainer action**, not CI. Skipping it breaks the serialized publish loop in `release.yml` for every alphabetically-later package (OIDC exchange 404s, workflow exits 1 — v0.4.20 incident: `@gjsify/tls-native` unbootstrapped → 60+ packages stuck at 0.4.19).
|**fast path — `gjsify onboard`**: ensures EVERY publishable package is published + trusted, minimally: whoami-gated login, per-package state probe, publish+trust only the gaps, ONE shared OTP for the whole sweep. Idempotent; `--dry-run`/`--json`/`--yes`. **It is a monorepo tool, not a gjsify-repo chore** — `--packages <dir-glob>` sweeps a repo with no workspace manifest at all (`gjsify/types`: 703 `@girs/*` directories under a root whose only tracked file is `.gitignore`), `--include`/`--exclude` filter by name, `--access`/`--no-build` cover the shapes this repo does not have. Two rules keep an empty sweep from reading as a finished one: a `--packages` glob matching NO directory is a HARD ERROR (a filter selecting nothing is a typo, never an intent — same rule as `gjsify foreach --include`), and the first output line names the repo root and every enumeration source with its count (`root=… | packages(*)=703`, also in `--json` as `root`/`sources`/`discovered`), because the package list IS the sweep's blast radius and a total alone cannot tell the right tree from a plausible wrong one. A THIRD rule replaces the `@girs/*` hardcode with something stronger than the name pattern it removed: a selected package whose own manifest names a DIFFERENT `repository` is REFUSED. Measured — `gjsify onboard` in `gjsify/ts-for-gir` selects 716 packages, 703 of them the generated `@girs/*` under `types-dev/*`, which are workspaces there but publish from `gjsify/types`; trusting those for ts-for-gir's `release.yml` points their OIDC exchange at a workflow that never publishes them, breaking the release the sweep exists to protect. A name pattern only ever covers the one family somebody was already bitten by; the manifest's own claim covers every monorepo holding another project's packages. (Absence of a `repository` field is not evidence of a mismatch and passes — and npm's `git+https://…` spelling had to be taught to `parseRepoFromGitRemote` first, which returned `null` for it, indistinguishable from "declares nothing".)
|manual per-package fallback: `gjsify workspace @gjsify/<name> build` → `cd packages/<pillar>/<name> && gjsify publish --access public --otp <code>` → `gjsify trust @gjsify/<name>` (infers repository from origin, defaults workflow `release.yml`; `--list`/`--dry-run`/`--force`; the npmjs.com Access web UI remains the hand-off fallback) → optional `gh workflow run release.yml -f verify_only=true` (per-package ✓/✗ audit).
|pre-flight: `gjsify whoami` verifies the `~/.npmrc` token (dead token → clear exit-1 message; `--json` for CI). Diagnostic: a `404` on the publish PUT is ambiguous (dead token vs missing package) — `gjsify publish` probes `GET /-/whoami` with the same header to disambiguate.
|same procedure for `-native` bridge packages (own npm packages). PR checklist: "if this PR adds a `@gjsify/*` package, the bootstrap is done before merge or queued as the next maintainer action."
|**DONE — `@gjsify/node-runtime-{darwin-arm64,darwin-x64,win32-x64}`.** Added by #1418/#1420 and bootstrapped since: all three answer `0.45.0` on the registry, and `check-shipped-runtime-packages.mjs` reports *6 live on npm, 0 declared pending bootstrap* over an EMPTY ledger (`status/pending-npm-bootstrap.json`, shared with the pre-release closure phase). That is the bidirectional rule working as designed — a declared name that IS published is also a failure there, so the ledger emptied itself rather than rotting into an exemption. The recipe below is kept because it is the recipe for the NEXT new name, not because anything is queued. **Only the npm account owner can do this** — it needs a publish credential and an OTP, and CI has neither (Trusted Publishing requires the package to exist first, so OIDC cannot create it). From a clean `main`, per target: `node packages/node-runtime/scripts/fetch-node-runtime.mjs --target <t> --out packages/node-runtime/node-runtime-<t>/bin` (downloads the pinned Node release, verifies its SHA-256 against the release's own `SHASUMS256.txt`) → `node packages/node-runtime/scripts/verify-node-runtime.mjs --package packages/node-runtime/node-runtime-<t>` → `gjsify publish packages/node-runtime/node-runtime-<t> --access public --otp <code>` → `gjsify trust @gjsify/node-runtime-<t>` (workflow `release.yml`). `gjsify onboard` does the same sweep in one pass, but read #1407 before believing its report: it counted a publish as done while npm had stored only the tarball and no packument, so **verify each name against the registry afterwards** — `npm view @gjsify/node-runtime-<t> version` — before adding it to, or removing it from, `status/pending-npm-bootstrap.json`. The payload is gitignored and ~35–41 MB packed per target, so the three publishes are ~117 MB of upload. Afterwards the release job publishes every later version by OIDC with no manual step.
|**DONE — `@gjsify/webview2-native` + `@gjsify/webview2-native-win32-x64`.** Added by #1494 (ADR 0035), bootstrapped 2026-09-03 before the 0.46.0 cut: both answer `0.45.0` on the registry, both have a Trusted Publisher on `release.yml`, and the published bridge tarball declares `"@gjsify/webview2-native-win32-x64": "0.45.0"` — the `workspace:*` rewrite `gjsify publish` performs, read back from the registry rather than trusted. Target BEFORE bridge, which is a CORRECTNESS property and not a style preference: npm SILENTLY SKIPS an `optionalDependency` that does not resolve, so a bridge-first bootstrap yields an install that SUCCEEDS with no typelib and no DLL.
|**The gap this pair exposed — the detection existed, but only AFTER the tag.** Measured 2026-09-03. `check-shipped-runtime-packages.mjs` is the pre-release half, but its `families` is a HARDCODED list of two (`packages/node-runtime/*`, `packages/node-gi/gtk-runtime-*`); the webview2 pair is in neither. What WOULD have caught a forgotten bootstrap is `verify-published-closure.mjs`, whose roster and edge assertions both name an absent package precisely — but its job (`verify-release-closure`) sits at the END of `release.yml`, after the tag and the release record. That is the second shape `status/sections/priorities.md` § 2 names: *"a job that runs only AFTER the merge … is simply absent from the PR, which reads identically"* to one that passed. Under it, `npm:publish` passes `--tolerate-untrusted-new`, which returns `{ok: true, action: 'skipped-untrusted-new'}` — so the v0.4.20 STALL is fixed, but the replacement failure mode is worse for detection: the release goes GREEN and the name is simply ABSENT, announced by one `~` line in a serial log carrying one line per published package. Then npm skips the unresolvable edge at install time, also silently. **The fix is a move, not a new rule:** `verify-published-closure.mjs` already runs on a bare checkout with no install and no build, so it now also runs in `audit-runtimes.yml` — the required `Detect runtime-triplet drift` job, on every pull request and every push to `main` — as `--phase pre-release`. Pre-flight for 0.46.0 had been done by hand and is what made that cut safe: all 209 non-private names under `packages/`, `examples/` and `showcases/` answered on npm, 0 absent. That is now the machine's question: `createContext({discoveryRoots: ['packages']})` yields exactly those 209 names, and the phase reports *209 existing, 374 release-pinned edges examined (66 optionalDependencies, 308 dependencies)* in ~14 s.
|**the PHASE selects the assertions, not the remediation sentence** — an earlier draft of the line above claimed only the sentence changed, and #1500 refuted that with measurements. Post-release asks *"is every candidate live at `package.json`'s version"*; pre-release CANNOT, because the train version is unpublished by construction. Two of the three consequences are unfixable by the person they block: a PR adding any new package goes red with the only remedy needing a publish credential and an OTP that CI does not have, and every cut red-lines `main` plus every open PR for the whole ~200-package sweep, since `.release-it.json` puts the version-bump commit on `main` BEFORE the sweep runs (a skipped publish job — the recorded v0.31.0 case — would hold it red for the rest of the cycle). So pre-release asks **presence of the NAME**, an answer that does not move when the train moves, and drops the "this release published NOTHING" assertion, which is a statement about a completed release. Everything decided from the MANIFESTS — a `private` target, a version-skewed literal pin, an unrecognised spec shape — is phase-independent and red in both. Measured A/B on one fixture tree whose names exist only at an older version: pre-release exit 0, post-release exit 1 on *published NOTHING*.
|**the declared-gap ledger `status/pending-npm-bootstrap.json`** keeps line 13's *"or queued as the next maintainer action"* branch alive, which a required gate with no escape hatch would delete. An absent name must be LISTED with the queued action and its owner; **a listed name that IS published FAILS too**, so the list empties itself at bootstrap instead of rotting into an exemption. Read in the pre-release phase ONLY — **a release does not get to declare its own gap**, so a bridge that shipped pinning an unbootstrapped name is red on the release even though the PR that added it was green. Four more rules make an entry unable to sit forever: a name this repo does not contain, a name no release publishes (`private` or off-train — "not published yet" is a category error there), and an empty reason all fail. **ONE ledger, TWO readers**: `check-shipped-runtime-packages.mjs` reads the same file for its two by-name families and keeps the DISCLOSURE rule that is its alone (no phase of the closure script reads prose). The rot this shape avoids is measured — a draft whose bidirectional arm looped over two families only let a declared-and-published name outside them pass with exit 0 forever (#1500), so the arm lives in the reader that enumerates all 331 packages.
|**a phase-selected check needs a strict argument parser, and the first one was not.** `--phase` selects the ASSERTIONS, so mis-parsing it is the class this whole phase exists to close, reintroduced by its own interface. The refused-phase guard only ever sees a wrong VALUE; measured 2026-09-03 against the first implementation, three spellings never reached it and fell through to the post-release default with no diagnostic — `--phase=pre-release`, a bare `--phase`, and `--phaze pre-release` each ran the POST-release assertions and exited **0** on this tree, i.e. a required pull-request check green over the question #1500 refuted for a pull request, and one that would red-line `main` for the duration of every cut. Every argument is now declared and an undeclared one is fatal; `--name=value` is accepted, a missing value is refused, and a value that looks like a flag counts as missing (`--attempts --json` otherwise set attempts to `Number('--json')` — NaN, silently the default — and swallowed the `--json`).
|**the positive-fact rule needed a pre-release arm of its own.** Post-release the floor is "the release published something"; pre-release that is never true, and the roster does NOT substitute for it, because the roster fires only on an UNDECLARED absence. Measured 2026-09-03: a tree with every publishable name declared pending exited **0** printing *"Every one of 0 publishable name(s) exists on npm"* — a success claim over an empty set, which is the one sentence the script's own header forbids. Pre-release now FAILS when not one name was confirmed. The ledger buys time for a queued publish; it does not get to become the answer to the question.
|the #1494 shape reports ONCE, not twice, and a red-proof that cannot tell those apart is measuring the wrong thing: `violations()` requires `isLive(e.from)`, so when a brand-new bridge AND its brand-new target are both absent only the ROSTER fires. Only "existing published bridge + brand-new target" trips both arms. Both are e2e cases in `tests/e2e/published-closure`, which drives the script against a local fake registry through `--root` fixture trees — including the ledger, which is why that file is read `--root`-relative.

### Two entry points, because CI has already built and a human has not

`npm:publish` is `gjsify run build && gjsify run build:examples && gjsify run npm:publish:prebuilt`, and **`release.yml` runs the second half only** — its job builds the workspace in its own two steps immediately above, in the same checkout and the same container, so the script's build was a REBUILD of the tree it had just produced. Measured on run 33735989472 (v0.46.0) from the API's own step timestamps: `Build packages` 5m16s, `Build examples` 3m04s, and the publish step then spent 8m41s before its first registry `PUT` — 41% of a 21m02s step, inside a 33m02s job (#1522). The split is not "delete the build from the script": run by hand there is no preceding step, and publishing from a stale `dist/` is worse than publishing slowly, so `npm:publish` stays whole and `npm:publish:prebuilt` is the half whose precondition is the two steps above it in the workflow.

### A 2xx from npm is an ACCEPTED write, not a durable one

**Measured 2026-09-03, v0.46.0, run 33735989472.** The job `Publish @gjsify/node-runtime-darwin-arm64 (bundled Node)` PUT 53863410 bytes, npm answered 2xx, `gjsify publish` printed `+ @gjsify/node-runtime-darwin-arm64@0.46.0` and **the job went green having published nothing**: minutes later the version endpoint 404'd, the tarball URL 404'd, `npm view` still answered `0.45.0` and the packument's `time` map had no `0.46.0` entry at all. Only a manual single-job rerun made it land. Payload size was NOT the cause — `darwin-x64` at 55189094 bytes, i.e. LARGER, published fine in the same rerun — and the client had always checked `res.ok`, so the plain success path is exactly what the code was written to print. `verify-published-closure.mjs` named the missing package at the end of the run, so detection existed; what did not exist was any check inside the step that claimed the success.
|**the write is EVENTUALLY consistent, with a measurable tail.** Correlating all 199 `+ <name>@0.46.0` lines of that release's serial sweep against each packument's own `time["0.46.0"]`: **180 (90.5%) were recorded 0.4-2.4 s BEFORE our success line** (median 0.6 s) — committed before the response came back — and **19 (9.5%) were recorded 56.2-251.7 s AFTER the 2xx**, three of them after the publish job's own `completed_at` (09:28:35Z). The extreme is `@gjsify/child_process`: PUT 09:25:08.7, `+` printed 09:25:10.3, registry `time` 09:29:21.996Z, **+4m11s**. So "not there" and "not there YET" are the same observation for up to ~4.2 minutes and no client-side signal separates them — which is why the fix is a bounded RETRY and not a single probe. **The mechanism is a second server-side WRITE, not a read cache**, and `dist.signatures` proves it: every one of the 19 late packages carries TWO signatures (same keyid, different sig), every one of the 180 carries one, and the client sent exactly one PUT per package (199 distinct names, no retry, no 5xx in the log) — so `time[version]` records that second write. Corroborated client-side rather than inferred: `@gjsify/child_process`'s +251.7 s is exactly the package that failed all three attempt-1 `node-runtime-*` jobs at 09:29:05 with `ETARGET / No matching version found for @gjsify/child_process@^0.46.0`, 15 s BEFORE its recorded time. A lag of this kind does not merely delay a report; it **cascades into every job that installs the release**.
|**the fix — `gjsify publish` reads back what it PUT.** After a 2xx it asks the registry for that exact `name@version` (one abbreviated packument, `cache-control: no-cache`, the same oracle and headers as `verify-published-closure.mjs`, so the per-package check and the closure job cannot disagree about what "published" means) and prints `+` only once the registry serves it. A 2xx that never resolves is its own outcome, `publish-unconfirmed` — not `published`, not `republish-tolerated`, not an HTTP `error` — exit 1, and its message states what was PUT, what was asked and what came back, because reconstructing the incident needed the registry rather than the log it already had. The response status and body are now also printed under `GJSIFY_PUBLISH_DEBUG`; before, a 200 and a 201 were indistinguishable in the log. The version record's `dist.tarball` is checked from the same response, which is the half #1407 split apart — it proves the registry ADVERTISES a tarball, not that the bytes are fetchable.
|**WHERE it runs is a cost decision, and the number is the one above.** A confirmed-on-the-first-probe read-back costs one ~0.6 s GET, so ~2 min across the 199-package sweep. Waiting out the tail does not: those 19 residual lags SUM TO 2554 s, i.e. a sweep on the 300 s default would have added ~43 min to a 33 min job. A batched end-of-sweep check cannot live in the command either — the sweep is `gjsify foreach --exec -- gjsify publish`, one child process per package, so there is no in-process hook to collect a pending set in. **And the 2554 s only quantifies the argument; the shape of it is that `foreach --exec` THROWS on a non-zero child** (`exited with code …`), so a fatal read-back would stop the sweep mid-roster on the first lagging package and leave a PARTIAL publish — the state this page's next section calls worse than no publish at all. Deferring in the sweep is not leniency, it is the only shape that does not trade this incident for that one. Hence BOTH, split along that cost: **the read-back is per package and FATAL by default** (300 s, above the measured 252 s maximum — that is what turns a green single-package job red, and single-package jobs are where the incident happened), and **`npm:publish` passes `--verify-defer --verify-timeout 5`**, which still confirms nine packages in ten and still names the suspect against the package that PUT it, while the minutes-long tail is left to the closure job that re-asks the same question over the whole roster. `--verify-timeout 0` disables the read-back, for a registry with no packument read path.
|**A TOLERATED 409 is read back too, and the reason it first was not is worth keeping.** A 2xx is npm accepting a write it has not necessarily durably applied; a 409 is npm *asserting* the version exists and refusing to overwrite it, which sounds like a statement about the registry's own state rather than a promise about a queued one. The incident's own recovery says otherwise: attempt 3 re-PUT `@gjsify/node-runtime-darwin-arm64` and was answered `409 already published` at **09:48:49.19**, while that packument's `time["0.46.0"]` is **09:49:07.419** — 18 s later — and the closure job had found the name absent at 09:44:28. So the assertion can precede the version being served, and this is the path every re-run of a `publish-unconfirmed` package takes: exempting it would leave the documented remediation reporting a success nothing checked. Cost is one GET on a path that only runs on a re-publish. It is also what makes the 300 s window affordable despite being a SAMPLE maximum (the 19 lags cluster in ~20-30 s buckets — 56(2), 76(3), 96(3), 127(4), 157(3), 189(1), 251(3) — and a top bucket as populated as the middle ones is a distribution cut off by the observation, not one decaying to zero): a window that turns out too short costs one re-run that CONFIRMS, not an unverified success.
|**The backstop had to be made to ask the same question.** `verify-published-closure.mjs` is where `--verify-defer` sends the tail, and two things were wrong with it for that job. It read the version KEY only, so the `dist.tarball` half — #1407's shape — of every deferred publish was checked by nothing; it now reads `dist.tarball` from the same abbreviated document, at no extra request. And its propagation retry never fired for the class it is needed for: the loop exited on `violations() === 0 && probeErrors() === 0 && liveCount > 0`, which is TRUE of a ROSTER-only name (`napi`, `node-gi`, the `gtk-runtime-*`/`node-runtime-*` bundles) that is merely not recorded YET — measured on the same run, 208 of 209 live, one absent, and neither failing closure job ever printed a `round 2/3 — re-querying` line. A deferral whose backstop cannot wait out the very lag it was handed is not a deferral.

### Release closure — a PARTIAL publish can be worse than no publish

**A publish sweep has no transaction, so its ORDER is a correctness property, not a preference.** Every publish path is fail-fast (`foreach`'s sequential loop rethrows; its topological driver's `failFast` kills the in-flight set), pack time rewrites every `workspace:*` to the EXACT released version (`resolveWorkspaceProtocol`), and npm SILENTLY SKIPS an `optionalDependency` that does not resolve — a platform mismatch is not an error and neither is a version that was never published. Compose those three and an abort in the wrong place leaves `@gjsify/<bridge>@<v>` live pinning `@gjsify/<bridge>-darwin-x64@<v>` that does not exist: the install SUCCEEDS and the consumer gets the new JS bridge with no typelib and no dylib — strictly worse than the previous version's error state, because the previous version at least failed loudly. Measured at 0.27.0 from the registry: `@gjsify/webgl` 19:38:22.572Z BEFORE `-darwin-arm64` 19:38:26.291Z and `-darwin-x64` 19:38:29.551Z, i.e. the window stood open on all eleven split bridges (0.27.1 is intact — it was an unguarded hazard, never a live incident).
|**PREVENTION is the sweep's order**: the sweep runs `gjsify foreach --topological`, and the load-bearing detail is that `buildDependencyGraph`'s `includeOptional` defaults to TRUE — so a platform child is a topological dependency of its bridge and ANY PREFIX of an aborted sweep is a resolvable tree. Measured with the real CLI over this tree: 60 of the 60 platform-sibling edges published parent-first without the flag, 0 with it. `publish-napi` has published children-first by hand since ADR 0017 (its comment states the reason); the workspace sweep simply never inherited the policy. e2e `foreach-command` asserts the `optionalDependencies`-are-edges property directly — that one graph default is all that keeps the order correct.
|**DETECTION is `scripts/verify-published-closure.mjs`, and since #1500 it runs in TWO phases** — `--phase pre-release` on every pull request from `audit-runtimes.yml` (§ *New `@gjsify/*` package* above has the reasoning and the measurements) and `--phase post-release` in its own `verify-release-closure` job at the end of `release.yml`, `needs:` every publishing job so it sees the whole release (incl. `publish-napi`, whose two edges are LITERAL exact pins rather than `workspace:*`) and `!cancelled()` so a FAILED publish still reports what npm now serves. Plain Node on a bare checkout — no install, no build, so the committed CLI bundle cannot stale it and it still runs when the release that would have installed the tree is exactly what failed. Package set from `createContext` (the conformance oracle, so it cannot disagree with `audit-runtimes --check` about which packages exist); only the DEFAULT_REGISTRY string is duplicated, because `@gjsify/npm-registry` lives behind a built `lib/`.
|**it asserts COUNTS, not the absence of findings** — the whole lesson: (1) ≥1 candidate live at the released version, else the release published nothing and there was no closure to check; (2) the TREE declares ≥1 release-pinned intra-repo edge — a manifest property, and the assertion that outlives a refactor, since an enumeration that stops seeing the platform siblings would otherwise let every future release pass on an empty set; (3) on a COMPLETE release ≥1 edge actually examined (implied by 1+2, asserted anyway); (4) every examined edge resolves. **An edge it cannot DECIDE is a FAILURE naming the target, never a skip, and the enumeration may drop EXACTLY ONE shape: a target that is not a package of this repo at all** (an external dep is the registry's problem). Dropping every target that was not itself a release candidate — the first spelling — silently swallowed two dead pins, both measured exiting 0 on "Every one of 1 … edge(s) … resolves": in-repo version SKEW behind a literal pin (parent at `<v>` declaring `"…-darwin-arm64": "<v>"` while that child's manifest sat at `<v-1>`), and a published package pinning a `private` sibling (`resolveWorkspaceProtocol` rewrites `workspace:^` to the target's version whether or not it is publishable). Both are decided from the MANIFESTS, no registry involved. **It deliberately does NOT fail an INCOMPLETE release in which no published package has a pinned dependency** — that is precisely what prevention promises, it can only co-occur with an already-red publish job, and a second misleading red is how a job gets ignored. But not-failing is not the same as not-reporting: **anything the script finds noteworthy reaches the artifact a human opens** — `problems` render as `> [!CAUTION]` and the not-fatal `notes` as `> [!WARNING]` ABOVE the summary table, which also carries a `Verdict` row in words, and notes are additionally emitted as `::warning::` annotations (the one channel that survives an unwritable summary file and renders next to the green check). The "NO edge was examined" sentence used to go to stdout ONLY, so the most likely partial release rendered as `Pinned edges examined | 0` with no alert under a green check — a missing signal reading as a pass, inside the guard built to remove that class.
|why exact-version presence is a complete answer with no semver engine: the released version is the MAXIMUM of the train, so `<v>`, `=<v>`, `^<v>` and `~<v>` all admit exactly one existing version. Absence is re-queried over a few rounds before it becomes a verdict (npm's CDN can serve a packument minted before the publish; a false red at release time costs a re-run of a workflow that did its job). **Recovery is a re-run**: `--tolerate-republish` no-ops for everything that already landed and publishes the rest. Detection without prevention would only SHORTEN the window, which is why the two shipped in one change.
|scope: manifest-declared edges only. `@gjsify/gtk-runtime-*` and `@gjsify/node-runtime-*` are resolved by NAME at install time with no `optionalDependencies` entry — whoever SHIPS an app declares the bundle, never the library that uses it (#910, reverted in #920) — so there is no edge to check. Their publish jobs USED to be the only guard, which meant the report arrived at release time, on the release: measured 2026-08-30 with `@gjsify/cli@0.44.0` as the control, all three `@gjsify/gtk-runtime-*` resolved at `0.44.0` and all three `@gjsify/node-runtime-*` answered 404, while every CI leg that stages an interpreter stayed green because it symlinks the package straight out of the tree. `scripts/check-shipped-runtime-packages.mjs` is the pre-release half — it enumerates both families from the tree (an empty family is a FAILURE, not a pass), asserts each has a publish leg in `release.yml` and a `@release-it/bumper` `out` glob, then asks the registry; an unpublished name must be listed in the shared `status/pending-npm-bootstrap.json` ledger AND disclosed in every doc that recommends depending on it, and a ledger entry naming a package that IS published fails too, so the list empties itself on bootstrap rather than rotting into an exemption. The DISCLOSURE half is this check's alone; the ledger's whole-tree rules live in the pre-release closure phase, which enumerates all 331 packages instead of two directories. One correction while it was being shared: this file used to say the closure script "cannot see" these six because its package set is the root `workspaces`. It is not — it passes `discoveryRoots: ['packages']`, precisely so `packages/napi/*` and `packages/node-gi/*` are not dropped, so all six ARE in its candidate set and its ROSTER arm does ask about them (measured 2026-09-03: 209 publishable candidates under `discoveryRoots` including these six, against 199 from the root `workspaces` globs including none — candidate count against candidate count, where an earlier spelling compared the 209 with the globs' TOTAL of 319). What is true is narrower and still the reason this check exists: no `optionalDependencies` edge points at them, so the EDGE arm is blind to them either way. The node-runtime resolver is `utils/ship/node-runtime.ts`, mirroring `resolveGtkRuntimeBundle()`; override `GJSIFY_NODE_RUNTIME`. The GTK-closure resolver on the SHIPPING side is `resolveGtkRuntime()` in `utils/ship/app-runtime.ts`, which mirrors `resolveGtkRuntimeBundle()`'s four candidates so what gets COPIED into a `.app` and what that `.app` FINDS at runtime cannot disagree; override `GJSIFY_GTK_RUNTIME`. What a third-party app author adds to their own `package.json` for a self-contained macOS bundle is listed in `docs/ship-formats.md` § *What a self-contained `.app` carries* and proven by `tests/e2e/ship-macos`.
