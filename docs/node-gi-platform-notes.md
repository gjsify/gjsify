|cross-runtime (#699): the ONE N-API binary also runs on **Bun and Deno**. Two libuv couplings made portable: (1) the toggle-ref GC drain uses `napi_threadsafe_function`, NOT `uv_async_*` — Deno exports no libuv symbols and Bun panics on `uv_async_init`; this is the FIRST wall (every GObject creation arms it). (2) main loop: Node keeps the uv-nesting bridge; Bun/Deno get `iterateMainContext` (pure `g_main_context_iteration`) driven from a runtime timer (`startMainContextPump`). Lazy symbol binding keeps never-called `uv_*` unresolved on Deno. Prebuild is Deno's ONLY install path (no postinstall build). `runAsync` imports `setImmediate` from `node:timers` (not a Deno global) + defers a blocking `run()` on all three. Verified: Node 261/261 (incl. GC-stress), Bun full core parity 215/215, Deno 26-file conformance subset green (`scripts/cross-runtime.mjs`; run ONE process per file — Bun/Deno share a process across files unlike Node's pool). **Measured on a musl aarch64 DEVICE, off CI** (2026-08-03). This does NOT close an arm64 hole — `node-gi.yml`'s `arm64` leg already builds the addon and runs the gjs/node/bun/deno golden-diff on a native `ubuntu-24.04-arm` Fedora container, then re-verifies the STAGED prebuild with `test:bun`+`test:deno`. What that leg structurally cannot see is what was measured here: **musl** (CI is Fedora/glibc everywhere), a **real consumer install** (`gjsify install @gjsify/node-gi@0.27.0` into a standalone project consuming the PUBLISHED tarball, not the checkout + a locally built addon), and **gjs 1.86.0** (the declared floor; Fedora 44 ships 1.88.x). Host: OnePlus 6T / postmarketOS, no node, no C++ toolchain. Result — **Bun 1.3.14 38/38** cross-runtime files, **Deno 2.9.4 35/38 + the 3 known #47 teardown non-gating, 0 failed**, and the new `signal-gtype-params` conformance program byte-identical to gjs on BOTH gjs 1.88.1 and gjs 1.86.0. Two libc facts fell out of it, both worth keeping: (a) the glibc-declared prebuild LOADS AND RUNS on a pure-musl host under Bun — musl's ldso resolves the `libc.so.6`/`libm.so.6` DT_NEEDED entries to ITSELF (its reserved `libc./libm./libpthread.…` name list), and the remaining NEEDED libs (`libglib-2.0`, `libgirepository-2.0`, `libcairo`, `libstdc++`, `libgcc_s`) all exist musl-built on Alpine. A musl TARGET would buy the arm64 host nothing today. **A successful LOAD is not proof that the symbol set resolved** — that claim shipped here and is wrong. Root-caused with the REAL artifact (`@gjsify/sab-native`'s pre-#955 prebuild, sha256 `a4437e96…` arm64 / `6696d423…` x64), measured on aarch64 musl AND in `alpine:3.24` x86-64: musl reports exactly TWO unresolvable symbols (`fcntl64`, `__cmsg_nxthdr` — the two `sab-helpers.c` names; `ftruncate64`/`mmap64` DO resolve via musl's LFS weak aliases), and `dlopen` behaves OPPOSITELY by mode: **`RTLD_NOW` fails at load, `RTLD_LAZY` LOADS** and the process dies at the first call through the deferred `JUMP_SLOT`. Both arches behave IDENTICALLY — there is no arch divergence. GI opens typelib backers with `G_MODULE_BIND_LAZY`, i.e. the lazy path, so a glibc-only symbol genuinely DOES hide from a load on musl, exactly as `packages/node/sab-native/src/vala/sab-helpers.c` describes; that comment is correct and must not be "fixed". **Methodological trap worth remembering:** a hand-built probe DSO does not reproduce this — Alpine's gcc defaults to `-z now`, stamping `DT_FLAGS BIND_NOW` into the probe, which overrides `RTLD_LAZY` and makes it fail at load like `RTLD_NOW`. The shipped prebuilds carry no `BIND_NOW` (Fedora prebuild toolchain), so a synthetic reproduction inverted the result and produced two successive wrong mechanisms before the real file was loaded. Always load the ARTIFACT. Second-order: a weak undefined symbol also resolves to NULL and dies at first call, so node-gi's own prebuild is cleared by an AUDIT rather than by its load — of 579 undefined symbols exactly 5 are weak and the only 3 unresolvable ones (`_ITM_{,de}registerTMCloneTable`, `__gmon_start__`) are NULL-guarded gcc boilerplate. What DEFEATS the hiding is binding eagerly: `.github/prebuild-toolchain/musl-build.sh` asserts `dlopen(RTLD_NOW)` for exactly this reason (post-#955 verified clean there on both arches), and its job is a live gate now — it lost its `workflow_dispatch` gate and its `continue-on-error`, so it runs on every PR and push `prebuilds.yml`'s paths reach. It still does not cover THIS addon: it builds `@gjsify/sab-native` + `@gjsify/lightningcss-native`, never node-gi (§ open-todos). Without a musl machine at all, the static equivalent is the glibc-floor `SHT_GNU_verneed` audit (#963) — which is what actually caught this. Also settled: there is no `gcompat`/`libc6-compat` and no `libc.so.6` FILE anywhere on that device, and musl's own `ldd` prints `libc.so.6 => /lib/ld-musl-x86_64.so.1`, which is the positive confirmation of the self-aliasing in (a). (b) Deno publishes NO musl build at all (`aarch64-unknown-linux-gnu` only), so its aarch64 leg has to run in a glibc environment — here `org.gnome.Platform//49` (glibc 2.42, gjs 1.86.0 = the repo's declared floor, which CI never exercises). Deno needs no `--node-modules-dir` flag when the tree is already materialised (`manual` and the default both worked); its `deno test` leg in `cross-runtime.mjs` passes `--node-modules-dir=auto`, which makes that leg need REGISTRY access for `node-addon-api` (a build-time-only dep no test imports) — invisible on CI, a hard stop in a network-less sandbox.

Only the SYMPTOM differed (`Unsupported type void, deriving from fundamental void`). node has no rpath, gjs has one into the wrong keg; the loader gap is the same. The gjs half is repaired one hop EARLIER, in the LAUNCHER: `buildNativeEnv()` in `@gjsify/cli` puts the same libdirs on the spawned gjs child's `DYLD_FALLBACK_LIBRARY_PATH` — a re-exec is impossible under gjs, and a bundle cannot repair it from inside (GI resolves typelib backers before the bundle's first line). |**batteries-included GTK bundles — `@gjsify/gtk-runtime-<os>-<arch>`** (`packages/node-gi/gtk-runtime-*`, tier 3, `os`/`cpu`-gated, `gtk/` payload GITIGNORED and built only on a runner of that target): the "no Homebrew / no gvsbuild" answer for the platforms where a system GTK is not a given — `darwin-arm64`, `darwin-x64`, `win32-x64`. The LOADER (`node-gi/gtk-runtime.js`) keys on NOTHING target-specific: it derives `${process.platform}-${process.arch}` and probes four candidates, so a new bundle is found by the mechanism that found the first. **A bundle must NEVER be a dependency of `@gjsify/node-gi`** — an installed bundle satisfies candidate 4, so a job that built the addon against Homebrew GTK re-execs onto the BUNDLE's typelibs with native code linked against a DIFFERENT GTK: wrong method entries, then a 29-minute timeout (#910 did it, #920 reverted it). **That still holds, and the precedence question it left open is now SETTLED — [ADR 0023](adr/0023-gtk-source-precedence.md).** node-gi declares no bundle; whoever SHIPS an app declares it (for the showcases, the `gjsify` CLI, which assembles the dlx tree). Which one wins is `decideGtkSource()`: a per-OS default (linux → system first; win32/darwin → bundle first), `GJSIFY_GTK_PREFER=bundle|system` to override, and one hard rule above the policy — a FROM-SOURCE addon never gets a bundle by default, which is #910 itself and the only part an override (explicit consent) may lift. Prohibiting the dependency alone was not enough: it left every Windows user with no GTK at all (#1063), because nothing installs the bundle and Windows ships no system stack. **ONE builder per OS, never per arch**: `packages/node-gi/scripts/build-gtk-runtime-darwin.mjs` serves both darwin packages, because nothing in the relocation pass (otool closure walk → `install_name_tool` `@loader_path` → ad-hoc `codesign`, mandatory on arm64 and harmless on Intel) is arch-dependent; the target is DERIVED from the running Node and `--out` is cross-checked against the destination package's own `os`/`cpu`, so a leg cannot write one arch's closure into the other's package. win32 keeps its own builder — genuinely different (no relocation; Windows resolves DLLs by search path at `LoadLibrary`). It lives under `packages/node-gi/` and NOT in repo-root `scripts/` on purpose: `packages/node-gi/**` is both the affected classifier's IGNORE list and `node-gi.yml`'s `paths:` trigger, so an edit runs node-gi's CI instead of forcing a full `main.yml` run. **Every macOS relocation assertion is brew-prefix DERIVED, never the literal `/opt/homebrew`** — that literal is the Apple-silicon prefix and is vacuously absent on Intel (`/usr/local`), so a hardcoded grep passes while proving nothing. Adding a target = a new published npm NAME ⇒ `gjsify onboard` before the release that ships it (§ New `@gjsify/*` package). **A bundle ships exactly the typelibs it can BACK, and the mapping is read from the typelib, not a table.** GI resolves a namespace with `g_module_open(<shared_library>)` out of the typelib header, so a shipped typelib whose library is absent RESOLVES, advertises its classes and dies in the constructor with "Failed to load shared library" — worse than an absent namespace, which fails cleanly. Measured on the published 0.27.1 tarballs: 6 of 38 darwin typelibs and 3 of 37 win32 typelibs were in that state (`Adw-1` on all three). The shared rule lives in `packages/node-gi/scripts/typelib-backers.mjs` (used by BOTH builders, unit-tested on Linux in `node-gi/test/gtk-runtime-bundle-gates.test.mjs`): drop an unbacked typelib, but FAIL the build when a KEPT typelib DEPENDS on it — `Pango-1.0` depends on `HarfBuzz-0.0`, so dropping HarfBuzz would break Pango/Gdk/Gsk/Gtk and the repair is the seed (`libharfbuzz-gobject`), never the drop. The finished bundle is re-read off disk and must ALSO assert positives: ≥1 backed typelib and every promised namespace present (`REQUIRED_NAMESPACES`, plus `Adw`+`GtkSource` under `--windowing`), so a filter that removed everything cannot pass green. **`release.yml` publishes the `--windowing` SUPERSET; the display-free default is the CONFORMANCE variant `node-gi.yml` builds.** Through 0.27.1 the release built display-free, so npm carried `"windowing": false, "dataBytes": 0` — an `Adw-1` typelib with no libadwaita, no `gschemas.compiled` (a hard `Gio.Settings` blocker) and no icon theme. **The third-party terms travel with the binaries** (`bundle-licenses.mjs`): `gtk/licenses/` + `gtk/THIRD-PARTY-NOTICES.md`, derived from the SOURCE PREFIX so the set cannot drift from the closure — per-binary on darwin (every dylib realpaths into `…/Cellar/<formula>/<version>/`, terms from the keg's own `.brew/*.rb`; an unattributable dylib FAILS the build) and prefix-wide on win32 (a flat gvsbuild tree cannot prove a per-DLL mapping, so the whole documented corpus ships and the notice says so). The darwin notice also states the modification the LGPL asks about: `install_name_tool` + ad-hoc `codesign`. **And the runtime DATA must be REAL FILES — copy it with `copyTreeDereferenced()` (`bundle-data.mjs`), NOT with `cpSync(…, { dereference: true })`.** That flag governs only the stat of the path handed to `cpSync`; every NESTED link is still copied as a link (measured: the first attempt at this fix passed it and 859 links under `share/icons/Adwaita` survived, each into `…/Cellar/adwaita-icon-theme/…`). Homebrew links a keg's tree into its prefix, `cpSync` defaults to `dereference: false`, so `share/icons/<theme>` was copied as a LINK into the Cellar — 0.2 MiB of links where the theme is 22 MB of files, and a symlink into a Cellar path is worthless in a tarball. Two things hid it: `actions/upload-artifact` FOLLOWS symlinks (the artifact looked complete) while `npm pack` does not, and the manifest's size came from `statSync`, which follows too — so `dirSize` now uses `lstat` and `findSymlinks` (`bundle-data.mjs`) FAILS a windowing build with any symlink under the data tree. A `test -d share/icons` CI check cannot catch this: a link to an existing directory satisfies it on the build host. **AND a declared data set that is MISSING must fail the build, never warn** (`verifyWindowingData`): every data step in both builders was warn-and-continue, which is how `"dataBytes": 0` reached npm, so the requirement is now re-read off the finished bundle and DERIVED — a set is required iff the bundle ships the namespace it belongs to (`Gio`→`gschemas.compiled`, `Gtk`→an icon theme with an `index.theme` AND files, `GdkPixbuf`→the gdk-pixbuf image loaders + `loaders.cache`, `GtkSource`→`share/gtksourceview-5`), which the `--windowing` namespace floor guarantees is non-empty. **ONE data-set list, BOTH builders.** The loaders lived in a win32-only sibling `build-gtk-runtime-darwin.mjs` **§ 2b — early, with the dylibs, not with the data**, because they are Mach-O images in a NESTED dir: `@loader_path` is the DEPENDENT's own dir, so a module at `lib/gdk-pixbuf-2.0/2.10.0/loaders/` needs `@loader_path/../../..` (hence `relocate()`'s `depPrefix`), `librsvg` must be a closure SEED because nothing LINKS it (a formula dep reached through `g_module_open` — which is also why `Rsvg-2.0.typelib` used to be dropped, the visible trace of the missing decoder), and § 3's `verifyRelocation` then covers them like every other image. **darwin's `loaders.cache` names each module `@loader_path/gdk-pixbuf-2.0/2.10.0/loaders/<leaf>`, NOT the bare leaf win32 uses.** Measured all four shapes on macOS 15.7.8 / brew gdk-pixbuf 2.44.7, with the addon |**The loader's contract — and what Linux does not need.** On **Linux** a distro GTK needs no help at all: the typelib's bare library leaf resolves for `Gtk`/`Gdk`/`Adw`/`Pango`/`Graphene` with no `GI_TYPELIB_PATH` and no `LD_LIBRARY_PATH`, and `Gtk.DrawingArea` subclasses correctly — measured both on the musl device above and inside `org.gnome.Platform//49`, because the system loader's default search path already covers the distro's own libraries. Worth stating explicitly, because it is exactly the step that FAILS on darwin (bullet above): a loader-path failure of that shape is never a node-gi or runtime defect. Where a BUNDLE answers instead, `resolveGtkRuntimeBundle()` (`node-gi/gtk-runtime.js`) probes four candidates in order — an explicit `GJSIFY_GTK_RUNTIME` dir, a staged `prebuilds/<target>/gtk/`, the sibling monorepo checkout, `require.resolve('@gjsify/gtk-runtime-<target>')` — and the last already covers a hoisted `node_modules/@gjsify/gtk-runtime-<target>`, so declaring the dependency edge would need no loader change (and must not be declared, for the #910 reason above). A bundle has two closures: the DEFAULT display-free set (loadable libraries + typelibs) and the `--windowing` SUPERSET that adds the runtime DATA a real window needs — the gdk-pixbuf loaders + `loaders.cache`, compiled GSettings schemas (`gschemas.compiled`), the Adwaita/hicolor icon themes + `icon-theme.cache`, and Fontconfig config/cache. `maybeWireGtkWindowingEnv` then keys the ENV wiring on the `gschemas.compiled` MARKER rather than on the target: with windowing data present it wires `GSETTINGS_SCHEMA_DIR` / `GDK_PIXBUF_MODULE_FILE` / `XDG_DATA_DIRS` / `FONTCONFIG_*`, and a display-free bundle carries no marker, so the wiring is a strict no-op and that load stays byte-unchanged. For a SPAWNED child the same job is the CLI's `detectNativePackages()` / `buildNativeEnv()`.

|**An APP's own GI library is a THIRD case, and neither of the two above covers it — `GJSIFY_GI_LIBRARY_PATH`.** An application that carries its own typelib plus the library behind it (`gjsify.ship.bundledTypelibs`) stages the pair FLAT in one directory of its own and points `GI_TYPELIB_PATH` there, so GI resolves the typelib and then `g_module_open`s a bare leaf nothing has located. On **linux** the generated launcher's `LD_LIBRARY_PATH` covers that. On **macOS it cannot be covered by an environment variable at all**: dyld strips every `DYLD_*` from a restricted process, and a hardened-runtime, Developer-ID-signed main executable IS restricted — a launcher that exported one works in development and stops working the day the artifact is signed. `activateGiLibraryPath()` did not cover it either: its dirs are the GTK bundle's `libDir` or `systemGiLibraryDirs()`, both answering "where is the GTK stack". Nor does the `GI_TYPELIB_PATH` derivation inside `systemGiLibraryDirs()` — that takes the typelib dir's PARENT, because GI's INSTALL layout puts typelibs in `<libdir>/girepository-1.0/`, while an app stages typelib and library as siblings, so the parent is a real directory holding nothing. So `GJSIFY_GI_LIBRARY_PATH` (`:`-separated, `;` on win32, absolute entries only — a relative one would resolve against the working directory, which for a double-clicked `.app` is `/`) is read by node-gi ITSELF, in JS, and handed to `gi_repository_prepend_library_path()`; dyld never sees it, which is the entire point. Its entries go in FRONT of the policy's: an explicitly-set variable is consent and outranks an inferred location (the precedence `GJSIFY_GTK_RUNTIME` already has over the probed bundle candidates), and on an overlapping leaf the app's copy is the one its own typelib was compiled against — splitting that pair is #910's ABI mismatch, not a missing file. **Measured at the loader, not at the wiring**: `test/gi-library-path-loads.test.mjs` copies a real backer into a scratch dir, points the variable at it and reads back which file the process actually mapped (`process.report` — `/proc/self/maps` on linux, `_dyld_get_image_name()` on darwin), against a control run with the variable unset that maps the system copy. It runs on the linux `build-test` leg via `npm test` and on BOTH macOS arches as its own step in `node-gi.yml`, with the loader variables unset and the TAP pass count asserted (a skip exits 0).

|**The release gate asserts a DECODE, not a file count (#996).** `verify-bundle-manifest.mjs` required every `windowingData.verified` set to have `files > 0`, and the published `darwin-x64` 0.28.0 bundle satisfied that perfectly — 860 icon files, `verified icons: 863` — while ZERO of them decoded: the addon kept its absolute Homebrew install names (`/usr/local/opt/glib/lib/libgobject-2.0.0.dylib`), so a Mac that HAS Homebrew glib loaded two GObject registries, type identity failed across the boundary and `Pixbuf.new_from_file()` on the bundle's own `open-menu-symbolic.svg` returned −1×−1. Same false-positive shape as `Pixbuf.get_formats()` listing `svg` on win32 while every decode failed, and the class [ADR 0018](adr/0018-os-axis-declaration.md) names: **do not let a file count stand in for a load.** The gate is a pure MANIFEST reader by design (the build log is not shipped), so the decode happens where the target platform is — in the builder — and travels to the gate as a RECORD: `packages/node-gi/scripts/decode-probe.mjs` spawns a child that points node-gi at the freshly built bundle (`GJSIFY_GTK_RUNTIME` + `GJSIFY_GTK_PREFER=bundle` + `NODE_GI_NATIVE=<addon>`), decodes a `.svg` and a `.png` THROUGH THE BUNDLE'S OWN LOADER — the bundled PNG when one ships, otherwise the decoded SVG `savev`'d to a temp PNG and read back (recorded as `source: 'saved-from-svg'`), which still drives the bundle's png loader and cannot fail a correct SVG-only icon theme — and writes `windowingData.decodeProbe = { ok, platform, gtkSource, bundleIsProbeTarget, svg: {file,width,height}, png: {…}, formats, loaderDir, loaderCache, loaderModules }`.
