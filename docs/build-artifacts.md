# Committed artifacts — git hooks, freshness, and what an exit code proves

> Detail for the root [AGENTS.md](../AGENTS.md) § Committed artifacts.
> The committed `packages/infra/cli/dist/*.gjs.mjs` bundles are the bootstrap path,
> so their staleness is a correctness problem, not a hygiene one.

## Git hooks

Plain bash hooks under `.githooks/`, no husky. `core.hooksPath` wired automatically by `gjsify install` (`maybeInstallGitHooks()`, gated so consumer projects are skipped); manual `node scripts/install-git-hooks.mjs` (idempotent; `--uninstall`, `--quiet`).
|`pre-commit`: staged files touching `packages/infra/cli/{src,package.json}` / `resolve-npm/lib/` (maps the bundle inlines) / `rolldown-plugin-gjsify/src/` (the pipeline the bundle inlines) → rebuilds + re-stages `packages/infra/cli/dist/{cli,affected}.gjs.mjs`; touching `packages/infra/tsc/` → rebuilds `dist/tsc.gjs.mjs`. Resolves `gjsify` via workspace `.bin` → PATH → committed bundle. **The hook AUTO-STAGES what it built, so a checkout that cannot resolve the polyfills would commit an unloadable bundle unseen** — that is why `gjsify build --app gjs` itself refuses to emit a bundle that still statically imports bare `node:` modules (`gjs-bundle-guard.ts`). **The oracle is the bundler's own module graph (each chunk's `imports`), never the emitted text** — a text scan cannot tell a statement from a `node:` specifier quoted in a string (a `@gjsify/process` test name and the CLI's `giNodeShimSource()` template both contain one; a grep gate failed them). The allowlist is EMPTY and stays that way. Nothing between `gjsify build` and CI ever executes the emitted GJS bundle — tsc/lint/unit/e2e all run the Node entry — so a green `--app gjs` exit was the only signal, and it lied.
|bypass: `--no-verify` or `SKIP_GJSIFY_HOOKS=1`. The hook is BEST-EFFORT, never the invariant: its trigger list is a four-path heuristic while the bundle inlines the whole workspace-dep closure, and it warns-and-skips with no reachable CLI (a bare worktree — the #821 case). The CI rebuild-and-compare below is what is exhaustive. Tests: `tests/e2e/git-hooks-cli-bundle-staleness/`.
|`post-rewrite`: covers the two rewrites `pre-commit` structurally CANNOT see — `git rebase` stages nothing, and `commit --amend` with nothing newly staged presents an empty staged set, so both leave a committed bundle stale with every local check green. WARNS only: a rewrite is not a place to block, and mid-rebase there is nothing safe to rebuild. Two verdicts — REBASED-UNDER (the new base moved closure source under a committed bundle, the #897 case) and NOT-REBUILT (the branch changed closure source without committing the bundle). Prefers the real closure oracle (`gjs -m dist/affected.gjs.mjs --changed-from-stdin --format=globs`), else falls back to `pre-commit`'s four-path prefix scan and SAYS SO — silence from an under-approximating scan reads as "all clear". Tests: `tests/e2e/git-hooks-post-rewrite-bundle-guard/`.
|**A child spawned with a hand-built `env` MUST carry `HOME`, and every `spawnSync` MUST carry a `timeout`.** That suite's sanitized-PATH test spawned `bash` with the environment reduced to `{PATH}` alone, and such a bash does not return: it spawns processes WITHOUT BOUND. Measured on linux-x64 — ONE 3-second call left 12794 `bash` processes; a suite run reached 4329 of them holding 78.7 GB, and the kernel resolved the resulting global OOM by killing unrelated desktop processes. Add `HOME` and the identical call is instant: 60 s hang + 12794 processes → 100 ms + 0. It hid because the PROBE and the invocation it gated were built from DIFFERENT env objects, so the call that hung was never the one under test — a precondition executed under another environment proves nothing about the one it guards. Build the child env ONCE and share it. The missing `timeout` is why it cost a day rather than a minute: an unbounded runaway is a MACHINE failure instead of a test failure, and the runner never returns a result to read — the first three attempts reported only `'test failed'` after 158 s, which is what a hang looks like from outside. `assertSpawnCompleted()` exists so a timeout reports as a timeout instead of arriving at the assertions as `status: null` + empty stdout, i.e. a confident diagnosis of the wrong failure.

### Committed-artifact freshness — verify against the SOURCE, not the version string

Tracked, version-locked build outputs: `packages/infra/cli/dist/{cli,affected}.gjs.mjs`, `packages/infra/tsc/dist/tsc.gjs.mjs`, `@gjsify/tsc`'s shipped `lib/lib*.d.ts`. FOUR guards, each catching a failure the others structurally cannot — do not collapse them.

|**Resolves at all** (`unresolved-workspace-import.ts`, every `gjsify build`, RESOLVE time): § Build — refuses the build when a `@gjsify/*` substitution can't resolve, on all four targets, naming importer + cause.
|**Is structurally loadable** (`gjs-bundle-guard.ts`, `--app gjs`, build time): refuses to emit a bundle whose module graph still statically imports bare `node:` — the shape an unresolvable alias target produces, which otherwise "succeeds" with a warning and writes an artifact aborting on every stock GJS. Stays alongside the resolve guard: it is a property of the ARTIFACT, covering bare `node:` arriving by routes the resolver doesn't model (user `--external node:fs`, a future plugin `{external:true}`).
|**Reaches only globals something installs** (`node-bundle-guard.ts`, `--app node`, build time): a GJS ambient global (`print`/`imports`/…) is a FREE IDENTIFIER, not an import — no chunk's `imports` mentions it. It is seeded by `@gjsify/node-gi/globals`, injected only when `detectNodeGiGlobals` finds one in a PRE-build analysis bundle — a PREDICTION. The guard re-runs the SAME acorn pass over what was actually emitted and fails on disagreement. Skipped when the shim WAS injected, and under `--globals none`. Not a second opinion — ONE oracle, two passes that must agree; disagreement = pipeline bug, never user code. Exactly that shipped: the analysis ran BEFORE the explicit-`--globals` register stub resolved, one of the two signals `isGjsSourceBuild()` reads, so the analysis graph routed `/register`→`@gjsify/empty` + emptied `@girs/*` while the real build resolved both — every ambient global reachable only THROUGH a register module was invisible; the excalibur showcase built green and died `ReferenceError: imports is not defined` on node AND bun while gjs ran fine.
|**Runs + reports the right version** (`.github/actions/gjsify-setup`, every job, BEFORE the build-output cache restore): boots each bundle under stock `gjs`, compares `--version` to the source of truth, + the single-`@gjsify/web-streams`-copy assertion. CANNOT catch a stale bundle — a bundle built from old source still reports the right version. Not theoretical: #821 changed the curated browser aliases (data the bundles INLINE) and merged fully green with both bundles stale; the pre-commit hook had warned-and-skipped itself (worktree, no node_modules).
|**Reproduces from source** (`scripts/verify-committed-bundles.mjs`, one step in `main.yml`'s build job, AFTER Build): rebuilds every committed artifact and compares BYTE-FOR-BYTE against `git show HEAD:<path>`. Byte-reproducibility is measured, not assumed — the bundles bake no absolute path/timestamp/host state, and the rebuild always runs the Node CLI entry so npm-vs-native engine never enters the comparison. **The property depends on DETERMINISTIC ENTRY ORDER, pinned in `globToEntryPoints`** (each glob's expansion sorted; pattern-list order preserved). Entry order is a bundle INPUT: rolldown derives exec order from a DFS starting at the entries and renders chunk imports in that order — while fast-glob's concurrent walker yields COMPLETION order (measured: 9 distinct orderings in 60 runs). Unsorted, a minority ordering emitted reordered imports + flipped `$N` suffixes, every bundle inlining those libs drifted a few bytes, and the build cache kept the raced order alive — which is why the divergence looked machine-bound. Guarded by `entry-points.spec.ts` + `tests/e2e/deterministic-library-build/`.
|what makes it trustworthy: (a) expected bytes from git, NOT the working tree (`gjsify run build` rewrites those files in place — a working-tree comparison would pass while checking nothing); (b) the artifact SET is discovered from `git ls-tree HEAD` and a bundle with no rebuild recipe is a hard error (exhaustive by construction); (c) pre-run bytes restored on exit, ONE snapshot before all recipes + ONE restore after (`--with-dependencies` rewrites `tsc.gjs.mjs` mid-run); (d) `--with-dependencies` pins the INPUTS — in CI the workspace `lib/esm` trees come from a cache whose `restore-keys` fallback can be another revision's, so rebuilding the closure first makes a mismatch mean staleness.
|the `@gjsify/tsc` recipe runs `GJSIFY_TSC_REFRESH_LIBS=1` on purpose: `pickLibSource()` normally KEEPS committed libs (a refresh races concurrent readers), which would make comparing them a check that cannot fail; the verify step runs alone, so forcing regeneration gives the version-locked lib set real coverage (a `TYPESCRIPT_VERSION` bump with un-regenerated libs is exactly the v0.7.2 `TS6053` cascade).
|**it BOOTSTRAPS the tree it needs — `--rebuild` is the release path.** Under GJS the only engine is `@gjsify/rolldown-native`, whose JS facade `lib/` is a build output `gjsify install` does not produce; on a fresh clone every recipe died "no usable bundler engine". `ensureBuildableWorkspace()` runs `scripts/bootstrap-native-facades.mjs` unconditionally, and **the COLD/WARM branch lives in the bootstrap itself** (`ensureNodeCliEntry()`: root `build:infra` when the Node CLI entry is absent, else build the facades directly; mtime-idempotent; recursion cut by a marker env). That move is the point: with the branch at the call site exactly one caller was correct — the release `publish-napi` job (checkout+install by design) missed it and `@gjsify/napi` was the ONE package that missed the v0.24.1 train while the release was otherwise green. `--print-plan` reports the branch without spawning (e2e `tests/e2e/bootstrap-cold-tree`). The engine's failure message is DERIVED from disk state (`diagnoseNativeEngine()`), not the rarest cause.
|**the cold-tree recovery itself needs NODE, and on a Node-less GJS host the diagnostic used to recommend two commands that both fail there.** Measured on postmarketOS/aarch64 (musl, gjs 1.88.1, no node) and reproducible anywhere by dropping the only `node` off `PATH`. **The distinction the message now draws is the load-bearing one: a CONSUMER install is unaffected** — the published `@gjsify/rolldown-native` tarball DOES contain `lib/esm/index.js` (verified against 0.26.1: 27 files, `package/lib/esm/index.js` present), and it is the workspace SYMLINK in a clone that shadows it. So "the engine's facade is missing" means "you are in a clone", never "the published package is broken" — reading it the other way is how this was first diagnosed as a dangling `main` in the tarball. `gjsify tsc` closed the compiler half (§ Sixth axis); the residual four `node scripts/*.mjs` calls are tracked, and the message says the limitation out loud instead of prescribing around it.
|**deliberately NOT unified with `main.yml`'s warm-cache probe (#862)**: the probe is a READ-ONLY post-condition on the WHOLE tree ("may a selective build trust this cache") that only DECIDES a path; the preflight is a pre-condition on TWO TOOLS that REPAIRS them. Strict containment, verified: every preflight path is a DECLARED output `verify-package-outputs.mjs` asserts, so probe-warm ⇒ preflight-no-op; the converse must NOT hold (a tree missing an unrelated `lib/types` is COLD for the probe yet buildable). Unifying breaks both directions. What they share is the POLICY: incomplete ⇒ "do the fuller thing", never "error".
|**scope:** ANY source the bundle inlines stales it, not just the hook's four paths — `@gjsify/{tar,semver,buffer,workspace,npm-registry,node-globals,…}` are all inlined. Editing one and committing without rebuilding reds the PR with exact commands. **Still unguarded:** committed `prebuilds/**` binaries (provenance proves inputs; nothing byte-compares, `status/open-todos.md`); `register-globals-closure.mjs` deliberately ungated (stale = fail-soft slower builds; its `--check` costs a full per-register sweep).

### Build outputs — an exit code is not evidence that anything was WRITTEN

`scripts/verify-package-outputs.mjs` (one step in `main.yml`'s build job, after Build) asserts every path a non-private workspace DECLARES — `main`/`module`/`types`/`typings`/`browser`/`bin`/`gjsify.bin` + every `exports` condition, recursively — exists on disk; a miss fails the build. Package set + path set both DERIVED (workspaces globs × package.json), deliberately NO per-package opt-out (an opt-out list drifts and then lies). `--only`/`--root`/`--allow-unbuilt` are for local iteration, never CI.
|**the failure it exists for (#67):** with `composite`/`incremental`, a `.tsbuildinfo` outliving its output tree makes `tsc` consider the project up to date — prints nothing, writes nothing, **exits 0**. Reproduced verbatim in `@gjsify/adwaita-core`. The package then publishes a `types` entry that does not exist; consumers hit `TS7016`, which reads like a consumer bug and gets papered over per-consumer.
|why nothing else saw it: `check` type-checks SOURCES; the build cache owns per output UNIT so a missing unit is a HIT; the packer's type-shipping guard deliberately doesn't fire on an ABSENT declaration (an unbuilt dev tree must still pack); `tsbuildinfo-containment` only proves containment. Why a post-condition, not co-locating the build info with the emit tree: co-location fixes one cause and fights the build cache (a loose file degrades `lib/` to whole-dir ownership = the v0.x clobber), and wouldn't catch a missing `main`, a never-wired build script, or an `exports` typo. The desyncing shape is NORMAL: 93 of 103 incremental tsconfigs put the build info outside the emit tree.
|**the same script IS `main.yml`'s warm-cache probe**, run before the build, COLD-on-failure rather than error: the selective path trusts the cache for every unchanged forward-dep, so "is the cache warm" IS "is the restored tree complete" — the three-directory `[ -d … ]` probe it replaced couldn't answer that (a ~4 MB archive held `@gjsify/xmlhttprequest`'s `lib/esm` but not `lib/types`, passed all three dirs, went selective, died on EVERY selective PR). Incomplete cache ⇒ full build.
|proves EXISTENCE, not freshness (that class belongs to `verify-committed-bundles.mjs`); wildcard subpaths checked to their static prefix; ~0.1 s.
|**caught a real one on its FIRST run**, not the package it was written for: `@gjsify/xmlhttprequest` declared `lib/types/*.d.ts` while its tsconfig set no `declarationDir` — the declared paths were never produced for ANYONE (published 0.23.0 ships the dangling pointer). Fixed at the tsconfig (`declarationDir` + `emitDeclarationOnly`). Sibling `fetch` has the same shape but declares matching paths — consistent, leave it.
|tests: `tests/e2e/package-outputs/` (matrix + the #67 mechanism end-to-end through the real committed `@gjsify/tsc` bundle).

**"Exists in the repo" is not "reaches a consumer" — `scripts/verify-tarball-outputs.mjs` asks the same declarations of the TARBALL.** Its sibling above is STRUCTURALLY blind here, because in this tree `lib/` always exists: a package may declare `main: lib/esm/index.js`, build it, pass the existence check, and still publish a tarball without the file — `lib/` is a gitignored build output, and with no `files` field npm falls back to gitignore semantics. The declaration is then a dangling pointer for everyone who installs it and NOTHING in the repo can tell. Same class as `@gjsify/xmlhttprequest` above, one layer out.
|**two oracles, each IMPORTED, never reimplemented**: what is DECLARED comes from `declaredPaths()` — the same collector `verify-package-outputs.mjs` uses, so the two checks cannot disagree about what a manifest promises; what is PACKED comes from `collectPackedFiles()` in `gjsify pack` itself. **Asking `npm pack --dry-run` instead would be the bug**: that is a SECOND packer, and the packer-glob incident (§ Sixth axis) is exactly what it costs — npm expanded `lib/lib*.d.ts`, `gjsify publish` did not, so an npm-based check would have been GREEN across the whole v0.4.37–0.7.2 window in which the published `@gjsify/tsc` shipped an empty `lib/`. gjsify's packer produces these tarballs, so gjsify's packer is the only honest answer.
|fires ONLY on the unambiguous mismatch — declared, PRESENT on disk, absent from the packed set. Absent-on-disk belongs to `verify-package-outputs.mjs`; claiming it here would red-line every unbuilt dev tree.
|`gjsify pack` keeps its own narrower `assertTypeDeclarationsShipped` (the #655 guard, `types`/`typings` only) — it fires at the moment of packing and works in a CONSUMER's tree. The superset is a repo script because it needs `declaredPaths()` from the still-`private` `@gjsify/manifest-conformance`, which a published `@gjsify/cli` cannot depend on (`status/open-todos.md`). Measured gap while that stands: narrow a `files` list so only `lib/esm/register.js` is excluded and `gjsify pack` exits 0 and writes a tarball whose declared `exports["./register"].default` is missing — 13 type files shipped, so the packer's guard never fires.
|**caught a real one on its first run too, and again not the package it was written for**: 6 of the 8 published showcases declare 13 `exports` subpaths (`./browser`, `./assets/*`, `./<name>-demo`) resolving into `./src/…` while `files` is `["dist"]`. Invisible because the website resolves them through the workspace symlink, where `src/` is on disk — the SAME shadowing illusion that makes a fresh clone look like a broken tarball (§ Committed-artifact freshness). `--scope core` is wired into `main.yml`; `--scope examples` is not yet, because the repair is a publishing-policy decision (`status/open-todos.md`).
|tests: the tarball cases live in `tests/e2e/package-outputs/` beside the sibling's, sharing its fixture harness — the two checks share `declaredPaths()`, so a fixture one understands the other must understand too.
