# Project status data and CHANGELOG.md maintenance

> Detail for the root [AGENTS.md](../AGENTS.md) § Governance (`status:`).
> `STATUS.md` is a gitignored RENDER — the authored data lives in `status/`.

## Project status & CHANGELOG.md Maintenance

**The status snapshot is DATA in `status/` (ADR 0016 + its amendment); the rendered `STATUS.md` is GENERATED and NOT COMMITTED.** The AUTHORED half — only what a human must judge — lives in `status/`: per-package `status` + prose in `status/status.json`, per-suite notes in `integration-coverage.md`, `open-todos.md`, `upstream-patch-candidates.md`, free-form fragments in `sections/`. The DERIVED half is read from the repo at render time (package lists from `packages/**`, tiers from `gjsify.tier`, runtime slots from `gjsify.runtimes`, platforms from `gjsify.platforms`, GNOME-lib usage from `gi://`/`@girs/*` source imports, static spec/`it()` counts, suite/e2e/showcase/example/refs counts). Same derive-don't-restate principle as `@gjsify/manifest-conformance` / `verify-package-outputs` — a hand-copied number IS the drift, so the authored file structurally CANNOT restate a derivable fact (`status.json` allows only `status`/`note`/`working`/`missing`; anything else fails validation). **Read the data directly; `npm run status:generate` renders the full snapshot into a gitignored `STATUS.md` when you want the tables.**

**Why the render is not committed** (do not re-commit it, do not add a freshness check): it derives from EVERY manifest, so a committed copy would stale on any merge and serialise unrelated PRs — the failure lands on whoever pushes next, not on whoever caused it. And its counts come from directory listings on DISK, not from git, so two correct checkouts legitimately disagree: the commit that introduced the generator baked `68` examples from a tree carrying untracked scratch dirs against the `63` a clean checkout counts, and the byte-check went red on its own PR for a reason no author could avoid. The committed GJS bundles earn that cost (a 20-minute rebuild, staled only by an *inlined* source); a one-second render staled by *any* manifest edit does not.

**Enforced by the `status-data` conformance rule** (registered in the manifest-conformance registry, selected by `audit-runtimes --check` → every PR, no install, no build): authored-data schema; entry coverage in BOTH directions (every published package under `packages/` has an entry, every entry names an existing package); authored `native` ⇒ `gjsify.prebuilds` declared; `## <dir>` headings in `integration-coverage.md` ↔ `tests/integration/*` bijection; `status/sections/` holds exactly the fixed section set; open-TODO headings must not be struck-through/✓/"Completed" (the delete-on-resolve rule is machine-checked).

**Per-change history goes in the COMMIT MESSAGE + CHANGELOG.md, not the status data.** Write the detailed narrative (root cause, what/why, gotchas) in the commit body — it is co-located with the diff and discoverable via `git log`/`git blame`. CHANGELOG.md records what shipped + when (release-it generates it from the conventional commits). The snapshot remains a CURRENT SNAPSHOT, not a log: no dated `Current state (…)` blocks, no `### Completed` done-log, no "Latest:" lines, no per-session summaries. (The old hand-maintained STATUS.md ballooned to ~1600 lines with drifted counts before the 2026-07 data migration; the earlier append-only log hit ~940 KB before its 2026-06-19 removal.)

**Update the DATA when the snapshot changes** — in the same PR:

| Trigger | Edit |
|---|---|
| New package added | Add its entry to `status/status.json` (missing entry = red `audit-runtimes --check`); tables/counts derive themselves |
| Package promoted (stub→partial→full) | Flip the entry's `status` (+ drop `working`/`missing` when leaving `partial`) |
| Bug fixed / workaround removed | Update the entry's `note`/`working`/`missing`; delete the resolved `status/upstream-patch-candidates.md` row |
| New integration suite | Add a `## <dir>` section to `status/integration-coverage.md` (enforced both directions) |
| Deferred item identified / resolved | Add to / **DELETE from** `status/open-todos.md` (a resolved item is removed — its record is the commit/CHANGELOG; the check rejects struck-through/Completed headings) |
| Anything derivable (counts, tiers, runtimes, platforms, GNOME libs, new Vala bridge arch) | Nothing to author — it derives itself on the next render |

Commit the `status/` data alone — there is no generated file to commit alongside it. A docs-only / pure-refactor / CI PR that changes none of the above needs **no** status edit. (`website/scripts/generate-coverage.mjs` derives the website's coverage numbers by calling the generator's exported `statusSummary()` — no rendered file involved.)

**Track open work in `status/open-todos.md`.** Every "out of scope" / "follow-up" / "later" note must have a `###` entry there. A resolved TODO is **deleted** — its record is the commit + CHANGELOG that closed it.

**Changelog entries ONLY in CHANGELOG.md** (release-it, from conventional commits). Never add dated changelog lines, "Latest:" entries, or per-session summaries to the status data.

**Every reference link in CHANGELOG.md must name the thing its href points at — gated at the cut by `scripts/check-changelog-references.mjs`**, which is also what EMITS the GitHub release body. The preset cannot be configured out of this: `conventional-commits-parser`'s reference regex reads the issue as `[\w-]+` (not digits) behind a free `owner/repo` prefix, so `#version`, `#ffffff`, `package.json#exports`, `pre-#955` and `#442/#121` all parse as issues and the writer invents the missing half of the URL. Narrowing `parserOpts.issuePrefixes` to a RegExp was measured to reject every artefact shape, but needs a JS config file AND leaves the writer's second producer (the `transform` that re-links the subject and `@mentions` off the preset's own `issuePrefixes`, the same path that renders the load-bearing `(#970)` squash suffix) untouched. So the gate lives over the emitted file, where one rule covers both producers — the discriminator is TEXT↔HREF agreement, because a fabricated href like `github.com/442/gjsify/issues/121` is perfectly well-formed and only its link text gives it away. Where both slug halves are fabricated (`2f0459f`'s "RSA PKCS#1 / PKCS#8" → `[1/PKCS#8](https://github.com/1/PKCS/issues/8)`) text and href agree and only the `KNOWN_REPOS` allowlist rejects it. Repair is drop-or-unlink and NEVER re-points a link: `PKCS#7`, `gjs#44` and `node-gtk #442/#121` name a standard, a GitLab project and another repo's issues, so a mechanical re-point trades a broken link for a confidently wrong one. Like `audit-runtimes`, it asserts POSITIVE facts before believing a clean file — a fixture matrix of the seventeen measured artefact shapes plus eight that must stay linked runs first, and the file must actually contain valid issue and commit links.

**THE FILE IS NOT THE PUBLISHED ARTEFACT, so the notes are derived FROM the file.** Repairing CHANGELOG.md does not repair the release notes: release-it computes `changelog` once, in memory (`lib/index.js:63`, frozen into the context at `:92`), and `lib/plugin/GitRelease.js:34` posts that context, so a shell hook — a separate process — cannot reach it. Measured with both plugins in a throwaway repo: after `--write` repaired the infile, `${changelog}` still carried `pre-#955`, `#version`, `442/#121`, `859/#861`, `PKCS#1`. 0.27.1 is what that publishes — `.../gjsify/pre-/issues/955` and `.../issues/version` in its public notes. Hence **two** wirings in `.release-it.json`: hook `before:git:beforeRelease` runs `--write` (after the plugin regenerates the infile, before `Git.beforeRelease()` stages it), and `github.releaseNotes` runs `--release-notes ${version}`, which `GitRelease.processReleaseNotes()` execs and whose stdout becomes the body. That second run re-asserts the whole infile and then prints its top section verbatim, so the body is a slice of the very bytes that get committed — the file and the notes cannot diverge, and a dirty section, a heading that does not name `${version}`, or a body over GitHub's 124000-char cap exits 1 and aborts the cut before the commit, the tag and the release exist. Both were rehearsed against real release-it: with the repair the emitted body equals the staged section byte-for-byte; without it the cut refuses and never reaches `Git commit`. **`--dry-run` exercises none of it** — release-it skips hooks, skips `releaseNotes`, and does not write the infile. **What a cut repaired is in the JOB SUMMARY, not the cut log**: release-it captures a hook's output into `log.verbose`, which `shouldLog()` suppresses without `--verbose` (measured — zero lines reached the log), so a *successful* repair is invisible there while a failure rides out in release-it's ERROR. Since repair is lossy, the script appends every repair, finding and emitted section to `$GITHUB_STEP_SUMMARY`. A silent cut log is not evidence that nothing was dropped.

**A generated section is not an explanation, so the body may carry a hand-written PREAMBLE: `docs/release-notes/next.md`**, published above the section by the same `--release-notes` run (`--prose` overrides the path). Write it in the PR that lands the change — the section already says *what* changed and never *why it mattered*; v0.28.0 is the worked example, where "make the GTK runtime bundles self-contained" names the fix and not the three silent defects it repaired. The preamble is an input to the SAME oracle, not a second one: it is swept by the reference detector, so a fabricated link in prose fails the cut exactly as one in the infile does — a hand-written paragraph is precisely where a plausible-looking one gets typed, and an unchecked second producer of the published body would reopen the hole 0.27.1 shipped. A version heading in it, or a composed body over the 124000-char cap, also fails; and the section must still appear in the emitted body VERBATIM, which held by construction while there was nothing to concatenate and is now asserted. **Prose is OPTIONAL and a missing one is ADVISORY** — a release must never be un-cuttable because nobody wrote prose — **but a STALE one is dropped**, which inverts the risk the advisory creates: having nothing to say costs a warning, while publishing the *previous* release's text under a new version is impossible. Git is the oracle (`git log <last tag>..HEAD -- <path>`), sound only because `--release-notes` runs at `github:beforeRelease`, i.e. BEFORE `Git.release()` creates the new tag — so the most recent tag is the last release and "changed since it" means "written during the cycle being cut". Nothing to reset by hand and no version to write into the file: after a release it is stale by definition, and the next prose is simply the next edit. **An advisory here can only reach a human through `$GITHUB_STEP_SUMMARY`** — the one place in this repo where a `::warning::` annotation is unavailable, because stdout IS the release body and the annotation would be *published*, while stderr is swallowed into `log.verbose` on a successful run. Covered by `tests/e2e/release-notes-preamble/`, the only place any of this runs before a real cut (`--dry-run` skips `releaseNotes`); its no-prose output was checked byte-for-byte against what the 0.28.0 cut actually published.
