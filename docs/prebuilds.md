## Native Extensions (Vala)

Vala → Meson → shared lib + GIR typelib → `gi://` import (example: `packages/framework/webgl/`). Prefer TS; Vala only for C-level access.

**gi:// ordering:** `GIRepository.prepend_search_path()` must run before `gi://Foo` resolves — static `gi://` imports resolve in ESM Linking, before code. Use `gjsify run` or a two-file loader (loader prepends, then `await import('./bundle.js')`).

**A `gi://` import's typelib-LOAD side effect does not exist on `--app node` — express it as an ACCESS.** `import GstApp from 'gi://GstApp?version=1.0'; void GstApp;` works on gjs (the specifier stays EXTERNAL; the import is always evaluated, and loading the namespace IS the side effect: instances like `pipeline.get_by_name('src')` then resolve their real type's methods). On node, `gjsGiNodePlugin` rewrites it into a virtual module resolving the namespace LAZILY on first property access — laziness that is load-bearing (it keeps GJS-only `gi://` paths from dragging `@gjsify/node-gi` into cross-platform node bundles at load, the #641 lesson). No side effect ⇒ tree-shaking DROPS the module (measured: zero `GstApp` refs in the bundle) and `appsrc.push_buffer` failed "not a function" while the identical source played on gjs. Touch the namespace inside a function something calls (`@gjsify/webaudio`'s `ensureGstAppLoaded()`); making the shim eager is NOT the fix — it would reintroduce the regression the laziness prevents.

### Prebuilds

Native libs in `prebuilds/<os>-<arch>/` (`.so`/`.dylib` + `.typelib`); `package.json`: `"files":["prebuilds"]`, `"gjsify":{"prebuilds":"prebuilds","platforms":["<the one target>"]}` — declaration + audit: § Runtime & platform model.

|**the artifacts live in PER-TARGET packages, not in the bridge (ADR 0017, the esbuild model).** A bridge `@gjsify/<x>` keeps its name, API and loader contract but ships NO `prebuilds/`; each declared target lives in `@gjsify/<x>-<os>-<arch>` (directory `packages/<pillar>/<x>-<os>-<arch>/`, a SIBLING — the workspace globs are `packages/<pillar>/*`, so a nested dir would not be a workspace member), which declares `os`/`cpu` and is referenced from the bridge as an `optionalDependencies` entry. A package manager installs the one that fits and SILENTLY skips the rest, because a platform mismatch on an OPTIONAL dependency is not an error. Measured before the split: 97.3 MB of committed binaries of which a linux-x64 consumer could load 31.5 MB.
|**the 60 manifests are GENERATED, never written** — `scripts/generate-platform-packages.mjs` (`--check` default, `--write` moves the directories with `git mv` and patches the parents). Every field is derived: name from parent + token, `os`/`cpu` from the token, version + tier from the parent, `libc`/`gjsify.glibcRequires` MEASURED from the ELF by the `prebuild-libc` rule's own reader (never a second copy of it — a hand-rolled loader predicate matched `ld-linux-*` but not ppc64le/s390x's `ld64.so.*`, so the generator and the rule disagreed about the same bytes). `--check` re-emits and compares; the `platform-packages` conformance rule IS that function, imported not reimplemented.
|**what moves to the child and what stays.** `gjsify.platforms` stays on the bridge as the single declaration and every child's one-element list is derived from it. What MOVES is everything that is a fact about a BINARY: the npm `libc` filter (leaving it on the bridge is an install-time regression — npm/yarn/pnpm all honour it, so an inherited `["glibc"]` refuses the pure-TypeScript half on musl hosts where it runs fine), `gjsify.glibcRequires`, and `gjsify.platformsUncommitted`. The exemption travels because it is what `prebuild-artifacts` trips on when the directory appears, and the directory now appears in the child; a split parent is out of that rule's scope entirely.
|**a DECLARED target gets a package even when its artifact is deferred.** `@gjsify/napi`'s darwin-arm64 is built by `release.yml` and staged into the tarball at pack time, never committed — with `prebuilds` gone from the bridge's `files` that staging packs nothing, so the artifact needs a package to ship FROM. It also claims the npm name when the target is declared rather than when its binary lands, which is the cheap half of the bootstrap below.
|**runtime discovery needs no new code path** — `detectNativePackages()` already scans every package in `node_modules` for `gjsify.prebuilds` + `prebuilds/<target>/`, so a split package is found by exactly the mechanism that found a bundled one. Only which tarball the directory arrives in changed.
|**adding a target is now a PUBLISHED NAME**, so `gjsify onboard` (first publish + Trusted Publisher, § New `@gjsify/*` package) must run for it BEFORE the release that ships it — an unbootstrapped name 404s the OIDC exchange and stalls every alphabetically-later package.

|**runtime env:** the CLI auto-sets `GI_TYPELIB_PATH` + the host loader's OWN search var (`LD_LIBRARY_PATH` linux / `DYLD_LIBRARY_PATH` darwin — dyld ignores the ELF one / `PATH` win32, `;`-separated) via `detectNativePackages(startDir)` + `buildNativeEnv(pkgs)` (exhaustive node_modules scan walking up). Used by `gjsify run` | `gjsify info` | `gjsify dlx` | `gjsify showcase`. `runGjsBundle()` calls it for CWD + `dirname(bundlePath)` so dlx-cache layouts pick up their full transitive prebuild set.
|**a LAUNCHER cannot scan at run time from inside GJS** — typelib lookup happens in the GJS runtime before the bundle's first line — so `buildNativeEnvPreamble()` (`utils/bin-shim.ts`) emits a `sh` preamble that GLOBS the install prefix ON EVERY LAUNCH (`<prefix>/node_modules/{@*/*,*}/prebuilds/<target>`, canonical + legacy spelling), used by the global launcher AND the workspace `.bin` shims. It used to EMBED the install-time scan, which makes the env a SNAPSHOT: a native package installed later is invisible, and an empty scan writes a launcher with NO preamble and says nothing — v0.24.1 shipped exactly that (`~/.local/bin/gjsify` with a bare `exec gjs -m …` while `@gjsify/rolldown-native` sat correctly installed), surfacing days later as "no usable bundler engine under GJS" in an unrelated project. Only ANCESTOR hits (hoisted layouts a one-root glob can't see) stay embedded; win32 keeps the baked form (its real launchers are `.cmd`/`.ps1`, and `PATH` is the DLL search path). Guarded by `tests/e2e/global-install-engine`, which RUNS the written launcher against a stub `gjs` and asserts the exported env — reading launcher text cannot tell a correct one from an empty one.
|**platform logic is a PURE function** of `(platform, arch, declaredPlatforms, existingDirs)` (`resolvePrebuildDirName`/`libraryPathVar`) so darwin/win32 branches are unit-tested from Linux by injecting foreign values; only final `dyld`/`LoadLibrary` behaviour is CI-only.
|**consumers:** showcases / dlx-runnable apps must declare every typelib-owning package as a runtime `dependency` (§ Showcase dep rule) — build-time inclusion does not ship the typelib in the tarball.
|**build:** `.github/workflows/prebuilds.yml` (x64+arm64 native + ppc64/s390x/riscv64 under QEMU, Fedora). **The LIBC axis is a leg of its own** — `build-prebuilds-musl` compiles `sab-native` + `lightningcss-native` inside `alpine:3.24` on native x64 and arm64 runners, load-tests each under Alpine's `gjs` and `dlopen(RTLD_NOW)`s them with no library-path variable set. It commits nothing and declares nothing: `-musl` is not a `gjsify.platforms` token (the distinction rides npm's `libc` field, § the OS axis), so its matrix entries carry `libc: musl` and `parseCiPlatforms()` drops libc-carrying targets from the promise map. That is what lets the leg be an ordinary PR/push gate instead of the dispatch-only canary it was — and the canary never ran once in CI, which is how a staging defect survived in it for its whole life. `check-committed-musl` is the second, cheaper half: no build, it just asks whether the committed glibc binaries resolve on real Alpine. Local: `gjsify workspace <pkg> build:prebuilds` / `gjsify foreach build:prebuilds` (meson + vala + GI `-devel` pkgs required). No root `build:prebuilds` script — yarn was dropped in Phase D.7d; scripts run via `gjsify run|workspace|foreach`.
|**staging goes through the shared `scripts/stage-prebuild.mjs`, never a hand-written `cp`.** It takes the target dir from the package's OWN `gjsify.platforms` (a local build can't invent a target CI doesn't reproduce; an undeclared host is a hard error) and matches artifacts by EXTENSION, so a library renamed in `meson.build` can't ship a stale set. The eleven per-package one-liners it replaced hard-coded target dir + `.so` suffix — why `build:prebuilds` staged nothing on macOS. Since ADR 0017 the DESTINATION is resolved, never defaulted (`resolveStageDir`): `gjsify.prebuilds` present → this package owns the artifacts; absent → the sibling platform package must exist, and if it does not that is an error naming the generator. The old `?? 'prebuilds'` default would recreate a directory INSIDE the bridge — untracked, absent from `files`, invisible to every conformance rule (they key on `gjsify.prebuilds`) and yet exactly where a developer's `build:prebuilds` appears to succeed. **The rule is MACHINE-CHECKED, because it drifted while being stated categorically here**: `tests/e2e/prebuild-change-gate` fails any step body in `prebuilds.yml` / `emulated-build.sh` / `musl-build.sh` matching `mkdir -p …prebuilds/` (or PowerShell's `New-Item …prebuilds`, so moving the `cp` to Windows is not the escape), and fails a `Collect @gjsify/…` step that does NOT call the stager (deleting a collect step satisfies a ban but uploads an empty artifact). Comment lines are stripped before the scan — several of them NAME the anti-pattern to explain why it is forbidden. It cost what the rule predicts: ~19 hand-written bodies against 30-odd stager references, and the `webgl`+`webrtc-native` linux `cp` lists omitted the `.gir` the darwin lists staged, so ten of the sixty per-target directories had a different file shape from every other one and nothing said so — `prebuild-artifacts` now says so, platform-agnostically, for every target (above). `release.yml`'s two `napi-prebuild-*` legs are the one remaining pair, outside the scan on purpose (`status/open-todos.md`).
|**three DESTINATIONS, and which one is right is a property of the JOB, not of the path.** `--scratch` = this package's own `prebuilds/<target>/`, for a CI BUILD leg that uploads and commits nothing (`prebuilds.yml`, every leg); no flag = the resolved destination, i.e. the per-target platform package, for anything whose bytes ARE the shipped artifact (`napi.yml`, `release.yml` — no `commit-prebuilds` exists there, so the untracked per-target directory is where a release stages from); `--dest <dir> --allow-undeclared` = outside every package, for a target no package declares and no sibling exists for (napi's win32 attempt → the gitignored `tmp/`). `--scratch` is a NAMED flag rather than a fallback so `resolveStageDir` keeps its refusal for developers and `--allow-undeclared` keeps meaning "this host is not a promised target" instead of being borrowed to unlock a destination. **`--dest` is the wrong one for a MULTI-package job, and the musl leg paid for it**: two bridges passed the same `--dest`, the stager replaces its destination rather than merging into it, so the second erased the first and the leg died on `Typelib file for namespace 'GjsifySabNative' (any version) not found` — a message naming musl and GI for a file the run itself had removed. `--scratch --allow-undeclared` DERIVES the destination from the package, so the collision cannot be expressed; the musl leg and `build-prebuilds-macos-experimental` both use that pair. A `--dest` under the workspace would also have been needed for the uploads to see anything at all: `/tmp/…` in a `--rm` container is not the bind-mounted tree, so both `if-no-files-found: error` uploads could never have found a file.
|**a derived target needs a per-job guard, because the `cp` got that invariant for free.** The stager derives `<os>-<arch>` from the HOST while the upload paths and verify steps name it literally (`linux-${{ matrix.arch }}` / `$PREBUILD`); a hand-written `mkdir -p "prebuilds/linux-${ARCH}"` could not disagree with them. So every staging job now asserts `hostStagingTarget()` against its own token BEFORE building — `build-prebuilds`, `build-prebuilds-macos`, `emulated-build.sh` (where a missing `--platform` makes a cached amd64 image run natively: the `run-on-arch-action` incident verbatim) and the musl leg, which had it first.
|**`commit-prebuilds` SYNCS BEFORE IT STAGES, and never rebases.** It used to commit the downloaded binaries and then `git pull --rebase origin main`. That is a request for git to merge a binary, and git has no merge driver for one — so on every run carrying a darwin artifact the replay died on the first dylib (`Cannot merge binary files: …libgjsifytls.dylib`, run 30864276535, 26848 insertions discarded, nothing pushed). DETERMINISTIC, not a race: Mach-O output is not byte-reproducible, so all 16 committed darwin dylibs are rewritten every run — measured across two consecutive bot commits, every one at an identical size, with every differing darwin-x64 byte being the `LC_UUID` payload or an `N_OSO` debug-map stab's object-file mtime (arm64 adds its ad-hoc code signature over those bytes). Zero bytes of code. So no 0.27.x could receive a rebuilt darwin dylib at all. The order is now: download → snapshot to `$RUNNER_TEMP` (a `reset --hard` would discard the downloads) → fetch + `reset --hard origin/main` → re-apply the snapshot → clear exemptions → stage → gate → commit → push, in `.github/prebuild-toolchain/sync-and-stage.sh`, which is IDEMPOTENT because the push retries by RE-STAGING (retrying the push alone would push a tree built on a stale base). **The snapshot holds only what the run CHANGED, not all sixty directories**: re-applying everything would resurrect a prebuild `main` legitimately deleted mid-run, and `git add` stages a resurrection as an ADDITION, invisible to the deletion guard. Its `git status` pathspec needs `:(glob)` — the bare `packages/*/*/prebuilds/` form matches NOTHING (default wildmatch has no `WM_PATHNAME`, so `*` crosses `/` and the pattern must match the whole path), which reports a clean tree on a dirty one and would have made every run green with the binaries discarded; a second, textual oracle now cross-checks the count for exactly that reason. **The gate on the pushed tree is enforced by a STAMP, not by step order**: `gate-pushed-tree.sh` writes the tree hash it audited and the push refuses any other tree, and re-gates after every re-stage. Held by `tests/e2e/prebuild-change-gate` — no `git pull`/`rebase` anywhere in the job, reset-before-`git add` in the script, stamp read by the push, bounded retry.
|**`commit-prebuilds` writes to the per-target packages; the BUILD legs deliberately do not.** Only the job that commits had to move: a build leg stages into the bridge as scratch space, uploads straight from it and never commits, and the macOS load-test steps read that path. `changed-packages.mjs` derives its package table from those same `path:` lines and maps `<bridge>-<target>` back to the bridge — taking the download path at face value would fill the table with 60 source-less packages, of which it then asks only questions about sources.

**A prebuild must resolve its own siblings from its own directory — machine-checked by `scripts/check-prebuild-loader-path.mjs`** (wired into `stage-prebuild.mjs`; parses Mach-O + ELF directly, no otool/readelf, so a Linux host verifies a committed darwin artifact it cannot run). The three Rust bridges (`rolldown-native`, `oxfmt-native`, `lightningcss-native`) ship TWO libraries whose leaf names differ ON PURPOSE: the Vala/GObject library the typelib names (`libgjsify<name>`) and the cargo cdylib it links (`libgjsify_<name>`, underscore) — the second is invisible to every other check (link succeeds, typelib found, failure lands at `dlopen` on a user's machine). `meson.build`'s per-OS branch must set BOTH: (1) the cdylib's install name normalised to `@rpath/<leaf>` (`install_name_tool -id`) BEFORE the Vala library links (ld64 copies the dependency's install name verbatim into `LC_LOAD_DYLIB`, and rustc's own has varied); (2) the self-relative search path — `build_rpath`+`install_rpath` `@loader_path` (Mach-O) / `$ORIGIN` (ELF); `build_rpath` is load-bearing because the shipped artifact is copied out of the build dir, never `meson install`ed. **`@loader_path`/`$ORIGIN` is NOT interchangeable with a library-path env var** — the env var only finds the BARE leaf the typelib records; the Vala→Rust hop must need nothing, or the prebuild only works under one launcher. Catches both failure modes: a sibling not staged (the darwin `rolldown-native` leg copied Vala `.dylib` + typelib and NOT the cdylib — a missing FILE reading exactly like a missing rpath) and a missing rpath.

**And a darwin prebuild must not carry the BUILD HOST — relocated by `scripts/relocate-macho.mjs`, enforced by the same `checkPrebuildDir()`** (#1102). Mach-O records each dependency by full install path where ELF records a bare soname, so a freshly-linked darwin artifact names the Homebrew prefix of whichever runner linked it and a Linux one structurally cannot. Measured on the published 0.34.0 tarballs and then across the whole tree: **all 12 darwin packages on BOTH arches** hard-linked `/usr/local/opt/…` (Intel runner) resp. `/opt/homebrew/opt/…` (Apple silicon) — i.e. each was correct by coincidence for the default prefix of its own builder and unloadable with no Homebrew, a custom `HOMEBREW_PREFIX`, MacPorts, or those formulae simply absent. `stage-prebuild.mjs` now rewrites every such load command to `@rpath/<leaf>` and writes the rpath list `@loader_path` → `@loader_path/../../../gtk-runtime-darwin-<arch>/gtk/lib` → `<brew prefix>/lib`, then ad-hoc re-signs (`install_name_tool` invalidates the signature; dyld on arm64 refuses a mis-signed dylib). **Bundle before system is ADR 0023's policy, not a new one** — darwin prefers the bundle, and a prebuild resolving its GLib differently from the process that loaded it is the two-GTKs-in-one-process failure #910 paid for; an `LC_RPATH` is fixed at link time, so the artifact encodes the DEFAULT and `GJSIFY_GTK_PREFER` stays a node-gi concern. **`LC_LOAD_DYLIB` absolute ⇒ FAIL, `LC_RPATH` absolute ⇒ REPORT**: dyld aborts the load over a missing hard dependency and silently skips a missing search path, so keeping the Homebrew prefix LAST is a working fallback rather than a defect — failing it would refuse the artifact the relocation deliberately produces, and would drop the Homebrew-only GJS host that works today. The predicate is DERIVED (`isBuildHostAbsolutePath`: absolute and not under `/usr/lib` or `/System`), never a prefix grep — a hardcoded `/opt/homebrew` test is vacuously false on an Intel runner and vice versa, so either alone passes green while proving nothing about the other arch, and the derived form also catches MacPorts and a home directory nobody would have listed. **Only an image with an `@rpath/` dependency gets rpaths**: an `@rpath` in an image's own `LC_ID_DYLIB` is a template the CONSUMER expands, so the Rust cdylibs (system libraries and nothing else) need none — and must not be given any, because cargo leaves no Mach-O header pad on x86-64 and `install_name_tool` then refuses with *"larger updated load commands do not fit"*. That is not repairable after the fact (the pad is fixed at LINK time); should a Vala bridge ever hit it the fix is `-Wl,-headerpad_max_install_names` in that `meson.build`, which is what the error says. **The whole rpath list is replaced, ORDER INCLUDED — every existing entry is deleted, then the wanted ones are added in sequence.** Deleting only the unwanted ones is not the same thing and shipped the bug: `install_name_tool -add_rpath` APPENDS, so an entry the linker had already baked in keeps its position and the additions land behind it, making the precedence a property of the link line rather than of the policy. Measured on the artifact CI built and committed from `main` — a freshly-linked `libgwebgl.dylib` carries `<brew>/lib` from the Homebrew link line, so it shipped `/usr/local/lib` AHEAD of the bundle, inverting ADR 0023 and re-creating #910's two-GLibs hazard on any host with both. It did not reproduce on the committed artifacts, whose version-PINNED Cellar rpaths (`/usr/local/Cellar/glib/2.88.2/lib`) were all deleted, so the order came out right there BY LUCK — which is why the regression guard in `tests/e2e/prebuild-loader-path/` asserts the ORDER of `searchPaths` and not its set: set-equality is blind to exactly this. Deleting and re-adding the same string costs nothing in header space, so the determinism is free. Those Cellar entries are dropped rather than kept for their own reason too: they name a formula VERSION, so two CI runs of one commit produced different bytes, and Homebrew symlinks every keg into `<prefix>/lib` anyway. Same shape as the win32 import-table check (#1096) and as `build-gtk-runtime-darwin.mjs` § 3 — the prebuilds were the one darwin artifact with no such gate, which is exactly why nothing noticed for eight releases.

**The node-gi ADDON is a darwin prebuild too, and it was the one the relocation never reached** (#1120). `packages/node-gi/node-gi/scripts/stage-prebuild.mjs` is a SECOND stager — node-gi is not a root workspace, it has its own CI, and `relocate-macho.mjs` is deliberately not importable across that line (`packages/node-gi/**` is `node-gi.yml`'s `paths:` trigger and the affected-classifier's ignore list, so an import either way makes one of the two lie). It only ever `copyFileSync`'d, so while all 12 other darwin packages were relocated the published `node_gi.node` kept `/usr/local/opt/glib/lib/libgobject-2.0.0.dylib` through eight releases. **An unrelocated addon fails differently from an unrelocated dylib, which is why nothing caught it**: those absolute paths RESOLVE on the ordinary Homebrew Mac, so there is no `ERR_DLOPEN_FAILED` to notice. `DYLD_FALLBACK_LIBRARY_PATH` — what `maybeReexecForGtkRuntime()` re-execs with to point at the bundle — is consulted ONLY for a path that fails to resolve, so it cannot redirect one that does. The addon therefore bound Homebrew's libgobject while the bundle's libgtk/libadwaita bound the bundle's via their own `@loader_path`: **two GObject type registries in one process**, ADR 0023's darwin bundle-first preference silently unhonoured by the very binary that implements it. `g_object_class_find_property` answered from the registry the types were not registered in and returned NULL for every property (`Adw.Application has no property 'application-id'` — also for `Gio.Application`, which declares it directly), and `g_type_from_name("GtkWidget")` returned 0 so a composite template on an `Adw.ApplicationWindow` subclass was rejected as "not a Gtk.Widget subclass". That second message now names the duplicate-registry cause instead, because it cost the diagnosis. The stager relocates the addon on darwin with the same derived predicate and full-list-replace discipline, and one EXTRA rpath ahead of the npm sibling: `@loader_path/gtk/lib`, the layout node-gi.yml stages for the env-free core-conformance run (`build-gtk-runtime-darwin.mjs` § 6 relocates a copy of the addon onto exactly that). Hence a local `darwinAddonRpaths()` rather than a shared one — the list genuinely differs, and `test/darwin-prebuild-rpaths.test.mjs` asserts its ORDER from any host. **`-Wl,-headerpad_max_install_names` is part of the fix, not an optimisation** (`binding.gyp`, `OS!='win'` branch): node-gyp's default leaves a header pad too small for four rpaths, and `install_name_tool` then refuses with *"larger updated load commands do not fit"* — measured here at exactly three, so the Homebrew fallback was the entry that silently would not fit. The pad is fixed at LINK time and unrepairable afterwards, which is the same wall the Rust cdylibs hit above.


**The four darwin verify steps read ONE table** — `.github/prebuild-toolchain/darwin-bridges.mjs`, a table of RECORDS (`dir`, GI `namespace`, a `klass` whose resolution forces `dlopen`, `rustSibling`) with three projections: the directory to glob for `.gir`, the `dir|ns|class` rows the GI load test reads, and the Vala library path the env-free `ctypes` dlopen takes (leaf DERIVED as `lib<namespace lowercased>`, the meson convention, and safe to derive because its only consumer names the file it could not open). NOT YAML: Actions has no anchors, a matrix would multiply the Homebrew closure by the bridge count, and the four uses are different projections rather than one list used four times. `PREBUILD_SKIP` filtering moved into the script — the `built()` shell helper was the fifth copy. Written because the four hand-written lists had already drifted: `rolldown-native` was in TWO of them, so the bridge whose #832 incident IS the reason the loader-path check exists was the one bridge that check never opened, and the `.dylib`-leaf assertion never read its GIR. `--check` holds the table against the job (every `Collect @gjsify/…` step needs a row and vice versa), driven by `tests/e2e/prebuild-change-gate`, which also fails any step in that job hard-coding two or more bridge directories.

**A macOS job's shell is bash 3.2, and `bash -n` on any Linux host says otherwise.** Apple ships no GPLv3 bash, so `/bin/bash` on every `macos-*` runner is 3.2.57 — and that is what `shell: bash` selects, not the Homebrew bash 5 also on the image. So `mapfile`/`readarray`, `declare -A`, `${var^^}`, `&>>` and `coproc` syntax-check clean everywhere a developer or a Linux leg would test them and die at RUN time with `command not found`, exit 127. Measured: `mapfile -t dirs < <(…)` in the loader-path step above passed `bash -n` on bash 5.3 locally and killed the darwin-arm64 leg at step 26, skipping the GI load test, the env-free dlopen and all eight uploads — the same wrong-shell false green AGENTS.md records for git-bash on Windows (§ Toolchain hygiene). The 3.2-safe collect idiom is `dirs=(); while IFS= read -r d; do dirs+=("$d"); done < <(…)`. Machine-checked by `tests/e2e/prebuild-change-gate`, scoped to the jobs whose `runs-on`/matrix `runner` names a `macos-*` image — those builtins are fine on a Linux leg and banning them everywhere would be a rule this repo does not mean.

**A prebuild never LOADED in CI is a prebuild nobody tested.** The macOS job once built six darwin-arm64 bridges and committed them without loading one. Every macOS job now ends in a real `gjs -c 'imports.gi.<Ns>.<Class>'` per bridge (resolving a class forces GI to call `…_get_type`, which is what dlopens the library — a typelib merely FOUND passes namespace lookup) plus an env-free `ctypes.CDLL(<abs path>)` with `DYLD_*` unset (proves the sibling hop rides `@loader_path` alone). ANY new prebuild job MUST end in a load test. **Same rule for the job's OWN platform, non-obviously**: a job can produce a loadable artifact for the WRONG arch — `uraimo/run-on-arch-action` ignores its `arch` input when a custom `base_image` is supplied (platform must ride the image ref: `base_image: --platform=linux/ppc64le fedora:43`), so the emulated legs compiled x86-64 and staged it into `prebuilds/linux-{ppc64,s390x,riscv64}/`; every downstream check passed, the artifact even LOADED on the runner. Only reading the image's own `e_machine` against its directory catches that — `audit-runtimes --check` now does. **The EMULATOR is toolchain and is pinned like one** (`docker/setup-qemu-action` + `tonistiigi/binfmt:qemu-v10.2.3`): the action's default reset binfmt to qemu 7.2, under which Fedora's package manager does not survive emulation (dnf segfaults on s390x, RPM transaction fails on ppc64). Reproduce any emulated leg locally: `podman run --platform linux/<arch> -v "$PWD:/workspace" -w /workspace <image> bash .github/prebuild-toolchain/emulated-build.sh` (a CI-only emulated build is a 20-min round trip per hypothesis). Weak/recommended deps are OFF in that script — they pulled pipewire/wireplumber into a Vala build and THEIR scriptlet was the failure.

**Prebuild provenance — a committed binary is only as trustworthy as the source it was linked against.** The `*-native` bridges compile upstream Rust crates by Cargo PATH dependency into `refs/<name>/`, and the `.so` is COMMITTED. Machine-checked by `node scripts/check-refs-pin.mjs <pkg-dir>` (runs in every `build:meson`; `GJSIFY_ALLOW_REFS_DRIFT=1` for a deliberate bump committed in the same change):
|**checkout drift** — a `refs/` working copy moved forward (an `update-submodules` sweep, a manual pull) and the next rebuild links THAT. The submodule set to verify is DERIVED from the package's own `src/rust/Cargo.toml` path deps.
|**version skew vs the npm engine** — `@gjsify/rolldown-native` and npm `rolldown` are two builds of the SAME bundler and must be the same release, else the engines disagree on some inputs only. Declared as `gjsify.refsLockstep: {"refs/rolldown": {"npm": "rolldown", "tag": "v{version}"}}`, checked against the installed npm version (same for `oxfmt-native` ↔ `refs/oxc` @ `oxfmt_v<X>`).
|**stale build dir** — ninja does NOT track Cargo path-dep sources: after swapping a submodule, `meson compile` says "no work to do" and re-stages the OLD binary. The check stamps `build/.gjsify-refs-pin` and fails loudly (fix: `rm -rf build src/rust/target`).
|**the crates.io half is pinned by a COMMITTED `src/rust/Cargo.lock` per bridge** (shipped via `files: ["src/rust"]`) — none of the three checks sees a crates.io transitive. Load-bearing with the prebuild change-gate: a run that never rebuilds never absorbs registry drift. ENFORCED on CI via `${CI:+--locked}` on the `cargo build` (a lock nothing checks is decoration); locally expands to nothing. GitHub Actions exports `CI=true` to steps and job `container:`s but a bare `docker run` inherits NOTHING — the emulated legs pass `-e CI=true` explicitly; a containerised step that forgets it still USES the lock but silently stops FAILING on a stale one. The lock is also a `rust_sources` input (ninja otherwise tracks only `Cargo.toml` + `src/**.rs`; a lock-only change would re-stage the OLD binary). Update = explicit act: `cargo update [-p <crate>]`, `cargo tree -d`, rebuild, commit the lock diff together; a `refs/` bump invalidates the lock and needs the same regeneration in that commit.
|**a lock does NOT replace `[patch.crates-io]` — crate IDENTITY is not a version choice.** `refs/oxc` publishes `oxc_allocator` AND path-deps it in-tree; the crates.io-only parsers pull it from the REGISTRY, and Cargo treats registry and path copies as SEPARATE crate instances even at the same version → `E0308 … multiple different versions of crate oxc_allocator`. A `[patch]` table is honoured only from the ROOT of the workspace being built — each `src/rust/` is its own root and must repeat the patch (as `@gjsify/oxfmt-native` does). When adding/bumping a `refs/` submodule that publishes its own crates: check `cargo tree -d` for a name appearing as both path and registry, patch it to the path copy.
|why it earns its keep: the committed `rolldown-native` prebuild had drifted BEHIND its pin, and the pin sat 41 commits past `v1.1.5` while the npm devDep was `1.1.4`; the gap contained a runtime-chunk change, so the rebuilt native engine emitted two chunks where npm emitted one and every `--app gjs --outfile` build keeping a standalone runtime chunk failed ("output.dir must be used"). **Still open:** nothing byte-compares a committed prebuild against a CI-built one (`status/open-todos.md`).
