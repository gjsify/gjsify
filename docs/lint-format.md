## Lint & format — oxc (oxlint + oxfmt)

`gjsify lint`/`format`/`fix` wrap **oxc** (full Biome replacement, no fallback). `gjsify check` stays the **tsc** orchestrator, unrelated.

- **Resolution — dual-engine (mirrors `bundler-pick.ts`):** `packages/infra/cli/src/utils/oxc-resolve.ts`. **oxfmt:** under GJS, `runOxc` prefers the `@gjsify/oxfmt-native` GI bridge (`shouldUseNativeOxfmt()` — runs the full oxfmt CLI in-process, Node-free `gjsify format`/`fix`; `GJSIFY_OXFMT=native|npm` is the explicit override, `native` throws when the prebuild isn't loadable); on Node (or when the prebuild is missing) it spawns the npm **Node launcher** (`node_modules/oxfmt/bin/oxfmt`) via `process.execPath`. **oxlint:** always spawned via its Node launcher — NOT the bare napi binary — because oxlint's JS-plugin host (the `gjsify/register-class-order` rule) lives in the launcher; a native oxlint bridge could only run the Rust rule subset (deferred, see `status/open-todos.md`). Tools are on-demand devDeps (resolved cwd → workspace-root → parents); a clear install hint names the expected `@oxlint/binding-<target>` / `@oxfmt/binding-<target>` napi package.
- **Spawning the Node launcher from the GJS bundle — two GJS-only gotchas (`spawnOxcLauncher`):** (1) the launcher command is `nodeBinary()`, NOT `process.execPath`. Under the committed GJS bundle `process.execPath` is the CLI bundle itself, so spawning it re-executed the CLI with `oxlint/bin/oxlint` as its first positional (yargs printed top-level help) and hung; `nodeBinary()` resolves to PATH `node` under GJS (a real Node host is required — oxlint has no native bridge yet; its absence surfaces as a clear `OxcNotFoundError`). (2) Under GJS the tool runs on **`spawnToCompletion`'s blocking path, not the streaming async one** — but NOT because an event is lost. The earlier note here claimed the async `Gio.Subprocess` `wait_async` exit/close callback is "not delivered back to JS under the bundle"; that is **wrong** (instrumented 2026-07-26 on gjs 1.88 — it fires, with the correct exit code). The real cause is **teardown**: `@gjsify/child_process`'s async `spawn()` calls `ensureMainLoop()`, which arms a GJS main-loop hook (`GLib.MainLoop.runAsync()` → `setMainLoopHook`); `eval_module` runs that hook once the entry module's top-level await settles and then blocks in `g_main_loop_run()` forever — GJS has no atexit hook, and only `process.exit()` (→ `quitMainLoop()` + `system.exit()`) tears it down. So **any command that async-spawns and then RETURNS NORMALLY parks at 0% CPU after the child has exited and been reaped**, which is indistinguishable from a lost callback. `lint`/`format`/`fix` end via `setOxcExitCode`, which deliberately does not exit on a clean run → hang; `foreach`/`workspace`/`check`/`runGjsBundle` end in `process.exit(…)` → fine, which is why hundreds of async children and 490+ GJS specs never hung. **Corrected general rule: from the GJS CLI bundle the async `spawn` is fine as long as the command terminates the process itself; a command that returns normally must use the blocking path.** That contract is the required `completion: 'exit' | 'return'` option on `spawnToCompletion` (`packages/infra/cli/src/utils/spawn.ts` — the single wrapper the six former copies now share). The blocking path additionally captures stdout/stderr (`'inherit'` is not forwarded through the GJS spawnSync path — diagnostics would be silently dropped) and re-emits them (`maxBuffer` 64 MB). On Node the async path is always used. Guarded by `tests/e2e/lint-gjs-launcher` + `tests/e2e/spawn-gjs-teardown` (both boot `dist/cli.gjs.mjs` under `gjs`). The same `process.execPath`-under-GJS trap still lurks in `showcase.ts`'s `spawn(process.execPath, [cliBin, 'dlx', …])` (`status/open-todos.md`).
- **Native formatter bridge:** `packages/infra/oxfmt-native/` — `@gjsify/oxfmt-native`, a Vala/GObject + Rust cdylib GI bridge (same pattern as `@gjsify/rolldown-native`; the npm `oxfmt` is a Rust napi binary GJS cannot load). The Rust shim links the **pure-Rust oxfmt CLI core** (`oxfmt::cli`, `default-features = false` → napi OFF) via Cargo path-deps into `refs/oxc`, pinned to the `oxfmt_v<X>` tag matching the workspace's npm `oxfmt` devDep. The pair is DECLARED as `gjsify.refsLockstep` on the package and machine-checked by `refs-pin` — do not restate the current version here, that copy went three releases stale while the check it described was not even wired up (the declaration was missing, so the rule read an empty table and verified nothing). Surface: `Formatter.run(args) → exit code` (full CLI in-process: `.oxfmtrc(.json)`/`.editorconfig` resolution, ignore handling, parallel walking, `--write`/`--check`/`--list-different`, stdout/stderr reporting identical to the npm launcher) + `Formatter.format(filename, bytes)` (single-shot in-memory, default options). NOT covered (napi-only upstream by design): the embedded CSS/HTML/Vue/Markdown Prettier `ExternalFormatter`, JS/TS config files (`.oxfmtrc.ts`), `--init`/`--migrate` (the CLI's own TS templates handle init), LSP + stdin mode. Ships `.so`/`.dylib`+`.gir`+`.typelib` per target in `prebuilds/<os>-<arch>/`, the set declared by `gjsify.platforms` (do not restate it here — this line read `linux-x64` while linux-arm64 and darwin-arm64 were already committed); optional peer dep of `@gjsify/cli`. Rebuild: `gjsify workspace @gjsify/oxfmt-native build:prebuilds` (needs meson + vala + cargo + `git submodule update --init refs/oxc`).
- **Config:** root `.oxlintrc.json` (correctness:error, typescript/consistent-type-imports, typescript/no-explicit-any:warn, unicorn/prefer-node-protocol:error, `no-restricted-globals`:error for the GJS ambient globals `imports`/`ARGV`/`print`/`printerr`/`logError` — see § Don't patch → "The legacy `imports.*` object is NOT an API"; scoped out for genuine GJS program sources via an override — eslint/no-unused-vars:warn, typescript/no-this-alias with `allowedNames` for the legitimate `this`-capture idiom: `self`/`el`/`blob`/`readable`/`root`/`node`/`receivedThis`, `options.reportUnusedDisableDirectives:error`) + `.oxfmtrc.json` (printWidth 120, 4-space, singleQuote, semi, trailingComma all, arrowParens always). `gjsify format --init` writes both from `src/templates/{oxlintrc.json.tmpl,oxfmtrc.tmpl}` (loaded with the static-read-inliner `readFileSync(new URL(...))` shape so they bake into the bundle). `gjsify fix` = `oxfmt --write` then `oxlint --fix`.
- **A bare `gjsify format` WRITES; there is no flagless report mode.** `--check` is the read-only CI mode (exit non-zero on drift), `--no-write` the read-only local one (`--list-different`) — the same shape the sibling `gjsify fix` already had, and what oxfmt's own bare invocation does. The previous report-only default is a MEASURED trap, not a preference: `gjsify format` was run twice over two unformatted files, wrote nothing either time and exited 0, while `--check` kept flagging the same two files — the command that looks like the fix was the diagnosis. Safe to flip because NOTHING in CI invokes a bare `gjsify format` — the only workflow call is `tree-checks`' `format --check` — so no verification step turns into a mutation. Asserted on the DEFAULT, not only on the flag, in `tests/e2e/oxc`.
- **`gjsify lint` is clean (0 errors) across the whole codebase, and CI enforces it** — the `tree-checks` job in `.github/workflows/main.yml` runs `gjsify lint` over the WHOLE repo (never selective; "lint is clean" is a repo-wide claim a per-file run cannot verify), beside `format --check` and `upgrade --check`. It gates on **errors only, which is oxlint's own exit semantics rather than a flag**: warnings leave the exit code at 0 unless you opt in with `--max-warnings`/`--deny-warnings`, which the step deliberately does not pass. The open warnings (mostly `typescript/consistent-type-imports` + `eslint/no-unused-vars`) stay visible in the log without failing the build.
- **Those three are their OWN job, and deliberately not `needs: build`.** They used to ride `check` and `build`, each carrying a comment declaring itself whole-repo — but both hosts are gated on the affected classifier's `skip-all`, so "whole repo" silently meant "whole repo, IF a workspace needed building". `skip-all` is an honest answer to a BUILD question that was answering a TREE question by accident. #1183 touched only classifier-IGNORE paths, skipped the matrix and landed unformatted code behind a green required check — `gate` reads a skipped `check` as a pass — and #1186 reformatted it afterwards. The same gap had already put its red on a stranger's PR once (#949/#960 → #957). Re-gating `check` would not have worked either: it additionally requires `build` to have SUCCEEDED, and `build` is skipped in exactly the case that matters. `packages/node-gi/**` and `packages/napi/**` are the largest IGNORE trees carrying lintable source, and neither `node-gi.yml` nor `napi.yml` has a lint or format step.
- **`tree-checks` drives the PUBLISHED bootstrap CLI, not the commit's** — a tree that is installed but not built has no other (ADR 0002). Honest for what the job claims, because the CLI only assembles argv: the ENGINES are the workspace's pinned `oxlint`/`oxfmt`, and `upgrade --check` reads the tree's own `package.json` files. Whether the CLI's own `lint`/`format` commands still work is a separate claim, held by `tests/e2e/{oxc,oxc-plugin,lint-gjs-launcher}` in the `e2e` job. Verified with a DISCRIMINATOR on both before landing, since a lint that silently loses its rules is the failure mode here: a bare `TODO` makes the JS-plugin rule `gjsify/todo-needs-anchor` fire under the published GJS bundle (so the plugin host really loads, rather than the Rust subset passing quietly), and one unformatted file makes `format --check` exit 1.
- **Findings are FIXED, not silenced** — autofix for `prefer-node-protocol`/`consistent-type-imports`/spread, manual fixes for the `correctness` longtail (`no-new-array` → `Array.from({ length })`, redundant parameter-property assignments dropped, dead code removed, a duplicate top-level `const seen` renamed, a `pipe()` `this`-alias dropped now that its handlers are arrow functions, regex membership tests → `startsWith`/`endsWith`, sqlite `allowUnknownNamedParameters` enforcement implemented). Genuinely-intentional patterns (NUL/ESC control-char regexes, listener-snapshot `[...set]` spreads whose copy is the point — a Set iterator is live, so an unsubscribe mid-fan-out would skip the next listener, `[...typedArray.slice()]` conversions an `assert.deepEqual` against an array literal needs, lossy number literals that ARE the napi conformance fixture, GObject `static new()` factories in `.d.ts`, deliberate class+interface merging, NAPI pending-exception rethrow in `finally`, Excalibur points-setter trigger, GJS `imports[name]` side-effecting access) carry a per-line `// oxlint-disable-next-line <rule> -- <reason>`. Do NOT blanket-disable rules.
- **A directive that suppresses NOTHING is an ERROR** — `options.reportUnusedDisableDirectives: "error"`. A disable comment CLAIMS that a finding was considered and accepted; when the rule it names is not enabled (or the code moved on), it documents a review that never happened. That is the shape of the `require('node:fs')` incident: `// eslint-disable-next-line @typescript-eslint/no-require-imports` comments sat next to the offending sites from 30 May until main went red, and `typescript/no-require-imports` was not in the `correctness` category, so they suppressed nothing (§ CJS-ESM Interop). Cleared the whole class in one change (60 sites, 27 files) because the rule regrows otherwise: 12 rules were named that this repo never enabled — `no-throw-literal`, `no-console`, `no-new`, `no-var`, `eqeqeq`, `no-eq-null`, `no-new-func`, `new-cap`, `no-multi-assign`, `no-negated-condition`, `no-await-in-loop` (ESLint-era leftovers on code adapted from upstream Node/undici/webtorrent) plus `no-constant-condition`, which IS enabled but exempts `while (true)` by default; and 16 `typescript/no-explicit-any` disables whose `any` had already been rewritten to `unknown`/`Record<string, unknown>`, leaving the comment behind. It is `error`, not `warn`: the CI gate is oxlint's own exit semantics, so a warning here would gate nothing. **It distinguishes decoration from necessity by construction** — the two load-bearing `@gjsify/http2` `no-require-imports` disables are never reported, and neither is any `-- <reason>` comment whose rule still fires (oxlint parses the ESLint `-- description` suffix). A per-rule "disables must state a reason" rule was considered and REJECTED: the tree still carries ~295 live directives (355 before this cleanup), nearly all bare, so that would invent a convention this repo does not have — and with the underlying rule enabled, silencing it already costs an explicit, review-visible comment.
- **Scope-outs are for what the linter provably cannot parse, never for valid source.** `.oxlintrc.json`'s `ignorePatterns` carries `website/src/components/AdwWidget.astro` with the reason inline (oxlint accepts JSONC comments): oxlint finds an `.astro` file's `<script>` blocks by plain text scan, so a literal `<script>` written inside a template JSX comment is read as a real script opener and the markup after it is parsed as JS. Every other `.astro` file stays linted — oxlint does check astro frontmatter, so blanket-ignoring `**/*.astro` would drop real coverage.
- **CSS/JSON formatting is DROPPED.** oxfmt formats JS/TS (+TOML) only. Biome's CSS/JSON formatting is NOT replaced — do not re-add Biome or another formatter for them.
- **Internal lint rules:** `packages/infra/oxlint-plugin-gjsify/` — the internal oxlint JS plugin, internal-only (NOT published to npm — no Trusted-Publisher bootstrap), wired via `.oxlintrc.json` `jsPlugins` + per-rule `"gjsify/<rule>":"error"`. Rules: `gjsify/register-class-order` (hoists `static` GObject metadata fields above a `GObject.registerClass` static block, with autofix) and `gjsify/deferred-process-exit` — a bare `process.exit()` does NOT halt under GJS (no atexit; the GLib loop may still be armed): the call RETURNS a scheduled exit, the statements after it still run, and the requested exit code can be lost (`gjsify storybook` with no stories reported the failure AND "Found 0 story file(s)" AND exited 0, while the same command exited 1 on bun). The rule flags a statement CONTAINING a bare exit when another statement follows it in the same statement list; tail-position exits are deliberately clean, and there is NO autofix (the right repair is context-dependent and a wrong one is a syntax error). Third rule: `gjsify/todo-needs-anchor` — a `TODO`/`FIXME`/`HACK`/`XXX` opening a comment line must anchor to `#123`, a forge issue URL, `open-todos` or `fixed upstream in …`; a bare marker has no owner and no retirement. It matches only the comment's OPENING word, so prose ABOUT a todo is not a finding. The `open-todos` form is additionally checked from the other side by the `status-data` conformance rule, which fails an anchor naming no `### ` heading in `status/open-todos.md` — the rule alone only looks for the substring, so a renamed or deleted entry would leave the marker pointing at nothing. Repairs: `return process.exit(…)` in a handler/async chain (the codebase-wide discipline — run.ts/workspace.ts document the double-exit core-dump history); in a SYNCHRONOUS value-returning helper `return` cannot halt the caller (under GJS `process.exit()` returns a forever-pending Promise, which the caller would receive as the value), so the sanctioned shape there is exit-then-`throw` with a reasoned `oxlint-disable-next-line` (see `commands/affected.ts`). e2e: `tests/e2e/oxc-plugin` (rule matrix) + `tests/e2e/storybook-no-stories` (the shipped behaviour, end-to-end under `gjs`). Fifth rule: `gjsify/no-css-side-effect-import` — a bare `import '<something that is CSS>';` registers NOTHING under any gjsify build, because `cssAsStringPlugin` emits `export default "<css>"` and a side-effect import of a module with no side effect is tree-shaken; measured on 0.41.0 as a ZERO-BYTE bundle for a probe entry whose only statement was `import '@gjsify/adwaita-fonts';` — the line `@gjsify/adwaita-web` carried for its whole life while declaring `font-family: 'Adwaita Sans'` and registering no face, invisible because a GNOME host supplies the typeface from fontconfig. It resolves the target package's `exports` off disk (not `createRequire().resolve()`, which answers only when the target FILE exists — half the interesting targets are unbuilt `dist/` outputs, and a rule that goes quiet on an unbuilt tree is quiet in CI). NO config override: the one legitimate site in the tree — `import '@fontsource/coming-soon'` in `website/src/components/ShowcaseSlideshow.astro`, where Astro really is a CSS pipeline (proven by the `@font-face{font-family:Coming Soon` rule and the emitted `.woff2` in `website/dist/_astro/common.*.css`) — carries a per-line reasoned disable instead. A directory override would neither be scoped to that line nor self-retire, while the directive is BOTH: with the rule off for `website/**` the same comment is reported as an unused directive, measured. The consumer-facing half — a BUILD that names the discarded import — is open in `status/open-todos.md`; the natural hooks for it (`generateBundle`/`renderChunk` payloads, `getModuleInfo`) are argument-less no-ops on the `@gjsify/rolldown-native` bridge, so it would have run under Node and silently not under GJS.
- **oxfmt is pre-1.0** (0.54) — formatting output may churn across minor releases; budget a possible re-reformat per oxfmt minor until 1.0. Bumping the npm `oxfmt` devDep requires re-pinning `refs/oxc` to the matching `oxfmt_v<X>` tag + rebuilding the `@gjsify/oxfmt-native` prebuild so both engines format identically.
- **`--globals auto` detection stays on acorn** — oxc's parser must NOT be repurposed for global detection (this migration is lint/format tooling only). See the Tree-shakeable globals invariants.
