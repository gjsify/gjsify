# The two gates before real GObject becomes the Android default (2026-10-15)

[ADR 0110](../adr/0110-real-gobject-becomes-the-android-default-and-the-subset-stays-tested-there.md)
makes the real-Gio engine the NativeScript Android default, but only behind two gates: finish
[ADR 0105](../adr/0105-real-gobject-backs-the-nativescript-subset-on-android.md) stage 2 by
**timing per-instance cost** against the pure-JS engine, and measure what the plugin costs a
**release** APK — compressed size per ABI, and cold start. This report closes both. It does not
flip the default and it does not judge whether the numbers are acceptable; that is ADR 0110 step 4.

Two hosts, both numbers from the same sources:

- **Host** — Intel i9-10900K, Fedora 44, Node v24.19.0, GLib 2.88.3, `@gjsify/node-gi` against
  the system GI stack.
- **Device** — the `x86_64` emulator `NsGi_API_36` (API 36, `sdk_gphone64_x86_64`),
  `@nativescript/android` 9.1.1, the GI closure from `@gjsify/gi-runtime-android`'s AAR.

Built from `~/.cache/gjsify-android/wt-stage4`, the same tree the stage-4 report used.

## Gate 1 — per-instance cost

### What is timed, and why these four rows

`packages/nativescript-bridge/gobject/src/bench.ts` is one engine-agnostic body, shipped with the
package and exported from its `index.ts`. `createGObject(door, engine)` takes the engine
explicitly, so a SINGLE process times both engines and neither leg can be a different build of
anything. The host entry is `src/bench.node-gi.mts` (`gjsify run bench:node-gi`); the device leg is
`tests/integration/nativescript-gi/app/specs/bench.ts`, which calls the identical body — host and
device cannot drift.

The subject is the class the vectors use: a registered class with two properties and one signal.
Four rows, because "construction cost" turned out to be two different questions:

- **`construct`** — `new Klass()` and nothing else.
- **`construct+first-read`** — construct, then read one property. The real engine builds its
  GObject twin **lazily**, in `twinOf` on first use, so `construct` alone does not pay for it.
  Without this row the measurement would report a cost of zero and be wrong.
- **`set+notify`** — one `set_property` plus the `notify` round trip it causes.
- **`emit`** — one signal emission to one connected handler.

Median over repeats, with min and max per repeat as the spread; warm-up repeats discarded;
constructed instances retained in an array so garbage collection is not charged to the timed loop.

### Host: 20 000 ops, 11 repeats, 3 warm-ups

ns/op, median (min–max):

- `construct` — pure-JS **304** (259–572), real-Gio **273** (247–411)
- `construct+first-read` — pure-JS **1968** (1088–4222), real-Gio **10462** (8382–26005) → **5.3x**
- `set+notify` — pure-JS **474** (445–874), real-Gio **21144** (19986–39676) → **44.6x**
- `emit` — pure-JS **131** (129–146), real-Gio **3165** (3119–3425) → **24.2x**

### Device: 4000 ops, 7 repeats, 2 warm-ups

ns/op, median (min–max):

- `construct` — pure-JS **479** (338–1566), real-Gio **268** (227–521)
- `construct+first-read` — pure-JS **2092** (668–5214), real-Gio **16225** (13066–21108) → **7.8x**
- `set+notify` — pure-JS **601** (496–681), real-Gio **59729** (56267–74990) → **99.4x**
- `emit` — pure-JS **223** (194–252), real-Gio **9782** (8777–11769) → **43.9x**

### Reading these numbers

**`construct` costs no measurably more on the real engine, and that is a property of the design,
not a surprise.** The subject's properties are plain `READWRITE`, so `constructRegistered` touches
no engine at all and the twin is not built yet. Both engines land in the same few hundred ns/op and
the spreads overlap; the ratio comes out slightly BELOW 1.0 on both hosts (0.90x, 0.56x) because
the pure-JS leg runs first and is therefore the less warmed one. The row is reported as "no
measurable difference" rather than as a ratio for that reason — a ratio there would be reporting
warm-up order.

**What real GObject actually costs is use, not creation.** First property read ~5–8x, a
set/notify round trip ~45x on the host and ~99x on the emulator, an emission ~24x and ~44x. Both
hosts agree on the shape; the emulator multiplies the native-crossing rows further, which is what
an emulated `x86_64` guest doing `g_object_set_property` would be expected to do.

**One row is unstable across sessions and is reported as such.** An earlier device run with 5
repeats and 1 warm-up gave real-Gio `emit` 5318 ns/op (21.9x) against the 9782 (43.9x) above. The
repeat count was raised to 7/2 after that run, and the same run had produced a nonsensical 0.30x
for `construct` from warm-up noise alone. Treat device `emit` as "tens of times slower, between
roughly 20x and 45x", not as 43.9x.

Absolute scale for context: the worst row is ~60 µs per set/notify on the emulator, so an
interaction doing a few dozen property writes stays under a frame. Nothing here says where the
budget runs out for a real UI; this is per-op cost, not a frame-time measurement.

### The benchmark is a script, not a CI gate

It lives next to the engine, runs on demand, and is wired into neither CI nor the device suite's
default run. On the device it sits behind a new build-time define, `__GJSIFY_GI_BENCH__`
(`GJSIFY_GI_BENCH=1`): the suite executes during module evaluation, BEFORE `Application.run()`,
so an always-on benchmark would put its seconds straight into the cold-start number measured in
gate 2 — and the on-device runner allows 180 s for the whole run.

## Gate 2 — the release APK

### How these APKs are built

`tests/integration/nativescript-gi/scripts/build-release-splits.mjs <b0|b|c>` builds one rung,
copying the outputs to `release-apks/<rung>/` because gradle writes `app-<abi>-release.apk` to one
fixed path and the next rung would overwrite it. Per-ABI splits are behind `-PgjsifyAbiSplits` in
`App_Resources/Android/app.gradle` — not unconditional, because `run-on-device.mjs` installs
`outputs/apk/debug/app-debug.apk` by path and a split build does not write that file.

The rungs are stage 4's ladder minus A0:

- **B0** — `GJSIFY_GI_PLUGIN=0`: `@gjsify/node-gi/gi` is aliased to `app/no-gi-stub.ts`, so node-gi
  is not in the bundle at all. The AAR is still a gradle dependency, so the payload is still in the
  APK. Verified on the device: `pure-js`, 29 of 29.
- **B** — `GJSIFY_GI_OPT_IN=0`: node-gi imported, the app declines the engine. Verified: `pure-js`,
  29 of 29.
- **C** — the default: imported and opted in. Verified: `real-gio`, 62 of 63.

**A0 (the payload not even packaged) is not measured.** It needs a gradle packaging exclusion that
changes the build in ways the delta cannot account for, and stage 4 measured carrying-but-not-
loading at noise size (~0–20 ms, equal minima) on arm64.

The one device failure in C is pre-existing and unrelated: `Gio.Settings vectors … an unknown key,
an out-of-range uint, an unknown signal and an unknown schema throw`. It is the same case the host
failed until the node-gi addon was rebuilt; the device's `libnode_gi.so` comes from the prebuilt
AAR, which is stale the same way.

### Two deviations from "release, minified"

**`ns prepare` needs `--release` as well, and this was a crash, not a nicety.** Without it Vite
emits a DEBUG bundle, whose `@nativescript/core` inspector modules call
`__registerDomainDispatcher` — a global only the debug Android runtime injects. Packaged into a
release APK, the app ran the whole suite, logged all 63 cases, and then died at the end of module
evaluation with `ReferenceError: __registerDomainDispatcher is not defined`, which reads like a
late app bug rather than a build mismatch. With `--release` the JS **is** minified: `bundle.mjs`
goes from 2714 kB to 1797 kB. All numbers below are from `--release` builds.

**R8 is NOT enabled, and it cannot change the delta.** NativeScript's generated
`platforms/android/app/build.gradle` leaves its `minify.*WithR8` hooks commented out and its
`release` buildType sets only `signingConfig`; turning R8 on would mean editing generated gradle.
R8 shrinks the Java DEX, not `.so` files and not typelibs — so it could move the APK's baseline
TOTAL but not the payload delta these rungs measure. Signing uses NativeScript's own gated
`signingConfigs.release` with the SDK debug keystore; which key signs an APK changes neither its
size nor its start-up time.

### Compressed size delta per ABI

Measured with `scripts/apk-size.mjs <apk> --against <apk>` on the release split APKs, by **entry
accounting**: COMPRESSED zip-entry sizes, never `stat` on the file, because gradle's incremental
packaging rewrites a previous APK in place and a file's length can belong to a build that is no
longer the one on disk. The script now reads which ABIs an APK actually carries off its entries, so
a split APK is not reported as "missing" the other ABI's libraries. `--against` is new: it diffs
every NON-payload entry between two APKs, which is how the JavaScript side of the cost becomes a
number instead of an assumption.

Per ABI, C against B0, compressed:

- **arm64-v8a** — payload entries (15 libraries + 7 typelibs) **15,746,594 B**, JS
  (`assets/app/bundle.mjs`) **+26,697 B**, total **15,773,293 B ≈ 15.77 MB**. APK 47,753,176 B
  with, 32,006,582 B without.
- **x86_64** — payload **16,907,482 B**, JS **+26,697 B**, total **16,934,181 B ≈ 16.93 MB**.
  APK 50,311,400 B with, 33,403,918 B without.

Of each payload total, typelibs are 205,466 B compressed; the rest is `.so`, stored uncompressed
(`stor`), which is why compressed and uncompressed differ by only ~0.5 MB. The largest single
entries are `libpixman-1.so` (2.90 MB arm64, 4.38 MB x86_64), `libgio-2.0.so`, `libglib-2.0.so`
and `libxml2.so`.

Splitting the JS delta between the two decisions: importing node-gi with the opt-in OFF is
**+18,450 B** (B against B0), and the opt-in itself adds the remaining **+8,247 B**. Three other
entries moved by a total of 2 bytes (`classes.dex`, `baseline.prof`, `treeStringsStream.dat`),
which is what "nothing else differs between these builds" looks like when stated as a number.

This is the first per-ABI release figure for the plugin, and it reconciles with stage 4's universal
DEBUG APK to within a kilobyte of libraries. Subtracting the typelibs, the libraries alone are
15,541,128 B (arm64) and 16,702,016 B (x86_64) — stage 4 reported 15,540,824 and 16,701,632 for
the same two sets, 688 B apart in total. The two reports' typelib figures differ by more
(205,466 B here against 226,324 B there) because the release packaging deflates the same seven
files harder, which is also why the two splits' payloads sum to 32,654,076 B against stage 4's
universal 32,468,780 B: a split build carries its own copy of the typelibs, so they are counted
twice here and once there.

### Cold start on the x86_64 emulator

`emulator-5554`, each rung installed on its own, one warm-up launch, then ten
`adb shell am start -S -W -n org.gjsify.NsGiTest/com.tns.NativeScriptActivity` launches with 8 s
between them, reading `TotalTime`. Two independent passes of ten, so twenty launches per rung.
Without root the page cache cannot be dropped, so this is a cold **process** on warm files — the
same method, and the same limitation, as the stage-4 arm64 measurement.

Median over all twenty, ms (min–max over twenty; per-pass medians in brackets):

- **B0** — plugin in the APK, node-gi not in the bundle: **450** (419–676) [427.5 / 469.5]
- **B** — node-gi imported, opt-in off: **457** (420–744) [451 / 457]
- **C** — opt-in on: **530** (477–899) [563.5 / 511.5]

Read as steps: importing node-gi **+7 ms**, the opt-in itself **+73 ms**, B0 to C **+80 ms
(+17.8 %)**.

Two honest qualifications. **Individual launches vary far more than the deltas do** — the spreads
overlap heavily, and the per-pass medians move by up to 52 ms between passes; it is the ordering
B0 < B < C that is stable, reproduced in both passes, not any single figure. And **`TotalTime` here
is first frame of a test app**: the vector suite runs during module evaluation, so C's number
includes executing 63 cases against real Gio, which is not what a shipping app does at startup.
Stage 4 measured the same way on arm64 and got ~83 ms / 6.5 % — nearly the same absolute step
against a much slower baseline (1263 ms on an SM-G960F against 450 ms here).

### arm64 release cold start (Galaxy S9)

Measured later the same day, on a real arm64 device: the USB Galaxy S9 (SM-G960F, /e/OS on Android 15),
release split `app-arm64-v8a-release.apk` per rung, built from
`origin/main` at a4781213fa (after #2236, so real GObject is already the Android default). The
ladder is the one above, `GJSIFY_GI_UI=0` in every rung. `libnode_gi.so` and the AAR were built
locally from that tree (the published 0.64.0 AAR is stale), not taken from npm.

Method as for the emulator: each rung installed on its own, one warm-up launch, then ten
`adb shell am start -S -W` launches (force-stop of the app's own package, 8 s apart), reading
`TotalTime`; two passes per rung in opposite order (B0, B, C, then C, B, B0), twenty launches per
rung. The page cache is not dropped (no root), so this is a cold process on warm files. Engine
verified on the device for B (`pure-js`) and C (`real-gio`). Device: battery 100 %, 26.4–26.6 °C
throughout, USB powered, screen woken before every launch, launcher in the foreground.

Median over twenty, ms (min–max; per-pass medians in brackets):

- **B0** — node-gi not in the bundle: **813.5** (777–850) [814 / 811]
- **B** — node-gi imported, opt-in off: **828.5** (783–884) [826.5 / 829.5]
- **C** — real engine on: **919** (896–970) [926 / 918]

Read as steps: importing node-gi **+15 ms**, the opt-in itself **+90.5 ms**, B0 to C
**+105.5 ms (+13.0 %)**. The ordering B0 < B < C holds in both passes and the C range does not
overlap B0's; B against B0 overlaps heavily and is within noise.

The same caveat as on the emulator applies: `TotalTime` is first frame of a test app, and C's
figure includes the vector suite running against real Gio during module evaluation. The step is
larger than stage 4's ~83 ms (universal debug APK, 6.5 %) and than the emulator's +80 ms, against
a baseline (~0.81 s) well below stage 4's 1263 ms.

### The opt-out after lazy loading (x86_64 emulator)

Both measurements above were taken while importing `@gjsify/node-gi` loaded `libnode_gi.so`
from its module body, so rung B paid for a library it never used. `@gjsify/node-gi` now loads
the native host on first use when the host asks for it (`LAZY_NATIVE` in `host.nativescript.js`;
desktop Node stays eager). A selected real engine that cannot load still fails loudly on every
call (ADR 0105 § 4).

Proof, API 36 x86_64 emulator, release split. The shell cannot read `/proc/<pid>/maps` of a
non-debuggable app and the libraries are stored uncompressed, so they are mapped out of
`base.apk` and never appear by name. A temporary probe in the app read its own
`/proc/self/maps` after the run and compared the `base.apk` mappings with the APK offset of
`lib/x86_64/libnode_gi.so` (0x26c0000–0x2798378). Rung B (opt-out, `pure-js`): no mapping in
that range. Rung C (`real-gio`): mappings at 0x26c0000, 0x270f000, 0x2791000 and 0x2797000.
The probe is not part of the measured builds.

Cold start, same method as above (one warm-up, ten launches 8 s apart, two passes in reversed
order, twenty per rung), medians in ms (min–max; per-pass medians):

- **B0**: **442.5** (406–748) [453 / 442.5]
- **B**: **456** (422–790) [438.5 / 459.5]
- **C**: **532** (489–1044) [596.5 / 516.5]

B against B0 is +13.5 ms, inside the pass-to-pass spread. The earlier emulator run gave +7 ms,
so the opt-out was already close on this machine; the gain here is that it no longer maps the
library or its closure, which the emulator's `TotalTime` resolves poorly. The arm64 opt-out
cold start on the Galaxy S9 is not measured yet.

## What is not measured

- **arm64 opt-out cold start (S9)** after lazy loading of the native host.

- **A0** — an APK without the payload packaged at all (see above).
- **R8/DEX shrinking**, and therefore the smallest achievable baseline APK total (see above).
- **Frame time, memory, or any whole-UI figure.** Gate 1 is per-op cost.
- Whether 15.8–16.9 MB per ABI and ~80 ms are **acceptable**. ADR 0110 step 4 decides that.
