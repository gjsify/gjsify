# 39. The prop surface is published, and a refused prop keeps throwing

- Status: **Proposed**
- Date: 2026-09-02
- Deciders: Pascal Garber
- Related: [ADR 0032 (React Native on the GTK host)](0032-react-native-on-the-gtk-host.md), [ADR 0036 (third-party React Native surfaces)](0036-third-party-react-native-surfaces.md), [ADR 0027 (GTK host layer)](0027-gtk-host-layer.md), [ADR 0016 (status as data)](0016-status-as-data.md)

## Context

ADR 0032 § 8 says gaps are loud, from one data source, and ADR 0036 § 6 says every
surface gets the same three readers — a build-time gate, a runtime refusal and
generated documentation. Both are about NAMES: may this application import
`FlatList`, is `expo-font` answered.

There is a second surface one grain finer, and it had none of that machinery: the
PROPS. `PRIMITIVES` in `src/primitives/table.ts` decides them, and that module was
not an entry point at all — the package's `exports` map published `.`, `./solid`,
`./router`, `./support-table` and the eighteen ADR 0036 surfaces, and none of them
answered "does `<Text>` take `onPress`?".

The consequence is that a prop refusal could only be discovered by RENDERING.

### The incident

A consumer — a real React Native application with a GTK4 desktop host — rendered
`<Text onPress={…}>`. The layer refuses `onPress` on a `Gtk.Label`, **correctly**: a
label emits no `clicked` (measured: `activate-current-link`, `activate-link`,
`copy-clipboard`, `move-cursor` and nothing else), and the fix is one `<Pressable>`.

The application's tab stack mounts all five tabs from the start route. The
`PrimitiveError` therefore came out of a render, uncaught, and React unmounts the
whole root when a render throws with no error boundary above it. So one refused prop
on one screen ended the ENTIRE tree — the home screen rendered nothing either.

Measured as two bundles of the same host rendering the same screen: **92 125 bytes**
of widget dump clean against **12 848 bytes** with the throw.

### Three smaller findings from the same port

- **`TextInput` had no instance type and no ref handle.** In React Native `TextInput`
  is a class — a value *and* a type — and its ref carries `focus()`, `blur()`,
  `clear()`, `isFocused()` and `setSelection()` (react-native 0.85.3's own
  `TextInput.d.ts`: three of its own plus `NativeMethods`' six). This layer declared a
  function and handed the ref the bare `Gtk.Widget`, so `useRef<TextInput>(null)` did
  not compile and `passwordRef.current?.focus()` was `undefined is not a function`.
  Both are ordinary React Native code. Every PROP had a table and a named refusal for
  every gap; the ref had neither.
- **`accessibilityLiveRegion` was refused as an unknown prop**, i.e. with the message
  for a typo. GTK has had `Gtk.Accessible.announce(message, priority)` since 4.14
  (measured on the 4.22.4 baseline: a method on the `Gtk.Accessible` interface, so
  every widget has it, taking LOW/MEDIUM/HIGH).
- **`autoComplete`, `textContentType` and `submitBehavior` were refused as unknown
  props too**, and each consumer had to decide separately what a desktop does with
  them.

## Decision

### 1. Publish the prop surface, as `@gjsify/react-native/prop-table`

A subpath, exactly as `./support-table` is one for imports, over the SAME data:
`propAnswer`, `acceptsProp`, `explainProp`, `propNames`, `propTable` and
`PRIMITIVE_VARIANTS`, all derived from `PRIMITIVES`. A consumer's test suite can now
assert `acceptsProp('Text', 'onPress') === false` before a window exists.

**One source, and it is enforced by construction rather than by comparison.** The
classifier and both refusal sentences live in `src/primitives/answers.ts`;
`resolve.ts` THROWS what `explainProp` RETURNS, the same string. `prop-table.spec.ts`
holds that for every refusal the table declares, on every primitive and both
`TextInput` variants, generated from the table so a row added tomorrow is covered
without anyone remembering to add a vector.

### 2. `PROPS.md` is generated, and generated by IMPORTING the table

`SUPPORT.md` is generated from `support-table.ts`' source by a regex parser, because
`check-rn-surface.mjs` runs in a job that deliberately does no install and no build.
The same constraint holds here and the same instrument does not: `primitives/table.ts`
spreads shared records (`...COMMON`) and CALLS functions to build refusal sentences
(`PRESSED_STYLE_IS_CSS('active:opacity-70')`), so a parser would report the spread
instead of the row's answer — a second truth about the one question the layer exists
to answer.

Node's own TypeScript type stripping resolves it: the generator `import()`s
`primitives/table.ts` and `primitives/answers.ts` directly, with no build, no install
and no flag on the Node the job pins. Those two modules therefore may hold **no
relative value import** — Node does not rewrite a `./x.js` specifier to `./x.ts` —
and `answers.ts`' header records that constraint at the other end.

`check-rn-surface.mjs` compares `PROPS.md` byte for byte, as it does `SUPPORT.md`, and
fails if `./prop-table` is not a declared subpath.

### 3. A refused prop keeps throwing

The incident is an argument for the static check, **not** for a softer refusal, and
this is the decision the incident could have gone the other way on.

A refusal that logged and rendered on would put a `<Text onPress>` on screen that
never fires — "a prop that silently does nothing is indistinguishable from a bug in
the application, forever", which is `table.ts`' own reason for throwing and this
layer's whole thesis (ADR 0027 rule 3: be loud, because GTK's failure mode is exit 0).
The delivery channel for the log would be a stderr stream that a desktop
application's user never sees.

And the blast radius is REACT's, not this layer's: a render-time throw with no error
boundary unmounts the root, for every library equally. The answers to it are the ones
React already has — an error boundary — plus the one that was missing, which is being
able to ask before rendering. That is § 1.

So: no behaviour change to the refusal. What changed is that the question is now
answerable statically.

### 4. `TextInput` gets an instance type and an imperative handle

`PrimitiveSpec.handle` is a table field, so both L3s read one answer —
`primitives/handles.ts` turns the kind into the object and React and Solid both hand
it to a `ref`. A handle built inside one binding would be a vocabulary the other does
not have.

Five members are answered over GTK and four are **refused by name**, because an absent
method is the `undefined is not a function` this closes:

| member | answer |
|---|---|
| `focus()` | `Gtk.Widget.grab_focus()` |
| `blur()` | `Gtk.Root.set_focus(null)`, and ONLY when this widget holds the focus — unguarded it takes the focus from whatever really had it |
| `clear()` | `Gtk.Editable.set_text('')`, or the buffer's own on a multiline input |
| `isFocused()` | `Gtk.Widget.is_focus()`, not `has-focus`: the latter is the GLOBAL focus and is false whenever the compositor has not activated the window |
| `setSelection()` | `Gtk.Editable.select_region()`, or `Gtk.TextBuffer.select_range` |
| `measure` / `measureInWindow` / `measureLayout` | refused: GTK has a geometry only after allocation inside a presented window, and before that every number is zero — indistinguishable from a real measurement. `Gtk.Widget.compute_bounds()` on `handle.widget` is the honest call, at a moment the caller knows |
| `setNativeProps` | refused: `handle.widget` IS the widget and every GTK property is settable on it by name; a second spelling taking React Native prop names would be a second prop table |

`handle.widget` is the one addition beyond React Native's surface, and it is what
keeps a port that already reached for `Gtk.Entry` API through the ref working.

The instance TYPE is an `interface TextInput extends TextInputHandle` merged with the
component function — a value and a type may share a name — so `useRef<TextInput>(null)`
resolves exactly as it does upstream.

### 5. `accessibilityLiveRegion` is answered on `Text` and refused elsewhere, with the real reason

React Native's prop is a DECLARATION: the platform watches this element's content and
speaks the change. `announce()` is IMPERATIVE: the caller supplies the moment and the
message. The bridge is only buildable where the layer knows both, and it knows both on
exactly one primitive — a `Gtk.Label`'s content IS a property, so `notify::label` is
the moment and `label` is the message.

`polite` → MEDIUM and `assertive` → HIGH are GTK's own definitions of ARIA's two
levels. GTK's `low` is absent as a target: React Native has three values and there is
no spelling to arrive from.

Everywhere else the prop is refused BY NAME with that reason — not "GTK4 has no
property", which would send a reader looking for one that has existed since 4.14. What
a `View` lacks is the watch: its content is a subtree, and GTK emits no signal when one
changes.

**It connects DIRECTLY, and that is the finding the obvious test does not make.** The
first implementation routed the announcement through the host's handler map as an
`on:notify::label` prop, which is where a signal binding belongs — and it announced a
change made from outside React while never announcing the one the application made.
The host SUPPRESSES a `notify::` raised inside its own property write (module-wide, by
design: it is what stops a controlled `<TextInput>` re-entering `onChangeText`), and a
`<Text>`'s content IS a host write. So the whole feature fired on exactly the path
nobody needs it on. The guard protects the APPLICATION from re-entering its own write;
this layer's announcement has to fire precisely on that write, so it subscribes the way
`press.ts` subscribes a gesture — `widget.connect()` with a disposer that really
disconnects, because GJS blocks a JS callback during the sweeping phase of GC. Both
bindings carry a vector that drives the change through the framework, and
`liveRegionWatchCount()` holds the other half: a `<Text>` with no live region and one
with `"none"` subscribe to nothing, which nothing but a count can tell apart.

### 6. Three props are declared no-ops, once, in the layer

`autoComplete` (Android autofill hint), `textContentType` (its iOS spelling) and
`submitBehavior` name a service a GTK desktop does not run. `ignored` and not
`refused`, for the reason `autoCapitalize` already is: they arrive on perfectly
ordinary React Native code that the author cannot rewrite into something a desktop
would honour, so throwing would refuse a correct program. The DECLARED no-op keeps
"GTK has no such service" apart from "the table forgot this name" — and writes the
argument down once here instead of once per application.

`Gtk.Accessible` does carry an `autocomplete` property and it is a different thing: a
widget that completes its own text, not a system that fills it in.

## Consequences

- **`@gjsify/react-native`'s `exports` map grows `./prop-table`**, and `files` grows
  `PROPS.md`. No new npm name, no bootstrap, no tier change.
- **`generate-exports.mjs` now imports TypeScript source.** That is a new capability
  for this repository's Node scripts and it constrains two modules: `primitives/
  table.ts` and `primitives/answers.ts` may hold no relative value import and no
  TypeScript construct that is not erasable. Both are checked by the generator running
  at all.
- **A `<TextInput>` ref's VALUE changed** — it is a handle, not the widget. `.widget`
  is the migration, and it is one line in a consumer. Every other primitive is
  unchanged.
- **The consumer-side shim that motivated all of this can be deleted.** That is the
  point: ADR 0036 § 5.1 asks "is there anything here a consumer cannot do for
  themselves?", and a construct-time handle, a table field and a published entry point
  are three answers of "no".

## What this does not decide

- **Whether the layer should install a root error boundary.** `AppRegistry` could
  render the `PrimitiveError`'s message instead of an empty window, which would bound
  the incident's blast radius without weakening the refusal. It is a real answer, it is
  React's own mechanism, and it is a separate change with its own measurement.
- **A prop-level gate at BUILD time.** The ADR 0032 § 8 gate reads import statements;
  reading JSX attributes is a different analysis with a different cost, and the
  published table plus a consumer's own test is what this ADR buys instead.
- **Handles for the other primitives.** React Native gives `NativeMethods` to every
  host component; this layer gives one to `TextInput`, which is where the measurement
  is. The table field is what makes the next one a row rather than a design.

## Amendment (2026-09-04) — § 5's shape is a route FAMILY, not one prop

§ 5 built `accessibilityLiveRegion` as a route that holds the whole decision and none
of the call, and read as if that were a concession made for one prop. It is the
general shape, and the accessibility props are the second family to use it: a
`to: 'accessible'` route carries the attribute set, the member and the GValue type as
DATA in `primitives/table.ts`, and `src/accessibility.ts` makes the
`Gtk.Accessible.update_property()`/`update_state()` call for both bindings. An
imperative GTK call is a route like any other.

Two things it added that outlive it:

- **`PropertyRoute.refuses` gives a mapped prop a per-value reason.** A value absent
  from `map` gets "Known: …", which is right for a typo and wrong for a real React
  Native spelling with no GTK member — `accessibilityRole="keyboardkey"` is not a
  typo. Seven role names are answered by name instead. The refusal's advice is held
  against the table by a vector, because three of those sentences first pointed at
  ARIA roles GTK has and this layer's `accessibilityRole` map does not.
- **`Gtk.Accessible:accessible-role` is NOT construct-only**, so the role is an
  ordinary property route rather than an imperative call. The received wisdom is why
  an application holding a finished widget through a ref drops the prop; measured on
  every widget class this table builds, the ParamSpec is `READABLE|WRITABLE` and a
  post-construction write sticks (`docs/react-native-gtk-measurements.md`, fact 6).

What is still refused is stated where it is decided, not here: the VALUE of an
accessible property or state cannot be read back in-process, so the vectors assert
presence and zero GTK diagnostics as a pair.
