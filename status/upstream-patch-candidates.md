| **A Promise-returning exported DBus method mis-marshals its resolved value on gjs 1.86.0** — the caller gets `org.gnome.gjs.JSError.ValueError: Service implementation returned an incorrect value type`. The `_handleDBusReply` continuation in `refs/gjs/modules/core/overrides/Gio.js` (reached via `retval?.then?.(r => _handleDBusReply(invocation, r))`) fails for EVERY resolved type — a bare `s`, a pre-packed `GLib.Variant`, an `ay` — not just byte arrays; the identical value returned SYNCHRONOUSLY marshals fine. Verified with a minimal external-`gdbus` reproducer. | @gjsify/devtools (`Screenshot`, the sole async method in the `org.gjsify.Devtools` interface), and any exported service with a Promise-returning method | Screenshot uses the `<Name>Async(params, invocation, fdList)` manual-reply convention — the method calls `invocation.return_value()` itself, which bypasses the broken continuation. The interface XML is unchanged (`wrapJSObject` falls back to `<Name>Async`). Extension handlers must follow the same convention if they ever go async (a comment marks the attach site). | **Fix the async reply path in GJS's Gio override** (`_handleMethodCall` → `_handleDBusReply`) so a Promise resolved to a plain value marshals identically to a synchronous return, OR document that Promise-returning methods are unsupported and only `<Name>Async` may reply asynchronously. Once fixed, collapse Screenshot back to a plain `async Screenshot(): Promise<Uint8Array>`. |
| **`Gda.SqlParser.parse_string()` corrupts the heap (`free(): invalid pointer`, process abort) when the parsed statement contains a `/* … */` block comment.** A `--` line comment parses fine; a block comment — leading, trailing, or mid-statement — triggers a double/invalid free inside libgda's lexer (`gi://Gda?version=6.0`, libgda 6.0 SQLite provider). Verified with a minimal reproducer: `parser.parse_string('/* c */ CREATE TABLE b(y TEXT)')` aborts the GJS process. | @gjsify/sqlite (`DatabaseSync.prototype.exec` / `prepare` — any SQL with a block comment) | `#splitStatements()` **strips comments** from each chunk before `parse_string()` sees them (line comments removed keeping the newline; block comments replaced with a space). Semantically transparent — SQL comments are inert outside quoted regions, which are preserved verbatim. The crash is unreachable from the public API as a result. | **Fix libgda's SQL lexer** (`libgda/sql-parser/` — the Flex/Lemon-generated tokenizer) so block comments are skipped without the bad free, OR expose a comment-stripping pre-pass. Until then comment-stripping in the splitter is the only safe option; it also blocks the long-term "let libgda tokenize/split" cleanup (see Open TODOs). |
| **`g_base64_decode_inplace()` is annotated `direction="inout"` over a `c:type="gchar*"` — one star — so honouring the annotation corrupts the caller's stack frame.** A real INOUT array is `gchar**`: the callee reads the in-container and reassigns the out-container. `glib/gbase64.h:57` declares `guchar *g_base64_decode_inplace (gchar *text, gsize *out_len)`, a single pointer, while `GLib-2.0.gir` marks `text` `direction="inout" transfer-ownership="full"` with `<array … c:type="gchar*"/>`. A binding that believes it hands the callee the ADDRESS of its own argument slot, so base64 is decoded over that slot and the read-back marshals — and frees — a pointer whose low bytes are payload. Measured on Fedora 44 / Node 24.15: five consecutive calls return 96, 208, 112, 240, 80 — the clobbered pointer, never data. gjs corrupts on the same call, so there is no oracle either. **Not detectable at runtime:** `c:type` is the only discriminator and it is NOT compiled into the typelib — compared field by field against a genuine `gchar***` INOUT (`GLib.OptionContext.parse`'s `argv`), the metadata is identical (direction INOUT, transfer EVERYTHING, tag ARRAY, is_pointer true, caller-allocates false). | @gjsify/node-gi (any INOUT container call), and equally every other GI binding incl. gjs and pygobject | None, and none is possible downstream. The call is removed from `test/arrays.test.mjs` with the evidence recorded there so it cannot be re-added, and `src/calls.cc`'s INOUT block states that its `container**` assumption comes from the annotation and cannot be verified. A per-function denylist was considered and rejected: it ossifies, and it cannot be complete — any mis-annotated callee anywhere has the same shape. | **Fix the annotation in GLib** (`glib/gbase64.c`, the `@text` gtk-doc block): the parameter is not an INOUT array. Either annotate it `(inout) (array length=out_len) (element-type guint8)` on a `gchar**` signature, or mark the function `(skip)` for introspection, which is what its aliasing return value argues for. **Second, deeper ask: give the typelib a discriminator** — the compiled typelib drops `c:type`, so no binding can tell a `T*` from a `T**` INOUT and every one of them corrupts memory identically. |
| **A callee that FILLS a by-value `GValue` array is annotated exactly like one that READS it.** `g_object_getv(n_properties, names[], values[])` writes its results into the caller's `GValue` cells, but the typelib records that parameter as direction=IN, caller-allocates=false, transfer=none — compared field by field against `g_parse_debug_string`'s genuinely read-only `keys`, the metadata is IDENTICAL. So no binding can tell the two apart, and a marshaller that hands the callee a copy of the array (which is what a by-value IN array means) silently drops the results. Measured on gjs 1.88.1: `action.getv(['name'], [value])` leaves the caller's GValue empty and reports no error. `Gst.Object.get_g_value_array` and `Gst.ControlBinding.get_g_value_array` carry the same shape. | @gjsify/node-gi (any by-value GValue array IN parameter), and equally gjs and every other GI binding | node-gi copies each cell BACK into the caller's `GValue` after the invoke, with `g_value_copy` (not a memcpy — the cell is unset immediately after, and a bitwise copy would leave the caller pointing at a string that unset frees). Harmless for the read-only callers: they leave the cell unchanged, so the copy-back writes the caller's own value into itself. Costs one `g_value_copy` per element. | **Fix the annotations in GLib/GStreamer**: `g_object_getv`'s `values` is `(inout)` (or `(out caller-allocates)`), not `(in)`. Then a binding can refuse or handle it deliberately instead of guessing. **Second, deeper ask, and the same one `g_base64_decode_inplace` makes above: the typelib needs a discriminator** — as it stands, "the callee reads this array" and "the callee fills it" are the same metadata, and every binding has to pick one behaviour for both. |
| `imports.byteArray.fromGBytes(gbytes)` memcpy's GBytes data into a fresh `JS::ArrayBuffer` even when the source GBytes wraps mutable mmap'd memory via `g_bytes_new_with_free_func`. `refs/gjs/gjs/byteArray.cpp::from_gbytes_func` does this deliberately — but that immutability assumption is wrong for our use case. | @gjsify/sab-native (`SharedBuffer.viewBytes`, `SharedBuffer.toBuffer`, `Buffer.from(sharedBuffer)`), and any future package that wants to expose mmap'd memory as a JS-mutable view | `viewBytes()` and `toBuffer()` are documented as fresh copies in current GJS. `readBytes()` keeps the same memcpy semantics it always had. Callers needing in-place mutation through a Buffer use `writeBytes()` to commit changes back. | **Add an explicit zero-copy path in GJS `byteArray`** — e.g. a sibling `byteArray.fromGBytesShared(gbytes)` that calls `JS::NewExternalArrayBuffer` instead of `JS::NewArrayBuffer + memcpy`. Caller-attests the GBytes is mutable + alignment-safe. **No internal alternative is viable today**: `JS::NewExternalArrayBuffer` requires a `JSContext*` which GJS does not expose to GObject-introspected `.so` plugins (verified — no native package in the monorepo links against `mozjs140`). A Vala/C-shim cannot call SpiderMonkey directly without first patching GJS to expose the JSContext (or add the helper itself). |
| `setTimeout` / `setInterval` return a `GLib.Source` BoxedInstance whose `.unref()` is `g_source_unref` (GLib refcount decrement) — clashes with Node.js `Timeout.unref()` ("don't keep event loop alive", refcount-irrelevant). Node-compat libraries (WebTorrent, bittorrent-dht, async-limiter, …) call `timer.unref()` as standard, each call partially frees the source → SIGSEGV in `g_source_unref_internal` at SM GC finalization. Compounded by GJS `_timers.js` calling `releaseSource(source)` before `drainMicrotaskQueue()`, opening a window where SM GC can finalize the BoxedInstance while GLib still holds a dispatch ref. | @gjsify/node-globals (timers), any Node.js code using setTimeout/setInterval under load, any GJS code that lets GLib.Source BoxedInstances reach the GC | `packages/node/globals/src/register/timers.ts`: full replacement of setTimeout / setInterval via `GLib.timeout_add` (numeric source ID, no BoxedInstance). Returns a Node-shaped `GjsifyTimeout` wrapper with no-op `.ref / .unref / .hasRef` and working `.refresh / Symbol.dispose / Symbol.toPrimitive`. **The cover is timers only.** This cell used to also claim a `GLib.Source.prototype.ref / .unref` no-op patch "as a safety net for BoxedInstances that leak from other gi APIs"; there is no such patch anywhere in the tree (`grep -rn 'Source\.prototype' packages/` finds one unrelated test), so a BoxedInstance reaching the GC from any OTHER gi API still crashes exactly as described on the left. A safety net that only a document believes in is worse than none. | **Two changes in GJS `_timers.js`** (modules/esm/\_timers.js): (1) reorder the dispatch closure so `drainMicrotaskQueue()` runs BEFORE `releaseSource(source)`, closing the SM-GC-during-drain window. (2) expose a Node-compatible `Timeout.unref() / .ref()` that tracks a "keep event loop alive" flag **instead of** mapping to `g_source_unref / g_source_ref`. Both changes can land independently; (2) alone eliminates the crash for Node-compat consumers. |

| **Top-level `await` + a registered main-loop hook + process exit from an async continuation deadlocks.** `imports.system.exit()` only sets GJS's internal `m_should_exit` flag + throws the uncatchable exit exception — it does **not** call `loop.quit()`. With a hook registered (which `ensureMainLoop()` does via `GLib.MainLoop.runAsync()`), `eval_module` drives the hook's **blocking** `loop.run()`; a bare `system.exit()` from a microtask never unblocks that nested loop, so the process hangs. Specific to a registered hook. Microtask draining is NOT affected — only teardown hangs. | @gjsify/utils (`ensureMainLoop`), and any entry module that combines top-level `await` with a server started via `ensureMainLoop()` | **Already mitigated for `process.exit()`:** `@gjsify/process`'s `exitProcess()` idle-schedules `quitMainLoop()` + `system.exit()`, so the process exits cleanly. The hole is only a **direct** `imports.system.exit()` from an async continuation under TLA, which gjsify cannot intercept. Documented guidance + a `main-loop.ts` JSDoc warning steer entry modules to a `main().catch(…)` body or an explicit `GLib.MainLoop().run()` torn down via `process.exit()`. Runnable proof: `docs/poc/tla-microtask-draining.gjs.mjs` + `.md`. | **Make a registered main-loop hook observe GJS's exit flag.** In `eval_module`/`run_main_loop_hook`, when `m_should_exit` is set from inside a job, quit the hook's loop (or document that hooks MUST be quit explicitly). Then a bare `system.exit()` from any continuation would terminate cleanly regardless of TLA. |
| `Gio.Subprocess.get_identifier()` returns `null` once the child is reaped — and GSubprocess reaps via a `g_child_watch_source` on the GLib **worker thread** context, so an instant-exit child can be reaped between `spawnv()` and the synchronous `get_identifier()`. Result: `child.pid` is `undefined` for a fast child under load, whereas Node always reports a numeric pid for a successful spawn. | @gjsify/child_process (`spawn`/`exec` `ChildProcess.pid` for instant-exit children) | `pid` is captured on the statement immediately after `spawnv()` (`_capturePidAtSpawn`) — the narrowest possible window; reliable for long-lived processes (the realistic pid consumers), best-effort for instant-exit children. All pid assertions spawn an alive-when-checked process. The `DO_NOT_REAP_CHILD` rewrite was scoped + rejected (regresses `child.kill()` to a shell-out, reimplements env/cwd/stdio/wait-status on a critical path). | **Expose the spawn-time pid in `Gio.Subprocess`** — keep `get_identifier()` returning the historical pid after reap, or add a spawn-time `pid` accessor. **Filed upstream:** [GNOME/glib#3981](https://gitlab.gnome.org/GNOME/glib/-/work_items/3981) (pure-C reproducer + proposed `g_subprocess_get_initial_identifier()`). **Maintainer verdict:** accessor "would be OK" but de-prioritised in favour of pidfds ([#1866](https://gitlab.gnome.org/GNOME/glib/-/issues/1866)) ⇒ no near-term upstream fix; the alive-process test + spawn-time capture is the stable downstream answer. |
| `Soup.WebsocketConnection` only emits the coalesced `message` signal — no fragment-level / frame-level hook is exposed over GI. A text message with invalid UTF-8 in a later fragment is only validated after libsoup has buffered the entire message, so the RFC 6455 "fail the connection at the first invalid byte" timing is unreachable from JS. | @gjsify/websocket (manifests as Autobahn cases 6.4.1–6.4.4 `behavior: NON-STRICT, behaviorClose: OK, remoteCloseCode: 1007`) | None needed at the application layer — libsoup itself sends close 1007 at end-of-message, which is RFC-correct but "late" by Autobahn's strict timing definition. No code is shipped to work around this. | **libsoup patch (`soup/websocket/*`)** — expose either a per-frame `incoming-fragment` signal or an opt-in "validate-as-you-go" mode on `SoupWebsocketConnection` for text opcodes. Either shape flips 6.4.x from NON-STRICT to strictly-OK. |
| **Deferred-GC SIGSEGV from JS-Boxed Sources allocated outside @gjsify/http.** Even with `@gjsify/http-soup-bridge` eliminating libsoup-side exposure, the MCP example still SIGSEGVs ~13 s after a single Node.js fetch with chunked SSE. Backtrace identical to the historic Boxed-Source race (`BoxedBase::finalize → g_source_unref` from GJS's deferred-GC heuristic), but the offending wrapper is allocated somewhere in the MCP-SDK / @hono/node-server / web-streams stack. | **`AdwViewStack` keeps a dangling `last_visible_child` when the page a transition is animating OUT is removed.** Read in `refs/libadwaita/src/adw-view-stack.c` (1.9.3): `set_visible_child` records the outgoing page in `self->last_visible_child` and calls `adw_animation_play`; `stack_remove` clears `self->visible_child` when it matches, then `g_clear_object (&page->widget)` and `g_object_unref (page)` — and never touches `self->last_visible_child`. The next `set_visible_child` calls `adw_animation_skip`, and `transition_done_cb` then reads `self->last_visible_child->widget` out of a freed `AdwViewStackPage`: `gtk_widget_set_child_visible: assertion 'GTK_IS_WIDGET (widget)' failed`, or a SIGSEGV. Reported against #1453 on gjs 1.88.1 / libadwaita 1.9.3 / GTK 4.22 / Wayland from a core dump — one crash in three runs, the assertion the other two, backtrace `add_page` → `set_visible_child` → `adw_animation_skip` → `transition_done_cb` → `gtk_widget_set_child_visible`. `AdwViewStack:enable-transitions = false` is NOT an escape: it only sets the animation's duration to 0, and `play()` still adds a tick callback and leaves `transition_running` TRUE for everything except a globally-disabled or unmapped widget — so the in-flight window survives. | @gjsify/react-native (`<Tabs>` over `Adw.ViewStack`), @gjsify/gtk-host (whose reconciler is what removes a page one at a time), and every GTK application that removes an `AdwViewStack` page from a MAPPED window | **None shipped, and the hazard is open.** The React-side driver is closed — `<Tabs>` no longer reads its own `set_visible_child_name` as a user press, so a deep link no longer produces the navigation churn that fed the removals (#1453) — but nothing stops a page being removed mid-transition. NOT reproduced in-process: the router's vectors never remove a `ViewStack` page one at a time, because React unmounts a deleted subtree from its top and the pages go with the stack; reaching it needs a route set that SHRINKS while the window is mapped. **What a consumer can do today:** hide the child before dropping it — `update_child_visible` clears `last_visible_child` when the page it names stops being visible (adw-view-stack.c:1073), so setting the child widget's `visible = false` and letting that notify land before the remove takes the dangling pointer out of play. Unverified against the crash, because the crash has no in-process vector yet. | **Clear `self->last_visible_child` in `stack_remove` when the page being removed is it**, the way `self->visible_child` already is two lines earlier — and unset its child-visible flag first, as `transition_done_cb` and `update_child_visible` both do. Not yet filed upstream; file it at gitlab.gnome.org/GNOME/libadwaita with the three-line C reproducer (`add_page` twice, `set_visible_child` to the second, `remove` the first while `transition_running`). |
