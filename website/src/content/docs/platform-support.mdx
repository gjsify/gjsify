This page answers one question: **will this work on my operating system?** Which
runtime to build for is a separate question, and [Runtimes](/gjsify/runtimes/) has
it. The two do not line up: a package can be fully cross-runtime and still be
Linux-only, because the native library underneath it is.

## The short answer

| | Linux | macOS | Windows |
|---|---|---|---|
| **Apps on GJS** (`--app gjs`) | supported | partial, see below | not available (no GJS host) |
| **Apps on Node/Bun/Deno** (`--app node`, via `@gjsify/node-gi`) | supported | supported | supported |
| **Browser builds** (`--app browser`) | supported | supported | supported |
| **The Node-free toolchain** (`gjsify build` under GJS) | supported | engines ship, not exercised in CI | not available |

Browser builds carry no native code at all, so they are portable by
construction. The GJS side is where the operating system matters.

## Windows

There is no GJS on Windows, so anything ending in a `gjs` process is out:
`--app gjs` bundles, `test:gjs`, and the examples built around them. That is an
upstream gap, not a missing task here: nobody ships a prebuilt `libgjs` for
Windows, and gjs has to be built against a SpiderMonkey that Windows package
managers do not provide in a form its build system takes.

Everything else works. Under Node, a Windows machine runs the toolchain
(`gjsify install`, `gjsify build` for `--app node`, `--app browser` and
`--library`, `gjsify check`, `gjsify clear`, `gjsify copy`), and showcases run on
the runtimes that are not GJS:

```powershell
gjsify showcase                                   # list them
gjsify showcase express-webserver                 # runs on node here
gjsify showcase express-webserver --runtime bun   # or deno
```

`gjsify showcase` picks the runtime itself, so that middle line runs the
showcase's `--app node` bundle without being told to. A showcase that declares no
support for the chosen runtime says so instead of crashing. Install the CLI from
npm on Windows: the Node-free bootstrap needs a `gjs` binary.

You do not have to supply GTK yourself. `@gjsify/gtk-runtime-win32-x64` ships the
GTK 4 / Adwaita closure that `@gjsify/node-gi` loads `gi://` namespaces from, so
there is no gvsbuild or system GTK to install. CI runs a real GTK window and the
full Adwaita storybook against that bundle.

Two host settings are worth getting right before you start, because both fail in
ways that do not name themselves:

- **Long paths.** Set
  `HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled` to `1`
  (needs elevation) and keep your checkout short, `C:\src\…` rather than a deep
  home directory. Nested `node_modules` runs past `MAX_PATH` quickly.
- **Line endings.** Prefer `core.autocrlf=false`. A default Git for Windows clone
  is not dirty, and `.gitattributes` already pins the byte-verified artifacts to
  LF whatever you configure.

Real file symlinks are optional: `gjsify install` links workspace packages with
NTFS junctions, which need no privilege. Turning on Developer Mode enables the
handful of tests that do want symlinks; without it they report themselves as
skipped.

## macOS

`--app node` is fully supported: builds, conformance and a real GTK/Adwaita
window are all exercised on Apple silicon, and `@gjsify/gtk-runtime-darwin-arm64`
ships the GTK 4 / Adwaita closure so you do not need a Homebrew GTK. Intel Macs
get the same builds and the same display-free conformance run against
`@gjsify/gtk-runtime-darwin-x64`; only the windowed GUI proof is arm64-only.

What is not proven is the **Node-free toolchain**. `gjsify build` under GJS needs
a bundler, `@gjsify/rolldown-native` is the one that runs there, and it does
publish `darwin-arm64` and `darwin-x64` prebuilds, along with
`@gjsify/lightningcss-native` and `@gjsify/oxfmt-native`. What is missing is a CI
job that drives `gjs -m install.mjs` all the way to `gjsify build` with no Node on
the machine. It may well work for you; nothing here promises it does. With Node
installed, the npm route is the fallback.

## Which native bridges reach your platform

A native bridge is a gjsify package that ships a compiled artifact. Each one
declares the `<os>-<arch>` targets it promises, and CI is held to that
declaration in both directions.

Read `✓` as "you can install this and it will have a binary for your platform".
`○` means the binary is built and published to npm but not committed to the
gjsify repository, which matters only if you are building gjsify from a clone.
`·` means that platform is not supported at all. The marks come from the same
rule the CI gate runs, so this table and the audit cannot disagree; the
[Internals page](/gjsify/how-it-works/#what-the-platform-marks-prove) explains
what each mark does and does not assert.

Column names are real directory names, spelled the way a running process computes
them about itself (`${process.platform}-${process.arch}`), so the declaration,
the committed prebuild, the CI job and the loader all use the same string.

## What a missing bridge costs you

Every native bridge is optional at runtime. Each one is loaded through a guarded
probe, so a missing prebuild degrades the feature rather than crashing your app.
What you lose:

| bridge | without it |
|---|---|
| `@gjsify/http-soup-bridge` | `@gjsify/http`'s server loses its GC-safe Soup message wrapper |
| `@gjsify/http2-native` | no raw h2c; `createServer()` stays HTTP/1.1 |
| `@gjsify/tls-native` | no OCSP parsing, no TLS session resumption or channel binding |
| `@gjsify/terminal-native` | `isatty`, window size and raw mode fall back to env heuristics |
| `@gjsify/sab-native` | no cross-process `SharedBuffer`; the rest of `worker_threads` is unaffected |
| `@gjsify/webgl`, `@gjsify/webrtc-native` | WebGL and WebRTC unavailable |

`@gjsify/sab-native` is Linux-only by design rather than by missing CI: it is
built on `memfd_create`, Linux `futex` syscalls and `SCM_RIGHTS`. The reasoning
is in [ADR 0013](https://github.com/gjsify/gjsify/blob/main/docs/adr/0013-sab-native-platform-scope.md).
