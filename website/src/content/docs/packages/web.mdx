Web APIs are globals, so there is nothing to import. Write the code you would write in a browser:

```typescript
const response = await fetch('https://api.example.com/data');
const data = await response.json();

const socket = new WebSocket('wss://echo.example.com');
socket.addEventListener('message', (event) => console.log(event.data));

const digest = await crypto.subtle.digest('SHA-256', new TextEncoder().encode('hi'));
```

An `--app gjs` build scans the bundled output, works out which globals your code actually reaches, and registers only those: `fetch` becomes a `Soup.Session` call, `WebSocket` a `Soup.WebsocketConnection`, `crypto.subtle` a GLib-backed implementation. An `--app browser` build uses the browser's own versions of the same source, and an `--app node` build leaves the ones Node, Bun and Deno already define to the runtime.

## Import a class explicitly

Sometimes you want the constructor as a value: to subclass it, to pass it around, or to keep a module free of globals. Every package exports its classes, and importing a package root has no side effects.

```typescript
import fetch, { Headers, Request, Response, FormData } from '@gjsify/fetch';
import { WebSocket } from '@gjsify/websocket';
import { localStorage } from '@gjsify/webstorage';
```

These specifiers only resolve in a GJSify build, so prefer the globals in code that also has to run on Node.js or in a browser.

## A global is missing at runtime

If a bundle dies with `ReferenceError: X is not defined`, the detector could not see `X`, usually because a library reads it through a stored `globalThis` reference. Keep auto detection on and name the identifier:

```bash
gjsify build src/index.ts -o dist/index.js --globals auto,matchMedia
```

Groups work too (`--globals auto,dom`). The full identifier and group list is in the [CLI Reference](/gjsify/cli-reference/#globals).

## Adwaita in the browser

For `--app browser` builds, the Adwaita design system comes over as Web Components:

| Package | What you get |
|---|---|
| `@gjsify/adwaita-web` | Adwaita as custom elements (AdwWindow, AdwHeaderBar, AdwPreferencesGroup, AdwCard, AdwSwitchRow, AdwComboRow, AdwSpinRow, AdwToastOverlay, AdwOverlaySplitView and more) plus the compiled stylesheet |
| `@gjsify/adwaita-core` | The behaviour behind those widgets, with no rendering: breakpoints, color scheme, toast queue, row state machines, alert-dialog responses |
| `@gjsify/adwaita-fonts` | Adwaita Sans as TTF files plus the `@font-face` CSS |
| `@gjsify/adwaita-icons` | Adwaita symbolic icons as importable SVG strings, plus a `toDataUri()` helper |

Start at the [Adwaita gallery](/gjsify/adwaita/): it shows every widget with a live preview and the code for GJS, Blueprint, the web and NativeScript.

| Package | What it is for |

## Where each API also runs

Every package declares the runtimes it supports, in a `gjsify.runtimes` field, and the answer differs per standard. `fetch`, `WebSocket`, `crypto.subtle`, `FormData`, `WebAssembly` and the compression streams are native on Node, Bun and Deno, so a build for those runtimes polyfills nothing. `EventSource`, `DOMParser`, `localStorage` and the DOM event classes carry a polyfill for them as well, and most of the pure TypeScript packages run in the browser and under NativeScript too. The GStreamer-backed `AudioContext` and `RTCPeerConnection`, and `XMLHttpRequest`, are declared for GJS and the browser only.

More than 50 packages across the Node, Web and DOM pillars ship a browser test suite that CI runs against real Firefox with Playwright. [Runtimes](/gjsify/runtimes/) has the full picture.
