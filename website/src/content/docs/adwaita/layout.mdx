An Adwaita window is a frame plus the containers that give it shape. The **window**
is the frame itself; a **bin** holds one replaceable widget where a slot calls for
it, a **clamp** holds content at a readable width (and a **scrollable clamp** when
that content scrolls), a **header bar** is the top chrome, a **toolbar view** frames
content between fixed bars, and a **wrap box** lets a run of
children flow onto new lines. None of them hold data: they position what you put
inside and adapt as the space around them changes.

The last three are the **adaptive** ones. A **breakpoint bin** gives breakpoints a
home without a window, a **multi-layout view** holds one set of children and several
arrangements of them, and a **layout slot** is the named hole one of those
arrangements leaves for a child.

<MoreInfo title="The ports, and what they follow">
Libadwaita is the reference, typed by
[`@girs/adw-1`](https://www.npmjs.com/package/@girs/adw-1).
[`@gjsify/adwaita-web`](https://github.com/gjsify/gjsify/tree/main/packages/web/adwaita-web)
and [`@gjsify/adwaita-nativescript`](https://github.com/gjsify/gjsify/tree/main/packages/nativescript-bridge/adwaita)
follow its naming, and where a port differs, the window that shows it says so. Both
answer `gi://Adw` and `gi://Gtk`. On NativeScript that resolves once you build with
`gjsify build --app nativescript --gi-renderer`.

The previews run the browser port, so behaviour Libadwaita drives natively (a toolbar
view revealing each bar independently, a clamp's tightening threshold) can be
simplified here.
</MoreInfo>

## Window

The frame everything else goes into. It styles no chrome of its own: you give it a
**content** widget — normally a [toolbar view](#toolbar-view) with a header bar — and
it asks for the size `Adw.Window` asks for, 360 × 200 px, unless you set a default
size yourself.

<MoreInfo title="The preview is a window drawn in the page">
`Adw.Window` is a toplevel. On the desktop it is a real window that the compositor
places, maximises, tiles and closes. A browser document has no window manager, so
`<adw-window>` is a framed box **in the page**: the frame libadwaita draws for a
client-side-decorated window, the content property, the breakpoints and the
open-dialog bookkeeping — and none of what a compositor owns, so no titlebar, no
minimise button and no window placement. What you put inside it behaves the same.
</MoreInfo>

<MoreInfo title="The NativeScript tabs were inflated on a device">
[`adwaita-gallery-nativescript`](https://github.com/gjsify/gjsify/tree/main/showcases/dom/adwaita-gallery-nativescript)
loads each template through NativeScript's own `Builder` and asserts the view tree it
built. That is the only way to tell a template that renders from one that renders
something else: an attribute arrives as a string, and a child a widget has no slot for
is added to the layout anyway.

A NativeScript template reaches these widgets through its `xmlns`, and the namespace is
a MODULE: NativeScript loads it and reads the element name off its exports, so
`xmlns:adw="~/adw"` needs an app-local `app/adw.ts` that re-exports what the markup
names. A bare package specifier there does not resolve. There is one barrel per library,
`~/adw` for `Adw.*` and `~/gtk` for `Gtk.*`, because the prefix is the only thing in XML
that can say which library a widget belongs to. Point both at one module and
`<adw:Button>` silently builds the GTK button.

The wrap box only recently joined them. `@gjsify/gtk-host` had no child policy for
`AdwWrapBox`, so a child placed in one was refused by name. That was deliberate: a
renderer guessing the policy would call `add`, `append` or `set_child` and be wrong at
exit 0. The policy is now curated against libadwaita, so the block has a tree like the
other three.
</MoreInfo>

<MoreInfo title="React Native primitives go in these containers too">
The Adwaita element is the same one the React tab shows, and a `<View>` or `<Text>` sits
in its default slot. The clamp, the header bar and the toolbar view carried a tab for
that pairing, and they were the only three blocks on the site with one, so the [React
Native page](/gjsify/frameworks/react-native/#adwaita-widgets) carries it in full
instead. Two facts from there are worth having before you try it. The primitives need
their token scales installed with `configureStyle({ tokens })` before the first render,
because a class naming a token you have not declared throws out of the render and leaves
an empty window at exit 0 with nothing in the log. And such a tree is a GTK window
rather than a phone screen, which is why it was never the NativeScript tab.
</MoreInfo>

## Application Window

The [window](#window) with one thing added: the **menubar** its application
installed. Turn **show menubar** off and the bar goes away; turn it on and the window
draws it, which is all `Gtk.ApplicationWindow:show-menubar` decides.

<MoreInfo title="A browser has no application">
On GTK the model belongs to a `Gtk.Application`, which installs it into every
application window it opens — a document has no application, so
`<adw-application-window>` takes the **menu model** itself, in the same portable form
`<gtk-menu-button>` takes, and reads it with the same parser. A menubar is a row of
menu **links**: each one becomes a button that opens its menu, and a link's own items
are what that menu holds.
</MoreInfo>

    ```ts
    import Gio from 'gi://Gio?version=2.0';

    Adw.init();

    // The menubar model: a row of LINKS, which is what `Gtk.Application:menubar` is.
    const menu = new Gio.Menu();

    file.append('New Window', 'app.new-window');
    file.append('Quit', 'app.quit');

    // is what decides whether the window DRAWS it.

    // top bar, which is where an application window's own menubar sits.
    const toolbarView = new Adw.ToolbarView();
    toolbarView.add_top_bar(new Adw.HeaderBar());
    toolbarView.add_top_bar(menubar);
    toolbarView.content = new Adw.StatusPage({ title: 'Your Library' });

    const window = new Adw.ApplicationWindow({ content: toolbarView, show_menubar: true });
    window.set_default_size(440, 240);
    ```

## Bin

The smallest container libadwaita ships: a widget that holds **one child** and
nothing else. It draws no frame of its own and hands the child its whole
allocation, which makes it the thing to reach for when a slot needs a single
replaceable widget. Setting a new child **replaces** the old one rather than
stacking beside it, and a child that already has a parent is refused.

## Clamp

Wrap long-form content in a clamp so it stops growing at a **maximum width** and
stays centred in anything wider. Below the **tightening threshold** the clamp starts
tightening the child, which keeps text at a comfortable measure on a large display
without wasting room on a small one.

<MoreInfo title="Why this block is shaped differently">
The layout exists once, as a Blueprint file, and every surface builds that file: GTK
compiles it to GtkBuilder XML, and the web and NativeScript ports build its
`?shared-tree` projection. The preview is that projection, built by
`@gjsify/adwaita-web`, and **Blueprint** under it is the file. The **Web Components**
and **NativeScript** tabs of **Code** hold the files of a project, picked in the small
row under the tab bar. The first is the same layout in the port's own markup,
`index.html` or `views/clamp.xml`, generated from the Blueprint file when the site is
built, so the ids match. The code that goes with it reaches an element by its id, which
is where the platforms differ: the web clamp takes its size as an attribute, the other
two as a property. The file marked **(Blueprint)** is that same code building the layout
from the Blueprint file instead of the markup.

The first tab is one program for four runtimes. Built with `gjsify build --app gjs` it
runs on GJS, and built with `--app node` the same source runs on Node.js, Deno and Bun
through `node-gi`. `build()` calls `Adw.init()` itself, so the builder knows `Adw.Clamp`
in a bare script too; inside an `Adw.Application` the call is harmless.
</MoreInfo>

## Clamp Scrollable

A clamp for a child that **scrolls**. A plain clamp would cut a list or a text
view off at its maximum width, scrollbar included; the scrollable clamp keeps
the scrollbar at the edge of the window and holds only the content at the
**maximum size**, with the same **tightening threshold** curve as the clamp
above. Its child has to be a scrollable one, a list view or a text view.

<AdwWidget title="Adw.ClampScrollable">
  <Fragment slot="preview">
    ```html

    <!-- tightening-threshold: The size above which the child is clamped. -->
    <adw-clamp-scrollable maximum-size="320" tightening-threshold="240" style="width:100%;height:120px;">
      <gtk-box orientation="vertical" spacing="6">
        <gtk-label label="Line 1: held at the clamp's width."></gtk-label>
        <gtk-label label="Line 2: while the rest scrolls."></gtk-label>
        <gtk-label label="Line 3: and the scrollbar stays at the edge."></gtk-label>
        <gtk-label label="Line 4: of the window."></gtk-label>
        <gtk-label label="Line 5: not at the edge of the content."></gtk-label>
      </gtk-box>
    </adw-clamp-scrollable>
    ```
  </Fragment>
  <Fragment slot="gjs">

## Wrap Box

Lay children out in a horizontal line and let them **wrap** onto new lines when
they run out of room. This is what you want for a variable-length run of tags,
chips or filter pills. **Child spacing** sets the gap between items on a line,

## Breakpoint Bin

Give breakpoints a home without a window. The bin holds **breakpoints**, each a
condition on its own size plus the properties to write while that condition holds,
and on every resize it applies the **last** one that matches — not the narrowest.
Its single child is whatever rearranges itself.

The markup form is `breakpoints`, a JSON array because `Adw.Breakpoint` is a
GObject rather than a widget and `add_breakpoint()` is the whole upstream API.
Each setter names a **target** (a selector for a descendant), an attribute
**property** and its **value**; the value the target held when the setter was
registered is what leaving the breakpoint restores.

<MoreInfo title="A bin with breakpoints has no minimum size">
Adding a breakpoint makes the bin measure no minimum on either axis, and the
`AdwBreakpointBin` docs say the stage must set `width-request` / `height-request`
for the smallest size you support. The preview does that with inline styles, which
is why the stage under this block is 300px wide: narrow it far enough and the
label swaps.
</MoreInfo>

<AdwWidget title="Adw.BreakpointBin" stage="width: 300px; height: 70px;">
  <Fragment slot="preview">
    ```html
    <adw-breakpoint-bin style="min-width: 150px; height: 60px;" breakpoints='[{"condition":"max-width: 200px","setters":[{"target":"#caption","property":"label","value":"Narrow"}]}]'>
      <gtk-label id="caption" label="Wide" class="title-1"></gtk-label>
    </adw-breakpoint-bin>
    ```
  </Fragment>
  <Fragment slot="gjs">
    ```ts
    import Adw from 'gi://Adw?version=1';
    import Gtk from 'gi://Gtk?version=4.0';

    const bin = new Adw.BreakpointBin();
    bin.set_size_request(150, 60);

    const caption = new Gtk.Label({ label: 'Wide', ellipsize: Gtk.EllipsizeMode.END });
    caption.add_css_class('title-1');
    bin.set_child(caption);

    // A breakpoint writes properties while its condition holds, and the LAST
    // one that matches wins. Leaving it restores the values the setters
    // captured when they were added.
    const narrow = new Adw.Breakpoint(Adw.BreakpointCondition.parse('max-width: 200px'));
    narrow.add_setter(caption, 'label', 'Narrow');
    bin.add_breakpoint(narrow);
    ```
  </Fragment>
  <Fragment slot="blueprint">
    ```blueprint
    using Gtk 4.0;
    using Adw 1;

    Adw.BreakpointBin {
      width-request: 150;
      height-request: 60;

      Gtk.Label caption {
        label: _("Wide");
        ellipsize: end;

        styles ["title-1"]
      }
    }
    ```

## Multi Layout View

One set of children, several arrangements of them. Every child has an **id**,
every layout has **slots** with ids, and switching layouts re-inserts each child
into the slot of the **same id** — which is how a secondary pane becomes a
sidebar in one arrangement and part of the content in another without the
application moving anything. **layout-name** picks the arrangement; the first one
declared is the one in use until you say otherwise.

An `Adw.Layout` is a GObject, so there is no `Adw.Layout` tag: here a direct
child carrying `name` **is** the layout, a direct child carrying `slot` is a
child, and an `<adw-layout-slot>` inside a layout is where that child lands.

<MoreInfo title="Why this block has no framework snippet">
A layout is a GObject upstream and each child is paired with a slot by a method
call, so neither half is a static tree in any of the dialects — the gallery ledger
says so rather than publishing markup that would render nothing. The browser
element carries both in markup, which is what the preview above shows.
</MoreInfo>

## Layout Slot

The named hole one layout of a multi-layout view leaves for a child. It takes the
child whose **id** matches its own, and its visibility follows that child's — so
hiding the child takes the hole with it and nothing more. The **id** is
construct-only upstream, which is why it is the one thing this element reads.

A slot on its own is a bin, and that is what the preview shows. To see the pairing
work, use the view above: the two slots in it are what the `secondary` and
`primary` children land in.

<MoreInfo title="Duplicate ids across layouts are the widget's own model">
The example in the libadwaita documentation puts an `AdwLayoutSlot` with
`id="primary"` in **both** layouts of one view — that is how a child follows a
layout change. The element resolves slots from the layout it is currently
mounting, never by looking an id up in the document, so two slots sharing an id
are ordinary.
</MoreInfo>
