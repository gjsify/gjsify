[`@gjsify/react-native`](https://www.npmjs.com/package/@gjsify/react-native) renders React
Native's **view vocabulary** — `<View>`, `<Text>`, `<Pressable>`, `className="flex-1 items-center"`
— into real `Gtk` and `Adw` widgets, over the same [host layer](/gjsify/frameworks/) the Solid,
Vue and React adapters bind to.

The package name is the documentation of one line in a bundler config: `'react-native'` →
`'@gjsify/react-native'`. That alias only works if the export surface mirrors React Native's own,
so this package exports every name `react-native` exports — including the ones it does not
implement.

:::note[New in `v0.43.0`]
The package is published at `0.43.0`, the version the whole
[release train](/gjsify/versioning/) carries — so it installs alongside the `@gjsify/gtk-host` it
renders through, with no version to reconcile between them.
:::

## What it promises, and what it does not

**It is not a promise that one source tree runs everywhere.** There is no bridge and no native
module host: this layer renders in-process onto GTK, which is why `NativeModules`,
`TurboModuleRegistry`, `UIManager` and `findNodeHandle` are *refusals* rather than stubs.

The promise is narrower and checkable. Porting is meant to be **cheap**, and every divergence
from React Native is meant to be **knowable before you run the app** rather than discovered in a
window that looks plausible. If you came expecting the first thing, the disappointment is the
correct one to have — a layer that pretended otherwise would spend your debugging time instead of
its own.

That is what the support table is for.

Your framework stays yours and arrives as a peer: `react` + `react-reconciler`, or `solid-js`.
Every one of them is optional, so install the one you render with — and mind the version ranges,
because an optional peer is not enforced on install and the
[React page](/gjsify/frameworks/react/) carries the measurement behind them.

The Solid binding (`@gjsify/react-native/solid`) renders the same primitives, and it exists for a
reason worth stating: with one framework binding, "the layers below are framework-agnostic" is a
claim rather than a measurement. A second binding that shares no rendering model with the first is
what turns it into one.

## The support table is the contract

One file — `src/support-table.ts` — gives every name `react-native` publicly exports a **status**
and a **one-line reason**. It is data, not prose, and more than one reader consumes it: the
runtime refusals throw the table's own sentence, the package README's support section is
*generated* from it, and the declared bundler gate is written against it.

`scripts/check-rn-surface.mjs` holds the table's key set against a **committed snapshot** of that
export list, on every run — so the table cannot quietly drop a name or invent one. Whether the
same run also catches an *upstream* bump depends on whether a `react-native` is installed to
compare against, which is why it prints which of the two it did; the
[toolchain section](#the-toolchain-as-it-actually-stands) has the consequence.

| Status | What it promises |
|---|---|
| `supported` | Implemented. |
| `partial` | Implemented with named limits — the entry lists them. |
| `planned` | On the map, not built yet. The tier says how soon. |
| `refused` | Will not be built, and there is a decision behind it. |
| `no-desktop-meaning` | Exists so an import resolves; does nothing, because a desktop window has no such concept. |
| `not-reachable` | Cannot be built in this toolchain at all — a capability statement, not a schedule. |

Tiers are `P1`, `P2` and `P3`, and a tier answers *when*: every `planned` and `partial` entry
carries one, and no `refused` or `not-reachable` entry does, because neither status is a schedule.
Some `supported` and `no-desktop-meaning` names carry none either — nothing about `EventEmitter`
or `Vibration` was ever scheduled, it was answered — so "everything outside a refusal has a tier"
is the tidier claim and the false one. `support-table.spec.ts` asserts both halves of the rule
that holds, because a paragraph like this one drifts back to the tidier claim on its own.

**Read the table rather than trusting a page.** This page can go stale on its own; the table
cannot, because code is generated out of it and a gate holds its key set. The per-name listing is
[generated into the package README](https://github.com/gjsify/gjsify/blob/main/packages/framework/react-native/README.md),
and the table is exported (`SUPPORT_TABLE`, `SUPPORTED_NAMES`, `explainUnsupported`,
`isImportable`) so a lint rule or a migration script of your own can read the same data.

### An unimplemented name refuses; it is not absent

Omitting a name would already be loud — a bundler reports `MISSING_EXPORT`. But what it reports is
"this package does not export `Animated`", which sends you to check your spelling. The table knows
something better: that `Animated` is tier P3, that it maps onto `Adw.TimedAnimation` and
`Adw.SpringAnimation`, and that it is not built yet.

So every unimplemented name is exported as a value that refuses with the table's sentence:

```
@gjsify/react-native: "Animated" is not implemented yet (tier P3). Genuinely mappable,
but it is a subsystem rather than a component. Doing it badly is worse than not doing
it. The GTK counterpart is Adw.TimedAnimation / Adw.SpringAnimation.
```

The example above used to be `FlatList`, which is the warning two paragraphs up making itself:
`FlatList` shipped, its sentence became `"FlatList" is available.`, and the illustration was
quietly false. **Any name on this page can move; the README's generated listing cannot.**

It throws on **property access**, not only on call, because `Animated.timing` and
`NativeModules.Foo` are property reads — and a module that reads one during its own evaluation
would otherwise get `undefined` and fail somewhere else entirely. The stand-in answers `typeof`
honestly, so a `typeof X === 'function'` feature check still works, and it is constructible, so a
`class X extends SomeRNThing` reaches the refusal instead of dying on a minified local name.

## What renders today

The primitives that render, each with the widget it becomes:

| Primitive | Becomes |
|---|---|
| `View` | `Gtk.Box` — or `Gtk.Overlay`, when one of its children is absolutely positioned |
| `Text` | `Gtk.Label` |
| `Pressable` | `Gtk.Button`, flat |
| `ScrollView` | `Gtk.ScrolledWindow` plus an implicit content box |
| `ActivityIndicator` | `Adw.Spinner` |
| `TextInput` | `Gtk.Entry`, or `Gtk.TextView` with `multiline` |
| `Switch` | `Gtk.Switch` |

Plus `Linking`, `Platform`, `Share` and `useColorScheme`; `AppRegistry` and Expo's
`registerRootComponent`; `EventEmitter`; and `unstable_batchedUpdates`, which is the identity call
it already is under React 19 and is kept because application code still wraps in it.

One export is **not** a React Native name and is part of the surface anyway: `configureStyle`
installs your project's token scales. The class families are declared by the styling layer, the
values belong to your project, and no React Native prop or API carries them — see
[Styling on GTK](/gjsify/frameworks/styling/).

### Two inverted defaults, written out on purpose

A React Native `View` is a **column** (`flexDirection` defaults to `'column'`) and a `Gtk.Box`
defaults to horizontal. A React Native `Text` **wraps** and a `Gtk.Label` does not. Both defaults
are set explicitly in the primitive descriptors, because both would otherwise be wrong in the same
way in every ported layout, and wrong *silently*: the window renders, every widget is there, and
the rows are columns.

## The divergences a porter hits first

Each of these is a table entry with a reason, not a gap someone forgot.

**The entry point needs an application id.** React Native hands `runApplication` a root tag from
a native host that already exists — an Activity, a `UIViewController`. Nothing exists yet here, so
`runApplication` must *create* the application and its window, which means it needs the one fact
React Native never has to ask for: the `GApplication` id. A phone host supplies the application
identity; a desktop one **is** the application.

```tsx
import { AppRegistry, Text, View } from '@gjsify/react-native';

function App() {
    return (
        <View className="items-center">
            <Text>Hello from GTK</Text>
        </View>
    );
}

AppRegistry.registerComponent('MyApp', () => App);

await AppRegistry.runApplication('MyApp', {
    applicationId: 'org.example.MyApp',
    title: 'My App',
});
```

`runApplication` resolves with the application's exit code, and it is `async` on purpose: GJS does
not drain the promise-job queue under a synchronous `Gio.Application.run`, so a view that loads
asynchronously would hang on its spinner forever.

The shell is built for you — an `Adw.ApplicationWindow` holding an `Adw.ToolbarView` and a header
bar, rather than a bare window, because a desktop window without a header bar cannot be moved or
closed on every compositor. React renders into the toolbar view's *content*, so that chrome
survives the first commit.

Anything beyond `items-*`, `flex-*` and the other token-free utilities needs your project's token
scales installed first, with `configureStyle`. The default scale is deliberately tiny, so the first
`mt-2xs` you write without configuring one is a named error listing what the scale does hold — not
a silently dropped class.

**A dialog is presented against a parent, never parented by it.** `Modal` is tier P1 and stays
`planned` for a measured reason: on libadwaita 1.9.3, `box.append(dialog)` calls `g_error()` —
SIGABRT and a core dump, not a catchable exception — but *only* when the box is rooted in a
window. A detached box accepts the append in silence, so a re-test on a bare box appears to
disprove it. `<Modal>` is therefore a **portal**, and the host has no portal seam yet. A refusing
export is strictly better than a `partial` that aborts the process the first time somebody renders
one.

**Every `partial` primitive refuses some of its props by name, and its table entry lists which.**
They share one shape, worth carrying with you: React Native puts the thing on the element as data,
and GTK puts it in a second object. Allocation arrives through a `vfunc_size_allocate` override
rather than a signal; focus and a long press are event controllers added to the widget; a multiline
`TextInput`'s text lives in a `Gtk.TextBuffer` and not in `value`; press state is a CSS `:active`
pseudo-class that never reaches the reconciler. So a refusal is not a to-do item — it names the GTK
object to reach for through a `ref`, or the class to write instead.

Which props those are stays in the table, for the reason this page keeps giving: a list repeated
here is the copy that drifts, and it is the copy a reader finds first.

## Platform files

[ADR 0032 § 9](https://github.com/gjsify/gjsify/blob/main/docs/adr/0032-react-native-on-the-gtk-host.md)
declares the resolution order a shared codebase should get:

```
foo.gtk.tsx      →  GTK-specific
foo.linux.tsx    →  OS-specific (likewise .macos / .windows)
foo.desktop.tsx  →  any desktop target
foo.tsx          →  base
```

**`.native` is deliberately not in that chain, and `.web` never is.** It looks like an oversight
and is the opposite: a `.native.tsx` is by definition written for a React Native runtime, so
reaching for it would feed the GTK build code that expects `NativeModules` — found only in the
window. Falling through to the base file is the honest outcome. `.web` is worse, because it looks
like the right choice for a desktop target while carrying exactly the DOM assumptions this design
rules out.

**None of that chain resolves yet.** The bundler's platform resolver today knows `.android`,
`.ios`, `.visionos` and `.native` — the NativeScript / React Native mobile order — and extending
it is where the desktop chain will land, never as a second plugin. Until then, a GTK build reads
the base file, and a `.gtk.tsx` beside it is a file nothing imports.

## The toolchain, as it actually stands

Two pieces of ADR 0032 § 8's build-time story are declared and not wired up, and it is worth
knowing which:

- **The `'react-native'` → `'@gjsify/react-native'` alias.** Import the package by its own name
  for now. The import surface is identical either way; what the alias buys is an *unmodified*
  application tree building.
- **The bundler gate** that would fail a build on an import the table marks unsupported, naming
  the file and the line. Nothing in the build pipeline reads the support table today, so the
  runtime refusal is the only reader that fires — a sentence at the right moment instead of a
  sentence before the run.

What does hold today: the runtime refusals, the generated README section, and
`scripts/check-rn-surface.mjs`. That last one compares the table against a committed snapshot of
React Native's export list on every run, and against the *installed* `react-native` whenever one is
resolvable — printing which of the two modes it ran in, because a gate that quietly degrades to the
weaker half is worth less than one that says so.

The **build recipe is React's, not this package's** — `--define 'process.env.NODE_ENV="production"'`
and `--exclude-globals navigator`, with the reason each flag exists on the
[React page](/gjsify/frameworks/react/#the-build-recipe-and-it-is-not-optional). It applies
unchanged here, because `react-reconciler` is what is underneath.

## Read the source

[`showcases/gtk/rn-design-system`](https://github.com/gjsify/gjsify/tree/main/showcases/gtk/rn-design-system)
is ADR 0032 § 11's regression proof: an ordinary design-system layer — badge, button, card, chip,
rule, rail, screen, section header, thumbnail, typography — written fresh under MIT against this
class vocabulary. Its probe asserts which widget each primitive became, which `css-classes`
landed, and what the generated rule behind each one says.

It is deliberately **not** comparable to the host-counter showcases listed on the
[UI Frameworks](/gjsify/frameworks/) page, which build one identical window through the host's own
tags once per adapter. This one asserts a different thing, so it is not another arm of that
comparison. It is also `private`, and therefore not in the `gjsify showcase` catalog — read it
from the checkout rather than reaching for `gjsify showcase rn-design-system`, which has nothing
to resolve.
