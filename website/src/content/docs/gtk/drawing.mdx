Three GTK widgets draw for themselves. The **drawing area** is the plain one: a blank
box, a size and a callback, and everything on screen is what the callback painted. The
**GL area** is the same idea with a GPU behind it. **Graphics offload** draws nothing at
all — it hands its one child to the compositor untouched, which is cheaper than
compositing a texture per frame.

What none of them have is styling. Their CSS nodes carry no rule in libadwaita's
stylesheet, so what you see here is geometry, not a theme.

<MoreInfo title="What the NativeScript port has">
None of the four. `@nativescript/core` has no canvas view, no WebGL view and no
compositor passthrough, and a drag icon is something the platform draws for you rather
than a widget you build. Each block's XML template tab says so instead of showing one.
</MoreInfo>

## Drawing Area

A blank widget you paint on. It has **no visual properties at all** — what you see is
whatever `set_draw_func` drew, and the draw function is called with the widget's
**allocation**, so it has to be ready for a size it did not choose.

**content-width** and **content-height** are the minimum *and* the natural size in one:
a parent may hand the area more room than it asked for, but never less. At 0 — the
default — the area has no intrinsic size at all and fills whatever box it is put in,
which is why an area with both at 0 and no size request disappears.

The draw function is called again whenever the area is drawn: when it first comes on
screen, when its size changes, when something covers it, and when you ask for it with
`queue_draw()`. That is the whole contract — repaint from the function, never
incrementally.

<MoreInfo title="Why a drawing area needs neither properties nor styling">
Because it is a blank widget with a blank node. `GtkDrawingArea` sets no CSS name of its
own, so its node is the generic `widget` node, and libadwaita's stylesheet has no rule
for it — there is nothing to theme, which is also why a draw function that paints a
background has to read the widget's own colour (`gtk_widget_get_color`) instead of
assuming one.
</MoreInfo>
## GL Area

The same idea with a GPU behind it. **auto-render** says whether `::render` is emitted
every time the widget draws, **has-depth-buffer** and **has-stencil-buffer** decide what
the framebuffer has in it, and **allowed-apis** is a *set* — `gl gles` (the default),
`gles` or `gl` — not a choice.

The two signals are the whole contract, and their order is the part applications get
wrong. `::resize` arrives with the **device-pixel** viewport (logical size × scale
factor) **before** the first `::render` and before every later one, so a program that
sets up its projection there cannot draw into a viewport nobody told it about.

The render flag is cleared *after* `::render`, so `queue_render()` from inside the
handler queues its frame and loses its flag — one render, not a loop. Nothing redraws on
its own either way: **auto-render** decides whether a draw you asked for ends in
`::render`, and animating means asking, from a tick callback.

One property refuses to change late. `allowed-apis` is read when the context is created,
so GTK refuses a write to a realized area — and the browser replica does the same, putting
the attribute back rather than starting a second context.

<MoreInfo title="What this replica actually is">
A `<canvas>` with a real WebGL context, and the block says so where a reader would
otherwise assume parity. Three differences are real and none of them is a bug: WebGL and
WebGL2 are both **ES**, so `api` always reports the ES flavour the browser gave out (no
browser offers desktop GL) and `allowed-apis` picks between two ES *versions*; WebGL
clears its drawing buffer after compositing unless the context asks it not to, so the
element creates the context with `preserveDrawingBuffer` — the counterpart of the texture
GTK keeps between frames; and `::create-context` still works, a handler supplying its own
context through `detail.context`. There is no frame clock here either, so a draw happens
when the allocation changes, when `queue_render()` asks for one, or when a property that
ends in `queue_draw` changes — an application animating a GL area asks for its frames,
exactly as it would in GTK.
</MoreInfo>

    ```html
    <gtk-gl-area id="area" style="width:240px;height:160px;">
    </gtk-gl-area>

    <script type="module">
        const area = document.getElementById('area');

        // ORDER, not decoration: `resize` carries the device-pixel viewport and arrives
        // before every `render`, the first one included.
        area.addEventListener('resize', (event) => {
            const { width, height } = event.detail;
            area.context.viewport(0, 0, width, height);
        });
        area.addEventListener('render', (event) => {
            // The context is the whole GL API, and the browser's is ES — see the note
            // above the block. A scene is a compiled program and a buffer; this tab is
            // about the ORDER of the two signals, and the story draws the triangle.
            const { context } = event.detail;
            context.clearColor(0.15, 0.16, 0.18, 1);
            context.clear(context.COLOR_BUFFER_BIT);
        });

        // Nothing redraws on its own. `queueRender()` asks for the next frame, and the
        // flag SURVIVES a request made from inside the handler — which is what a tick
        // callback is: the browser's stand-in for GLib's.
        function tick () {
            area.queueRender();
            requestAnimationFrame(tick);
        }
        tick();
    </script>
    ```
  </Fragment>
  <Fragment slot="gjs">
    ```ts
    import Gtk from 'gi://Gtk?version=4.0';
    import Gdk from 'gi://Gdk?version=4.0';
    import GLib from 'gi://GLib?version=2.0';

    const area = new Gtk.GLArea({ autoRender: true, hasDepthBuffer: false });
    // A SET, read when the context is created — GTK refuses a write to a realized area,
    // so it belongs before the first render.
    area.allowed_apis = Gdk.GLAPI.GL | Gdk.GLAPI.GLES;

    // ORDER: `resize` first (device pixels — logical size × scale factor), then `render`.
    area.connect('resize', (area, width, height) => {
        area.get_context().viewport(0, 0, width, height);
    });
    area.connect('render', (area) => {
        // The context IS the whole GL API — `gdk_gl_context_*` mirrors GL — so the
        // browser replica's `WebGLRenderingContext` answers to the same calls. A scene is
        // a compiled program and a buffer: `gl.use_program` and `gl.draw_arrays`.
        const gl = area.get_context();
        gl.clear_color(0.15, 0.16, 0.18, 1.0);
        gl.clear(0x4000);
    });

    // Nothing redraws on its own: a tick callback asking per frame is what animates it.
    GLib.timeout_add(GLib.PRIORITY_DEFAULT, 33, () => {
        area.queue_render();
        return GLib.SOURCE_CONTINUE;
    });
    ```

## Graphics Offload

A wrapper that draws **nothing itself**: it hands its one child to the compositor as it
is, skipping the texture round-trip a frequently changing child would otherwise pay on
every frame. It is worth it for video and nothing else, and GTK falls back to normal
rendering whenever it cannot — there is no failure mode to handle.

**enabled** says whether the attempt is made at all (**enabled** from the start,
**disabled** to opt out). **black-background** paints black over the whole allocation
*before* the child, which is what letterboxing needs: an aspect ratio that does not match
the screen leaves bars, and the property makes them black in CSS rather than in an
application's own drawing code.

What the widget will **not** do is the list worth reading before you reach for it: a
rounded corner that clips the content, a transform more complex than a translation and a
scale, a filter such as opacity or grayscale, and translucent content all rule offload
out. An offloaded child is best kept bare.

<MoreInfo title="What this replica actually is">
A wrapper that carries the enum, the black rectangle and the bin layout — and **not** the
passthrough, because no browser API hands a surface to a compositor. When `enabled` is
`enabled` the replica sets `will-change: transform` on its own box, which is the browser's
own statement that a layer may be composited without being drawn into a texture first; that
is the whole of what a document can do here, and the block says so rather than implying
GTK's optimisation is available.
</MoreInfo>
