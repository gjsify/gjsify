### N-API host in GJS (`@gjsify/napi`)

The inverse of node-gi at the native-ABI level: run Node's **N-API `.node` addons IN GJS** via an N-API-over-mozjs-140 implementation. ADR 0011 (Accepted); engineering plan out-of-repo (werkstatt no-dev-plans rule).
|package `packages/napi/napi`, tier 3, NOT a workspace member (own `napi.yml`; classifier-ignored like `packages/node-gi/**`). Build = the `-native` template: meson + thin Vala `GjsifyNapi.init()` GI surface + C++ napi in ONE `.so`+`.gir`+`.typelib`. Bootstrap: the running `JSContext` (`gjs_context_get_current`/`get_native_context`) + a JSNative `loadAddon(path)` (exports = return value, load failure = JS exception, reentrant). `napi_value` = a GC-traced `JS::Heap<JS::Value>` arena slot — SpiderMonkey's MOVING GC forbids Bun's raw-boxed-value trick and `JS::Rooted` handle scopes. Symbol binding: the shim self-promotes its `napi_*`/`node_api_*` into global scope so an UNMODIFIED node-gyp addon's undefined symbols bind to ours (as Node/Bun export the ABI from the main binary).
|**transparent build integration SHIPPED** — `napiNodeAddonPlugin`, the forward mirror of `gjsGiNodePlugin`; always-on for `--app gjs` (inert unless a native-addon specifier is in the graph). resolveId `order:'pre'` claims `bindings`/`node-gyp-build`/direct `.node`/napi-rs `@scope/pkg-<triple>` siblings/napi-rs GENERATED-loader ENTRIES and load-emits a virtual module returning `loadAddon('<abs .node>')` (shims import `@gjsify/napi` by bare specifier, bundled normally; callable helpers stay CJS for cjs-compat). `resolveAddonPath` replicates node-gyp-build's OWN probe order (`build/Release`→`build/Debug`→`prebuilds/<target>`, napi-tag preferred, abi-tolerant). **napi-rs entry replacement (#840)**: `detectNapiRsEntry` recognises a generated loader by a package.json SIGNAL (a `napi` config object OR `<self>-<triple>`/`napi.packageName`-scoped `optionalDependencies` siblings — `isNapiRsSibling` knows BOTH schemes; `rolldown`/`oxfmt`/`oxlint` use the foreign-scope one) AND the resolved file being an entry the manifest NAMES — `main`, `module` or `exports["."]`, matched modulo the `.js`/`.mjs`/`.cjs` twin, walking `exports["."]` only, skipping the `browser` condition (the wasm/pure-JS fallback must keep resolving) and `types`. `main` alone was not enough: `lightningcss` declares `main: node/index.js` and ships `node/index.mjs` beside it — comparing only `main` rejected the very file being bundled. The module is swapped for `module.exports=loadAddon(<HOST-triple sibling .node>)` — sibling selected BY HOST TRIPLE, never declaration order (`gjsify install` materialises EVERY platform package; "first that resolves" baked a Mach-O binary into a Linux bundle). **A BARE specifier reaches the handler** (resolved before testing, memoized): a napi-rs loader acquires its binary through a template literal, so entry replacement is the only lever. The `idFilter` is asserted Rust-`regex`-compatible — it crosses to the native core as a STRING, and Rust rejects the whole pattern on any lookaround/`\0`, silently disabling every interception under GJS. **Every rewrite is GATED on `@gjsify/napi` being resolvable** (`ensureNapiAvailable`) — declining leaves normal resolution (and a package's JS/wasm fallback) working, and stops the committed `cli.gjs.mjs` varying with whether the package happened to be installed. `rawImporter` is normalised at the boundary: `@gjsify/rolldown-native` round-trips hook payloads through JSON and passes `null` (not `undefined`) for "no importer" — `dirname(null)` failed whole GJS builds as UNHANDLEABLE_ERROR. **A gjsify ADR-0017 platform package is NOT a napi-rs sibling, and only the manifest can say so** (`isGjsifyNativeBridge`, keyed on `gjsify.platforms`/`gjsify.prebuilds`): ADR 0017 spells a target `<os>-<arch>` and names the package `<self>-<os>-<arch>`, which IS napi-rs' `<self>-<triple>` scheme whenever the two vocabularies agree — they differ on Linux by the libc token (`linux-x64` vs `linux-x64-gnu`) and agree EXACTLY on `darwin-x64`/`darwin-arm64`. So every split native bridge looked like a napi-rs package on darwin only, and the sibling probe — `ctx.resolve('@gjsify/webgl-darwin-x64')`, an artifact-only package with no JS entry — did not return null: `skipSelf` skips only this plugin, so the `unresolved-workspace-import` guard still ran and (correctly, for a real import) made the unresolvable bare `@gjsify/*` FATAL. `gjsify build --app gjs` of any consumer of any split bridge therefore died on darwin with "cannot resolve the workspace package", invisible to every Linux job. The probe is now also fatal-safe and warns instead of aborting — a name misread must never be able to kill a build. So `import Database from 'better-sqlite3'` just works after `gjsify install @gjsify/napi`; `loadAddon(path)` stays the escape hatch. Unit `napi-node-addon.spec.ts`; e2e `napi-transparent-app-gjs` (real `lightningcss`, planted foreign-platform sibling, run under stock gjs) + byte-vs-Node `transparent-gate.mjs` (bufferutil/utf-8-validate/sqlite3/`@node-rs/argon2` all byte-identical).
