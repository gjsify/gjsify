## Framework — `packages/framework/*`

Composition-first (Remix/Astro/SvelteKit feel). Anything NOT Node/Web/DOM/infra belongs here. Showcases use raw `Adw.Application`+`ApplicationWindow`+`ToolbarView`+`HeaderBar` — the purpose is demonstrating the API, not hiding it; a helper lands here only when it delivers what inline bootstrap cannot (multi-subsystem wiring, convention-over-config, composable lifecycle). **Framework vs DOM:** `packages/dom/` = DOM spec impls; `packages/framework/` = composable widgets/helpers gluing DOM↔GTK without being DOM spec.

### Storybook (`@gjsify/stories` + `@gjsify/storybook`)

Reusable GTK component explorer. Stories = `StoryWidget` subclasses with `static getMetadata(): StoryMeta` (title `"Category/Name"` groups the sidebar; `controls` drive a live two-way-bound Adwaita panel), exported as a `StoryModule`. Consumers add `@gjsify/storybook`, write `*.story.ts`, run `gjsify storybook` — no per-project storybook app. Config: `package.json#gjsify.storybook` (`applicationId`, `title`, `stories` dir, `globals` — `auto,dom` for canvas/DOM stories — and `runtime` `gjs`|`node`). That block is MACHINE-CHECKED by the portable `storybook` conformance rule: the declared `stories` dir (default `src`) must exist and hold at least one `*.story.*`, resolved exactly the way the command resolves it — a typo used to surface only when someone ran `gjsify storybook`, and the one CI job that does is path-filtered to `packages/node-gi/**`, i.e. advisory. One story serves the GTK / browser (`@gjsify/adwaita-storybook`) / NS (`@gjsify/storybook-nativescript`) renderers via the pure `stories` contract + `storybook-core` logic.

**Self-verify (node-gi capstone):** `installStorybookProbe(app, window)` + `probeEnabled()` (env `GJSIFY_STORYBOOK_PROBE`, gated exactly like devtools so production is byte-unchanged) drive a running storybook HEADLESSLY IN-PROCESS, no DBus (reuses `captureWidgetPng`/`dumpTree`): assert sidebar categories, chrome tree, a story renders its widget subtree, window rasterises to a non-empty PNG → exit 0/1. This is how `gjsify storybook --runtime node` proves the full Libadwaita gallery renders on Node on Linux AND Windows (`--windowing` GTK bundle, no gvsbuild): CI `storybook-node-gi-bundle` → `gtk-smoke` + `windows-gtk-storybook`.

### Devtools (`@gjsify/devtools` + bridge)

Drive/inspect/**screenshot a running GJS/GTK app over DBus** — self-verify a GUI without a human. Opt-in, prod-safe.

|wire: `this.connect('startup', () => installDevtools(this))` — bus connection + object path exist only after the app registers; GC-roots the service against the DBus self-cycle |enable: `GJSIFY_DEVTOOLS=1 <app>` (else no-op returning `null`) |dest = app-id, path = `<app-dbus-object-path>/devtools`, iface `org.gjsify.Devtools`
|**the CAPTURE is OS-agnostic; the TRANSPORT was the only Linux-shaped part.** `captureWidgetPng` is pure in-process GTK4/GSK (`get_native().get_renderer()` → `Gtk.WidgetPaintable` → `render_texture` → `save_to_png_bytes`) — no grim, no portal, no GStreamer, no OS branch, CI-proven on darwin-arm64. What macOS and Windows lack is the SESSION BUS, so `installDevtools` also speaks GDBus **peer-to-peer**: `Gio.DBusServer` on a socket address (`GJSIFY_DEVTOOLS_ADDRESS` / `options.address`), the SAME `DevtoolsService.export()` per incoming peer connection. Precedence is ONE pure function, `chooseDevtoolsTransport` (spec-checked, four rows): explicit address → the app's bus connection (**Linux byte-unchanged**) → no usable bus ⇒ AUTO-PICK a socket → bus answers but app unregistered ⇒ the call-site diagnostic, no fallback. Auto-picking is the point: `GJSIFY_DEVTOOLS=1` is a request for a control plane, and a service constructed-but-never-exported is the silent absence the whole transport removes. The auto-picked address is logged AND published to `<runtime-dir>/gjsify-devtools/<app-id>[.<instance>].address` (`devtoolsAddressFilePath`, deleted on `GApplication::shutdown`) — the bus-less analogue of `DBUS_SESSION_BUS_ADDRESS`, so `gjsify debug` needs no configuration either. Bridge side mirrors it (`chooseClientTransport`): `--address` → env → published file (**above** the bus: the file is positive evidence an app of that id is listening NOW) → session bus → hard error naming all three. A peer call carries NO destination bus name; `nameHasOwner`/`listInstances` answer from the connection instead of the daemon.
|**`installDevtools` is TOTAL — it returns `null`, it never throws.** It is an opt-in diagnostic wired into `startup`/`activate` handlers (storybook before `present()`, adwaita-app before `onStartup`), and GJS LOGS an exception thrown in a handler and SWALLOWS it — so a throw costs the consumer the REST of that handler and reads as "my app hangs with no window". Every failure is one stderr line naming the address and the way out (`devtools stayed OFF, the app is unaffected — …`); the fallible work lives in one inner function so totality is structural. Address hygiene for the pinned `unix:path=` recipe: `stop()` unlinks the socket but an abnormal exit (Ctrl-C/SIGKILL/crash) does not, and binding over the leftover inode fails `ADDRESS_IN_USE` exactly like a live server (both measured, gjs 1.88.1) — so a socket PROVEN dead (connect refused) is reclaimed, a LIVE one is never stolen, and a non-socket at that path is never deleted (a typo'd address must not be a delete primitive). The auto-picked `unix:tmpdir=` cannot go stale, which is why "pick a fresh address" is not the answer for a pinned one: the bridge was told to dial exactly that path.
|**the published address file is a CLAIM, and the BRIDGE verifies it.** It outranks the session bus, but nothing makes it true: it is removed on `unexport()` (not only on `GApplication::shutdown`, which itself covers SIGTERM but not SIGINT/SIGKILL), and on macOS/Windows `GLib.get_user_runtime_dir()` degrades to the user CACHE dir, where a leftover file survives REBOOTS. So `connectToDevtools` dials-then-falls-back: a published address that does not answer (`G_IO_ERROR_NOT_FOUND`, measured) is DELETED and resolution continues down the precedence to the session bus or to the three-ways-in diagnostic — never a raw localised GIO error out of `runDevtoolsMcp`'s first statement. An EXPLICIT `--address`/`GJSIFY_DEVTOOLS_ADDRESS` does not fall back: pinned on both sides, so a dead one must be reported, not routed around.
|**per-connection exports, and flags per ADDRESS FAMILY.** `DevtoolsService` keys its `Gio.DBusExportedObject`s by connection — a peer server hands out one connection per client with no shared registry, so a single slot served the FIRST client and left every later one seeing `UnknownMethod` for all 26 methods. `unix:` gets `AUTHENTICATION_REQUIRE_SAME_USER` (EXTERNAL uid match); `nonce-tcp:` MUST get `NONE` — measured on gjs 1.88.1, that flag rejects every TCP client (`Unexpected lack of content when trying to read a line`) because TCP carries no peer credentials, and the nonce file's permissions are the secret there — measured AND spec-checked: GDBus writes it mode 0600, binds 127.0.0.1 only, and a client that skips the 16 nonce bytes gets no reply at all. win32 detection is `GLib.DIR_SEPARATOR === 92` (GLib's own introspected compile-time constant — no uname probe, no dep).
|**macOS operational facts** (measured on the Intel test VM): `dbus-run-session` AS SPELLED EVERYWHERE ELSE cannot run there (Homebrew's dbus listens on launchd → `DBUS_LAUNCHD_SESSION_BUS_SOCKET is empty`) — pass `--config-file=<conf>` whose `<listen>` is `unix:tmpdir=/tmp` (`packages/node-gi/node-gi/test/session.conf`, used by its `test:dbus`). `DYLD_*` must be exported by the shell that `exec`s `gjs` (SIP strips it through `nohup`/`sh`). Cold start took 94 s before the control plane answered on a GPU-less VM (1 s warm) — anything waiting on it must POLL `GetStatus`, never sleep a fixed time.
|methods: `Screenshot(scope:s)→ay` (PNG; `scope` = `''`/`window` for the active window, or a widget path to shoot ONE widget) · `DumpTree`/`GetProperty(path,prop)`/`GetFocused`/`ListToplevels` (stable `toplevel:N/child:M` paths) · `FindWidget(selector)→s` (first VISIBLE+mapped widget matching `Type`/`:css-class`/`Type:css-class`, depth-first from the active window, `''` when none — widget paths are POSITIONAL, so a path written into a script is wrong the moment a widget is inserted above it, and every click-driving caller was re-walking `DumpTree` JSON in its own language to avoid that) · `SendKey(accel, path)→b` (deliver a key to the key controllers of a widget — empty path = the FOCUSED widget; the half of headless driving `ActivateWidget` does not cover, since nothing could be TYPED and every `Gtk.EventControllerKey` handler was therefore unverifiable. Emits `key-pressed` on the widget's own controllers rather than fabricating a `Gdk.Event` — GTK4 made events opaque with no public constructor — so it proves the HANDLER, not GDK's routing; pair with `GetProperty(path,"focusable")`, because an unfocusable widget swallows every real key silently) · `ActivateWidget(path)→b` (click-drive: `gtk_widget_activate` for Button/Entry/Toggle + GtkListBox select-row/`row-activated` fallback for nav+preference rows — the mutating counterpart of `GetProperty`) · `GetStatus` · `ListActions`/`ActivateAction`/`ChangeActionState` · `ResizeWindow`/`PresentWindow` · `DumpCss`/`SwapCss` · `DumpGSettings`. `opts.extend` adds app-specific methods (storybook does via `buildStorybookDevtoolsExtension`); `opts.instance`/`GJSIFY_DEVTOOLS_INSTANCE` scope multi-instance
|cluster (`packages/framework/devtools*`): `@gjsify/devtools` (GTK adapter) · `devtools-protocol` (transport-agnostic `MethodRegistry`, pure TS, shared by GTK/NS/browser) · `devtools-mcp` (host-side MCP bridge `runDevtoolsMcp(profile)`; profiles storybook/browser/cdp/nativescript) · `devtools-cdp` (`InspectorProtocolClient` over a WebKit remote inspector) · `devtools-browser`
|CLI `gjsify debug`: MCP↔devtools bridge for a running devtools-enabled app; **stdout = MCP channel, all logs → stderr only**
|ad-hoc: `gdbus call --session --dest <app-id> --object-path <path>/devtools --method org.gjsify.Devtools.Screenshot ""` → `ay` PNG bytes; unpack the `(ay)` variant from a tiny GJS caller (gdbus itself can't save binary)

### Bridge pattern

Pairings: `HTMLCanvasElement`(2d)→`Canvas2DBridge`→`Gtk.DrawingArea`(Cairo) | (webgl)→`WebGLBridge`→`Gtk.GLArea`(libepoxy) | `HTMLIFrameElement`→`IFrameBridge`→`WebKit.WebView` | `HTMLVideoElement`→`VideoBridge`→`Gtk.Picture`(gtk4paintablesink).

Protocol: (1) bridge creates the DOM element internally (2) app uses standard DOM API (3) bridge translates GTK↔Web lifecycle (signals/draw_func/render ↔ rAF/events/ready). Each bridge owns an isolated `BridgeEnvironment`. Common API: `onReady(cb)`, `installGlobals()`, element getter, `environment`. DOM backing: Image→GdkPixbuf | Canvas2D→Cairo.ImageSurface+PangoCairo | WebGL→Gtk.GLArea+libepoxy | IFrame→WebKit.WebView | Video→Gtk.Picture+GStreamer.

`WebGLBridge` names the GL it got: `WEBGL_debug_renderer_info` implemented (spec'd `VENDOR`/`RENDERER` stay masked), `bridge.rendererInfo` reads it, a CPU rasteriser (`isSoftwareRenderer`) costs ONE stderr line — a GPU-less host is otherwise invisible: every draw call succeeds, only the frame budget tells. DIAGNOSTIC ONLY — the same driver carries a demand-driven three.js scene and needs 1.1 s for one textured full-screen draw in a game, so a renderer swap keys on a MEASURED frame budget, never this string. Canvas clones PLAIN (`_createCloneTarget`): one GLArea, it stays with the original.
`WebGLBridge` on resize: dispatches DOM `resize` + re-invokes the last rAF callback (demand-driven re-render, no animation loop). `WebGL2RenderingContext` overrides `texImage2D`/`texSubImage2D`/`drawElements` from the WebGL1 base (bypasses WebGL1 format/type validation); native Vala handles all GLES 3.2 formats.

**HiDPI is NOT symmetric between the two canvas bridges, and the asymmetry is the whole bug class.** GTK silently pre-scales a `Gtk.DrawingArea`'s Cairo context, so Canvas2D code written in logical pixels renders sharp with nothing to do. `Gtk.GLArea` does not: its framebuffer is `allocation × scale-factor` and `gl.viewport` is raw device pixels. So the GL side must report the DRAWING BUFFER in device pixels (`canvas.width`/`height`, hence `gl.drawingBufferWidth`) while CSS layout size stays logical (`clientWidth`/`offsetWidth`), and `installGlobals()` publishes `devicePixelRatio` as an ACCESSOR over the widget's live `get_scale_factor()` — the identity `clientWidth × devicePixelRatio === canvas.width` is what makes an unmodified Three.js/Excalibur viewport cover the whole framebuffer. Reporting the allocation as `canvas.width` (as it did until 2026-08) is invisible at scale-factor 1 — every desktop, CI runner and test VM — and on the first scale-factor-3 host drew each scene into the bottom-left NINTH of its widget: measured on a OnePlus 6T / postmarketOS / GNOME Mobile, where the teapot, the pixel-postprocessing and the Excalibur showcases all rendered a 120×218 corner of a 360×655-logical widget. `@gjsify/dom-elements`' register seeds `devicePixelRatio: 1` as the widget-less default only. A real `Gtk.GLArea` cannot regression-test this (its host reports 1); `html-canvas-element.spec.ts` varies the scale factor through a stub, which is the point of that stub.

**`WebGLBridge` declares which GL APIs it ACCEPTS, never GLES-only.** `set_use_es(true)` is `set_allowed_apis(GDK_GL_API_GLES)` — GLES *exclusively* — and macOS offers no GLES profile at all (its GDK backend is CGL-only, capped at desktop GL 4.1), so on every darwin host that call left the GLArea permanently in error (`get_error()` = "Application does not support OpenGL API", `get_context()` null, no `render` signal, not one pixel). The bridge therefore sets `set_allowed_apis(GL | GLES)` and lets GDK pick: measured on gtk 4.22, a both-allowed context realizes GLES 3.2 on Wayland/Mesa (identical to what `set_use_es(true)` produced — Linux is byte-unchanged) and desktop GL 4.1 on macOS. The choice MUST be made before realize — `gtk_gl_area_set_allowed_apis` asserts `!gtk_widget_get_realized`, so there is no "retry wider after a failed realize" recovery.
**What the darwin GL 4.1 ceiling still costs, measured on macOS 15.7 / GdkMacosGLContext (`4.1 APPLE-21.1.1`, GLSL 4.10):** (1) `glInvalidateFramebuffer`/`glInvalidateSubFramebuffer` are GL 4.3 and absent, hence the `epoxyGlVersion() >= 43` gate in `webgl2-rendering-context.vala` — libepoxy ABORTS on a missing entry point rather than returning null. They are also the ONLY two missing: of the 219 `epoxy_gl*` entry points `libgwebgl.dylib` references, `dlsym` against `OpenGL.framework` resolves 217 (`nm -u <lib> | sed -n 's/^ *_epoxy_//p' | grep -E '^gl[A-Z]'`, then `ctypes.CDLL('/System/Library/Frameworks/OpenGL.framework/OpenGL')`). (2) **GLSL ES 3.00 does not compile, so `shaderSource()` REWRITES the dialect** — `#version 300 es` needs ARB_ES3_compatibility (core in GL 4.3) and the 4.1 compiler refuses it (`version '300' is not supported`), while GLSL ES 1.00 is accepted via ARB_ES2_compatibility, core in 4.1: that ONE version between the two extensions is why WebGL1 worked here first. On a desktop context lacking the extension, `shaderSource()` substitutes `#version <the context's GLSL> core` (4.10 on macOS) and changes nothing else, so **WebGL2 content DOES draw on darwin** — measured end to end on macOS 15.7.9 / GL 4.1 core: an unmodified `#version 300 es` pair compiles, links, draws, and `readPixels` returns the shader's colour. The predicate is the EXTENSION, not the OS: Mesa's `4.6 (Compatibility Profile)` on win32 has it and is NOT rewritten; `#version 100` comes back byte-for-byte unchanged. Construct-by-construct measurement: `packages/framework/webgl/README.md`. (3) The API-level GLES 3.0 spellings desktop 4.1 has no equivalent for stay missing — `GL_PRIMITIVE_RESTART_FIXED_INDEX` (4.3 on desktop) and the mandatory ETC2/EAC formats; both surface as a draw-time error, not a compile failure. Host diagnosis: `gjsify run packages/framework/webgl/scripts/probe-gl-host.js` reports the negotiated API, the version, the scale factor, the logical-vs-device sizes and the shader-dialect matrix, and draws a shader-free pattern so a blank window cannot be mistaken for a failed shader. Remaining darwin gaps: `status/open-todos.md`.

### GTK Host (`@gjsify/gtk-host`)

The element model UI-framework renderers (Vue/React/Solid/Angular) bind to — **ADR 0027**, table provenance **ADR 0028**, full contract + measurements in [gtk-host/README.md](gtk-host/README.md). These rules bind work here (a live count here drifted once already). (1) **One table, adapters as subpaths**: no adapter may contain a widget name literal or an insertion rule — hand-maintained per-framework tables stalled `react-gtk`, `react-native-gtk4` and `svelte-gjs`, and GTK4 forces the question by deleting `GtkContainer` (no generic `add`; `Gtk.Buildable.add_child` is a **vfunc only** — `typeof headerBar.add_child === 'undefined'`). (2) **The shadow tree is the truth**: `parent`/`first`/`next` are the host's own, anchors never enter the GTK tree (an empty `v-if` branch must not shift a sibling index — what stalled `gnome-vue`), and text goes to the descriptor's `textSink` or is refused BY TAG NAME. (3) **Be loud, because GTK's failure mode is exit 0**: `box.orientation = 'vertical'` keeps HORIZONTAL with no diagnostic at all, writing a read-only property does not throw, and a generic `insert_before` on a `Gtk.ListBox` bypassed the row wrap and emitted 1 230 783 `Gtk-WARNING` lines at exit code 0. Hence ParamSpec coercion, named refusals, and conformance vectors that read the REAL tree (`./conformance`) and assert IDENTITY across a reorder, not just order. (4) **Two facts, never one**: `attached` (GTK has taken this node) is not `widget !== null` (it has been materialised) — every framework builds bottom-up, and conflating them made the tail rotation touch non-children. And nothing is written down before GTK agrees: props, listeners, slots and layout are all recorded only AFTER the operation that can reject them, because `materialize` replays them verbatim and a rejected value re-throws from the next rebuild. Every spec asserts zero GTK diagnostics per test (`installDiagnosticsGate()`) — without it the whole mis-parenting class is invisible, which is how a keyed reorder could be a no-op on screen while 127 tests stayed green. (5) **The table is GENERATED, and the type surfaces are gated NEGATIVE-first**: 164 widgets from the GIR, 26 with a curated placement rule and the rest `uncurated` — creatable and settable, never fillable by guess. `gjsify tsc` cannot check a type surface (it checks it against itself), so `scripts/check-type-surfaces.mjs` compiles fixtures carrying **assertions that must FAIL** across three dialect halves (`jsx`, `vue`, `react`) and re-runs each with its load-bearing settings flipped: drop `noImplicitAny` and `jsxImportSource` together and nearly every JSX negative goes green at exit 0, and dropping `strictTemplates` silences an unknown prop, an unknown EVENT and an unresolved tag while wrong value types still error, so the gate looks alive while checking the wrong half. The counts are deliberately gone: they were wrong here for as long as they existed, and the gate prints all of them on every run. (6) **Both legs are CI-wired per ADR 0030**: `test:gjs` runs in main.yml's sharded sweep; `test:gjs-on-node` builds the SAME suite `--app node` and runs it over node-gi as node-gi.yml's `gtk-host-node` job — one corpus, so a gjs-green/node-red diff is attributable. Attribution needs the two legs to be ONE program, and a per-runtime EXPORT CONDITION is what breaks that: the node build of a genuine GJS source ROUTES `solid-js` past its `node` key (`REVERSE_BRIDGE_ENTRY_ROUTES`) — that key is the SSR build with an empty `createEffect`, 16 suites red as "a property update that never reaches GTK". A route, not a condition: `browser` would fix solid and hand `ws` a `throw`. (7) **Three adapters — `/solid`, `/vue`, `/react`; every measurement is in the README, two routing facts are here.** `/react` REQUIRES `--define 'process.env.NODE_ENV="production"' --exclude-globals navigator`: without them `--globals auto` answers `document`/`HTMLCanvasElement`/`Path2D`/`navigator` with the GTK-backed DOM registers and the bundle silently grows gi://Gdk, GdkPixbuf, Pango, PangoCairo. And its HostConfig is READ from the installed `react-reconciler` through a Proxy in `react.spec.ts` — never hand-listed, because the factory destructures the whole config at construction and a hand-kept list drifts.

### GTK→DOM Event Bridge (`@gjsify/event-bridge`)

`attachEventControllers(widget, getElement)` attaches GTK4 controllers → DOM events: EventControllerMotion→pointer/mouse move+enter/leave/over/out | GestureClick→pointer/mouse down/up, click, dblclick, contextmenu | EventControllerScroll→wheel | EventControllerKey→keydown/keyup | EventControllerFocus→focus/focusin/blur/focusout. W3C UIEvents dispatch; GTK widget-relative coords → offsetX/Y/clientX/Y; `key-map.ts` maps ~80 Gdk keyvals → DOM key/code (L/R modifiers, Numpad location). Canvas2D/WebGL bridges call it in their constructors. Event classes live in `@gjsify/dom-events`.

### Context factory registry

`HTMLCanvasElement.registerContextFactory` — `@gjsify/canvas2d` registers `'2d'` (Cairo); `@gjsify/webgl` registers `'webgl'`/`'webgl2'` via subclass override + fallthrough.

**Framework packages** (`packages/framework/<name>/`): flat `@gjsify/<name>` (NOT `framework-<name>`), composition-first, no top-level side effects in `index.ts`. Global registration follows **ADR 0012** (ownership, not pillar membership): (a) a framework pkg MUST NOT register a global a Web/DOM pillar register already owns — it imports the pillar's *granular* register subpath from the module that needs it, never from `index.ts` (`canvas2d`'s bridge → `@gjsify/dom-elements/register/canvas`); a second registration silently REPLACES the pillar's factory — the bug that produced the rule. (b) It MAY ship a `/register` only for globals it owns, or is the only GJS-slot distribution of, which no pillar can host without taking a GTK/WebKit dep it must not have. (c) Any such `/register` follows the FULL tree-shakeable convention incl. globals-map + alias mirrors + `register.spec.ts` — never a private back door. (d) A register import that is a FUNCTIONAL dependency must survive the `--app node` alias layer: `isGjsSourceBuild` in `app/node.ts` is the single gate, and it must stay the same question `emptyGirs` asks — the two disagreeing dropped canvas2d's `'2d'` factory on the node target. (e) `installGlobals()` and `/register` must install the SAME set — imperative and tree-shakeable spellings of one contract. Current exceptions: `@gjsify/iframe/register` (WebKit-backed), `@gjsify/canvas2d/register` (`ImageData`, `Path2D`), `@gjsify/webgl/register` (`WebGL(2)RenderingContext` — only impl is the gwebgl Vala bridge).
