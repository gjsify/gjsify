## NativeScript Bridge — `packages/nativescript-bridge/*`

Native API wrappers for the NativeScript (Android/iOS) runtime slot. Packages here use `java.*`/`NS*` globals exposed by the NS V8 runtime — analogous to `packages/framework/*` using `gi://`. `runtimes.nativescript:'native'`, all other slots `'none'`.

**Convention:** pure TS, no `gi://`/`@girs/*` value imports. Platform detection via `typeof java !== 'undefined'` (Android) / `typeof NSFileManager !== 'undefined'` (iOS); `assertNativeScript()` throws `'Platform not supported'` off-NS — specs exploit this to run on GJS + Node without a device.

**`@nativescript/core` value imports — the UI-widget exception.** `fs`/`platform` bridges key on runtime globals only and import nothing from `@nativescript/core`. UI-widget bridges (`adwaita`) DO `import { GridLayout, … } from '@nativescript/core'` to subclass real NS views — the NS analogue of framework packages importing `@girs/*` classes. `@nativescript/core` is an OPTIONAL peer, NOT in the workspace install, so a local ambient `src/ns-core.d.ts` declares the narrow slice used (real types win when a consumer installs them) and `gjsify tsc` stays green off-device; bundler-context globals in `src/ns-globals.d.ts`. **Consequence for specs:** a widget module's `extends GridLayout` evaluates the bare specifier at module-eval — unresolvable off NS — so specs must NOT import widget classes (nor the re-exporting package root); they import only the NS-core-free surface and validate against mocks.

### NativeScript build integration

Slot semantics: § Runtime & platform model. Build specifics:
|native-bridge identifiers (`java.*`, `android.*`, `androidx.*`, `kotlin.*`, `NS*`, `UI*`, `CG*`, `NSObject`) are NOT externalized and NOT aliased — the NS runtime provides them as globals (like GJS's `imports.gi.*`).
|build: `gjsify build --app nativescript src/foo.ts --outfile dist/foo.ns.mjs` → ESM bundle (esnext, codeSplitting:false); NS consumers feed it to `@nativescript/webpack`/`@nativescript/vite` as the entry.
|**`@nativescript/core` + subpaths are EXTERNAL** — an app works only with the ONE core instance the runtime boots, and the downstream NS bundler resolves the specifier. Being an optional peer absent from the workspace install, it was unresolvable before that: every UI-widget bridge failed to build, unnoticed because nothing built them. Held by e2e `ns-bridge-bundles`, a BUILD leg — it never EVALUATES a module on NS V8 (a top-level `new TextEncoder()` compiles here and dies on device), which only `tests/integration/nativescript` does.
|**platform-file resolution**: `platformResolvePlugin` resolves `foo.android.ts` / `foo.ios.ts` / `foo.native.ts` BEFORE `foo.ts` (platform from `NATIVESCRIPT_PLATFORM`/`NATIVESCRIPT_BUNDLER_ENV`). Deliberately a `resolveId` HOOK, not `resolve.alias` — `@nativescript/vite`'s function-based platform alias is rejected by Vite 8/Rolldown; gjsify fixes it at the root. Wired into `app/nativescript.ts` + `gjsifyNativescript()`. e2e `ns-platform-resolve`.
|**platform defines**: `nativescriptPlatformDefines(platform,{dev})` bakes `__ANDROID__`/`__IOS__`/`__APPLE__`/`__VISIONOS__`/`__DEV__` into `transform.define` → per-platform branches statically resolved + DCE'd (matches the globals `@nativescript/vite` seeds).
|**Vite-8 composer `@gjsify/nativescript-vite`**: loads upstream `typescriptConfig({mode})` and fixes the returned config: (1) DROPS `resolve.alias` entries with function replacements (Rolldown rejects them; the resolver plugin + string aliases cover it), (2) REMOVES the `'commonjs'` plugin (`@rollup/plugin-commonjs` crashes Rolldown; Rolldown does CJS natively), (3) REMOVES `'ns-typescript-check'` — a bundler bundles, it does not type-check; the gate is `gjsify tsc`. Strip, don't silence: the vite-side check runs a SEPARATE program with the full NS Android globals that under TS 6 fatally flags the STANDARD NS `createNativeView(): android.view.View` override — it would fail every build on a universal NS idiom. **Patches are GATED on the `@nativescript/vite` major** (`detectNativescriptViteMajor()` resolves the MAIN entry and walks up to the package root's `package.json` — NOT the `/package.json` subpath, which 8.x's exports map does not expose: `resolve('@nativescript/vite/package.json')` throws `ERR_PACKAGE_PATH_NOT_EXPORTED` → caught → `undefined`, so the major-8 gate NEVER FIRED and the legacy patch set ran — fixed; resolved from the project root cwd first, lib-relative fallback; genuinely-absent → fail-safe = "patches needed"). Major ≤2/unknown → (1)+(2)+(3); ≥8 (native Vite-8/Rolldown rewrite) → (1)/(2) are no-ops, SKIPPED, only (3) remains + one info log. All strips idempotent + no-op-if-absent. `applyVite8Fixes(config, major?)` takes an override (e2e tests both branches without two installs).
|**framework-peer stubbing (8.x)**: upstream's config chain statically imports the Vue/Solid/React/Angular compilers at module eval (they are upstream `peerDependencies`) — a framework-LESS core NS app cannot even load the config (`ERR_MODULE_NOT_FOUND: '@vue/compiler-sfc'`). `stubMissingFrameworkPeers()` registers Node synchronous hooks (`module.registerHooks`, Node 22.15+/24): a resolve hook routes each MISSING peer to a synthetic stub URL, a load hook serves ESM with a default proxy + the named exports upstream imports (scanned from upstream source). Only missing peers — a Vue/Solid app keeps its real compilers. `resolve.alias` CANNOT do this (the eager import runs when Node imports the config, before any Vite alias). No `registerHooks` (old Node) → clear `npm install <peers>` hint. e2e `ns-vite-fixes`.
|export: `defineNativescriptConfig(opts?, userConfig?)` → async Vite config (userConfig merged LAST — the composability seam). Consumer: `vite.config.ts` = `export default defineNativescriptConfig();` + `nativescript.config.ts` `bundler: 'vite'`. NS packages are OPTIONAL peers; only hard dep = `@gjsify/vite-plugin-gjsify`. Validated: the `@nativescript/canvas` three.js teapot builds on Vite 8 (612 modules) and renders on-device, 0 `gi://`/`@girs` leakage.
|**SBG bundle-sync fix** (`nativescriptSbgBundleSyncFix()`, merged over upstream, under user config): `@nativescript/vite@8` names non-vendor chunks `[name]-[hash].mjs` and leaves `emptyOutDir` unset; the NS CLI copies the staging dir ADDITIVELY into `platforms/android/…/assets/app/` (never deletes) → every content-changing build adds a new hashed chunk, the Android SBG sees `NativeScriptActivity extends` twice → `File already exists …`. Fix: stable chunk names (no `[hash]`) + `emptyOutDir:true` → rebuilds overwrite instead of accumulate (one manual clean of pre-existing hashed chunks still needed once).
|**xmlns-barrel registration** (`gjsify-nativescript-xmlns-barrels`, inside `gjsifyNativescript()` so BOTH paths get it): NS apps referencing barrel modules ONLY via XML `xmlns="~/MOD"` break under vite — upstream's bundler context registers XML + code-behind + CSS but NOT standalone barrels (`index.ts` without an `.xml` sibling), so `global.loadModule("widgets/index")` returns `null` in an ESM bundle (no `global.require` fallback) → `Module 'SourceView' not found` (`@nativescript/webpack`'s xml-namespace-loader registered every `.ts`, hiding this). The plugin AUGMENTS the generated `virtual:ns-bundler-context` module: scans app XML for `xmlns="~/MOD"`, prepends `import * as` + appends `registerModule(...)` per barrel without an `.xml` sibling. Validated on-device (easy6502 app-android). e2e `ns-vite-fixes`.
|low-level alternative (the preset the composer wraps): `plugins: [nativescript(), ...gjsifyNativescript()]` from `@gjsify/vite-plugin-gjsify` (gi://→empty, platform resolution, platform defines, node aliases).
|build-feature ownership roadmap: upstream's NS-specific vite features migrate into gjsify's build stepwise; Level-3 blocker = the NS CLI's hardcoded bundler switch (`webpack|rspack|vite`) → `bundler: 'gjsify'` needs an upstream PR (`status/open-todos.md`).
