## Build — Rolldown, platform plugins

Targets: **GJS** `--app gjs` (`assert`→`@gjsify/assert`, externals `gi://*`+`cairo`+`system`+`gettext`, `firefox140`) | **Node** `--app node` (`@gjsify/process`→`process`, `node24`) | **Browser** `--app browser` (`esnext`) | **NativeScript** `--app nativescript` (esnext, codeSplitting:false; § Cross-runtime tracks).

Engine: **Rolldown** (Vite 8's production bundler; under GJS the only engine is the `@gjsify/rolldown-native` GI bridge, on Node the npm `rolldown` — picked by `bundler-pick.ts`). The orchestrator returns `{ options, plugins }` that the CLI composes into `rolldown(...)` + `.write()`; Rollup-shaped plugins also run under Vite for sister GJS apps. Key files: `packages/infra/rolldown-plugin-gjsify/src/app/{gjs,node,browser,nativescript}.ts` | `.../utils/{scan-globals,auto-globals}.ts` | `packages/infra/resolve-npm/lib/{index,globals-map}.mjs`.

**Built-in defaults are not user-config.** Per-app externals and compile targets are owned authoritatively by the app orchestrator; `bundler.external` from `package.json#gjsify` / `.gjsifyrc.*` is APPENDED, never replaces; `bundler.transform.target` overrides only deliberately. Redundant entries like `external: ["^gi:", "cairo", …]` or `transform.target: "firefox140"` are dead weight — omit them. `^gi:` as an exact-string entry never matches anything (exact matching is literal; real specifiers like `gi://Gtk?version=4.0` are caught by the prefix predicate). Set externals only for *additional* unbundled deps.

**ONE exception, OPT-IN PER CALL SITE: `toolchainAnchor`.** A `@gjsify/*` the PROJECT cannot resolve may fall back to the copy installed beside the running CLI. `gjsify build` never sets it; the three callers of `BuildAction.bundleFileForGjsCached` each do, saying why. It is NOT an intrinsic toolchain marker and no comment may claim one — the `node` shim `gjsify run` puts on the PATH routes ANY project's `node <file>` through that helper, a consumer's `"start": "node ./src/main.mjs"` included. What contains it: PROJECT FIRST (consulted only after normal resolution returns `null`, so a warm tree is byte-unchanged) and a `this.warn` on every rescue naming package + anchor, so a mixed artifact never has a healthy build's log. The anchor is a FILE PATH used as the importer of a second `this.resolve`, never a second resolver: `--app gjs` omits both `import` and `require` from `conditionNames`, so a `createRequire().resolve()` would resolve under `require` and put a `cjs-compat.cjs` shim in a GJS bundle. WHY: a `node scripts/x.mjs` re-entered as `--node-script` on a Node-less host bundles `--app gjs`, and `--globals auto` alone pulls TWENTY-ONE `@gjsify/<pkg>/register` subpaths into a ONE-LINE script — none built in a cold clone, so the ADR 0002 bootstrap died at `build:infra` (measured, postmarketOS/aarch64, gjs 1.88.1) and the same failure blocked `check-refs-pin.mjs`, hence `build:prebuilds`. The alternative was building most of the polyfill tree first, on every host including those that never bundle a script. Same two-anchor shape as `commands/tsc.ts`. e2e `node-script-cold-workspace`.

**Unresolvable `@gjsify/*` edge = build ERROR, never a silent external** (`plugins/unresolved-workspace-import.ts`, composed LAST — `resolveId` `order:'post'` — by all four `--app` targets). Rolldown's default for an unresolvable id is to EXTERNALISE it: an `UNRESOLVED_IMPORT` warning, the original specifier re-emitted, exit 0. For `gjsify build` that is wrong at exactly the wrong moment, because the edge that failed IS the substitution: `node:fs` → `@gjsify/fs` → (no `node_modules`, or an unbuilt `lib/`) → the bundle re-imports `node:fs`. Measured on `dist/cli.gjs.mjs`: 1 bare `node:` import on main vs 11 from a worktree with no `node_modules` — and the pre-commit hook AUTO-STAGED that artifact while tsc/lint/format/unit/e2e stayed green, because none of them executes the emitted GJS bundle.
|the legitimate-vs-broken line (a blanket "fail on any external" breaks every real build): a DECLARED external is legitimate — the guard asks the target's OWN externals predicate (the same one `externalsPlugin` enforces) so the two cannot drift. Fatal in exactly two shapes: (a) the specifier has a substitution-table entry naming a `@gjsify/*` package, (b) the specifier IS a bare `@gjsify/*`. Everything else (a missing `lodash`, alias shim paths, user `--alias`) keeps the old fall-through — widening to every bare specifier would make genuinely-optional peers fatal. A `@gjsify/*` edge is NOT optional; the target cannot run without it.
|mechanics: `order:'post'` gives every deliberate claim (alias/napi/gi-node plugins at `pre`, imports-empty/externals at normal) first refusal; it then re-runs the resolution Rolldown would have run next (`this.resolve(candidate, importer, {skipSelf:true})`) and returns it — a healthy build is byte-identical. Only a genuine `null` throws, naming specifier, substitution target, importer + the three likely causes. **`null` is the contract on BOTH engines** — `@gjsify/rolldown-native` REJECTED a plain miss instead, fixed at the bridge (`isResolveMiss`) because nine `this.resolve`/`ctx.resolve` sites here assume `null`, none with a catch, one a bare presence probe. A REAL failure (EACCES, corrupt manifest, another hook throwing on purpose) still rejects, and is neither swallowed nor rescued: rethrown with this plugin's context and the original as `cause`. NOT composed for `--library` (bare imports preserved on purpose — the consumer resolves them). Unit `unresolved-workspace-import.spec.ts`; e2e `tests/e2e/unresolved-workspace-import/`.

**Deepkit** (`@gjsify/rolldown-plugin-deepkit`): runtime reflection via `@deepkit/type-compiler`; default `reflection: false`. Keep disabled unless the project uses Deepkit runtime types — its emitter transforms TS `extends` method definitions into invalid `function extends()` syntax on user code.

**GJS target process bootstrap** (`plugins/process-stub.ts`): the GJS target always prepends a minimal synchronous `globalThis.process` stub via `renderChunk(order:'post')` — packages like `glob`/`path-scurry` read `process.platform` at top level during `__esm` lazy init, before any import side effect fires; the full `@gjsify/process` is wired afterwards by `--globals auto`. The same byte-1 banner carries `GJS_WELLKNOWN_SYMBOLS_STUB`: gjs 1.88 has no native `Symbol.dispose`/`asyncDispose`, so the banner defines them AS the registered symbols (`Symbol.dispose ||= Symbol.for("Symbol.dispose")`) — the exact fallback key the tsc/esbuild/babel/bun `using` downlevel helpers use. Without it, `{ [Symbol.dispose](){} }` lands under the `"undefined"` key and `using` throws `Object not disposable` (broke `@anthropic-ai/claude-agent-sdk`; silently dead-keyed our own `fs.FileHandle[Symbol.asyncDispose]`/`timers[Symbol.dispose]`). All pieces single-line (zero source-map drift), idempotent; user banners compose after; a leading shebang is hoisted to byte 0 (SpiderMonkey rejects `#` anywhere else). **The banner MUST reach every GJS ambient global through `globalThis.` — never a bare identifier**: it shares the entry chunk's top-level scope, so a bare `imports` binds to any top-level `const imports` a bundled module declares — still in its TDZ at byte 1 → `ReferenceError … before initialization` at load, before any program code. The generated `@girs/gjs` shim declares exactly that, hidden only because tree-shaking usually drops it. Guarded by `process-stub-banner.spec.ts` (asserts on the banner string — fails on the mistake, not a downstream symptom). It also carries the **GI search-path prologue** (`plugins/gi-runtime-paths.ts`, filled by the CLI): system GI libdirs, prepended at startup only where the running host shows BOTH its `girepository-1.0` and the darwin marker scoping that rule — a build-time platform gate would bake the runner's OS into a platform-neutral bundle, and the `girepository-1.0` alone puts `/usr/local/lib` ahead of the distro's stack on a `--prefix=/usr/local` Linux box. MEASURED BOUND: ESM evaluates imports before the body, so it reaches what the bundle loads AFTER evaluation starts, never a static `gi://` import. e2e `tests/e2e/gi-runtime-prologue`; the open half is in `status/open-todos.md`.

**Blueprint** (`@gjsify/vite-plugin-blueprint`): `.blp` → XML string via `blueprint-compiler` (GJS+browser; same plugin under Vite and Rolldown). Types: add `@gjsify/vite-plugin-blueprint/types` to tsconfig.

**Platform files + React Native (ADR 0032 §§ 2, 8, 9).** `plugins/platform-resolve.ts` is ONE plugin with the chain as a PARAMETER, so the tree has one resolution order: `nativescriptSuffixChain()` = `.<android|ios|visionos>` → `.native`, `desktopSuffixChain()` = `.gtk` → `.<linux|macos|windows>` → `.desktop`, both then base. **`.native` and `.web` are NOT rungs of the desktop chain** and the plugin WARNS naming a refused sibling it walked past — the fall-through is § 9's decision, the silence around it was not. `desktopOsSuffix()` is the one ambient `process.platform` read here. `siblingIndex: true` is on for desktop and OFF for NS (byte-identical mandate); the +14%-on-`dist/cli.gjs.mjs` measurement behind it is on that option's doc comment.
|**`--dialect react-native` is OPT-IN** (`PluginOptions.dialect`, `--dialect react-native`), gjs + node, never inferred — reasons in `plugins/react-native-alias.ts`. It composes the § 2 alias line (`react-native` → `@gjsify/react-native`, package ROOT only; a subpath is a named refusal, an unresolvable target a named error, never a silent external) and the § 8 support gate as a **prePlugin** — it must see the ORIGINAL source or `import type` is already stripped and the five free type-only imports become five build errors.
|the gate READS the table, never a copy: it resolves `@gjsify/react-native/support-table` from the PROJECT and imports the built module (not a dependency — tier 1 may not depend on tier 3). Scan = acorn + acorn-typescript in `utils/scan-named-imports.ts`, because `transform` is the only hook BOTH engines give that carries source. TWO blind spots, both stated in those files and TESTED: forms carrying no name, and syntax acorn-typescript 1.4.13 cannot parse (measured) — each a WARNING, never a build error, because a false violation is how a gate gets switched off. Unit `platform-resolve.spec.ts` + `react-native-{alias,gate}.spec.ts` (fixtures that must parse beside fixtures that must NOT); e2e `tests/e2e/{desktop-platform-resolve,react-native-gate}/`.

**The `gi://` arms — `--gi-renderer`, OPT-IN, browser + nativescript (ADR 0034 stage 9).** Composes `plugins/gi-renderer.ts` ahead of `gjsImportsEmptyPlugin` and flips `emptyGirs:false` on the same build, so `@girs/adw-1` reaches its real body and its inner `gi://` lands on the arm — the node-gi composition exactly; the answer is the target's widget renderer (`GI_RENDERERS` in resolve-npm). Without it `gi://Adw` is an empty module and `class X extends Adw.ActionRow` throws `Class extends value undefined` — measured on both targets, and the e2e keeps that row as its CONTROL on its own stub hosts. Three refusals, each where its fact is first knowable: unanswered NAMESPACE and mismatched `?version=` at build time from `resolveId`; an absent MEMBER at runtime through a Proxy that prints what the namespace has, these namespaces being sparse by construction. **Its EMITTED refusal may not quote a `gi://` URL** — the arm's OWN e2e asserts `!bundle.includes('gi://')`, a SUBSTRING, and that string is reachable (measured); namespace and version are named separately. That suite is the rule's ONLY source: `app-browser`/`ns-bridge-bundles` hold the same rule but never pass `--gi-renderer`, so the arm cannot reach them. Build-time refusals DO quote it — thrown, never emitted. Why + retirement: the plugin header, ADR 0034 § Amendment 12, `status/open-todos.md`. e2e `tests/e2e/gi-renderer-arms`.

**By-name `bundler.plugins` under GJS — auto-bundled.** `gjsify.bundler.plugins` entries (`{name, export?, options?}`) resolve from the project's `node_modules`. On Node: plain dynamic `import()`. Under GJS that fails for any plugin whose source imports an `exports`-map subpath (GJS's loader doesn't follow exports maps — same limitation as the register-subpath rule, but on a consumer plugin we don't control). Fix: `resolveUserPlugins` takes an injectable `loadModule`; under GJS the CLI swaps the import for a nested `buildApp('gjs', { preserveDefaultExport: true })` that bundles the plugin to one self-contained ESM, then imports that. `--globals auto` stays on (the plugin's toolchain may touch `document` at module-eval); `preserveDefaultExport` keeps the factory-as-default-export alive (the wrapper's `export *` drops `default` otherwise — breaks `@mdx-js/rollup`). Cached under `node_modules/.cache/gjsify/plugins/` keyed by source path, invalidated when the entry OR the project lockfile is newer (a dep bump rewrites the lockfile, not the entry mtime); `GJSIFY_NO_PLUGIN_CACHE=1` forces rebuild. The nested config carries no `bundler.plugins` → no recursion. Tests: `resolve-plugin-by-name.spec.ts` + `tests/e2e/plugins-by-name-gjs/`.

**Host-runtime detection — `@gjsify/rolldown-plugin-gjsify/runtime`.** `isGjs()` (the `globalThis.imports.gi` probe) and `isNode()` (GJS-guarded so `@gjsify/process`'s `process.versions.node` is not a false positive) are the single source of truth for build tooling — no inline copies. Pure module on a dedicated `./runtime` subpath so light callers don't pull the plugin index. Deliberately NOT in `@gjsify/utils` (that is a gjs-runtime `@girs/*`-importing package; consumers here are infra).

**Vite-plugin track** (`@gjsify/vite-plugin-gjsify`): the dev-side mirror of `gjsify build --app browser` — a dual-target web app builds with `gjsify build`, develops under Vite. `gjsifyBrowser({ reflection: false })` spread into Vite `plugins` composes the same browser pieces: `gjsImportsEmptyPlugin` (`@girs/*`/`gi://` → empty — they leak transitively via `@gjsify/unit`), blueprint, opt-in deepkit, plus a `config()` hook setting polyfill aliases (`process`/`assert` → `@gjsify/empty`/`@gjsify/assert`, mergeable), `resolve.conditions: ['import','browser']`, browser mainFields, `define: { global/window: 'globalThis' }`, `build.target: 'esnext'`, `optimizeDeps.exclude` (esbuild prebundle can't resolve `gi://`). By default NO `cssAsStringPlugin` — a browser app wants real CSS through Vite's pipeline; opt-in `cssAsString: true` for parity with `--app browser`/`--app gjs` unified styling (author `.css`/`.scss`, import as string, apply per target: `Gtk.CssProvider.load_from_string` on GJS, a `<style>` element in the browser — trades Vite CSS HMR for parity).

**CSS** (`plugins/css-as-string`): `.css`/`.scss`/`.sass` → JS string default export via a `load` hook. Rolldown removed its experimental CSS bundling, so the plugin reads via lightningcss `bundleAsync` and emits `export default <string>` — bypassing Rolldown's CSS classification. Sass compiles to flat CSS first (`sass` `compile`, no further lightningcss lowering on Sass output); CSS `@import` bundling built in. GTK4 lowering: `--app gjs` passes `targets: { firefox: 60<<16 }` so nesting/modern selectors flatten to what GTK4's CSS engine accepts; browser/node keep CSS pristine. Opts `cssAsStringPlugin({ targets, bundle })`; `bundle:false` keeps raw `@import`.

**Asset loaders** (`gjsify.loaders`, `plugins/text-loader`): extension → `'text'` | `'dataurl'` map for files Rolldown doesn't classify (top-level config key, not under `bundler`). `dataurl` infers MIME from extension; right choice for Excalibur `ImageSource`. Example: `"loaders": { ".glsl": "text", ".ui": "text", ".png": "dataurl" }`.

**`bundler.define` alias**: top-level `bundler.define` is auto-mapped to `bundler.transform.define` (canonical) with a one-time WARNING — without the alias the token survives as a bare identifier and crashes GJS at load with `ReferenceError`.

**App-build single-file invariant**: `--app gjs|node|browser` produces ONE bundle file — the entry is wrapped in a `\0gjsify-entry:<path>` virtual module (console shim + globals inject stub, then re-export) + `output.inlineDynamicImports: true`. Library mode (`--library esm|cjs`) preserves modules and imports.

**`--app browser` HTML entry (Vite-style)**: pass an `index.html` as entry → the CLI bundles the first local `<script type="module" src>`, then emits a processed `index.html` beside the bundle with the script src rewritten (POSIX-relative). CSS is NOT extracted — it travels in the JS bundle via css-as-string, injected by app code. Implemented as an engine-portable post-bundle CLI step (`applyBrowserHtml` — the native rolldown engine has no `emitFile`, so it can't be a plugin). Helpers `utils/html-entry.ts`; single-`.html`-input only; needs explicit `--outfile`. e2e `tests/e2e/browser-html-entry`.

**Per-package build cache — `--cached` (ADR 0006).** `gjsify workspace|foreach <script> --cached` skips build-ish scripts for workspaces with unchanged inputs, restoring stored outputs. Env default `GJSIFY_BUILD_CACHE=1`; explicit `--no-cached` wins; script mode only.
|key = sha256 over: layout version | script+args | toolchain salt (cli/tsc/rolldown/typescript versions) | the package's own input hash (`src/**` + package.json + root tsconfigs) | input hashes of the FULL transitive workspace-dep closure (composing closure hashes, not recursive keys, keeps keys well-defined on the cyclic dev graph). Keys pinned to run-START tree state (eager hashing).
|storage `node_modules/.cache/gjsify/build/<pkg>/<key>/`, 2 keys per package, oldest evicted.
|outputs: candidate dirs (`lib/`, `dist/`, `dist-templates/`) diffed against a pre-run snapshot; only what the script modified is stored/restored. Ownership is per output UNIT, not per candidate dir — a candidate holding only sub-directories expands to per-child units (`lib/esm`, `lib/types`); loose files ⇒ whole-dir. That distinction is load-bearing: `build:gjsify` writes `lib/esm`, `build:types` writes `lib/types`; whole-dir ownership would let a `build:gjsify` HIT wipe `lib/types` — the script never runs on a hit, nothing regenerates the `.d.ts`, and the package publishes a dangling `types` entry. Bump `BUILD_CACHE_LAYOUT_VERSION` whenever granularity changes.
|SAFETY (the v0.x clobber incident): a package without the script is never touched; a dir the build never modifies — a committed no-build `lib/` (`@gjsify/tsc`, `@gjsify/resolve-npm`) — is never recorded, so never restored over. All cache errors fail soft to an uncached run.
|opt-out `gjsify.buildCache: false` for builds writing OUTSIDE the candidates (set on `@gjsify/adwaita-web`, which generates into `src/`).
|impl `utils/build-cache.ts` (+spec) | e2e `tests/e2e/build-cache/` | CI persists the cache dir.

### `--globals` modes (GJS) — canonical, incl. the permanent invariants

|**auto (default)**: detection + verification. Pass 1 bundles in-memory via `rolldown(...).generate()` (unminified, no disk I/O); acorn parses each chunk for free identifiers (`Buffer`) + host-object member exprs (`{globalThis,global,window,self}.Buffer`) against `GJS_GLOBALS_MAP`. Per-chunk parsing (concatenation would duplicate top-level declarations and acorn rejects it) → union. The detected set is expanded via the COMMITTED **register-globals closure map** (`@gjsify/resolve-npm/register-globals-closure`, generated by `packages/infra/cli/scripts/generate-register-closure.mjs`): per register subpath, every global its bundled code transitively references — the static answer to what the legacy loop re-discovered one bundle at a time. Pass 2 verifies (subset convergence); a stale/missing closure entry is fail-soft: detection grows past the expansion and the loop keeps iterating (cap 5) with a regenerate hint. Typical build = 2 analysis bundles + final. Regenerate the map (`--check` = CI-style freshness diff) whenever a register module changes which globals it references or a register path is added to the map.
|**PERMANENT invariants** (learned, do not relitigate): (1) **analyse bundled output AFTER tree-shaking, never source.** Source-level approaches (regex, per-source AST via `transform`, metafile, inject-plugin shape) were tried + rejected — false positives from isomorphic guards (`if(typeof window!=='undefined')…`), dynamic-branch imports, bracket-notation access. The after-tree-shaking property is load-bearing and bundler-agnostic; do NOT reintroduce source scanning however good a new bundler's per-source parser is — Oxc is no exception. Detection stays on acorn over unminified bundled output. (2) **analysis passes MUST NOT minify** — the minifier wraps the bundle in an IIFE aliasing `globalThis` to a short var (`g.Blob`), defeating MemberExpression detection; `auto-globals.ts` passes `minify:false` to the inner build. (3) **detection is iterative** — tree-shaking creates a dependency cycle: pass 1 has no globals injected so global-gated code is shaken; injecting pulls NEW code referencing more globals; repeat until stable (cap 5). (4) **METHOD_MARKERS for monkey-patched APIs** — a register that patches a method on a host object (canonical: `gamepad/register` sets `navigator.getGamepads`; no free identifier appears) needs a `<host>.<method>` → identifier entry in `detect-free-globals.ts`.
|**auto,\<extras\>**: safety net for value-flow indirection the detector can't follow (Excalibur stores `globalThis` in `nativeComponent`, then calls `nativeComponent.matchMedia()`). Forms: `auto,dom` / `auto,FontFace,matchMedia` / `auto,dom,fetch` — extras seeded into pass 1. If auto injects a false positive: explicit list or file an issue.
|**explicit list / group aliases** `node`/`web`/`dom` (from `GJS_GLOBALS_GROUPS`): no auto-detect. **none**: disables injection.
|**`--app node` (reverse bridge)**: `auto` detects ONLY the GJS ambient globals (`print`/`imports` → `@gjsify/node-gi/globals`) — web/dom registers are NEVER auto-injected (plain-Node loadability guarantee for cross-platform packages). EXPLICIT identifiers (`auto,dom,XMLHttpRequest,…`) inject the SAME register modules the gjs target would AND lift the `@gjsify/empty` register routing + `@girs/*` emptying for that build (`enableGjsRegistersForNode`, gated on the inject stub) — how a genuine GJS app gets `document`/`HTMLCanvasElement`/XHR over node-gi. A plain-`auto` node build is byte-unchanged. Blueprint composes on the node target too (`--app node` runs REAL GTK). **The same lift also carries `REVERSE_BRIDGE_ENTRY_ROUTES`**: packages whose `node` export condition is not a node build of the same program but a DIFFERENT one. So far exactly `solid-js`, whose `node` (and `deno`, and `worker`) key is `dist/server.js` — the SSR build with an EMPTY `createEffect` — so the initial render was perfect and every reactive update silently never reached GTK, reddening 16 of `@gjsify/gtk-host`'s node-leg suites as `Expected ["second"], Actual ["first"]` while the identical source passed on gjs, read under ADR 0030 as a node-gi defect. A ROUTE, and NOT a `conditionNames` change, for two measured reasons: dropping `node` from the list does nothing (`platform: 'node'` implies it), and the lever that does work — `browser`, which outranks `node` in solid-js's map — is the symmetric defect. The gjs target affords `browser` only because `getAliasesForGjs` already replaced the node-facing npm packages; the reverse bridge keeps them real, and `ws` declares `browser` FIRST pointing at a one-line `throw new Error('ws does not work in the browser…')` — `pass 19/19` to `0/5 passed, 10 failed` in the node-gi consumer harness, every one `W.WebSocket is not a constructor`. One named package resolves differently; the resolve options themselves are byte-identical for both node build kinds, pinned by `packages/infra/cli/src/node-reverse-registers.spec.ts`.

Key files: `utils/detect-free-globals.ts` (acorn AST) | `utils/auto-globals.ts` (orchestrator) | `utils/scan-globals.ts` (explicit) | `resolve-npm/lib/globals-map.mjs`.

### GLib MainLoop

`ensureMainLoop()` (`@gjsify/utils`, re-exported from `@gjsify/node-globals`): idempotent, non-blocking, no-op on Node. Used in `http`/`net` `listen()`, `dgram.bind()`. **GTK apps MUST NOT use it** — an Adwaita/GTK app runs via `Application.runAsync()` (never sync `run()`: with a blocking run the promise-job queue starves and synchronous view loads hang on the spinner — the reason `runAdwaitaApp` exists).
