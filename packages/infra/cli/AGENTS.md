> Scope: this directory. Repo-wide rules live in the [root AGENTS.md](../../../AGENTS.md) — read that first.

> committed, and CI byte-compares it. The trap it leaves behind is different but not
> gone: `node_modules/.bin/gjsify` prefers an on-disk `dist/cli.gjs.mjs` over

> edited — and nothing in CI sees that any more. `gjsify run build` is the fix.

## CLI — commands & install invariants

```bash
gjsify foreach build|test|check           # each script across all workspaces, topologically
gjsify workspace @gjsify/<name> <script>  # one workspace; -d/--with-dependencies builds the dep closure first
gjsify run <script>                       # root script; gjsify run dist/gjs.js runs a bundle
gjsify run --node-script <file.mjs>       # an unbundled Node-style script, on the host runtime (bundled for GJS on the fly)
gjsify tsc …                              # Node-free tsc via the @gjsify/tsc bundle (args verbatim)
gjsify publish|whoami|login|logout        # Node-free npm publish/auth (npm-otp header, no web-OAuth)
gjsify trust [pkg] | gjsify onboard [--packages <glob>]  # Trusted-Publisher / publish+trust sweep, ANY monorepo
gjsify upgrade [--latest|--minor|--patch|--align|--check] [-p glob]   # workspace-wide dep upgrades; --check = CI drift gate
gjsify ship [linux|darwin|windows] [--target <fmt..>] [--stage]   # phase 1: assemble ONE staged payload for that OS's LAYOUT (ADR 0024)
gjsify ship --from-stage <dir> [--expect-target <os>-<arch>]   # phase 2: pack a stage, no project needed
gjsify install [--immutable|--refresh-lockfile] | gjsify dlx <pkg> | gjsify showcase <name> | gjsify storybook | gjsify debug
gjsify dev [entry] [--runtime <r>] [--script <s>]   # watch → rebuild → relaunch; the templates' `dev` script
gjsify prune [-g] [--dry-run]              # drop installed packages this host cannot use (ADR 0025)
```

**`gjsify dev` exists because `gjsify build --watch` cannot serve the host it is for**: that flag
drives rolldown's watcher API, which only the npm engine exposes (`bundler-pick.ts` throws under
`@gjsify/rolldown-native`), so the one suite proving watch works (`tests/e2e/build-watch`, driven
under Node) proves it only where Node is available. `dev` asks for no watcher API — `fs.watch`
plus an in-process `runCli(['build', …])` — and shares the loop with `gjsify storybook --watch`,
where it was written first (`utils/watch-loop.ts`). WHAT to build is not re-declared:
`utils/dev-plan.ts` reads the project's own `build:gjs`/`build:node` script and puts the CLI
flags on top, so the dev loop and `gjsify run build` cannot drift into different bundles.

**A command that SUPERVISES owes three things a one-shot command never does** — all three
paid for on the GJS host, with every Node test green (`utils/watch-loop.ts` holds the
measurements): `holdMainLoop()`, because nothing else keeps a GJS process alive once its entry
module settles; `markDaemonCommand()`, because `gjsify run`'s in-process fast path otherwise
exits on a resolution that is not completion; and an output filter, because the build's own
write is a change under the watched dir. `tests/e2e/dev-command` drives BOTH hosts — a
Node-only row cannot fail for any of it.

**`gjsify ship` writes `.deb` and `.rpm` ITSELF** — no `dpkg-deb`, no `rpmbuild`, no vendored
packer, because the packer has to run under GJS, offline, and on a Fedora CI image where
`dpkg-deb` does not exist. What that bought, and the defect `rpm`-as-an-independent-oracle caught
on the first artifact: [ADR 0024](../../../docs/adr/0024-ship-installable-artifacts.md) §
Implementation status.

**A FORMAT DECLARES WHERE IT CAN BE PACKED** (ADR 0024 § A3) — `FormatDescriptor.host` is
`finishOn`/`requiredTools`/`oracle`, and `flatpak` is the first that is not `'any'`. Four things
follow, each with a silent-failure story in
[docs/ship-formats.md](../../../docs/ship-formats.md): the gates fire BEFORE the project's `build`
script; `defaultFormatIds(os)` is a SECOND derivation from `FORMATS`, because a bare `gjsify ship`
must not demand `flatpak-builder` of every project that packaged a `.deb`; `deriveDepends` takes a
`DistroFormatId`, because a Flatpak has no `Depends:` field at all; and **`flatpak-builder
--show-manifest` is not a validator** (it took `buildsystem: "nonsense"` at exit 0). Flatpak's whole
content is one prefix row (`/app`) plus `buildsystem: simple` + `cp -a stage/.` — that is what
removes meson from the sandbox — and the six `gjsify.flatpak` BUILD keys have a per-KEY deprecation
window into `gjsify.ship.flatpak` that `flatpak init` resolves too (one-sided, it would silently
rewrite the manifest that command commits); the `AppMetadata` half is an alias and is NOT deprecated.

**AND WHICH OS'S LAYOUT IT WRAPS** — `FormatDescriptor.layoutOs`, NOT `host.finishOn`; `gjsify ship
<linux|darwin|windows>` picks the layout, `defaultFormatIds(os)` filters on both, and a bare
`gjsify ship` on Linux stays `deb` + `rpm`. `planStage` emits ONE prefix-relative plan and
`layout.ts`'s `place()` is the map — that split is what lets `tests/e2e/ship-layout` state the map
ITSELF and check § 2's "one payload, a handful of layouts" as an equality — restated by M2a as
*modulo the map PLUS an enumerated addition set*, never relaxed to a subset check. **A statement about a
SHIPPED ARTIFACT is not one about assembly**: reading § 4's runtime table, `--target` and
`assertPayloadMatchesArch` as if they were cost three measured defects, all in
[docs/ship-formats.md](../../../docs/ship-formats.md) § The layout axis — read it before touching
`layout.ts`.

**`gjsify ship` is TWO PHASES, and the boundary is a TYPE** (ADR 0024 § A2): `--stage` assembles and
writes `.gjsify-ship-stage.json`, a CLOSURE rather than a settings dump; `--from-stage <dir>` packs it
where no project exists. The packers take `PackSettings` — the half that crosses — so a
`settings.bundlePath` read added to `deb.ts` is a COMPILE error, not a manifest field nobody noticed.
Every omission from that closure fails silently at exit 0, which is why `tests/e2e/ship-from-stage`
DELETES the project between the phases; without the deletion a reach-back succeeds and proves nothing.

**`gjsify foreach -p` builds the CLI's OWN runtime closure serially first** — every child BOOTS the CLI, so a parallel sweep otherwise reads the `lib/` trees its siblings write (macOS run 31130155911). The set is DERIVED, and the two cheaper derivations were measured wrong: `utils/cli-runtime-closure.ts` carries both numbers.

**A `--app gjs` artifact is refused when the RUNTIME cannot load it, not when the bundler complains.** `utils/gjs-bundle-guard.ts` reads each emitted chunk's `imports` (the bundler's own module graph, both engines) and throws on any BARE specifier the target did not declare external — `node:` keeps its own message and its own symptom ("Unsupported URI scheme"), everything else gets "Module not found", because GJS's ESM loader has no node_modules walker and does not follow `exports` maps. The `node:`-only version of this guard missed the whole class: a `.tsx` with no JSX configuration makes oxc default to the automatic runtime with `importSource: "react"`, so the bundle carries `react/jsx-runtime`, rolldown reports `UNRESOLVED_IMPORT` as a WARNING, `gjsify build` exits 0, and `gjs -m` dies with `ImportError: Module not found: react/jsx-runtime`. The legitimate-vs-broken line is the one `rolldown-plugin-gjsify` draws a layer up and for the same reason: the guard asks the target's OWN predicate (`createGjsExternalsPredicate`) so a DECLARED external stays legitimate, and `chunk.imports` lists sibling CHUNKS by bare fileName, so the emitted set is excluded by name. Two companions: `utils/jsx-config.ts` REFUSES a `.tsx`/`.jsx` entry that configures no JSX at all before bundling anything (gjs only — on node/browser the react default is a legitimate answer), and `assertGjsBundleParses` syntax-checks the artifact when the effective setting PRESERVES JSX, the only way raw JSX reaches a bundle. Both JSX facts are measured, not read off the TypeScript docs: `bundler.transform.jsx` OVERRIDES tsconfig, and tsconfig `"jsx": "react-native"` — documented as preserving — is NOT preserved by oxc. The refusal leads with PRESERVE-plus-compiler and explicitly names `@gjsify/gtk-host` as the WRONG `importSource`: its `/jsx-runtime` is a TYPE surface whose `jsx()` throws by design, so recommending it would trade a build that fails for one that dies at the first element. The parse is conditional because it is not free: acorn over the repo's largest bundle (`dist/cli.gjs.mjs`, 6.8 MB) is ~850 ms. e2e `tests/e2e/jsx-config-gate/`.

**`gjsify system-check` asks the RUNTIME question about a GI library — its typelib, not its `.pc` file.** `pkg-config --modversion` answers "is the DEV package installed", the wrong question for a library an app merely LOADS on every distro that splits `-dev` out: measured on postmarketOS/aarch64, libadwaita 1.9.2 installed and running, `✗ libadwaita` under **Required**, exit 1. GTK4/libadwaita/libsoup3 resolve through `findSystemTypelib()` (`gi-typelib.ts` — the file `gi_repository_require()` itself resolves, same under GJS and Node, no `dlopen`); the VERSION still comes from pkg-config where it exists, so a bare `✓` means "library here, `.pc` absent". pkg-config stays sole oracle where the dev package IS the subject (`gobject-introspection-1.0` gates `g-ir-scanner`). **blueprint-compiler is checked ONCE**, via `checkBlueprintCompiler()`'s resolver; the `required` `checkBinary` twin was deleted — it missed on win32 (MSYS2 keeps it off PATH by design) and exited 1 with or without a `.blp` in the project.

**`gjsify system-check` also compares TYPES against the library, not just presence.** `@girs/*` types are generated ahead of time from ONE upstream release and loaded against whatever the host has, and GIRepository structurally cannot notice: it matches the API version (`4.0`) only, so a `Gtk-4.0.typelib` from GTK 4.12 and one from 4.23 both satisfy `gi://Gtk?version=4.0`. Measured on a maintainer workstation: host GTK **4.22.4**, `@girs/gtk-4.0@4.1.0` generated from **4.23.0**, `gjsify tsc` exit 0 on `Gtk.RestoreReason.RECOVER` (`@since 4.24`) and `TypeError: … is undefined` at runtime, with `✓ GTK4 (4.22.4)` printed beside it. The declaration to check against already existed — every `@girs/*` carries `libraryVersion` (ADR 0008 names it) and NOTHING read it. `checkTypeSkew()` is that missing half: `major.minor` only (a micro difference does not change the API set, and noise trains people to ignore output), `ahead` (compiles then throws — the direction worth reporting) vs `behind` (API you have is invisible), printed BEFORE the all-found early return because a skew is invisible to every presence check by construction. **Scope is a measured subset and not a policy choice**: `libraryVersion` is an upstream version only where the GIR declares a `<package version>`, else ts-for-gir emits the NAMESPACE version, which looks like one and is not — 12 real / 17 degenerate / 3 absent across 32 installed packages, and `@girs/gdk-4.0`'s `4.0.0` (GDK ships inside GTK) would otherwise report an 18-minor skew that does not exist. Hence an explicit binding table + `isDegenerate`, and a deliberate false NEGATIVE for a library genuinely at `<namespace>.0`. The 17 are unreachable from this field at all; closing them needs the installed library's own `.gir` (`status/open-todos.md`). Readers are injectable so every skew branch is unit-tested from any host — same reason `resolvePrebuildDirName` is pure.

**`gjsify install` (native backend, `install-backend-native.ts`) — semantics + invariants:**
|lockfile preservation: a resolve seeds itself with the versions pinned in `gjsify-lock.json` and only resolves new/changed deps — adding ONE package never bumps unrelated transitives. `--immutable` = frozen/CI; `--refresh-lockfile` = re-resolve all newest-in-range; mutually exclusive. Prefer `gjsify install <pkg>` over hand-editing the lock; if you must hand-merge, keep the diff to the new subtree.
|**os/cpu/libc — the tree is RESOLVED for every platform and INSTALLED for one.** `gjsify-lock.json` records each entry's platform DECLARATION (`os`/`cpu`/`libc`) and the VERDICT is recomputed per host at install time (`applyPlatformFilter`) — that split is what makes one committed lockfile install a per-host subset instead of a machine snapshot. `--os/--cpu/--libc` (npm's config keys) override the target, so one Linux box reviews the darwin/musl branches. REQUIRED + incompatible → EBADPLATFORM (`--force` installs it anyway); OPTIONAL + incompatible → `inert`: not downloaded, still locked, and `--force` deliberately does NOT lift it (npm ignores it there too). **Optionality belongs to the EDGE, is DERIVED as a fixpoint (`computeOptionalFlags`), and is never trusted from the file** — and a name a publisher lists in BOTH `dependencies` and `optionalDependencies` is OPTIONAL, npm's documented override. `@parcel/rust@2.16.4` declares all eight of its napi platform packages in both blocks, so a `dependencies`-only walk made `@parcel/rust-darwin-x64` REQUIRED and failed every Linux install of any tree containing parcel with EBADPLATFORM, while `npm install` on the same manifest exits 0 and records all eight as optional. It looked like a non-problem because the same napi shape is usually published in ONE block — measured: `oxlint`, `esbuild` and `rollup` list their bindings in `optionalDependencies` only, so they always installed fine, and `install-platform-filter`'s offline corpus is written that way too. Which block a publisher picks is not something this installer may assume. Both walks therefore go through `requiredDepEntries`, and the edge kinds are PERSISTED (lockfile **v4**) so the fresh-resolve path and the `--immutable` path cannot disagree about the same tree; a pre-v4 lockfile is still READ but never short-circuits the resolve. Tests: unit `install-optional-edges.spec.ts`; e2e `install-platform-filter` (the rules, offline fixture) + `install-optional-both-blocks` (the real published package, network-guarded).
|**the GJS bundler engine is topped up on a PROJECT install** (#1005): it is an OPTIONAL PEER of `@gjsify/cli` on purpose (a plain `npm install` on Node/win32 must not fetch Linux prebuilds), but npm 7+ skips optional peers and this backend does not resolve `peerDependencies` at all — so under GJS, where there is no npm `rolldown` fallback, `gjsify build` had nothing to load. `ensureProjectGjsEngine()` installs the engine set when `@gjsify/cli` is in the tree, **the host can run gjs** (NOT `isGjs()` — the launcher prefers the GJS bundle whenever `command -v gjs` succeeds, so a Node-installed tree is routinely GJS-built), no engine is reachable by the same walk the BUILD uses, and `--immutable` was not passed. **NOT recorded in the lockfile** (`installPackages` writes one only under `resolved && opts.lockfile`), so a consumer's `gjsify-lock.json` is never rewritten by it; under `--immutable` it warns and names the durable fix instead. ADR 0020 records the simpler shape (`optionalDependencies`) that would retire this policy entirely.
|**a non-usage failure must not leave through yargs' usage path.** `cli-app.ts` registers one `.fail()` handler; `cli-fail.ts` classifies on **`msg`**, not `err` (every validation/parse failure passes a string, only a handler rejection passes `null`), the usage branch `showHelp`s and **throws** (registering a handler removes yargs' own exit, and validation calling `fail()` does not stop the command — measured), and the runtime branch prints NOTHING because `index.ts` is the single printer. Note `@types/yargs` is 17 while `yargs` is 18, so the `msg: string` type is a lie the handler narrows past. `cli-fail.spec.ts` pins the routing against a real yargs instance so an upgrade that changes it reds a test instead of silently restoring the help dump.
|**the prefix is a write-only union until pruned** (ADR 0025): `applyPlatformFilter` keeps a foreign-platform package from being INSTALLED and nothing removed one an EARLIER install placed — a real user-global prefix held 420 MB of them, laid down by the CLI version that predated the filter (their VERSIONS are what prove accretion rather than a live filter defect). `gjsify prune` and an automatic pass after install/self-update remove exactly what `checkPlatform` says this target cannot use, so a pruned prefix converges on what a fresh install would place; a package declaring NO platform is never touched. **The automatic pass reads the MEASURED host and refuses outright when `--os/--cpu/--libc` is set** — inherited, those flags would make `install -g foo --os=darwin` delete every linux package in the user's shared prefix. `gjsify prune --os=darwin` stays legal: a request is not a side effect. Reachability ('nothing points at this') needs a root record no prefix carries yet — `status/open-todos.md`.
|non-destructive (ADR 0001): an install mutates ONLY `node_modules/`, `gjsify-lock.json`, XDG cache/global prefix, and (for `install <pkg>`) `package.json`. It NEVER deletes/overwrites a build artifact (`lib/`, `dist/`, committed bundles) or git-tracked files outside that set; cleaning is a separate explicit command (`gjsify run clear`). e2e: `install-non-destructive` + `install-workspace-source-safety`.
|concurrency (ADR 0001): prefix mutations run under the per-prefix cross-process lock (`node_modules/.gjsify-install-lock/`, mkdir-exclusive + stale-steal); shared XDG caches stay lock-free because every write is atomic tmp+rename.
|hang safety — an install must never hang forever, three layers: (1) `--timeout` wall-clock budget (default 30 min) aborts in-flight fetches; (2) the abort only rescues awaits that OBSERVE the signal — `extractTarball` takes none and a dropped Gio stream-close event under GJS wedges a decompress at 0% CPU — so each extract races a per-extract stall timer + the signal (`extractWithStallGuard`, 120s default, `GJSIFY_EXTRACT_STALL_MS`); (3) a hard-exit backstop force-exits after the budget + grace, so ANY residual never-settling await fails non-zero.
|version-skew: `warnOnCliVersionSkew` prints one actionable line when the running `@gjsify/cli` differs from the workspace pin — a mismatched CLI is the documented root of install stalls (lock discarded → full re-resolve → wedge-prone extract) and silent-wrong-builds; align via `gjsify self-update`.
|**bin entries honour `gjsify.bin`, and a GJS bin is a generated LAUNCHER, not a link.** `linkBins` reads the EXTRACTED package's manifest (npm's abbreviated packument does not carry `gjsify.*`, so a packument-only read structurally cannot see it) and hands `pickBinMap` the answer; `gjsify.bin` wins over npm `bin`, and only then does `writeBinEntry` emit the `sh` launcher carrying `buildNativeEnvPreamble` instead of the usual symlink — plain-Node bins keep the link path unchanged. This is not cosmetic: on a Node-LESS GJS host the npm bin's `#!/usr/bin/env node` is simply unrunnable (`env: can't execute 'node'`), and the dead shim took `gjsify build` down with it: "no usable bundler engine under GJS" on a host where the engine was correctly installed and loadable — because the launcher was then also the only thing exporting `GI_TYPELIB_PATH` for the engine's prebuild. Measured end-to-end on postmarketOS/aarch64 (musl, gjs 1.88, no node/npm/git): install → build → run now works through `node_modules/.bin/gjsify` with no hand-set env. **The second half of that reason expired with ADR 0021** and the rule did not: `activateNativePrebuilds()` now puts every detected prebuild on girepository's OWN typelib + library search paths in-process, so the CLI's engines no longer need the launcher at all (`gjs -m …/dist/cli.gjs.mjs build …` works with both variables deleted — `tests/e2e/launcher-free-build/`). Do NOT re-derive "the CLI cannot repair it from inside" from `LD_LIBRARY_PATH` being frozen at process start: that is true of ld.so and irrelevant, because girepository consults its own paths first. The launcher stays because a Node-less host still needs a runnable bin, and because `gjsify run <bundle>` hands prebuilds to a CHILD process, which only an environment can do. The three helpers (`pickBinMap`, `buildShLauncher`, `normalizeBinMap`) live in `bin-shim.ts` and are shared with `linkGlobalBins` — they were duplicated per-call-site before, and the drifted copy was exactly the one missing `gjsify.bin`.
