## CLI — commands & install invariants

```bash
gjsify foreach build|test|check           # each script across all workspaces, topologically
gjsify workspace @gjsify/<name> <script>  # one workspace; -d/--with-dependencies builds the dep closure first
gjsify run <script>                       # root script; gjsify run dist/gjs.js runs a bundle
gjsify tsc …                              # Node-free tsc via the @gjsify/tsc bundle (args verbatim)
gjsify publish|whoami|login|logout        # Node-free npm publish/auth (npm-otp header, no web-OAuth)
gjsify trust [pkg] | gjsify onboard       # Trusted-Publisher config / full first-publish+trust sweep (one shared OTP)
gjsify upgrade [--latest|--minor|--patch|--align|--check] [-p glob]   # workspace-wide dep upgrades; --check = CI drift gate
gjsify install [--immutable|--refresh-lockfile] | gjsify dlx <pkg> | gjsify showcase <name> | gjsify storybook | gjsify debug
```

**`gjsify system-check` also compares TYPES against the library, not just presence.** `@girs/*` types are generated ahead of time from ONE upstream release and loaded against whatever the host has, and GIRepository structurally cannot notice: it matches the API version (`4.0`) only, so a `Gtk-4.0.typelib` from GTK 4.12 and one from 4.23 both satisfy `gi://Gtk?version=4.0`. Measured on a maintainer workstation: host GTK **4.22.4**, `@girs/gtk-4.0@4.1.0` generated from **4.23.0**, `gjsify tsc` exit 0 on `Gtk.RestoreReason.RECOVER` (`@since 4.24`) and `TypeError: … is undefined` at runtime, with `✓ GTK4 (4.22.4)` printed beside it. The declaration to check against already existed — every `@girs/*` carries `libraryVersion` (ADR 0008 names it) and NOTHING read it. `checkTypeSkew()` is that missing half: `major.minor` only (a micro difference does not change the API set, and noise trains people to ignore output), `ahead` (compiles then throws — the direction worth reporting) vs `behind` (API you have is invisible), printed BEFORE the all-found early return because a skew is invisible to every presence check by construction. **Scope is a measured subset and not a policy choice**: `libraryVersion` is an upstream version only where the GIR declares a `<package version>`, else ts-for-gir emits the NAMESPACE version, which looks like one and is not — 12 real / 17 degenerate / 3 absent across 32 installed packages, and `@girs/gdk-4.0`'s `4.0.0` (GDK ships inside GTK) would otherwise report an 18-minor skew that does not exist. Hence an explicit binding table + `isDegenerate`, and a deliberate false NEGATIVE for a library genuinely at `<namespace>.0`. The 17 are unreachable from this field at all; closing them needs the installed library's own `.gir` (`status/open-todos.md`). Readers are injectable so every skew branch is unit-tested from any host — same reason `resolvePrebuildDirName` is pure.

**`gjsify install` (native backend, `install-backend-native.ts`) — semantics + invariants:**
|lockfile preservation: a resolve seeds itself with the versions pinned in `gjsify-lock.json` and only resolves new/changed deps — adding ONE package never bumps unrelated transitives. `--immutable` = frozen/CI; `--refresh-lockfile` = re-resolve all newest-in-range; mutually exclusive. Prefer `gjsify install <pkg>` over hand-editing the lock; if you must hand-merge, keep the diff to the new subtree.
|**os/cpu/libc — the tree is RESOLVED for every platform and INSTALLED for one.** `gjsify-lock.json` records each entry's platform DECLARATION (`os`/`cpu`/`libc`) and the VERDICT is recomputed per host at install time (`applyPlatformFilter`) — that split is what makes one committed lockfile install a per-host subset instead of a machine snapshot. `--os/--cpu/--libc` (npm's config keys) override the target, so one Linux box reviews the darwin/musl branches. REQUIRED + incompatible → EBADPLATFORM (`--force` installs it anyway); OPTIONAL + incompatible → `inert`: not downloaded, still locked, and `--force` deliberately does NOT lift it (npm ignores it there too). **Optionality belongs to the EDGE, is DERIVED as a fixpoint (`computeOptionalFlags`), and is never trusted from the file** — and a name a publisher lists in BOTH `dependencies` and `optionalDependencies` is OPTIONAL, npm's documented override. `@parcel/rust@2.16.4` declares all eight of its napi platform packages in both blocks, so a `dependencies`-only walk made `@parcel/rust-darwin-x64` REQUIRED and failed every Linux install of any tree containing parcel with EBADPLATFORM, while `npm install` on the same manifest exits 0 and records all eight as optional. It looked like a non-problem because the same napi shape is usually published in ONE block — measured: `oxlint`, `esbuild` and `rollup` list their bindings in `optionalDependencies` only, so they always installed fine, and `install-platform-filter`'s offline corpus is written that way too. Which block a publisher picks is not something this installer may assume. Both walks therefore go through `requiredDepEntries`, and the edge kinds are PERSISTED (lockfile **v4**) so the fresh-resolve path and the `--immutable` path cannot disagree about the same tree; a pre-v4 lockfile is still READ but never short-circuits the resolve. Tests: unit `install-optional-edges.spec.ts`; e2e `install-platform-filter` (the rules, offline fixture) + `install-optional-both-blocks` (the real published package, network-guarded).
|non-destructive (ADR 0001): an install mutates ONLY `node_modules/`, `gjsify-lock.json`, XDG cache/global prefix, and (for `install <pkg>`) `package.json`. It NEVER deletes/overwrites a build artifact (`lib/`, `dist/`, committed bundles) or git-tracked files outside that set; cleaning is a separate explicit command (`gjsify run clear`). e2e: `install-non-destructive` + `install-workspace-source-safety`.
|concurrency (ADR 0001): prefix mutations run under the per-prefix cross-process lock (`node_modules/.gjsify-install-lock/`, mkdir-exclusive + stale-steal); shared XDG caches stay lock-free because every write is atomic tmp+rename.
|hang safety — an install must never hang forever, three layers: (1) `--timeout` wall-clock budget (default 30 min) aborts in-flight fetches; (2) the abort only rescues awaits that OBSERVE the signal — `extractTarball` takes none and a dropped Gio stream-close event under GJS wedges a decompress at 0% CPU — so each extract races a per-extract stall timer + the signal (`extractWithStallGuard`, 120s default, `GJSIFY_EXTRACT_STALL_MS`); (3) a hard-exit backstop force-exits after the budget + grace, so ANY residual never-settling await fails non-zero.
|version-skew: `warnOnCliVersionSkew` prints one actionable line when the running `@gjsify/cli` differs from the workspace pin — a mismatched CLI is the documented root of install stalls (lock discarded → full re-resolve → wedge-prone extract) and silent-wrong-builds; align via `gjsify self-update`.
|**bin entries honour `gjsify.bin`, and a GJS bin is a generated LAUNCHER, not a link.** `linkBins` reads the EXTRACTED package's manifest (npm's abbreviated packument does not carry `gjsify.*`, so a packument-only read structurally cannot see it) and hands `pickBinMap` the answer; `gjsify.bin` wins over npm `bin`, and only then does `writeBinEntry` emit the `sh` launcher carrying `buildNativeEnvPreamble` instead of the usual symlink — plain-Node bins keep the link path unchanged. This is not cosmetic: on a Node-LESS GJS host the npm bin's `#!/usr/bin/env node` is simply unrunnable (`env: can't execute 'node'`), and because that launcher is ALSO the only place `GI_TYPELIB_PATH` can be exported before the GJS runtime boots (GI resolves the typelib before the bundle's first line — the CLI cannot repair it from inside), the dead shim took `gjsify build` down with it: "no usable bundler engine under GJS" on a host where the engine was correctly installed and loadable. Measured end-to-end on postmarketOS/aarch64 (musl, gjs 1.88, no node/npm/git): install → build → run now works through `node_modules/.bin/gjsify` with no hand-set env. The three helpers (`pickBinMap`, `buildShLauncher`, `normalizeBinMap`) live in `bin-shim.ts` and are shared with `linkGlobalBins` — they were duplicated per-call-site before, and the drifted copy was exactly the one missing `gjsify.bin`.
