# AGENTS.md — gjsify

IMPORTANT: Prefer retrieval-led reasoning over pre-training-led reasoning — consult `refs/` submodules and `@girs/*` types before pre-trained knowledge.

Node.js/Web/DOM API + Framework for GJS (GNOME JS). npm-workspaces monorepo, v0.26.1, ESM-only, GNOME libs. Bootstraps via the committed `packages/infra/cli/dist/cli.gjs.mjs` GJS bundle — `gjsify install --immutable` is the supported install path (no yarn / no Node-only npm CLI required at runtime). Pillars: **Node.js** `packages/node/` | **Web** `packages/web/` | **DOM** `packages/dom/` | **Framework** `packages/framework/` | **NativeScript bridge** `packages/nativescript-bridge/` | `packages/infra/` + `packages/gjs/` = supporting infra. Package counts, per-package status tables and metrics are DERIVED — authored status data in `status/`, rendered on demand by `npm run status:generate`, never here.

## Governance — non-negotiable

|doc: update AGENTS.md immediately on any architectural decision (package boundaries, API patterns, build, deps, cross-cutting) — never leave drift between sessions
|adr: decisions that span multiple pillars/repos, change a published contract (versioning, tiering, artifact strategy), or scope a whole track get an ADR under `docs/adr/` (numbered, MADR-style) BEFORE implementation; follow-up work tracked in `status/open-todos.md`; AGENTS.md still gets its update when the change lands
|tier: every published pkg declares `package.json#gjsify.tier` — 1 core (stability promise) / 2 product (best effort) / 3 experimental (no promise; new axes start here) per ADR 0003; deps+optionalDeps must point to same-or-lower tier (devDeps/optional peers are the seams; `@gjsify/node-gi` hard-deps forbidden per ADR 0005); enforced by `scripts/audit-runtimes.mjs --check` in CI; membership derived from the manifests (`npm run status:generate`)
|required checks: `main` is branch-protected and exactly THREE checks block a merge — **`CI gate (GJS)`** (`main.yml`), **`Detect runtime-triplet drift`** (`audit-runtimes.yml`), **`Lint commit messages`** (`commitlint.yml`). That set is not a preference: a required check that does not RUN on a PR blocks it forever ("Expected — waiting for status"), so only the three workflows with NO `paths:` filter on their `pull_request` trigger are eligible. Everything path-filtered (`node-gi`, `napi`, `prebuilds`, `deploy-docs`, `cli-cross-platform`) stays ADVISORY — read it before merging; it cannot be required without first moving its `paths:` from the trigger down to the jobs. Requiring a matrix leg by name is equally out: its check name carries the unexpanded `${{ matrix… }}` when skipped. **`CI gate (GJS)` is the only job in `main.yml` whose exit code is a verdict** — `ci-summary` reports and never gates (it was GREEN next to a red `Build Fedora 44` on #910, so requiring it buys a false green). The gate treats `skipped` as pass (selective CI working) and `cancelled` as fail (a superseded run demonstrated nothing), and its first step re-derives the job list from `main.yml` and fails if its own hand-written `needs:` misses one — a job outside the gate is a job that cannot block a merge. WHY AT ALL: with an empty required set `gh pr merge --auto` does not wait, it merges instantly; that is how #910 landed with 12 checks still running
|declarations: `gjsify.runtimes` (runtime axis), `gjsify.platforms` (OS axis), `gjsify.headless` (intra-GJS layering) and `gjsify.prebuilds` are per-package declarations, each MACHINE-CHECKED — full model + every invariant in § Runtime & platform model, which is authoritative. No declaration without a check; no promised prebuild target without a real, loadable artifact (or an explicit reasoned `platformsUncommitted` entry) behind it
|manifest-conformance: every "does this DECLARATION match reality" check is a RULE in ONE registry — `@gjsify/manifest-conformance` (`packages/infra/manifest-conformance/`, plain committed `lib/*.mjs`, NO build, the `@gjsify/resolve-npm` shape). Each rule declares the manifest `fields` it governs; the `field-coverage` rule DERIVES the set of `gjsify.*` keys declared across the tree and FAILS on any key no rule claims — a new declaration kind cannot be added without a check, which is the failure every rule here was written in reaction to. Honest escape: `scripts/manifest-conformance/unchecked-fields.mjs`, a key → REASON ledger (reason mandatory, printed every run, FAILURE the moment a rule claims the key or the field stops being declared). SCOPE decides where a rule lives: `portable` (manifest + files + binaries only — `package-outputs`, `prebuild-artifacts`, `headless`, `field-coverage`) lives in the package and is correct in any consumer tree; `repo` (`runtimes-drift`, `runtimes-reachability`, `curated-alias-routing`, `tier`, `platforms-ci`, `refs-pin`) knows THIS repo's layout and stays in `scripts/`. REGISTRATION ≠ SELECTION: `package-outputs` + `refs-pin` register (so coverage sees their fields) but are not selected by `audit-runtimes --check` (post-condition on a built tree / needs initialised submodules). **The CI gate stays a plain Node SCRIPT, never a CLI command**: `audit-runtimes.yml` runs `--check --strict` on EVERY `pull_request` with no `paths` filter, with NO install and NO build — routing it through the committed `dist/cli.gjs.mjs` would reintroduce exactly the staleness circularity `verify-committed-bundles.mjs` exists to break (a rule added in source but not rebuilt into the bundle would silently not run). `node scripts/audit-runtimes.mjs --rules` lists the registry

## Runtime & platform model

The ONE model for "where does this code run and who checks the claim". Four orthogonal axes, each a `package.json#gjsify.*` declaration with a machine check behind it. Everything else in this file references this section.

### The axes

|**Runtime axis — `gjsify.runtimes`**: quadruplet `{gjs, node, browser, nativescript}`, each slot ∈ {`polyfill`, `native`, `partial`, `none`}. Declares which JS RUNTIMES a package serves and how; says NOTHING about operating systems. NativeScript is the 4th slot (V8 on Android/iOS, metadata-driven native bridge — conceptually GJS↔GNOME with `java.io.File`/`NSFileManager` instead of `Gio.File`); optional `gjsify.nativescriptPlatforms: ['ios','android']` (default both) narrows capability WITHIN the slot — iOS/Android are deliberately NOT separate slots (NS itself ships one core with internal platform branching; if divergence ever forces a quintuplet, `VALID_TARGETS` in `runtime-aliases.mjs` is a 1-line change). If a package doesn't declare `nativescript`, the drift check skips that slot (backfill is opportunistic).
|**OS axis — `gjsify.platforms`**: the `<os>-<arch>` targets a pkg with a native build system (meson/node-gyp) or a prebuild dir PROMISES a prebuild for. ONE spelling everywhere: `${process.platform}-${process.arch}` (`linux-x64`/`linux-arm64`/`darwin-arm64`/`win32-x64`; `ppc64`/`s390x`/`riscv64` identical in every vocabulary) — it is what a running process computes about itself, so resolution needs no translation. The retired uname spelling (`linux-x86_64`) is enforced OUT on every WRITE path and tolerated READ-only (`prebuildDirCandidates` probes declared → canonical → legacy) so pre-rename tarballs still load. The two axes are blind to each other BY DESIGN, and that blindness is measured: the whole native-bridge set stayed Linux-only while the project described itself as platform-independent, because `runtimes` says nothing about OSes. Never let one axis answer the other's question.
|**Intra-GJS layering — `gjsify.headless`** (ADR 0015): a package that DOCUMENTS itself as headless declares either `true` (root entry reaches NO typelib: no `gi://`, no `@girs/*` value import, no bare `cairo`/`system`/`gettext`, no `imports.*`) or a LIST of forbidden typelib namespaces (`["Gdk","GdkPixbuf","Gsk","Gtk","Adw"]` — headless *of GTK*, Cairo/Pango still fine). `audit-runtimes --check` walks the ROOT import graph from `exports["."]` (relative imports AND `@gjsify/*` workspace edges) and fails on any forbidden reach. ROOT-ONLY IS THE POINT: a side-effect SUBPATH may legitimately reach them (`@gjsify/canvas2d-core/gdk`, imported explicitly by `dom-elements/register/canvas` + `canvas2d`) — scanning `src/**` would flag the fix itself. Why the axis exists: the runtime axis is structurally blind here — a `gi://Gdk` import is an INPUT to the drift check (it made the declaration agree BETTER), and the ADR-0014 reachability pass only visits `polyfill`/`partial` slots, which a `node:none`/`browser:native` package has none of. That blind spot is how `@gjsify/canvas2d-core` — split out of `@gjsify/canvas2d` precisely to be GTK-free — imported `gi://Gdk` (= `libgtk-4.so` in GTK4) at five call sites for its whole life. Declared today on `canvas2d-core` + `adwaita-core`; NOT on the pure-TS contracts (`stories`/`storybook-core`/`devtools-protocol`) whose all-`polyfill` slots ADR 0014 already enforces.
|**Build target — `--app gjs|node|browser|nativescript`**: how a BUILD selects a runtime; the alias layer routes each `@gjsify/<X>` per its declared slots (§ Slot routing). ONE `--app node` bundle serves node, bun AND deno (Node-API is their common ABI) — `--runtime <gjs|node|bun|deno>` on `gjsify showcase|run|storybook` selects the LAUNCHER, not a different bundle (shared map `packages/infra/cli/src/utils/runtimes.ts`). NB `gjsify.example.runtimes` (which runtimes a showcase SHIPS artifacts for, § Showcase) is a distinct field from `gjsify.runtimes` (slot routing).

### OS axis enforcement — declared vs built vs loadable

`scripts/audit-runtimes.mjs --check` holds, per native package:
|three DECLARATION invariants: a committed `prebuilds/<target>/` is declared · a declared target is produced by a CI job · a pkg shipping prebuilds has a workflow that reproduces them (a hand-built binary nothing rebuilds drifts from its sources in silence). Declared-vs-built is symmetric — changing CI forces changing the declaration and vice versa. `--platforms` renders the OS × package matrix (`--markdown` feeds the website's Platform Support page). **These three compare declarations to EACH OTHER, so all stay green on a promise with nothing behind it** — a target with no directory is simply absent from the compared "shipped" set, which is how `@gjsify/oxfmt-native` declared `darwin-arm64` with no artifact for weeks. Hence:
|the prebuild-ARTIFACT invariant: for every pkg naming a committed `gjsify.prebuilds` dir, each declared target is OPENED. (1) EXISTENCE: `prebuilds/<target>/` exists and holds a shared library in that OS's format (`.so`/`.dylib`/`.dll`) plus the `.typelib` without which `GI_TYPELIB_PATH` resolves nothing. (2) LOADABILITY, because a directory that exists proves nothing (#832: a required macOS job built two bridges and only COPIED them; the bug was a missing sibling FILE reading exactly like a broken rpath) — STRUCTURALLY on every artifact regardless of target (the image's own machine matches its directory; every `libgjsify*` sibling staged + reachable via `$ORIGIN`/`@loader_path` per the shared `binary.mjs` parser; every library leaf the TYPELIB records present, since that leaf is what GI hands to `dlopen`), and FUNCTIONALLY — a real env-free `dlopen` — only for the checking host's OWN `${process.platform}-${process.arch}`. A cross-arch prebuild CANNOT be loaded on a Linux runner and the audit does not pretend otherwise: both counts are printed separately every run, and a bridge whose SYSTEM deps the runner lacks is reported as not-load-tested, never as broken. The ONE binary parser (Mach-O/ELF/PE + GI typelib) lives in `@gjsify/manifest-conformance` `lib/binary.mjs`, re-exported by `scripts/check-prebuild-loader-path.mjs` — extend it, never add a second.
|escape hatch `gjsify.platformsUncommitted: {"<target>": "<why>"}` — declared AND CI-built but deliberately not committed here (today: `@gjsify/napi` darwin-arm64, uploaded by `napi.yml` for a release to ship). Deliberately awkward to abuse: the reason is mandatory and PRINTED every run, the target must already be in `gjsify.platforms` (you can only defer what you promise), and the entry becomes a FAILURE the moment the directory appears. An honest "not shipped here" is available; a silent gap is not.
|CI parsing: `parseCiPlatforms()` reads `prebuilds.yml`'s matrix as STATIC YAML (job `runs-on` → OS, `arch:` entries filtered to tokens that actually name a CPU, so an `arch:` that is an ACTION INPUT cannot become a phantom `linux-none` target) — an expression-driven matrix hides the arch tokens and fails all ten native packages; teach the parser first if it ever has to become dynamic. A target is attributed to a package when a STEP names the package AND carries a production verb — moving a build script into a file is safe, deleting the per-package upload steps is not.

### Slot routing — how `--app <target>` resolves `@gjsify/<X>`

Implemented by `packages/infra/resolve-npm/lib/runtime-aliases.mjs`: reads each package's declared quadruplet at config time and emits a derived alias map COMPOSED UNDER the hardcoded `ALIASES_*_FOR_*` baseline (hardcoded wins on conflict).
|rules: `polyfill` → `@gjsify/<X>/<target>` when the package's `exports` declares that platform-entry subpath (ADR 0014, e.g. `@gjsify/os` → `@gjsify/os/browser`), else no rewrite · `partial` → NO rewrite (the shared impl's degradation IS the contract; VALUE-export parity with the root is the promotion gate to `polyfill`, machine-checked by `platform-entry-parity`) · `native` → `@gjsify/<X>/globals` (re-exports the runtime-native value) · `none` → `@gjsify/empty`.
|ONE hop, deliberately: the map `aliasPlugin` receives is already merged flat across four tiers (derived → curated `ALIASES_*` → per-target overrides → user `--alias`, later wins) and resolves each alias target in exactly one hop (`skipSelf: true`). A resolver CHAIN would apply slot routing to USER aliases — `--alias node:stream=@gjsify/stream` (the node-gi consumer harness's entire mechanism; 34 polyfills declare `node:"native"`) would bounce to `@gjsify/stream/globals` = Node's own builtin, and the suite would measure nothing. Measured: chaining changes 0 of 114 `gjs` and 0 of 148 `node` entries; the only 4 changes on `nativescript` are regressions — which is why `ALIASES_NODE_FOR_NATIVESCRIPT` is deliberately NOT composed (a bridge declaring `nativescript:"native"` in the "I AM the native impl" sense routes to a `globals.mjs` it does not ship → `@gjsify/empty`; open TODO). Composing a table is an explicit per-table decision.
|`aliasPlugin` NEVER rewrites an import whose importer is a `\0gjsify-*` virtual module (`isGjsifyVirtualModuleId`) — gjsify-generated module bodies name the RUNTIME module they need; a user `--alias node:module=…` reaching `gjsGiNodePlugin`'s `createRequire` import once made `@gjsify/module` unbuildable on every runtime.
|a `native`-declared package missing its `globals.mjs` falls back to `@gjsify/empty` with a warn-once naming the gap.
|**a `partial` package's CURATED alias must name its `./<target>` subpath, never the package root.** `partial` is not rewritten by the derived layer, so a curated bare `@gjsify/<X>` hands the bundler the GJS body with `@girs/*` emptied to `{}` — `partial` degrading into "crashes at first use" instead of "degrades at call time" (this shipped for `crypto` + `zlib`). Naming the subpath is only safe at value-export parity, so it stays a per-package curated decision. Machine-checked FATAL by `curated-alias-routing`: no curated bare-specifier alias may resolve to the root of a package that ships a `./browser` entry.
|**the ten `browser:"partial"` slots are RESOLVED as partial, not pending**: `crypto` `dns` `fs` `http` `https` `module` `sqlite` `worker_threads` `ws` `zlib` each ship a real `src/browser.ts`; eight of the ten already MEET the parity gate (only `fs` −34 and `https` −2 do not), yet none is promotable — in every case a named export is unavailable on the browser platform ITSELF (no DNS resolver, no inbound socket, no TLS socket below JS, no synchronous CJS loader, no synchronous WebCrypto digest, no synchronous CompressionStream, no synchronous MessagePort drain, no file-change notification API, no SQLite engine). Each package's row in the Node table names its blocking export. **Corollary: parity is necessary but NOT sufficient** — it passes `sqlite`, whose `DatabaseSync` throws from its constructor; a green `platform-entry-parity` is not a promotion mandate. A routed entry must also have no unconditionally-throwing value export.
|**every browser redirect is NAMED; `@gjsify/empty` is a last resort that must carry a CLASSIFICATION.** `@gjsify/empty` is an anonymous, export-less `export default {}` shared by a dozen unrelated specifiers: in an emitted bundle a DELIBERATE stub is indistinguishable from an ACCIDENTAL alias (the camouflage that let `@gjsify/canvas2d`'s build emit a stray `@gjsify/empty` import unnoticed), and rolldown makes a named import from it a HARD ERROR that blames the empty module, not the module the user imported. So `ALIASES_NODE_FOR_BROWSER_TABLE` names `@gjsify/<X>/browser` wherever an entry exists, and each remaining `@gjsify/empty` carries an inline tag: **(A)** wireable now (`dns/promises`, blocked on a `./browser/promises` subpath) · **(A')** native-available, wants a `/globals` re-export not an empty module (`node-fetch`, `isomorphic-ws`) · **(B)** simulatable but unbuilt (`cluster`→Web Workers, `dgram`→WebRTC data channels, `v8.serialize`→`structuredClone`, `readline`→any stream, `tty.isatty`→`false`) · **(C)** impossible (`http2`, `inspector`; `repl`/`wasi` have no owning package to host a stub). An untagged `@gjsify/empty` is the bug — the tag makes remaining work visible instead of implied.
|**`(C)` gets a NAMED THROWING STUB at `@gjsify/<X>/browser` and the package KEEPS `runtimes.browser:"none"`** (today: `child_process`, `net`, `tls`). The stub exports the module's REAL named shape (the root's value exports — the same `collectValueExports` oracle parity uses) so linking succeeds, and throws a structured `ENOTSUP` naming the MODULE, RUNTIME and CALLING SITE (`err.gjsifyModule`/`gjsifyRuntime`/`gjsifyImporter`; the importer frame is fixed by construction since `unsupported()` is only called from an exported binding). `none` stays honest — the stub does not make the module usable, it makes the unusability legible. Exports whose answer IS platform-independent stay REAL (`net.isIP*`, `tls.checkServerIdentity`, the RFC constant tables, `hasOcspSupport()`→`false`); a blanket thrower would replace one lie with another. The throw helper is deliberately LOCAL per file (a browser platform entry imports NOTHING and cannot leak GJS) — lift to `@gjsify/utils/core` once it grows past a handful. A `(C)` stub self-declares with the `Slot: browser:"none"` marker so `audit-runtimes`' `browser_src_is_unsupported` signal doesn't read the mere existence of `src/browser.ts` as a promotion to `polyfill`.

### Strategy & portability portfolio

GJS = primary target, NON-NEGOTIABLE. Long-term: "alles unter allem lauffähig" — share what's shareable across GJS / Node / browser / NativeScript; runtime-specific where not. **Opportunistic, not driven**: existing GJS-bound packages stay GJS-only (no refactor budget; NO "while-I'm-here" scope creep in bug-fix PRs); NEW packages whose impl is pure-TS-portable get cross-runtime treatment from day one; GJS remains the test driver for everything (the only runtime where all three pillars need polyfill).
|the six axes: **1** Node-API (`packages/node/*`) · **2** Web-API (`packages/web/*`) · **3** DOM (`packages/dom/*`) · **4** design-identity — carry a runtime's design system to OTHER runtimes: `@gjsify/adwaita-{web,fonts,icons}` → browser, `@gjsify/adwaita-nativescript` → real NS widgets, shared behavior lifted into headless `@gjsify/adwaita-core` (ADR 0004) · **5** platform-bridge — carry a runtime's NATIVE platform to OTHER runtimes: `@gjsify/iframe`/WebKit precedent; ACTIVE tracks node-gi + napi (§ Cross-runtime tracks); GTK-on-browser stays a non-goal (design-identity is the right tool) · **6** bundled toolchains (§ Cross-runtime tracks).
|**new-package convention — the runtime axis is the FIRST clarification question**: (a) `gi://`/`@girs/*` value-imports → GJS-only (`runtimes.{node,browser}:"none"`); (b) pure TS, no platform-native deps → all-`polyfill` from day one, tested on all runtimes; (c) native runtime equivalent exists → declare `"native"` for that slot, ship `<pkg>/globals` (Node) or browser-conditional export. Canonical exemplars to mirror (package.json + `src/test.{mts,browser.mts}` layout): `@gjsify/dom-events` (`{gjs:polyfill,node:polyfill,browser:native,nativescript:native}`); `@gjsify/abort-controller`/`@gjsify/dom-exception` (same but `node:native` + `globals.mjs`).
|`@gjsify/utils` split (ADR 0014): `@gjsify/utils/core` = the cross-runtime half (pure + GJS-guarded: `makeCallable`, `deferEmit`, `initErrorV8Methods`, `gio-errors` errno map, `registerGlobal`, `notImplemented`/`warnNotImplemented`, `queueMicrotask`, `structuredClone`, `nextTick`, `ensureMainLoop`/`quitMainLoop`); the barrel adds the six GJS-only modules (`byte-array`, `cli`, `file`, `fs`, `gio`, `path`). A package whose `browser`/`nativescript` slot is `polyfill`/`partial` MUST import `/core` — importing the barrel is a DECLARATION that it reaches GLib/Gio; `audit-runtimes --check` enforces it. Split on measured imports, never on module name (`gio-errors.ts` is pure despite the name).
|universal `-core` split (convention, not mandate): logic shared by ≥3 runtimes MAY split into platform-agnostic core + thin adapters — but a `/core` SUBPATH is the DEFAULT over a new `-core` PACKAGE: a new published `@gjsify/*` name needs a tier, a quadruplet and the manual first-publish + Trusted-Publisher bootstrap (§ Package convention), and skipping that breaks the serialized release train for every alphabetically-later package. A separate package only for a genuine cycle or independent external consumers (`@gjsify/canvas2d-core`).
|**graduation** (2026-05-28): axes 1–4 are OUT of experimental status — document them per-axis, and describe what is validated BY NAME (integration suites, Playwright browser tests, autobahn, named showcases); never blanket "WinterCG-compatible"/"Node-compatible runtime" claims. Axis 5 pre-graduation. The per-package slot tables + audit drift are derived from the manifests, which are the single source of truth.
|non-goals: turning gjsify into a runtime; replacing Node/browser-native APIs where they exist; spec conformance beyond what a correct polyfill needs; tracking `refs/node-gtk` as a live fork (read-only derivation source); refactoring existing GJS-bound packages cross-runtime.

### Bridge pattern

Pairings: `HTMLCanvasElement`(2d)→`Canvas2DBridge`→`Gtk.DrawingArea`(Cairo) | (webgl)→`WebGLBridge`→`Gtk.GLArea`(libepoxy) | `HTMLIFrameElement`→`IFrameBridge`→`WebKit.WebView` | `HTMLVideoElement`→`VideoBridge`→`Gtk.Picture`(gtk4paintablesink).

Protocol: (1) bridge creates the DOM element internally (2) app uses standard DOM API (3) bridge translates GTK↔Web lifecycle (signals/draw_func/render ↔ rAF/events/ready). Each bridge owns an isolated `BridgeEnvironment`. Common API: `onReady(cb)`, `installGlobals()`, element getter, `environment`. DOM backing: Image→GdkPixbuf | Canvas2D→Cairo.ImageSurface+PangoCairo | WebGL→Gtk.GLArea+libepoxy | IFrame→WebKit.WebView | Video→Gtk.Picture+GStreamer.

`WebGLBridge` on resize: dispatches DOM `resize` + re-invokes the last rAF callback (demand-driven re-render, no animation loop). `WebGL2RenderingContext` overrides `texImage2D`/`texSubImage2D`/`drawElements` from the WebGL1 base (bypasses WebGL1 format/type validation); native Vala handles all GLES 3.2 formats.

**HiDPI is NOT symmetric between the two canvas bridges, and the asymmetry is the whole bug class.** GTK silently pre-scales a `Gtk.DrawingArea`'s Cairo context, so Canvas2D code written in logical pixels renders sharp with nothing to do. `Gtk.GLArea` does not: its framebuffer is `allocation × scale-factor` and `gl.viewport` is raw device pixels. So the GL side must report the DRAWING BUFFER in device pixels (`canvas.width`/`height`, hence `gl.drawingBufferWidth`) while CSS layout size stays logical (`clientWidth`/`offsetWidth`), and `installGlobals()` publishes `devicePixelRatio` as an ACCESSOR over the widget's live `get_scale_factor()` — the identity `clientWidth × devicePixelRatio === canvas.width` is what makes an unmodified Three.js/Excalibur viewport cover the whole framebuffer. Reporting the allocation as `canvas.width` (as it did until 2026-08) is invisible at scale-factor 1 — every desktop, CI runner and test VM — and on the first scale-factor-3 host drew each scene into the bottom-left NINTH of its widget: measured on a OnePlus 6T / postmarketOS / GNOME Mobile, where the teapot, the pixel-postprocessing and the Excalibur showcases all rendered a 120×218 corner of a 360×655-logical widget. `@gjsify/dom-elements`' register seeds `devicePixelRatio: 1` as the widget-less default only. A real `Gtk.GLArea` cannot regression-test this (its host reports 1); `html-canvas-element.spec.ts` varies the scale factor through a stub, which is the point of that stub.

## NativeScript Bridge — `packages/nativescript-bridge/*`

Native API wrappers for the NativeScript (Android/iOS) runtime slot. Packages here use `java.*`/`NS*` globals exposed by the NS V8 runtime — analogous to `packages/framework/*` using `gi://`. `runtimes.nativescript:'native'`, all other slots `'none'`.

**Convention:** pure TS, no `gi://`/`@girs/*` value imports. Platform detection via `typeof java !== 'undefined'` (Android) / `typeof NSFileManager !== 'undefined'` (iOS); `assertNativeScript()` throws `'Platform not supported'` off-NS — specs exploit this to run on GJS + Node without a device.

**`@nativescript/core` value imports — the UI-widget exception.** `fs`/`platform` bridges key on runtime globals only and import nothing from `@nativescript/core`. UI-widget bridges (`adwaita`) DO `import { GridLayout, … } from '@nativescript/core'` to subclass real NS views — the NS analogue of framework packages importing `@girs/*` classes. `@nativescript/core` is an OPTIONAL peer, NOT in the workspace install, so a local ambient `src/ns-core.d.ts` declares the narrow slice used (real types win when a consumer installs them) and `gjsify tsc` stays green off-device; bundler-context globals in `src/ns-globals.d.ts`. **Consequence for specs:** a widget module's `extends GridLayout` evaluates the bare specifier at module-eval — unresolvable off NS — so specs must NOT import widget classes (nor the re-exporting package root); they import only the NS-core-free surface and validate against mocks.

### `--globals` modes (GJS) — canonical, incl. the permanent invariants

|**auto (default)**: detection + verification. Pass 1 bundles in-memory via `rolldown(...).generate()` (unminified, no disk I/O); acorn parses each chunk for free identifiers (`Buffer`) + host-object member exprs (`{globalThis,global,window,self}.Buffer`) against `GJS_GLOBALS_MAP`. Per-chunk parsing (concatenation would duplicate top-level declarations and acorn rejects it) → union. The detected set is expanded via the COMMITTED **register-globals closure map** (`@gjsify/resolve-npm/register-globals-closure`, generated by `packages/infra/cli/scripts/generate-register-closure.mjs`): per register subpath, every global its bundled code transitively references — the static answer to what the legacy loop re-discovered one bundle at a time. Pass 2 verifies (subset convergence); a stale/missing closure entry is fail-soft: detection grows past the expansion and the loop keeps iterating (cap 5) with a regenerate hint. Typical build = 2 analysis bundles + final. Regenerate the map (`--check` = CI-style freshness diff) whenever a register module changes which globals it references or a register path is added to the map.
|**PERMANENT invariants** (learned, do not relitigate): (1) **analyse bundled output AFTER tree-shaking, never source.** Source-level approaches (regex, per-source AST via `transform`, metafile, inject-plugin shape) were tried + rejected — false positives from isomorphic guards (`if(typeof window!=='undefined')…`), dynamic-branch imports, bracket-notation access. The after-tree-shaking property is load-bearing and bundler-agnostic; do NOT reintroduce source scanning however good a new bundler's per-source parser is — Oxc is no exception. Detection stays on acorn over unminified bundled output. (2) **analysis passes MUST NOT minify** — the minifier wraps the bundle in an IIFE aliasing `globalThis` to a short var (`g.Blob`), defeating MemberExpression detection; `auto-globals.ts` passes `minify:false` to the inner build. (3) **detection is iterative** — tree-shaking creates a dependency cycle: pass 1 has no globals injected so global-gated code is shaken; injecting pulls NEW code referencing more globals; repeat until stable (cap 5). (4) **METHOD_MARKERS for monkey-patched APIs** — a register that patches a method on a host object (canonical: `gamepad/register` sets `navigator.getGamepads`; no free identifier appears) needs a `<host>.<method>` → identifier entry in `detect-free-globals.ts`.
|**auto,\<extras\>**: safety net for value-flow indirection the detector can't follow (Excalibur stores `globalThis` in `nativeComponent`, then calls `nativeComponent.matchMedia()`). Forms: `auto,dom` / `auto,FontFace,matchMedia` / `auto,dom,fetch` — extras seeded into pass 1. If auto injects a false positive: explicit list or file an issue.
|**explicit list / group aliases** `node`/`web`/`dom` (from `GJS_GLOBALS_GROUPS`): no auto-detect. **none**: disables injection.
|**`--app node` (reverse bridge)**: `auto` detects ONLY the GJS ambient globals (`print`/`imports` → `@gjsify/node-gi/globals`) — web/dom registers are NEVER auto-injected (plain-Node loadability guarantee for cross-platform packages). EXPLICIT identifiers (`auto,dom,XMLHttpRequest,…`) inject the SAME register modules the gjs target would AND lift the `@gjsify/empty` register routing + `@girs/*` emptying for that build (`enableGjsRegistersForNode`, gated on the inject stub) — how a genuine GJS app gets `document`/`HTMLCanvasElement`/XHR over node-gi. A plain-`auto` node build is byte-unchanged. Blueprint composes on the node target too (`--app node` runs REAL GTK).

Key files: `utils/detect-free-globals.ts` (acorn AST) | `utils/auto-globals.ts` (orchestrator) | `utils/scan-globals.ts` (explicit) | `resolve-npm/lib/globals-map.mjs`.

## Don't patch — implement at the source

We own ~every Web/Node/DOM API. First question for any new feature: *"which package owns this, can we implement it there?"* — never *"where can we monkey-patch it in?"*. Patching propagates uncertainty ("which code installed this?"); first-class methods are self-documenting.

**Hard rules:**

- **Reading globals:** prefer `import { X } from '@gjsify/<pkg>'` over `(globalThis as any).X` in impl code. Imports give bundlers tree-shaking visibility, TS real types, surface missing deps as build errors. `globalThis` reads only justified for: (1) writes in register modules; (2) existence probes in register modules (`if (typeof globalThis.X === 'undefined') { globalThis.X = X }`); (3) debug flags (`globalThis.__GJSIFY_DEBUG_X`); (4) GJS runtime bootstrap (`globalThis.imports.*` before `@girs/*` resolves); (5) genuinely soft deps (rare — fallback to `Error` if `DOMException` not registered); (6) `globals.mjs` Node adapter — re-exports native value (`export default globalThis.crypto`) so alias layer can redirect bare specifiers on Node. Only non-register file allowed to read `globalThis.X` without `as any`.
- **The legacy `imports.*` object is NOT an API — it is the GJS host, and the node target does not have it.** `gi://<Ns>` and the bare `system`/`gettext`/`cairo` built-ins resolve on BOTH gjs (externals) and node/bun/deno (aliased to `@gjsify/node-gi/*` and rewritten to `requireGi`); `imports.gi.X` / `imports.system.X` / `imports.byteArray.X` resolve on gjs ONLY, and off it they are a bare-identifier `ReferenceError` — thrown at the CALL, so the package tests green and the failure surfaces in a consumer. `@gjsify/node-gi/globals` seeds them, but it is injected only when a bundle is DETECTED to need them, so a package that reaches for `imports` is making its own correctness depend on a build-time prediction about somebody else's bundle. Three shipped bugs, all the same shape: `@gjsify/canvas2d-core`'s `_toDataURL` (`imports.gi.Gio` → `ReferenceError` at the first `toDataURL()` on node/bun/deno), `@gjsify/fetch`'s root-relative rewrite (`globalThis.imports.system.programPath` → probe `undefined` → every `fetch('/res/…')` died with `ERR_INVALID_URL`, while `@gjsify/xmlhttprequest` and `@gjsify/dom-elements` did the IDENTICAL rewrite through `import System from 'system'` and worked), and `@gjsify/crypto`'s `fillRandom` (bare `imports.gi.GLib` inside a `try`, so the `ReferenceError` was CAUGHT and silently degraded to `Math.random()`). Portable replacements exist for every one: `gi://Ns` · `import system from 'system'` · `GLib.Bytes.prototype.toArray()` (the GJS core override, mirrored by node-gi) instead of `imports.byteArray.fromGBytes` · `TextDecoder` instead of `imports.byteArray.toString`. Rule (2) above still allows the `globalThis.imports?.gi?.X` PROBE shape for a genuine runtime check — it is `undefined` off GJS instead of throwing, and the ambient-globals detector deliberately ignores it so it cannot drag the native addon into a cross-platform bundle. Never the bare form, and never a probe inside a `catch` that hides which runtime you are on. Enforced TWICE, at different layers: at the SOURCE by the `no-restricted-globals` lint rule (`.oxlintrc.json` — `imports`/`ARGV`/`print`/`printerr`/`logError` are errors across `packages/**`, with genuine GJS PROGRAM sources — examples/showcases/tests/node-gi/napi, where a bare ambient global is exactly the auto-globals-injection signal — scoped out by an override; the probe shape and an explicit in-file `declare` stay silent by construction), and at the ARTIFACT by `node-bundle-guard.ts` (§ Committed-artifact freshness), which still catches whatever reaches a `--app node` bundle by any other route. On its first run the lint rule found two more live members beyond the three shipped bugs (`@gjsify/webrtc`'s `isDeviceMonitorSafe` — a bare `imports.gi.GLib` inside a swallowing `catch`, the crypto shape again — and the `runAsync([imports.system.programInvocationName, ...ARGV])` line triplicated across `@gjsify/{adwaita-app,storybook,devtools-browser}`; portable spelling `[system.programArgs]`, which is what ARGV IS on gjs).
- **Patching classes you own:** method belongs to a monorepo class (`URL.createObjectURL`→`@gjsify/url`, `Headers.getSetCookie`→`@gjsify/fetch`) → put it on the class, NOT on `globalThis.X.method=…` in a register module. Patch only when target is genuinely external (native global we can't subclass, third-party type).
- **"No module to import from":** check again — workspace almost certainly has `@gjsify/dom-*`/`@gjsify/web-*`/`@gjsify/node-*` exporting the class. Add the dep. Legit exceptions: (a) pre-registration bootstrap; (b) values with no module form (GJS `imports`, Node's `process.argv` before `@gjsify/process` loads).
- **Pure-JS → native swap:** before replacing a pure-JS impl with a (partly) native one in any pkg, ask: *is the pure-JS path still load-bearing on browser / Node / NativeScript?* If yes — KEEP the pure-JS code, lift it into a `-core` (or `/core` subpath) package that the native pkg depends on as a fallback. Native goes in front for the runtime that has it; the core stays as the default for the others. Mirrors `@gjsify/canvas2d-core` ⇆ `@gjsify/canvas2d` (Cairo-backed). Never delete portable code just because one platform got faster; the others still need it. The `/core` SUBPATH is the DEFAULT choice over a new `-core` PACKAGE: a new published `@gjsify/*` name needs a tier, a runtime quadruplet and a MANUAL npm first-publish + Trusted Publisher bootstrap, and skipping it breaks the serialized release train for every package after it alphabetically (the `@gjsify/tls-native` v0.4.20 incident: 60+ packages stuck). Reach for a separate package only when there is a genuine package-level CYCLE to break or independent external consumers (`@gjsify/canvas2d-core`). Exemplar: `@gjsify/utils/core` (ADR 0014).

## Code anti-patterns — measured

Recurring shapes LLM-written code gets wrong (cf. GNOME reviewers' list, 2026-07). Every rule below has been paid for in THIS repo — the incident is the rule, and the linked mechanism is what keeps the class visible.

|**try/catch around a call that cannot throw.** Before wrapping, answer: *can this block throw at all?* For GI calls read the GIR — only `throws="1"` functions raise a GError→JS exception; a method that reports failure via a return code cannot throw, and "best-effort" is ignoring a return value, not wrapping a non-throwing call. A kept catch must STATE ITS REASON. Measured (#880, the `eslint/no-empty` sweep): the empty catch around the http2 teardown GOAWAY flush hid that the flush never wrote (the flag it was called after made it early-return — the peer only ever saw a bare FIN); try/catches around `GLib.Source.destroy` (no throw path) and around SessionBridge calls that report via return codes were deleted; the legitimate swallows (Gio close/shutdown on an already-dead peer, temp-cert cleanup, spec teardown) now say why. `eslint/no-empty` is `error` — a bare `catch {}` does not land. The worst variant swallows a `ReferenceError` from a missing binding into a silent wrong answer (see the `crypto` `Math.random()` incident above and § CJS-ESM rule 1).
|**paranoid probes for what the workspace guarantees.** Redundant `x?.m?.()` / `typeof x.m === 'function'` on our own classes or lockfile-pinned deps is written to span versions that don't coexist here, and it hides real bugs as silent no-calls. The SANCTIONED probes are the documented ones: register existence guards (§ Tree-shakeable globals rule 2), host-runtime detection (`isGjs()`/`isNode()` single source § Build; the `globalThis.imports?.gi` probe shape; NS `typeof java !== 'undefined'`), optional native-bridge loads (`imports.gi.GjsifyX` in try/catch — the typelib genuinely may be absent), `isNativeStreamUsable` before replacing a native stream. Each guards a REAL per-runtime/per-install variance and says so at the site. Everything else: import it and call it.
|**comments that restate the code.** Comment WHY, never WHAT — a restating comment is a second copy the reviewer must diff against the code, and their drift reads as documentation while being a bug. JSDoc for public APIs; trivial/internal code stays bare.
|**duplication instead of a helper.** The SECOND copy is where you lift a helper — copies drift, and the drifted copy fails in a CONSUMER while the owning package's tests stay green. Measured (#869): the root-relative-URL rewrite existed hand-written in three packages, and the drifted one (`fetch`) broke every root-relative fetch on node while its siblings worked; the entropy chain was two locally-defensible copies wrong in composition (webcrypto row). The literal line `app.runAsync([imports.system.programInvocationName, ...ARGV])` is currently triplicated across `storybook`/`devtools-browser`/`adwaita-app` — a consolidation target, not a pattern to extend. The lift targets exist and are the pattern: `@gjsify/utils/core`, `storybook-core`, `adwaita-app` are each "the helper the copies forced".
|**scattered lifecycle.** Init and teardown live together: cleanup beside creation, ownership in ONE place, wired to the exit the host actually HAS — and teardown must not assume the process lives long enough. Measured: the GStreamer pipeline registry (webaudio row) exists because per-call-site `set_state(NULL)` could not fix teardown spread over sites with process-lifetime assumptions; `decodeAudioDataSync` tears down in `finally` so a throw cannot leak a PLAYING pipeline. No `_destroyed`/`_enabled` boolean flags where nulling the reference says the same and cannot desync; release children BEFORE chaining up to the parent's destroy, never after.
|**shelling out where an API exists.** A spawned command line is an injection surface and a quoting-bug factory. Standing in-repo counter-example (fix at next touch, never copy): `@gjsify/fs`'s GJS `linkSync`/`link` run ``GLib.spawn_command_line_sync(`ln ${existing} ${new}`)`` — unquoted interpolation, so a path with a space or shell metachar breaks or injects (`packages/node/fs/src/{sync,callback}.ts`). When a subprocess IS the job, pass an argv array (`Gio.Subprocess`), never an interpolated command line.
|**monolithic entry points.** `index.ts` = barrel re-exports only; commands/views/features are modules composed by a thin entry. A class owning bootstrap AND business logic AND IO is three classes.
|**toolkit imports in shared code.** A shared/core module importing UI libraries is the layering bug `gjsify.headless` machine-checks (§ Runtime & platform model — the `canvas2d-core` `gi://Gdk` incident). Don't rely on discipline; declare the headless claim so CI holds it.

## Tree-shakeable globals — `/register` subpath convention

Every pkg registering anything on `globalThis` MUST follow these rules.

1. **No side effects in `src/index.ts`.** Root = named exports only. Any top-level `globalThis.X=…`/`defineProperty(globalThis,…)` there = regression → move to `register.ts`.
2. **Side effects in `src/register.ts`**, importing from `./index.js`, idempotent (twice must not throw): function/class → `if (typeof globalThis.X === 'undefined') { (globalThis as any).X = X; }`; plain value (process, Buffer) → `if (!('X' in globalThis)) { Object.defineProperty(globalThis,'X',{value:X,writable:true,configurable:true}); }`; DOM constructors (GTK-only) → unconditional `defineGlobal`; streams → `isNativeStreamUsable(globalThis.X,'method')` before replacing.
3. **`package.json` subpaths + `sideEffects`:**
   ```jsonc
   "exports": {
     ".":                    { "default": "./lib/esm/index.js" },
     "./register":           { "types": "./lib/types/register.d.ts", "default": "./lib/esm/register.js" },
     "./register/<feature>": { "default": "./lib/esm/register/<feature>.js" }
     // "./globals": "./globals.mjs"  // optional native re-exports for Node
   },
   "sideEffects": ["./lib/esm/register.js","./lib/esm/register/*.js","./globals.mjs"]
   ```
   `sideEffects` pinned to register-only, and it MUST stay — never `false` on a register-providing package. `./register` catch-all keeps `types`; granular subpaths only need `default`.

   **`register.ts` vs `globals.mjs` — distinct patterns:** `register.ts` WRITES our GJS impl to globalThis (GJS; injected by `--globals auto`; aliased to `@gjsify/empty` on Node). `globals.mjs` READS globalThis and re-exports the native value (Node; the `ALIASES_WEB_FOR_NODE` alias target). Cross-platform `import { subtle } from 'webcrypto'` → GJS: our impl; Node: alias → `@gjsify/webcrypto/globals` re-exporting native `globalThis.crypto`.
4. **Globals map is authoritative.** Every identifier a register writes MUST map in `resolve-npm/lib/globals-map.mjs` → its bare `/register` subpath — a missing entry makes `--globals auto` silently fail to inject; pointing at the catch-all when a granular subpath exists pulls the whole register module into the bundle.
5. **Alias layer mirrors the map** in `resolve-npm/lib/index.mjs`: `ALIASES_WEB_FOR_GJS` (`<pkg>/register` → `@gjsify/<pkg>/register`), `ALIASES_WEB_FOR_NODE` (both forms → `@gjsify/empty`), `ALIASES_GENERAL_FOR_NODE` (non-web registers).
6. **Tests import `/register` explicitly** (`import 'fetch/register'`) — no implicit reliance on root imports. **Examples and application code must NOT import `/register` directly**: rely on `--globals auto` (the default). Explicit register imports pull the catch-all into the bundle instead of the granular subpaths actually used, AND paper over detection gaps — if auto misses a global, fix the detector or add `--globals auto,<extra>` to the build script; an explicit import hides the bug.
7. **Users rely on `--globals auto`** (§ Build); source-level `import '<pkg>/register'` remains supported + equivalent.
8. **Exception — intra-package class inheritance:** a root class extending a global constructor (`class TextLineStream extends TransformStream`) runs its class body at module load → `index.ts` may side-effect-import its OWN `/register`. Document in the file header. Current: `@gjsify/eventsource`.
9. **Granular subpaths.** Each register module in `src/register/<feature>.ts` (related identifiers share a file); catch-all `src/register.ts` re-exports via side-effect imports. When splitting: own file, `exports` entry, `sideEffects` glob coverage, catch-all import, globals-map → GRANULAR path, all three alias maps.
10. **Adding a new global — checklist:** implement → register file with rule-2 guard → catch-all → `exports`+`sideEffects` → granular globals-map entry → three alias maps → (new pkg) add to `@gjsify/{node,web}-polyfills` → `register.spec.ts` → website cli-reference Known identifiers → regenerate the register-globals closure map (`generate-register-closure.mjs`; stale = fail-soft, extra analysis passes).

**Invariant (permanent): `@gjsify/<pkg>/register[/<feature>]` MUST NEVER be externalized for `--app gjs`.** GJS's native ESM loader has no node_modules walker AND does not follow `package.json#exports` maps for bare specifiers — an externalized register subpath throws `Module not found` at runtime even with the file on disk. Enforced in `app/gjs.ts` via `createGjsExternalsPredicate`: `isRegisterSubpath(id)` short-circuits to force-inline BEFORE the user-external check, and register-subpath entries are filtered out of the exact-name `external` array. The predicate is applied through the shared `externalsPlugin` resolveId hook (`{ external: true }`) — NOT a function `external` option, because `@gjsify/rolldown-native` JSON-serializes options to the Rust core and silently DROPS function values; the resolveId form is honoured by both engines AND by the `--globals auto` analysis passes. Matching is by SHAPE (`*/register`, `*/register/<feature>`, resolved register disk path) so the carve-out scales with no allow-list. Verified by `auto-globals.spec.ts`. Until upstream GJS gains an exports-map-aware resolver, inlining is the only safe option.

## CJS-ESM Interop (GJS)

Three SEPARATE mechanisms share the word `require`; conflating them is how a latent `ReferenceError` hides for months. (1) is a rule about OUR source; (2)/(3) are interop for FOREIGN code — inbound and outbound. Neither (2) nor (3) is a general `require` polyfill, and neither makes (1) safe.

### 1. Our source is ESM — never a bare `require`

`"type": "module"`, no ambient `require` binding. **A bare `require(...)` in our own source is a latent `ReferenceError`.**
|**THE TRAP — bundled code is shimmed, published `lib/` is not.** Inside a `--app gjs|node` bundle a bare `require('node:fs')` WORKS: rolldown resolves the (aliased) specifier and rewrites the CALL to `__toCommonJS(<bundled module>)` at build time — mechanism (2) catching our mistake as a side effect. The unbundled ESM `lib/` — what we PUBLISH, what every `node lib/index.js` path loads — has no `require` and throws. A site whose only production caller runs a committed `dist/*.gjs.mjs` can sit broken indefinitely and go red the first time anything reaches it through `lib/`.
|**a swallowing `catch` turns it into a silent wrong answer.** `try { require('node:x') } catch { return <fallback> }` converts the ReferenceError into an unverified result: `oxc-resolve.ts` left `libc` pinned to `'gnu'` and told musl hosts to install the wrong binding; `app/gjs.ts` returned an unverified shim path — and since bare `require` only resolves INSIDE a bundle, the `createRequire` fallback written FOR the bundled case was the one branch bare `require` could reach, while the unbundled case it was meant to rescue returned early every time. Catch only around an operation with a real failure mode, and say which.
|**write instead:** a static `import` (the default — `node:*` is aliased per target), or `createRequire(import.meta.url)` as a NAMED import from `node:module` when you specifically need an exports-map-aware RESOLVER (`@gjsify/module`'s polyfill rejects synchronous BUILTIN loads through it — resolve paths, don't load modules). `await import(...)` is ordinary ESM, not a `require`.
|**enforced, not merely documented:** `.oxlintrc.json` sets `typescript/no-require-imports: "error"` — it is NOT in the `correctness` category, so it must be listed explicitly; until it was, the rule NEVER RAN and the `eslint-disable-next-line @typescript-eslint/no-require-imports` comments at some offending sites were pure decoration. Unused-disable reporting is also an error (§ Lint) so that decoration cannot sit next to a live bug again. An `overrides` entry turns the rule OFF for `**/*.cjs`/`**/*.cts` (CJS files — `require` is their module syntax: the `cjs-compat.cjs` shims, CJS fixtures).
|**a per-site disable needs a STATED REASON + tracked TODO — never bare.** All three spellings suppress (`@typescript-eslint/…`, `typescript/…`, `oxlint-…`). Only sanctioned sites today: the two lazy native-dispatcher loads in `@gjsify/http2` (static import would drag the optional typelib-backed `http2-native` into every consumer; the ESM fix needs async `connect()`/`listen()`) — latent ReferenceErrors on the unbundled path, tracked in `status/open-todos.md`.
|`require` TEXT that is not a binding stays legal (generated fixture source, `node -e` one-liners, worker templates, comments) — the rule sees bindings.

### 2. Inbound — third-party CJS is resolved at BUILD time

A bundled npm dep's `require('stream')` is resolved by rolldown (`__commonJSMin` wrap, internal `__require`). Nothing is injected at runtime, and **`app/node.ts` deliberately sets NO `createRequire` banner** — one collided with yargs' own (`Identifier 'require' has already been declared`).

### 3. Outbound — `cjs-compat.cjs` is a PUBLISHING concern

`@gjsify/{stream,events,assert}` ship a `cjs-compat.cjs` via `exports['.'].require`, for an EXTERNAL CJS consumer whose `require('stream')` must get the constructor (so `util.inherits(Child, Stream)` works). `alias.ts` forwards `extraOptions.kind` to `this.resolve()` so the `require` condition can match the original call site (regression: `tests/e2e/cjs-require-stream`). **Where the condition is SELECTED is the subtlety:** `--app node`'s esm `conditionNames` include `'require'` → picks `cjs-compat.cjs`; `--app gjs`'s are `['browser','import']` (comment in `setupForGjs` explains why) → under GJS the constructor comes from the `"module.exports"` string-export below; `cjs-compat.cjs` is dead weight there. Forwarding `kind` is necessary, not sufficient.

### The namespace-vs-constructor fix

Bundling wraps ESM with `__toCommonJS` → a namespace object, not a constructor; a bundled CJS `require('stream')` (pngjs, mute-stream, readable-stream, …) then dies at load with `Stream is not a constructor` / `superCtor.prototype … undefined`.
|**Fix (active): the `"module.exports"` string-export** — for a pkg whose CJS `module.exports` must be a single callable (Node's dual shape — `stream`, `events`), add after `export default _default;`: `export { _default as 'module.exports' };` (ES2022 arbitrary-string export). Rolldown's `__toCommonJS` special-cases an OWN `"module.exports"` property on the namespace and returns it verbatim → a bundled `require('<name>')` yields the callable, normal ESM imports untouched. Engine-agnostic. Regression fixture: `packages/node/stream/src/cjs-interop.fixture.cjs` + `inheritance.spec.ts`.
|Historical note: the esbuild-era "Fix 1" (output unwrap in `onEnd`) was NOT ported to Rolldown; "Fix 2" (`cjs-compat.cjs`) still ships but is only selected on `--app node` (above).

```bash
gjsify install [--immutable|--refresh-lockfile] | gjsify dlx <pkg> | gjsify showcase <name> | gjsify storybook | gjsify debug
```

**`gjsify install` (native backend, `install-backend-native.ts`) — semantics + invariants:**
|lockfile preservation: a resolve seeds itself with the versions pinned in `gjsify-lock.json` and only resolves new/changed deps — adding ONE package never bumps unrelated transitives. `--immutable` = frozen/CI; `--refresh-lockfile` = re-resolve all newest-in-range; mutually exclusive. Prefer `gjsify install <pkg>` over hand-editing the lock; if you must hand-merge, keep the diff to the new subtree.
|non-destructive (ADR 0001): an install mutates ONLY `node_modules/`, `gjsify-lock.json`, XDG cache/global prefix, and (for `install <pkg>`) `package.json`. It NEVER deletes/overwrites a build artifact (`lib/`, `dist/`, committed bundles) or git-tracked files outside that set; cleaning is a separate explicit command (`gjsify run clear`). e2e: `install-non-destructive` + `install-workspace-source-safety`.
|concurrency (ADR 0001): prefix mutations run under the per-prefix cross-process lock (`node_modules/.gjsify-install-lock/`, mkdir-exclusive + stale-steal); shared XDG caches stay lock-free because every write is atomic tmp+rename.
|hang safety — an install must never hang forever, three layers: (1) `--timeout` wall-clock budget (default 30 min) aborts in-flight fetches; (2) the abort only rescues awaits that OBSERVE the signal — `extractTarball` takes none and a dropped Gio stream-close event under GJS wedges a decompress at 0% CPU — so each extract races a per-extract stall timer + the signal (`extractWithStallGuard`, 120s default, `GJSIFY_EXTRACT_STALL_MS`); (3) a hard-exit backstop force-exits after the budget + grace, so ANY residual never-settling await fails non-zero.
|version-skew: `warnOnCliVersionSkew` prints one actionable line when the running `@gjsify/cli` differs from the workspace pin — a mismatched CLI is the documented root of install stalls (lock discarded → full re-resolve → wedge-prone extract) and silent-wrong-builds; align via `gjsify self-update`.
|**bin entries honour `gjsify.bin`, and a GJS bin is a generated LAUNCHER, not a link.** `linkBins` reads the EXTRACTED package's manifest (npm's abbreviated packument does not carry `gjsify.*`, so a packument-only read structurally cannot see it) and hands `pickBinMap` the answer; `gjsify.bin` wins over npm `bin`, and only then does `writeBinEntry` emit the `sh` launcher carrying `buildNativeEnvPreamble` instead of the usual symlink — plain-Node bins keep the link path unchanged. This is not cosmetic: on a Node-LESS GJS host the npm bin's `#!/usr/bin/env node` is simply unrunnable (`env: can't execute 'node'`), and because that launcher is ALSO the only place `GI_TYPELIB_PATH` can be exported before the GJS runtime boots (GI resolves the typelib before the bundle's first line — the CLI cannot repair it from inside), the dead shim took `gjsify build` down with it: "no usable bundler engine under GJS" on a host where the engine was correctly installed and loadable. Measured end-to-end on postmarketOS/aarch64 (musl, gjs 1.88, no node/npm/git): install → build → run now works through `node_modules/.bin/gjsify` with no hand-set env. The three helpers (`pickBinMap`, `buildShLauncher`, `normalizeBinMap`) live in `bin-shim.ts` and are shared with `linkGlobalBins` — they were duplicated per-call-site before, and the drifted copy was exactly the one missing `gjsify.bin`.

## Native Extensions (Vala)

Vala → Meson → shared lib + GIR typelib → `gi://` import (example: `packages/framework/webgl/`). Prefer TS; Vala only for C-level access.

**gi:// ordering:** `GIRepository.prepend_search_path()` must run before `gi://Foo` resolves — static `gi://` imports resolve in ESM Linking, before code. Use `gjsify run` or a two-file loader (loader prepends, then `await import('./bundle.js')`).

**A `gi://` import's typelib-LOAD side effect does not exist on `--app node` — express it as an ACCESS.** `import GstApp from 'gi://GstApp?version=1.0'; void GstApp;` works on gjs (the specifier stays EXTERNAL; the import is always evaluated, and loading the namespace IS the side effect: instances like `pipeline.get_by_name('src')` then resolve their real type's methods). On node, `gjsGiNodePlugin` rewrites it into a virtual module resolving the namespace LAZILY on first property access — laziness that is load-bearing (it keeps GJS-only `gi://` paths from dragging `@gjsify/node-gi` into cross-platform node bundles at load, the #641 lesson). No side effect ⇒ tree-shaking DROPS the module (measured: zero `GstApp` refs in the bundle) and `appsrc.push_buffer` failed "not a function" while the identical source played on gjs. Touch the namespace inside a function something calls (`@gjsify/webaudio`'s `ensureGstAppLoaded()`); making the shim eager is NOT the fix — it would reintroduce the regression the laziness prevents.

### Prebuilds

Native libs in `prebuilds/<os>-<arch>/` (`.so`/`.dylib` + `.typelib`); `package.json`: `"files":["prebuilds"]`, `"gjsify":{"prebuilds":"prebuilds","platforms":["<the one target>"]}` — declaration + audit: § Runtime & platform model.

|**the artifacts live in PER-TARGET packages, not in the bridge (ADR 0017, the esbuild model).** A bridge `@gjsify/<x>` keeps its name, API and loader contract but ships NO `prebuilds/`; each declared target lives in `@gjsify/<x>-<os>-<arch>` (directory `packages/<pillar>/<x>-<os>-<arch>/`, a SIBLING — the workspace globs are `packages/<pillar>/*`, so a nested dir would not be a workspace member), which declares `os`/`cpu` and is referenced from the bridge as an `optionalDependencies` entry. A package manager installs the one that fits and SILENTLY skips the rest, because a platform mismatch on an OPTIONAL dependency is not an error. Measured before the split: 97.3 MB of committed binaries of which a linux-x64 consumer could load 31.5 MB.
|**the 60 manifests are GENERATED, never written** — `scripts/generate-platform-packages.mjs` (`--check` default, `--write` moves the directories with `git mv` and patches the parents). Every field is derived: name from parent + token, `os`/`cpu` from the token, version + tier from the parent, `libc`/`gjsify.glibcRequires` MEASURED from the ELF by the `prebuild-libc` rule's own reader (never a second copy of it — a hand-rolled loader predicate matched `ld-linux-*` but not ppc64le/s390x's `ld64.so.*`, so the generator and the rule disagreed about the same bytes). `--check` re-emits and compares; the `platform-packages` conformance rule IS that function, imported not reimplemented.
|**what moves to the child and what stays.** `gjsify.platforms` stays on the bridge as the single declaration and every child's one-element list is derived from it. What MOVES is everything that is a fact about a BINARY: the npm `libc` filter (leaving it on the bridge is an install-time regression — npm/yarn/pnpm all honour it, so an inherited `["glibc"]` refuses the pure-TypeScript half on musl hosts where it runs fine), `gjsify.glibcRequires`, and `gjsify.platformsUncommitted`. The exemption travels because it is what `prebuild-artifacts` trips on when the directory appears, and the directory now appears in the child; a split parent is out of that rule's scope entirely.
|**a DECLARED target gets a package even when its artifact is deferred.** `@gjsify/napi`'s darwin-arm64 is built by `release.yml` and staged into the tarball at pack time, never committed — with `prebuilds` gone from the bridge's `files` that staging packs nothing, so the artifact needs a package to ship FROM. It also claims the npm name when the target is declared rather than when its binary lands, which is the cheap half of the bootstrap below.
|**runtime discovery needs no new code path** — `detectNativePackages()` already scans every package in `node_modules` for `gjsify.prebuilds` + `prebuilds/<target>/`, so a split package is found by exactly the mechanism that found a bundled one. Only which tarball the directory arrives in changed.
|**adding a target is now a PUBLISHED NAME**, so `gjsify onboard` (first publish + Trusted Publisher, § New `@gjsify/*` package) must run for it BEFORE the release that ships it — an unbootstrapped name 404s the OIDC exchange and stalls every alphabetically-later package.

|**runtime env:** the CLI auto-sets `GI_TYPELIB_PATH` + the host loader's OWN search var (`LD_LIBRARY_PATH` linux / `DYLD_LIBRARY_PATH` darwin — dyld ignores the ELF one / `PATH` win32, `;`-separated) via `detectNativePackages(startDir)` + `buildNativeEnv(pkgs)` (exhaustive node_modules scan walking up). Used by `gjsify run` | `gjsify info` | `gjsify dlx` | `gjsify showcase`. `runGjsBundle()` calls it for CWD + `dirname(bundlePath)` so dlx-cache layouts pick up their full transitive prebuild set.
|**a LAUNCHER cannot scan at run time from inside GJS** — typelib lookup happens in the GJS runtime before the bundle's first line — so `buildNativeEnvPreamble()` (`utils/bin-shim.ts`) emits a `sh` preamble that GLOBS the install prefix ON EVERY LAUNCH (`<prefix>/node_modules/{@*/*,*}/prebuilds/<target>`, canonical + legacy spelling), used by the global launcher AND the workspace `.bin` shims. It used to EMBED the install-time scan, which makes the env a SNAPSHOT: a native package installed later is invisible, and an empty scan writes a launcher with NO preamble and says nothing — v0.24.1 shipped exactly that (`~/.local/bin/gjsify` with a bare `exec gjs -m …` while `@gjsify/rolldown-native` sat correctly installed), surfacing days later as "no usable bundler engine under GJS" in an unrelated project. Only ANCESTOR hits (hoisted layouts a one-root glob can't see) stay embedded; win32 keeps the baked form (its real launchers are `.cmd`/`.ps1`, and `PATH` is the DLL search path). Guarded by `tests/e2e/global-install-engine`, which RUNS the written launcher against a stub `gjs` and asserts the exported env — reading launcher text cannot tell a correct one from an empty one.
|**platform logic is a PURE function** of `(platform, arch, declaredPlatforms, existingDirs)` (`resolvePrebuildDirName`/`libraryPathVar`) so darwin/win32 branches are unit-tested from Linux by injecting foreign values; only final `dyld`/`LoadLibrary` behaviour is CI-only.
|**consumers:** showcases / dlx-runnable apps must declare every typelib-owning package as a runtime `dependency` (§ Showcase dep rule) — build-time inclusion does not ship the typelib in the tarball.
|**build:** `.github/workflows/prebuilds.yml` (x64+arm64 native + ppc64/s390x/riscv64 under QEMU, Fedora). Local: `gjsify workspace <pkg> build:prebuilds` / `gjsify foreach build:prebuilds` (meson + vala + GI `-devel` pkgs required). No root `build:prebuilds` script — yarn was dropped in Phase D.7d; scripts run via `gjsify run|workspace|foreach`.
|**staging goes through the shared `scripts/stage-prebuild.mjs`, never a hand-written `cp`.** It takes the target dir from the package's OWN `gjsify.platforms` (a local build can't invent a target CI doesn't reproduce; an undeclared host is a hard error) and matches artifacts by EXTENSION, so a library renamed in `meson.build` can't ship a stale set. The eleven per-package one-liners it replaced hard-coded target dir + `.so` suffix — why `build:prebuilds` staged nothing on macOS. Since ADR 0017 the DESTINATION is resolved, never defaulted (`resolveStageDir`): `gjsify.prebuilds` present → this package owns the artifacts; absent → the sibling platform package must exist, and if it does not that is an error naming the generator. The old `?? 'prebuilds'` default would recreate a directory INSIDE the bridge — untracked, absent from `files`, invisible to every conformance rule (they key on `gjsify.prebuilds`) and yet exactly where a developer's `build:prebuilds` appears to succeed.
|**`commit-prebuilds` writes to the per-target packages; the BUILD legs deliberately do not.** Only the job that commits had to move: a build leg stages into the bridge as scratch space, uploads straight from it and never commits, and the macOS load-test steps read that path. `changed-packages.mjs` derives its package table from those same `path:` lines and maps `<bridge>-<target>` back to the bridge — taking the download path at face value would fill the table with 60 source-less packages, of which it then asks only questions about sources.

**A prebuild must resolve its own siblings from its own directory — machine-checked by `scripts/check-prebuild-loader-path.mjs`** (wired into `stage-prebuild.mjs`; parses Mach-O + ELF directly, no otool/readelf, so a Linux host verifies a committed darwin artifact it cannot run). The three Rust bridges (`rolldown-native`, `oxfmt-native`, `lightningcss-native`) ship TWO libraries whose leaf names differ ON PURPOSE: the Vala/GObject library the typelib names (`libgjsify<name>`) and the cargo cdylib it links (`libgjsify_<name>`, underscore) — the second is invisible to every other check (link succeeds, typelib found, failure lands at `dlopen` on a user's machine). `meson.build`'s per-OS branch must set BOTH: (1) the cdylib's install name normalised to `@rpath/<leaf>` (`install_name_tool -id`) BEFORE the Vala library links (ld64 copies the dependency's install name verbatim into `LC_LOAD_DYLIB`, and rustc's own has varied); (2) the self-relative search path — `build_rpath`+`install_rpath` `@loader_path` (Mach-O) / `$ORIGIN` (ELF); `build_rpath` is load-bearing because the shipped artifact is copied out of the build dir, never `meson install`ed. **`@loader_path`/`$ORIGIN` is NOT interchangeable with a library-path env var** — the env var only finds the BARE leaf the typelib records; the Vala→Rust hop must need nothing, or the prebuild only works under one launcher. Catches both failure modes: a sibling not staged (the darwin `rolldown-native` leg copied Vala `.dylib` + typelib and NOT the cdylib — a missing FILE reading exactly like a missing rpath) and a missing rpath.

**A prebuild never LOADED in CI is a prebuild nobody tested.** The macOS job once built six darwin-arm64 bridges and committed them without loading one. Every macOS job now ends in a real `gjs -c 'imports.gi.<Ns>.<Class>'` per bridge (resolving a class forces GI to call `…_get_type`, which is what dlopens the library — a typelib merely FOUND passes namespace lookup) plus an env-free `ctypes.CDLL(<abs path>)` with `DYLD_*` unset (proves the sibling hop rides `@loader_path` alone). ANY new prebuild job MUST end in a load test. **Same rule for the job's OWN platform, non-obviously**: a job can produce a loadable artifact for the WRONG arch — `uraimo/run-on-arch-action` ignores its `arch` input when a custom `base_image` is supplied (platform must ride the image ref: `base_image: --platform=linux/ppc64le fedora:43`), so the emulated legs compiled x86-64 and staged it into `prebuilds/linux-{ppc64,s390x,riscv64}/`; every downstream check passed, the artifact even LOADED on the runner. Only reading the image's own `e_machine` against its directory catches that — `audit-runtimes --check` now does. **The EMULATOR is toolchain and is pinned like one** (`docker/setup-qemu-action` + `tonistiigi/binfmt:qemu-v10.2.3`): the action's default reset binfmt to qemu 7.2, under which Fedora's package manager does not survive emulation (dnf segfaults on s390x, RPM transaction fails on ppc64). Reproduce any emulated leg locally: `podman run --platform linux/<arch> -v "$PWD:/workspace" -w /workspace <image> bash .github/prebuild-toolchain/emulated-build.sh` (a CI-only emulated build is a 20-min round trip per hypothesis). Weak/recommended deps are OFF in that script — they pulled pipewire/wireplumber into a Vala build and THEIR scriptlet was the failure.

**Prebuild provenance — a committed binary is only as trustworthy as the source it was linked against.** The `*-native` bridges compile upstream Rust crates by Cargo PATH dependency into `refs/<name>/`, and the `.so` is COMMITTED. Machine-checked by `node scripts/check-refs-pin.mjs <pkg-dir>` (runs in every `build:meson`; `GJSIFY_ALLOW_REFS_DRIFT=1` for a deliberate bump committed in the same change):
|**checkout drift** — a `refs/` working copy moved forward (an `update-submodules` sweep, a manual pull) and the next rebuild links THAT. The submodule set to verify is DERIVED from the package's own `src/rust/Cargo.toml` path deps.
|**version skew vs the npm engine** — `@gjsify/rolldown-native` and npm `rolldown` are two builds of the SAME bundler and must be the same release, else the engines disagree on some inputs only. Declared as `gjsify.refsLockstep: {"refs/rolldown": {"npm": "rolldown", "tag": "v{version}"}}`, checked against the installed npm version (same for `oxfmt-native` ↔ `refs/oxc` @ `oxfmt_v<X>`).
|**stale build dir** — ninja does NOT track Cargo path-dep sources: after swapping a submodule, `meson compile` says "no work to do" and re-stages the OLD binary. The check stamps `build/.gjsify-refs-pin` and fails loudly (fix: `rm -rf build src/rust/target`).
|**the crates.io half is pinned by a COMMITTED `src/rust/Cargo.lock` per bridge** (shipped via `files: ["src/rust"]`) — none of the three checks sees a crates.io transitive. Load-bearing with the prebuild change-gate: a run that never rebuilds never absorbs registry drift. ENFORCED on CI via `${CI:+--locked}` on the `cargo build` (a lock nothing checks is decoration); locally expands to nothing. GitHub Actions exports `CI=true` to steps and job `container:`s but a bare `docker run` inherits NOTHING — the emulated legs pass `-e CI=true` explicitly; a containerised step that forgets it still USES the lock but silently stops FAILING on a stale one. The lock is also a `rust_sources` input (ninja otherwise tracks only `Cargo.toml` + `src/**.rs`; a lock-only change would re-stage the OLD binary). Update = explicit act: `cargo update [-p <crate>]`, `cargo tree -d`, rebuild, commit the lock diff together; a `refs/` bump invalidates the lock and needs the same regeneration in that commit.
|**a lock does NOT replace `[patch.crates-io]` — crate IDENTITY is not a version choice.** `refs/oxc` publishes `oxc_allocator` AND path-deps it in-tree; the crates.io-only parsers pull it from the REGISTRY, and Cargo treats registry and path copies as SEPARATE crate instances even at the same version → `E0308 … multiple different versions of crate oxc_allocator`. A `[patch]` table is honoured only from the ROOT of the workspace being built — each `src/rust/` is its own root and must repeat the patch (as `@gjsify/oxfmt-native` does). When adding/bumping a `refs/` submodule that publishes its own crates: check `cargo tree -d` for a name appearing as both path and registry, patch it to the path copy.
|why it earns its keep: the committed `rolldown-native` prebuild had drifted BEHIND its pin, and the pin sat 41 commits past `v1.1.5` while the npm devDep was `1.1.4`; the gap contained a runtime-chunk change, so the rebuilt native engine emitted two chunks where npm emitted one and every `--app gjs --outfile` build keeping a standalone runtime chunk failed ("output.dir must be used"). **Still open:** nothing byte-compares a committed prebuild against a CI-built one (`status/open-todos.md`).

## Git hooks

Plain bash hooks under `.githooks/`, no husky. `core.hooksPath` wired automatically by `gjsify install` (`maybeInstallGitHooks()`, gated so consumer projects are skipped); manual `node scripts/install-git-hooks.mjs` (idempotent; `--uninstall`, `--quiet`).
|`pre-commit`: staged files touching `packages/infra/cli/{src,package.json}` / `resolve-npm/lib/` (maps the bundle inlines) / `rolldown-plugin-gjsify/src/` (the pipeline the bundle inlines) → rebuilds + re-stages `packages/infra/cli/dist/{cli,affected}.gjs.mjs`; touching `packages/infra/tsc/` → rebuilds `dist/tsc.gjs.mjs`. Resolves `gjsify` via workspace `.bin` → PATH → committed bundle. **The hook AUTO-STAGES what it built, so a checkout that cannot resolve the polyfills would commit an unloadable bundle unseen** — that is why `gjsify build --app gjs` itself refuses to emit a bundle that still statically imports bare `node:` modules (`gjs-bundle-guard.ts`). **The oracle is the bundler's own module graph (each chunk's `imports`), never the emitted text** — a text scan cannot tell a statement from a `node:` specifier quoted in a string (a `@gjsify/process` test name and the CLI's `giNodeShimSource()` template both contain one; a grep gate failed them). The allowlist is EMPTY and stays that way. Nothing between `gjsify build` and CI ever executes the emitted GJS bundle — tsc/lint/unit/e2e all run the Node entry — so a green `--app gjs` exit was the only signal, and it lied.
|bypass: `--no-verify` or `SKIP_GJSIFY_HOOKS=1`. The hook is BEST-EFFORT, never the invariant: its trigger list is a four-path heuristic while the bundle inlines the whole workspace-dep closure, and it warns-and-skips with no reachable CLI (a bare worktree — the #821 case). The CI rebuild-and-compare below is what is exhaustive. Tests: `tests/e2e/git-hooks-cli-bundle-staleness/`.

### Committed-artifact freshness — verify against the SOURCE, not the version string

Tracked, version-locked build outputs: `packages/infra/cli/dist/{cli,affected}.gjs.mjs`, `packages/infra/tsc/dist/tsc.gjs.mjs`, `@gjsify/tsc`'s shipped `lib/lib*.d.ts`. FOUR guards, each catching a failure the others structurally cannot — do not collapse them.

|**Resolves at all** (`unresolved-workspace-import.ts`, every `gjsify build`, RESOLVE time): § Build — refuses the build when a `@gjsify/*` substitution can't resolve, on all four targets, naming importer + cause.
|**Is structurally loadable** (`gjs-bundle-guard.ts`, `--app gjs`, build time): refuses to emit a bundle whose module graph still statically imports bare `node:` — the shape an unresolvable alias target produces, which otherwise "succeeds" with a warning and writes an artifact aborting on every stock GJS. Stays alongside the resolve guard: it is a property of the ARTIFACT, covering bare `node:` arriving by routes the resolver doesn't model (user `--external node:fs`, a future plugin `{external:true}`).
|**Reaches only globals something installs** (`node-bundle-guard.ts`, `--app node`, build time): a GJS ambient global (`print`/`imports`/…) is a FREE IDENTIFIER, not an import — no chunk's `imports` mentions it. It is seeded by `@gjsify/node-gi/globals`, injected only when `detectNodeGiGlobals` finds one in a PRE-build analysis bundle — a PREDICTION. The guard re-runs the SAME acorn pass over what was actually emitted and fails on disagreement. Skipped when the shim WAS injected, and under `--globals none`. Not a second opinion — ONE oracle, two passes that must agree; disagreement = pipeline bug, never user code. Exactly that shipped: the analysis ran BEFORE the explicit-`--globals` register stub resolved, one of the two signals `isGjsSourceBuild()` reads, so the analysis graph routed `/register`→`@gjsify/empty` + emptied `@girs/*` while the real build resolved both — every ambient global reachable only THROUGH a register module was invisible; the excalibur showcase built green and died `ReferenceError: imports is not defined` on node AND bun while gjs ran fine.
|**Runs + reports the right version** (`.github/actions/gjsify-setup`, every job, BEFORE the build-output cache restore): boots each bundle under stock `gjs`, compares `--version` to the source of truth, + the single-`@gjsify/web-streams`-copy assertion. CANNOT catch a stale bundle — a bundle built from old source still reports the right version. Not theoretical: #821 changed the curated browser aliases (data the bundles INLINE) and merged fully green with both bundles stale; the pre-commit hook had warned-and-skipped itself (worktree, no node_modules).
|**Reproduces from source** (`scripts/verify-committed-bundles.mjs`, one step in `main.yml`'s build job, AFTER Build): rebuilds every committed artifact and compares BYTE-FOR-BYTE against `git show HEAD:<path>`. Byte-reproducibility is measured, not assumed — the bundles bake no absolute path/timestamp/host state, and the rebuild always runs the Node CLI entry so npm-vs-native engine never enters the comparison. **The property depends on DETERMINISTIC ENTRY ORDER, pinned in `globToEntryPoints`** (each glob's expansion sorted; pattern-list order preserved). Entry order is a bundle INPUT: rolldown derives exec order from a DFS starting at the entries and renders chunk imports in that order — while fast-glob's concurrent walker yields COMPLETION order (measured: 9 distinct orderings in 60 runs). Unsorted, a minority ordering emitted reordered imports + flipped `$N` suffixes, every bundle inlining those libs drifted a few bytes, and the build cache kept the raced order alive — which is why the divergence looked machine-bound. Guarded by `entry-points.spec.ts` + `tests/e2e/deterministic-library-build/`.
|what makes it trustworthy: (a) expected bytes from git, NOT the working tree (`gjsify run build` rewrites those files in place — a working-tree comparison would pass while checking nothing); (b) the artifact SET is discovered from `git ls-tree HEAD` and a bundle with no rebuild recipe is a hard error (exhaustive by construction); (c) pre-run bytes restored on exit, ONE snapshot before all recipes + ONE restore after (`--with-dependencies` rewrites `tsc.gjs.mjs` mid-run); (d) `--with-dependencies` pins the INPUTS — in CI the workspace `lib/esm` trees come from a cache whose `restore-keys` fallback can be another revision's, so rebuilding the closure first makes a mismatch mean staleness.
|the `@gjsify/tsc` recipe runs `GJSIFY_TSC_REFRESH_LIBS=1` on purpose: `pickLibSource()` normally KEEPS committed libs (a refresh races concurrent readers), which would make comparing them a check that cannot fail; the verify step runs alone, so forcing regeneration gives the version-locked lib set real coverage (a `TYPESCRIPT_VERSION` bump with un-regenerated libs is exactly the v0.7.2 `TS6053` cascade).
|**it BOOTSTRAPS the tree it needs — `--rebuild` is the release path.** Under GJS the only engine is `@gjsify/rolldown-native`, whose JS facade `lib/` is a build output `gjsify install` does not produce; on a fresh clone every recipe died "no usable bundler engine". `ensureBuildableWorkspace()` runs `scripts/bootstrap-native-facades.mjs` unconditionally, and **the COLD/WARM branch lives in the bootstrap itself** (`ensureNodeCliEntry()`: root `build:infra` when the Node CLI entry is absent, else build the facades directly; mtime-idempotent; recursion cut by a marker env). That move is the point: with the branch at the call site exactly one caller was correct — the release `publish-napi` job (checkout+install by design) missed it and `@gjsify/napi` was the ONE package that missed the v0.24.1 train while the release was otherwise green. `--print-plan` reports the branch without spawning (e2e `tests/e2e/bootstrap-cold-tree`). The engine's failure message is DERIVED from disk state (`diagnoseNativeEngine()`), not the rarest cause.
|**deliberately NOT unified with `main.yml`'s warm-cache probe (#862)**: the probe is a READ-ONLY post-condition on the WHOLE tree ("may a selective build trust this cache") that only DECIDES a path; the preflight is a pre-condition on TWO TOOLS that REPAIRS them. Strict containment, verified: every preflight path is a DECLARED output `verify-package-outputs.mjs` asserts, so probe-warm ⇒ preflight-no-op; the converse must NOT hold (a tree missing an unrelated `lib/types` is COLD for the probe yet buildable). Unifying breaks both directions. What they share is the POLICY: incomplete ⇒ "do the fuller thing", never "error".
|**scope:** ANY source the bundle inlines stales it, not just the hook's four paths — `@gjsify/{tar,semver,buffer,workspace,npm-registry,node-globals,…}` are all inlined. Editing one and committing without rebuilding reds the PR with exact commands. **Still unguarded:** committed `prebuilds/**` binaries (provenance proves inputs; nothing byte-compares, `status/open-todos.md`); `register-globals-closure.mjs` deliberately ungated (stale = fail-soft slower builds; its `--check` costs a full per-register sweep).

### Build outputs — an exit code is not evidence that anything was WRITTEN

`scripts/verify-package-outputs.mjs` (one step in `main.yml`'s build job, after Build) asserts every path a non-private workspace DECLARES — `main`/`module`/`types`/`typings`/`browser`/`bin`/`gjsify.bin` + every `exports` condition, recursively — exists on disk; a miss fails the build. Package set + path set both DERIVED (workspaces globs × package.json), deliberately NO per-package opt-out (an opt-out list drifts and then lies). `--only`/`--root`/`--allow-unbuilt` are for local iteration, never CI.
|**the failure it exists for (#67):** with `composite`/`incremental`, a `.tsbuildinfo` outliving its output tree makes `tsc` consider the project up to date — prints nothing, writes nothing, **exits 0**. Reproduced verbatim in `@gjsify/adwaita-core`. The package then publishes a `types` entry that does not exist; consumers hit `TS7016`, which reads like a consumer bug and gets papered over per-consumer.
|why nothing else saw it: `check` type-checks SOURCES; the build cache owns per output UNIT so a missing unit is a HIT; the packer's type-shipping guard deliberately doesn't fire on an ABSENT declaration (an unbuilt dev tree must still pack); `tsbuildinfo-containment` only proves containment. Why a post-condition, not co-locating the build info with the emit tree: co-location fixes one cause and fights the build cache (a loose file degrades `lib/` to whole-dir ownership = the v0.x clobber), and wouldn't catch a missing `main`, a never-wired build script, or an `exports` typo. The desyncing shape is NORMAL: 93 of 103 incremental tsconfigs put the build info outside the emit tree.
|**the same script IS `main.yml`'s warm-cache probe**, run before the build, COLD-on-failure rather than error: the selective path trusts the cache for every unchanged forward-dep, so "is the cache warm" IS "is the restored tree complete" — the three-directory `[ -d … ]` probe it replaced couldn't answer that (a ~4 MB archive held `@gjsify/xmlhttprequest`'s `lib/esm` but not `lib/types`, passed all three dirs, went selective, died on EVERY selective PR). Incomplete cache ⇒ full build.
|proves EXISTENCE, not freshness (that class belongs to `verify-committed-bundles.mjs`); wildcard subpaths checked to their static prefix; ~0.1 s.
|**caught a real one on its FIRST run**, not the package it was written for: `@gjsify/xmlhttprequest` declared `lib/types/*.d.ts` while its tsconfig set no `declarationDir` — the declared paths were never produced for ANYONE (published 0.23.0 ships the dangling pointer). Fixed at the tsconfig (`declarationDir` + `emitDeclarationOnly`). Sibling `fetch` has the same shape but declares matching paths — consistent, leave it.
|tests: `tests/e2e/package-outputs/` (matrix + the #67 mechanism end-to-end through the real committed `@gjsify/tsc` bundle).

## Lint & format — oxc (oxlint + oxfmt)

`gjsify lint`/`format`/`fix` wrap **oxc** (full Biome replacement, no fallback). `gjsify check` stays the **tsc** orchestrator, unrelated.

- **Resolution — dual-engine (mirrors `bundler-pick.ts`):** `packages/infra/cli/src/utils/oxc-resolve.ts`. **oxfmt:** under GJS, `runOxc` prefers the `@gjsify/oxfmt-native` GI bridge (`shouldUseNativeOxfmt()` — runs the full oxfmt CLI in-process, Node-free `gjsify format`/`fix`; `GJSIFY_OXFMT=native|npm` is the explicit override, `native` throws when the prebuild isn't loadable); on Node (or when the prebuild is missing) it spawns the npm **Node launcher** (`node_modules/oxfmt/bin/oxfmt`) via `process.execPath`. **oxlint:** always spawned via its Node launcher — NOT the bare napi binary — because oxlint's JS-plugin host (the `gjsify/register-class-order` rule) lives in the launcher; a native oxlint bridge could only run the Rust rule subset (deferred, see `status/open-todos.md`). Tools are on-demand devDeps (resolved cwd → workspace-root → parents); a clear install hint names the expected `@oxlint/binding-<target>` / `@oxfmt/binding-<target>` napi package.
- **Spawning the Node launcher from the GJS bundle — two GJS-only gotchas (`spawnOxcLauncher`):** (1) the launcher command is `nodeBinary()`, NOT `process.execPath`. Under the committed GJS bundle `process.execPath` is the CLI bundle itself, so spawning it re-executed the CLI with `oxlint/bin/oxlint` as its first positional (yargs printed top-level help) and hung; `nodeBinary()` resolves to PATH `node` under GJS (a real Node host is required — oxlint has no native bridge yet; its absence surfaces as a clear `OxcNotFoundError`). (2) Under GJS the tool runs on **`spawnToCompletion`'s blocking path, not the streaming async one** — but NOT because an event is lost. The earlier note here claimed the async `Gio.Subprocess` `wait_async` exit/close callback is "not delivered back to JS under the bundle"; that is **wrong** (instrumented 2026-07-26 on gjs 1.88 — it fires, with the correct exit code). The real cause is **teardown**: `@gjsify/child_process`'s async `spawn()` calls `ensureMainLoop()`, which arms a GJS main-loop hook (`GLib.MainLoop.runAsync()` → `setMainLoopHook`); `eval_module` runs that hook once the entry module's top-level await settles and then blocks in `g_main_loop_run()` forever — GJS has no atexit hook, and only `process.exit()` (→ `quitMainLoop()` + `system.exit()`) tears it down. So **any command that async-spawns and then RETURNS NORMALLY parks at 0% CPU after the child has exited and been reaped**, which is indistinguishable from a lost callback. `lint`/`format`/`fix` end via `setOxcExitCode`, which deliberately does not exit on a clean run → hang; `foreach`/`workspace`/`check`/`runGjsBundle` end in `process.exit(…)` → fine, which is why hundreds of async children and 490+ GJS specs never hung. **Corrected general rule: from the GJS CLI bundle the async `spawn` is fine as long as the command terminates the process itself; a command that returns normally must use the blocking path.** That contract is the required `completion: 'exit' | 'return'` option on `spawnToCompletion` (`packages/infra/cli/src/utils/spawn.ts` — the single wrapper the six former copies now share). The blocking path additionally captures stdout/stderr (`'inherit'` is not forwarded through the GJS spawnSync path — diagnostics would be silently dropped) and re-emits them (`maxBuffer` 64 MB). On Node the async path is always used. Guarded by `tests/e2e/lint-gjs-launcher` + `tests/e2e/spawn-gjs-teardown` (both boot `dist/cli.gjs.mjs` under `gjs`). The same `process.execPath`-under-GJS trap still lurks in `showcase.ts`'s `spawn(process.execPath, [cliBin, 'dlx', …])` (`status/open-todos.md`).

## Testing

### Framework `@gjsify/unit`

```ts
import { describe, it, expect, on } from '@gjsify/unit';
export default async () => {
  await describe('module.function', async () => {
    await it('should do X', async () => { expect(result).toBe(expected); });
  });
  await on('Gjs', async () => { /* GJS-only */ });
};
```
Matchers: `toBe|toEqual|toBeTruthy|toBeFalsy|toBeNull|toBeDefined|toBeUndefined|toBeLessThan|toBeGreaterThan|toContain|toMatch|toThrow` + `.not`. Run: `gjsify workspace @gjsify/<pkg> run test[:node|:gjs]`; e2e: `node --test tests/e2e/<name>/run.mjs`.

### Rules

1. **Cross-platform pkgs:** `node:` prefix for all Node imports (value+type); **never import `@gjsify/*` directly** (except `@gjsify/unit`); aliased Web pkgs via bare specifier.
2. **GJS-only pkgs** (dom-elements, webgl): import `@gjsify/*` directly; no `test:node`. 2b. **GJS-only spec files in cross-platform pkgs** (`*.gjs.spec.ts` or `on('Gjs', …)`): direct `@gjsify/*` imports allowed — use to test impl-private internals TYPE-SAFELY instead of `as any`. 2c. **Internal-only helpers** (`src/internal/`, not in `exports`): may import sibling `@gjsify/*` even in production code; the public surface still follows rule 1.
3. Node tests prove the TEST is correct; GJS tests prove OUR impl. Both must pass.
4. Common `*.spec.ts`: both platforms, no `@girs/*`. Platform-specific parts minimal.
5. Layout: `src/index.ts` | `src/*.spec.ts` | `src/test.mts` (entry).
6. **Never weaken tests** — fix the impl. No platform guards.
7. **`/register` side-effect tests in a dedicated `register.spec.ts`**, never the common spec — even for a pure-JS global, `/register` can pull GTK/Cairo via its import chain and crash Node. Common spec tests the class via named import; `register.spec.ts` tests the wiring (GJS-only, `on('Gjs',…)`). Cross-platform pkgs: `/register` test → `.gjs.spec.ts`.

**Regression tests from examples:** a real-world example uncovering a bug (GC, missing globals, CJS-ESM, MainLoop) ALWAYS gets a targeted test in the relevant `*.spec.ts` — examples are integration validation, regression tests the permanent net.

**Test sources:** port from `refs/` (`refs/node-test/` primary; `refs/deno/ext/{web,fetch,crypto,…}` for Web API), rewritten in `@gjsify/unit` with bare specifiers — never copied verbatim, never weakened. Select core behavior, GNOME-relevant edge cases, errors, cross-platform; skip V8 internals/native addons/stubbed features.

### Browser tests — `tests/browser/` (Playwright, Firefox/SpiderMonkey)

Third axis alongside `test:gjs`/`test:node`. **The goal is GJS, not the browser**: they verify the native browser platform behaves the way our GJS impl claims — they do NOT test our GJS packages in a browser. **`src/test.browser.mts` must use browser globals directly** — never import `@gjsify/<pkg>` impls or spec files that do: Web APIs are already global in the browser, and importing our packages drags `@girs/*`/`gi://` in transitively, forcing workaround aliases. The correct fix is always a clean test file, not more aliases. **`@girs/*` or `gi://*` appearing in a browser/Node bundle = a missing alias somewhere in the chain — fix the import; never mask with `external:` (unresolvable bare specifiers) or a blanket empty-module map.** Build: `build:test:browser` → `gjsify build src/test.browser.mts --app browser` (the target's `gjsImportsEmptyPlugin` silences what leaks via `@gjsify/unit`; only two aliases exist: `assert`→`@gjsify/assert`, `process`→`@gjsify/empty`). 12 packages have browser tests; GJS-only packages (webaudio, webrtc, gamepad) have none — no browser equivalent of libsoup/GStreamer/Manette. Run: `cd tests/browser && npx playwright test --project=firefox` (add `--project=chromium` for engine diffs).

### Selective CI — affected-only test runs

CI's `linux` job is gated by `gjsify affected` (diff vs PR base → which tiers run). The `changes` job boots a **dedicated committed classifier bundle** `packages/infra/cli/dist/affected.gjs.mjs` on plain ubuntu+gjs — NOT the full CLI bundle, which eagerly imports `gi://Soup` (via npm-registry→fetch) that the classifier host lacks; booting it there crashed → `continue-on-error` failed OPEN to a full run on every PR (the silent regression the split fixed). The dedicated bundle pulls only GLib/Gio/GioUnix. Guarded by `tests/e2e/affected-classifier-bundle`; the pre-commit hook rebuilds it too. **Place new tests where the classifier finds them:** spec files `<workspace>/src/**/*.spec.ts` (seed = that workspace, no closure expansion); integration suites `tests/integration/<name>/` declare every exercised pillar in `dependencies` (the forward-graph walk fires the tier); e2e `tests/e2e/<name>/` runs only when `tests/e2e/**` is touched or on a global trigger — no per-workspace functional tests there; browser `tests/browser/specs/`.

**Closure model — PRODUCTION deps only.** The reverse-dependency closure walks `dependencies`/`optionalDependencies`, NOT `devDependencies` (`includeDev: false`): a test re-runs for a RUNTIME relationship; devDep edges are the toolchain, and with the umbrella polyfill metas they fanned any single change out to ~210 of 221 workspaces. Consequence: **a package's spec must not import a cross-package sibling it declares only as a devDependency** — that edge is invisible to the closure. The integration forward walk stays `includeDev: true` (over-running is cheap). Backstop: push-to-main + nightly run the FULL suite.

**Global triggers** (force full run): `packages/infra/{workspace,cli,rolldown-plugin-gjsify,resolve-npm}/**`, `packages/gjs/unit/**` (the test framework every spec imports — a devDep, so the prod-only closure can't reach its consumers), `gjsify-lock.json`, root `package.json`/`tsconfig*`, `scripts/audit-runtimes.mjs`, `.github/workflows/main.yml`. **Ignored** (no run, no seed): `**/*.md`, `refs/**`, `website/**`, `docs/**`, every workflow EXCEPT `main.yml`, `.githooks/**`, `flatpak/**`, `packages/node-gi/**` + `packages/napi/**` (own CI — without the carve-out their files map to no workspace and force a conservative full run), `LICENSE*`, `.gitignore`, top-level `STATUS|CHANGELOG|AGENTS|CLAUDE|README.md`. **Precedence: IGNORE wins over GLOBAL_TRIGGERS** — ignored files are dropped FIRST, so `packages/infra/cli/README.md` does not force a full run; a docs-only PR is `skip-all` even when it edits infra READMEs. When adding a workflow or top-level dir the classifier doesn't know, update `affected.ts`'s tables + spec — silent mis-categorisation is the most common way to leak slowdowns back into the PR loop.

**IGNORE is scoped to `main.yml`, not to the repo** — the classifier is booted only by `main.yml`'s `changes` job and only `main.yml` reads its outputs, so "ignored" means "cannot change what `main.yml` builds or tests", never "unimportant". Reading it as a global claim is how the table stays under-filled: half of it has always been this kind of entry (`packages/node-gi/**`, `packages/napi/**` are load-bearing inputs to their OWN workflows), so the `OTHER_WORKFLOW_INPUTS` sub-table groups them and each entry NAMES the workflow that does gate it. **Membership is a two-part claim and both halves must hold: `main.yml` must not read the path, and some other workflow must.** Scoping is per-PATH, not per-name — `main.yml` DOES run manifest-conformance code, but reaches it by importing the `packages/infra/manifest-conformance/lib/**` WORKSPACE (which must keep seeding normally); only the `scripts/`-side repo-scoped half is ignored. Four directories had leaked into a conservative full run before the contract was written down.

**SCRIPT_COUPLINGS — a build input with NO manifest edge to follow.** The closure walk's only edges are `dependencies`/`optionalDependencies`, so when directory A is a real build input to workspace B because **B's build SCRIPT reads it** (`node scripts/…`, a `cpSync`, a repo-wide glob) no walk reaches B and the coupling must be DECLARED in `affected.ts`'s `SCRIPT_COUPLINGS`. **This one is silent in the WORSE direction**: an unmodelled path lands in `unmatched` and at least fails towards a full run, while this looks perfectly healthy — the input's own workspace seeds, a small green closure is reported, B is never rebuilt, and B's build-output cache keeps serving the copy it made before the change. The entry that exists (`templates/**` → `@gjsify/create-app` + force `run-e2e`) is the measured case: `templates/*` ARE workspaces, so a template change always seeded its own `@gjsify/template-<name>` and looked handled, while the real consumer is unreachable twice over — it lives at `packages/infra/create-gjsify/` (a directory-name search misses it) and inlines templates into the build-cache candidate `dist-templates/` via `node scripts/process-template.mjs`. #853 passed only by accident of also touching root `package.json`. `why` is mandatory and names the script; a declared seed that is not a workspace fails LOUDLY to a full run naming itself (degrading quietly would restore the exact invisible no-rebuild the table prevents). **Three more couplings are safe only by accident** — `stage-prebuild.mjs` → 11 native packages, `check-refs-pin.mjs` → the 3 Rust bridges, `bootstrap-native-facades.mjs` → the infra facades — because `scripts/` is in neither IGNORE nor any workspace, so a change there lands in `unmatched`. Anyone carving `scripts/` (or a subtree) into IGNORE to save a full run MUST add the matching entries in the same change, or those three convert straight into the silent stale-artifact failure.

**`include-args` transport — UNQUOTED tokens; zero matches are FATAL.** The classifier emits a space-separated list of already-shell-safe tokens consumed by an UNQUOTED `$INCLUDE_ARGS` expansion (spliced through `su … sh -c` nesting; expansions are never re-scanned for quoting). When `affected` once emitted `--include '@gjsify/fs'`, the apostrophes stayed IN the globs, every pattern matched zero workspaces, `gjsify foreach` exited 0, and **every selective PR built nothing in 0.65 s** while later steps inspected the cache-restored tree. Pre-quoting for unknown nesting cannot work; emitting tokens needing no quoting can (`assertShellSafeWorkspaceName`; unsafe name → non-zero → full run). **The silence was the real defect**: `gjsify foreach` now FAILS when an `--include` PATTERN matches zero workspaces — scoped to the pattern, not the final selection (`--shard`/`--exclude`/script-presence legitimately narrow to empty). No opt-out flag: an escape hatch would re-arm the silence.

**Kill switch**: repo/org variable `GJSIFY_CI_FORCE_FULL=1` short-circuits the classifier. Heavy hammer — disables ALL selective gates; set only to debug a suspected mis-gate, then unset.

### Integration tests — `tests/integration/`

tape→unit: `t.equal`→`toBe` | `t.deepEqual`→`toStrictEqual` | `t.ok/notOk`→`toBeTruthy/Falsy` | `t.error(err)`→`expect(err).toBeFalsy()` | `t.throws(fn)`→`toThrow()` | `t.plan/t.end` omitted | callback cleanup → promisified. **Never weaken**; failure → root-cause fix. Exception: pre-known out-of-scope gap → wrap in `on('Node.js', …)` + document in header + `status/open-todos.md`. Suites + pass counts: `status/integration-coverage.md` (webtorrent, socket.io, streamx, chokidar, autobahn, claude-agent-sdk, devtools-cdp, …).

**Non-port suites:** `autobahn/` runs the crossbario fuzzingserver in Podman/Docker against BOTH `@gjsify/websocket` (W3C/Soup) and `@gjsify/ws` drivers — isolates wrapper-layer from transport-layer bugs; baselines committed under `reports/baseline/`, diffed by `scripts/validate-reports.mjs`; not in CI (Podman-in-CI needs privileged containers). `devtools-cdp/` drives `InspectorProtocolClient` against a live WebKit remote inspector — opt-in via `GJSIFY_CDP_INSPECTOR_PORT` (unset ⇒ one passing "skipped" test); launch recipe in the suite README.

## Package convention

`packages/<pillar>/<name>/` → `@gjsify/<name>`, ONE workspace version (release train, ADR 0008 — compatibility guaranteed only within a release), `"type":"module"` | exports `./lib/esm/index.js` (+ `./lib/esm/register.js` if globals) | `sideEffects` pinned register-only | scripts `build:gjsify|build:types|build:test:{gjs,node}|test|test:{gjs,node}` | deps `@girs/*`, devDep `@gjsify/unit`, workspace deps `workspace:^`. Layout: `src/index.ts` (pure named exports) | `src/register.ts` | `src/*.spec.ts` | `src/test.mts`. Full register rules: § Tree-shakeable globals.

**Framework packages** (`packages/framework/<name>/`): flat `@gjsify/<name>` (NOT `framework-<name>`), composition-first, no top-level side effects in `index.ts`. Global registration follows **ADR 0012** (ownership, not pillar membership): (a) a framework pkg MUST NOT register a global a Web/DOM pillar register already owns — it imports the pillar's *granular* register subpath from the module that needs it, never from `index.ts` (`canvas2d`'s bridge → `@gjsify/dom-elements/register/canvas`); a second registration silently REPLACES the pillar's factory — the bug that produced the rule. (b) It MAY ship a `/register` only for globals it owns, or is the only GJS-slot distribution of, which no pillar can host without taking a GTK/WebKit dep it must not have. (c) Any such `/register` follows the FULL tree-shakeable convention incl. globals-map + alias mirrors + `register.spec.ts` — never a private back door. (d) A register import that is a FUNCTIONAL dependency must survive the `--app node` alias layer: `isGjsSourceBuild` in `app/node.ts` is the single gate, and it must stay the same question `emptyGirs` asks — the two disagreeing dropped canvas2d's `'2d'` factory on the node target. (e) `installGlobals()` and `/register` must install the SAME set — imperative and tree-shakeable spellings of one contract. Current exceptions: `@gjsify/iframe/register` (WebKit-backed), `@gjsify/canvas2d/register` (`ImageData`, `Path2D`), `@gjsify/webgl/register` (`WebGL(2)RenderingContext` — only impl is the gwebgl Vala bridge).

Shared utils: `@gjsify/utils` — check before duplicating; extract only when a 2nd package needs it; `/core` vs barrel split in § Runtime & platform model. `@gjsify/stream` direct imports allowed in internal modules/tests needing non-standard exports; all public code uses `node:stream`.

### New `@gjsify/*` package: first-publish + Trusted Publisher bootstrap

npm Trusted Publishing (OIDC) requires the package to ALREADY EXIST — the **first publish is a manual maintainer action**, not CI. Skipping it breaks the serialized publish loop in `release.yml` for every alphabetically-later package (OIDC exchange 404s, workflow exits 1 — v0.4.20 incident: `@gjsify/tls-native` unbootstrapped → 60+ packages stuck at 0.4.19).
|**fast path — `gjsify onboard`**: ensures EVERY publishable workspace is published + trusted, minimally: whoami-gated login, per-package state probe, publish+trust only the gaps, ONE shared OTP for the whole sweep. Idempotent; `--dry-run`/`--json`/`--yes`.
|manual per-package fallback: `gjsify workspace @gjsify/<name> build` → `cd packages/<pillar>/<name> && gjsify publish --access public --otp <code>` → `gjsify trust @gjsify/<name>` (infers repository from origin, defaults workflow `release.yml`; `--list`/`--dry-run`/`--force`; the npmjs.com Access web UI remains the hand-off fallback) → optional `gh workflow run release.yml -f verify_only=true` (per-package ✓/✗ audit).
|pre-flight: `gjsify whoami` verifies the `~/.npmrc` token (dead token → clear exit-1 message; `--json` for CI). Diagnostic: a `404` on the publish PUT is ambiguous (dead token vs missing package) — `gjsify publish` probes `GET /-/whoami` with the same header to disambiguate.
|same procedure for `-native` bridge packages (own npm packages). PR checklist: "if this PR adds a `@gjsify/*` package, the bootstrap is done before merge or queued as the next maintainer action."

|adding: `showcases/{dom,node}/<name>/` + `"files":["dist"]`, no `"private"` → export browser entry/assets/package.json → add as dep in `packages/infra/cli/package.json` → rebuild CLI. Discovery is a dynamic scan of the CLI's `@gjsify/example-*` deps.

## Project status & CHANGELOG.md Maintenance

**The status snapshot is DATA in `status/` (ADR 0016 + its amendment); the rendered `STATUS.md` is GENERATED and NOT COMMITTED.** The AUTHORED half — only what a human must judge — lives in `status/`: per-package `status` + prose in `status/status.json`, per-suite notes in `integration-coverage.md`, `open-todos.md`, `upstream-patch-candidates.md`, free-form fragments in `sections/`. The DERIVED half is read from the repo at render time (package lists from `packages/**`, tiers from `gjsify.tier`, runtime slots from `gjsify.runtimes`, platforms from `gjsify.platforms`, GNOME-lib usage from `gi://`/`@girs/*` source imports, static spec/`it()` counts, suite/e2e/showcase/example/refs counts). Same derive-don't-restate principle as `@gjsify/manifest-conformance` / `verify-package-outputs` — a hand-copied number IS the drift, so the authored file structurally CANNOT restate a derivable fact (`status.json` allows only `status`/`note`/`working`/`missing`; anything else fails validation). **Read the data directly; `npm run status:generate` renders the full snapshot into a gitignored `STATUS.md` when you want the tables.**

**Why the render is not committed** (do not re-commit it, do not add a freshness check): it derives from EVERY manifest, so a committed copy would stale on any merge and serialise unrelated PRs — the failure lands on whoever pushes next, not on whoever caused it. And its counts come from directory listings on DISK, not from git, so two correct checkouts legitimately disagree: the commit that introduced the generator baked `68` examples from a tree carrying untracked scratch dirs against the `63` a clean checkout counts, and the byte-check went red on its own PR for a reason no author could avoid. The committed GJS bundles earn that cost (a 20-minute rebuild, staled only by an *inlined* source); a one-second render staled by *any* manifest edit does not.

**Enforced by the `status-data` conformance rule** (registered in the manifest-conformance registry, selected by `audit-runtimes --check` → every PR, no install, no build): authored-data schema; entry coverage in BOTH directions (every published package under `packages/` has an entry, every entry names an existing package); authored `native` ⇒ `gjsify.prebuilds` declared; `## <dir>` headings in `integration-coverage.md` ↔ `tests/integration/*` bijection; `status/sections/` holds exactly the fixed section set; open-TODO headings must not be struck-through/✓/"Completed" (the delete-on-resolve rule is machine-checked).

**Per-change history goes in the COMMIT MESSAGE + CHANGELOG.md, not the status data.** Write the detailed narrative (root cause, what/why, gotchas) in the commit body — it is co-located with the diff and discoverable via `git log`/`git blame`. CHANGELOG.md records what shipped + when (release-it generates it from the conventional commits). The snapshot remains a CURRENT SNAPSHOT, not a log: no dated `Current state (…)` blocks, no `### Completed` done-log, no "Latest:" lines, no per-session summaries. (The old hand-maintained STATUS.md ballooned to ~1600 lines with drifted counts before the 2026-07 data migration; the earlier append-only log hit ~940 KB before its 2026-06-19 removal.)

**Update the DATA when the snapshot changes** — in the same PR:

| Trigger | Edit |
|---|---|
| New package added | Add its entry to `status/status.json` (missing entry = red `audit-runtimes --check`); tables/counts derive themselves |
| Package promoted (stub→partial→full) | Flip the entry's `status` (+ drop `working`/`missing` when leaving `partial`) |
| Bug fixed / workaround removed | Update the entry's `note`/`working`/`missing`; delete the resolved `status/upstream-patch-candidates.md` row |
| New integration suite | Add a `## <dir>` section to `status/integration-coverage.md` (enforced both directions) |
| Deferred item identified / resolved | Add to / **DELETE from** `status/open-todos.md` (a resolved item is removed — its record is the commit/CHANGELOG; the check rejects struck-through/Completed headings) |
| Anything derivable (counts, tiers, runtimes, platforms, GNOME libs, new Vala bridge arch) | Nothing to author — it derives itself on the next render |

Commit the `status/` data alone — there is no generated file to commit alongside it. A docs-only / pure-refactor / CI PR that changes none of the above needs **no** status edit. (`website/scripts/generate-coverage.mjs` derives the website's coverage numbers by calling the generator's exported `statusSummary()` — no rendered file involved.)

**Track open work in `status/open-todos.md`.** Every "out of scope" / "follow-up" / "later" note must have a `###` entry there. A resolved TODO is **deleted** — its record is the commit + CHANGELOG that closed it.

**Changelog entries ONLY in CHANGELOG.md** (release-it, from conventional commits). Never add dated changelog lines, "Latest:" entries, or per-session summaries to the status data.

## Commit conventions

Conventional commits `<type>[scope]: <description>`, imperative, ≤50-char subject; commitlint enforces on every PR. **All types surface in CHANGELOG.md** (`.release-it.json` `types`) — use the best fit, none is dropped: `feat` `fix` `perf` `revert` `docs` `refactor` `build` `ci` `chore` `test`; `style` hidden. Scope = lowercase package name without `@gjsify/` (`fix(rolldown-plugin-gjsify): …`), `(e2e)` for e2e suites, omit when crossing packages.

## PR size — prefer few large ones

CI here is deliberately broad (Fedora build + verify-committed-bundles + four
test shards + four e2e shards + browser + cross-runtime + macOS/Windows legs),
so a full pass is ~25 minutes. That cost is per PR, not per commit, which makes
the arithmetic one-sided: **land one large feature PR rather than several small
stacked ones.** A stack of four pays the 25 minutes four times, and every merge
into `main` in between forces the next PR in the stack to re-merge and — if it
touches `packages/infra/cli/src/` — to rebuild and re-verify the committed
bundle. Measured on the Windows-port work: four stacked PRs cost three
main-merge rounds and two bundle rebuilds before anything landed.

**Do not idle on CI.** It starts on push and can be watched while work
continues; a green run is a gate on MERGING, not on writing the next commit.
Push, keep going, check back. Watch the WORKFLOW status rather than the check
list — a workflow that has not spawned its jobs yet contributes zero checks, so
"no pending checks" reads as green before anything has started.

### Sixth axis — bundled toolchains (Node-free build chain)

NPM toolchains that are plain TS/JS (no native addons) can be re-bundled with `gjsify build --app gjs` and run under GJS — a Node-free version of the tool without reimplementing it. NOT for native-addon tools (rolldown, oxc binaries) — those get the GI-bridge treatment (`@gjsify/{rolldown,lightningcss,oxfmt}-native` + dual-engine pick).

**Exemplar `@gjsify/tsc`** (`packages/infra/tsc/`): wraps upstream `typescript`'s `lib/_tsc.js` into a GJS bundle shipped as the `gjsify-tsc` bin; `typescript` stays a build-time devDependency; bundle COMMITTED to `dist/tsc.gjs.mjs` (paired `.gitignore` re-include); runtimes `{gjs:"polyfill",node:"none",browser:"none"}`; pinned `TYPESCRIPT_VERSION` in `src/index.ts` (tracks the workspace TS invariant, § Constraints).
|**gjsify SELF-HOSTS its type-checking on it**: every package `check` = `gjsify tsc --noEmit`, and `build:types` (the `.d.ts` emit, incl. project-reference variants) is ALSO `gjsify tsc` — emit validated BYTE-IDENTICAL to node tsc; perf ≈ 1.3× node tsc at full-workspace parallel scale (single-package startup-dominated). `typescript` is now only the seed the bundle is built from. A `@gjsify/tsc` bug breaks every `check`/`build:types` → guarded by `tests/e2e/self-host-tsc`.
|**default-library resolution**: tsc finds its `lib.*.d.ts` beside `_tsc.js`, so the ~108 libs ship INSIDE the package (`lib/lib*.d.ts`, COMMITTED via gitignore exception + reproduced by `build-bundle.mjs` before each bundle build) and the bundle's baked `__filename` spec is re-pointed `typescript/lib/_tsc.js` → `@gjsify/tsc/lib/_tsc.js` (always resolvable from the bundle). `build-bundle.mjs` does NOT blindly refresh: the pure `pickLibSource()` decides `refresh` only when the devDep EXACTLY matches the pin AND ships a complete set (has `lib.esnext.full.d.ts`, ≥ committed count), else `keep` committed, else `error` — a partial CI `typescript` install once copied a broken `lib/` over the correct committed one → the v0.7.2 Fedora-44 main-red `TS6053` cascade. ### Bundled-artifact dependency classification — `dependencies` vs `devDependencies`

A package belongs in `dependencies` **IFF something a consumer runs needs it on disk at runtime.** The trap: "it's inlined into the GJS bundle ⇒ devDependency" holds ONLY when the bundle is the sole consumed artifact.
|**pure-bundle** (`@gjsify/tsc` — bin = the GJS bundle, no consumed Node `lib/`): bundled deps genuinely are devDependencies.
|**dual-entry** (`@gjsify/cli` — `bin: lib/index.js` Node entry AND `gjsify.bin: dist/cli.gjs.mjs`): npm wires the bin to the NODE entry, whose `lib/**` imports its deps from `node_modules` at runtime even though they are ALSO inlined in the GJS bundle. `cosmiconfig`, `yargs`, `get-tsconfig`, `pkg-types`, the `@gjsify/*` runtime set — all stay `dependencies`. Moving a `lib/**`-imported dep to devDependencies breaks `gjsify` as an npm dep — guarded by `tests/e2e/create-app` (scaffolds a consumer, runs the bin; a misclassified dep fails `ERR_MODULE_NOT_FOUND`).
|**cold-build corollary**: a `lib/**`-imported dep must be fully BUILT before anything spawns the Node CLI entry (ESM link time) — a dep whose `build:infra` step only emits `lib/types` makes `node <cli>` unloadable on a cold tree, while a warm cache hides it (and the failure blocks the cache save → self-sustaining). Both obvious escapes are circular (those deps' `build:gjsify` needs the native facade only the Node CLI can bootstrap), so `scripts/bootstrap-native-facades.mjs` tsc-emits `lib/esm` for the outliers in its `CLI_RUNTIME_DEPS` before spawning the CLI (mtime-skipped; root build re-emits with Rolldown later). An uncovered dep is caught by an explicit link probe with an actionable message.
|optional GJS-native fast-paths with an npm fallback → optional `peerDependencies` (`@gjsify/rolldown-native` ↔ npm `rolldown`). **A GLOBAL GJS install has no npm fallback** — and the native install backend never resolves peerDependencies — so the global installer lays the engine set down explicitly: `installGjsEnginePackages()` (`@gjsify/{rolldown,lightningcss,oxfmt}-native`) wired into `install -g` + `self-update`, best-effort per engine (missing platform prebuild warns + continues; `rolldown-native` failure is loud), before `linkGlobalBins`. Do NOT make these hard deps of `@gjsify/cli` (every Node/macOS/Windows `npm install @gjsify/cli` would fetch linux prebuilds). e2e `global-install-engine`.
|`gjsify self-update` resolves the production `dependencies` tree by default (`--skip-deps` = bundle-only fast path) so an update pulls matching bridges/engines instead of leaving them skewed; it also REPAIRS a prefix missing `rolldown-native` even when versions match. Safe only because every `@gjsify/*` is published — an unpublished workspace-internal package would 406 the resolve (the historical `@gjsify/v8` failure).

## Writing agent context files

Pipe-delimited | single-line directives | strip prose | abbreviated keys (req,opt,str,int,bool,len,min,max,def) | flatten with brace expansion | "Prefer retrieval-led reasoning" preamble. Compression: 70–80% token reduction | preserve actionable info + structural boundaries | keep non-obvious code examples | never compress error messages / edge-case docs | never compress away the INCIDENT that justifies a rule — a rule without its reason gets "simplified" back into the bug.
